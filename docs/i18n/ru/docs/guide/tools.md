# Инструменты: xEdit, BodySlide, DynDOLOD, PGPatcher, FNIS

Инструмент, запущенный через Eidos, видит **объединённый вид**, внутри
собственного Proton-префикса игры. Он читает то, что прочитает игра - все
включённые моды, в порядке приоритета - а всё, что он пишет, попадает в
Overwrite, откуда одним щелчком превращается в настоящий мод.

## Те, которые Eidos находит сам

Некоторые инструменты названы достаточно однозначно, чтобы их можно было найти,
а не объявлять, и xEdit - очевидный случай: `FO4Edit.exe` для Fallout 4,
`SSEEdit.exe` для Skyrim SE, `TES5Edit.exe` для оригинала и так далее - вместе с
их близнецами **QuickAutoClean**, то есть той самой кнопкой для грязных правок,
о которых постоянно предупреждает LOOT. Eidos ищет их по имени файла в:

- папке установки игры и деревьях `Root/` включённых модов;
- **`mods/` этой инстанции**, куда инструменты ставят пользователи MO2;
- **папке инструментов**, заданной в Preferences (General -> Tools), для
  каталога, общего для нескольких инстанций - `/mnt/Games/Tools` и тому подобное.

Распространённые генераторы находятся так же, каждый для игр, которые он поддерживает: Pandora, Nemesis, FNIS, BodySlide, DynDOLOD, TexGen, xLODGen и Synthesis.

`PGPatcher.exe` находится тем же способом в играх на Creation Engine и приходит с аргументом, без которого не может работать - см. [ниже](#почему-pgpatcher-требует---ignore-mo2vfscheck).

Список зависит от игры, так что инстанции Skyrim никогда не предложат редактор
Fallout. Поиск останавливается на четвёртом уровне вложенности, потому что пул
модов - это сотни тысяч файлов, а это выполняется при каждом построении списка
инструментов, и он не идёт по символическим ссылкам. Найденный так инструмент
настраивается ровно так же, как введённый вручную: его runtime-зависимости
выводятся из имени по тому же правилу, что и всё описанное ниже.

Если инструмент лежит где-то ещё или нужны другие аргументы, добавьте его
вручную - пользовательская запись с тем же названием перекрывает всё найденное
автоматически.

## Очистка плагина, который LOOT помечает как грязный

После сортировки LOOT вкладка Diagnostics перечисляет плагины, которые LOOT
помечает как грязные (dirty), для игр, у которых есть и xEdit, и данные LOOT об
очистке (Skyrim LE, SE и VR, Enderal SE, Fallout 3, New Vegas, Fallout 4 и 4 VR,
Oblivion, Starfield). Если Eidos находит xEdit, зарегистрированный в Executables
или лежащий в любом месте инстанции, где Eidos ищет инструменты, на карточке
есть Clean all, а у каждого грязного плагина в меню его строки есть Clean with
QuickAutoClean; иначе карточка предлагает добавить xEdit в Executables. Eidos не
скачивает xEdit. Он запускает режим QuickAutoClean программы xEdit на одном
плагине за раз, через объединённый вид, с `-qac -autoexit -autoload`. xEdit
сохраняет очищенный плагин поверх загруженного, а в объединённом виде это новый
файл в Overwrite; Eidos переносит его в мод с именем `Cleaned plugins`, который
создаётся включённым в конце списка, где он выигрывает все конфликты. В плагин в
его собственном моде или в папке Data игры ничего не записывается. Чтобы
отменить очистку, отключите `Cleaned plugins` или скройте в нём один файл.

Резервные копии, кэш и журнал xEdit попадают в `<instance>/logs/qac-<time>/`, за
пределы объединённого вида, а строка состояния показывает числа из этого
журнала. После удачной очистки Eidos удаляет эту папку, после неудачной
оставляет её. Размер и дату плагина, из которого сделана каждая копия, Eidos
записывает в `Cleaned plugins/meta.ini`. Когда этот плагин меняется, вкладка Health сообщает, что копия устарела, и предлагает её скрыть.

## Как добавить

В GUI: **Tools -> Executables**, затем Add. Из командной строки:

```sh
eidos tool skyrimse add BodySlide "<path>/CalienteTools/BodySlide/BodySlide.exe"
eidos tool skyrimse                       # list what is registered
eidos tool skyrimse run BodySlide         # run it through the merged view
eidos tool skyrimse run BodySlide --print # show the command without running it
eidos tool skyrimse run --exe "<path>/GenerateFNISforUsers.exe"   # запустить exe один раз, не регистрируя его
eidos tool skyrimse run "SSEEdit QuickAutoClean" --output-mod "Cleaned plugins" -- -qac -autoexit -autoload Dawnguard.esm
```

`--output-mod <mod>` собирает вывод этого запуска в `mods/<mod>`, что бы ни говорила собственная настройка инструмента.

Расширитель скриптов, бинарник игры и лаунчер определяются автоматически;
регистрировать нужно только дополнительные инструменты.

### Указывайте на настоящий файл, где бы он ни лежал

Регистрируйте исполняемый файл там, где он реально находится. Если инструмент
установлен как мод, это внутри папки мода:

```
~/.local/share/Colony/Eidos/instances/skyrimse/mods/BodySlide.../CalienteTools/BodySlide/BodySlide.exe
```

(это путь глобальной инстанции - для портативной то же правило действует внутри
её собственной папки, `<instance>/mods/...`; учтите, что такой абсолютный путь -
единственное, что не переживёт ПЕРЕМЕЩЕНИЯ портативной папки в будущем).

Eidos переписывает этот путь на путь в объединённом виде перед запуском, поэтому
инструмент работает из `<game>/Data/CalienteTools/BodySlide/` и видит там же
файлы всех остальных модов. Это важнее, чем кажется: BodySlide поставляется с
**пустым** каталогом `SliderSets`, а все тела, которые он умеет собирать,
приходят из CBBE и модов на одежду. Запущенный из своей собственной папки мода
он не находит ничего и выглядит сломанным.

MO2 делает то же самое переписывание и по той же причине - в его собственном
комментарии назван FNIS.

Инструмент в **выключенном** моде переписать нельзя, потому что его файлов нет и
в виде. Eidos сообщает об этом и запускает его из его собственной папки, а не
делает вид, что всё в порядке.

## Инструменты из списка Mod Organizer 2

Список Wabbajack или другой экземпляр MO2, открытый как экземпляр Eidos, хранит свой `ModOrganizer.ini`, и настроенные там исполняемые файлы можно скопировать в `tools.ini`:

```sh
eidos tool /path/to/list import-mo2           # показать, что будет добавлено
eidos tool /path/to/list import-mo2 --write   # добавить
```

В окне в диалоге «Исполняемые файлы» есть кнопка **Импорт из ModOrganizer.ini** и флажок у каждой записи, который можно снять. Пока вы не нажмёте «Сохранить», ничего не записывается.

Пути на `Z:` это пути Linux, и они остаются как есть. Путь на другой букве диска переносится в папку списка, если называет эту папку (`D:\Lists\MyList\tools\SSEEdit.exe` становится `<list>/tools/SSEEdit.exe`), в исполняемом файле, рабочем каталоге и аргументах. Загрузчик расширителя скриптов и исполняемый файл игры становятся простыми именами, поэтому запускаются из папки игры, поверх которой Eidos монтирует представление, как и встроенные записи. Записи, указывающие в другое место (системная программа Windows, инструмент вне списка), показываются как пропущенные с причиной, а название, которое уже есть в `tools.ini`, никогда не заменяется.

## Вывод инструмента в его собственный мод

Генератор - FNIS, Nemesis, BodySlide, DynDOLOD, Synthesis - пишет сотни файлов.
По умолчанию они попадают в Overwrite вместе со всем остальным. Задайте
**Capture output into** в редакторе Executables, и вывод этого запуска пойдёт в
указанный мод:

```
Tools -> Executables -> (your tool) -> Capture output into: FNIS Output
```

Pandora, Nemesis, FNIS, BodySlide и Synthesis появляются с уже заданным модом для перехвата: `Pandora Output`, `Nemesis Output`, `FNIS Output`, `BodySlide Output` и `Synthesis Output`. DynDOLOD, TexGen и xLODGen появляются без него, потому что пишут в выходную папку, которую вы им укажете.

Мод создаётся, если его нет. Переносятся только файлы, созданные ЭТИМ запуском;
всё, что уже было в Overwrite, там и остаётся, поэтому два инструмента с целями
захвата не крадут вывод друг у друга. Запуск, ничего не записавший, не оставляет
после себя пустого мода.

Это делается после запуска, а не переводом слоя записи на мод, как поступает
MO2. Перевод слоя записи на мод поднял бы его на верхний приоритет на весь
запуск - перевернув каждый конфликт с его участием и перевернув их обратно
потом - и писал бы прямо поверх собственных файлов мода без copy-up. Захват
приводит к тому же итоговому состоянию без того и другого.

Если целевой мод выключен, вывод всё равно записывается, но игра его не увидит,
поэтому при следующем запуске инструмент сгенерирует те же файлы заново. Eidos
предупреждает, когда это так.

### Когда его вывод устарел

Eidos запоминает, из каких модов, порядка плагинов, профиля и исполняемого файла получен вывод инструмента. Когда что-то из этого меняется, вкладка Diagnostics сообщает об этом, а на карточке есть кнопка **Run <tool> again**, которая запускает инструмент с его нынешними настройками.

Для генератора, чей устаревший вывод ломает игру, например Pandora или Nemesis, добавьте `check_before_play=1` в его запись в `tools.ini` или включите **Ask before playing when its output is out of date** в диалоге Executables. Тогда Run сначала спросит: запустить инструмент или всё равно играть. Выбор «играть» помнится, пока моды, плагины или профиль снова не изменятся или пока окно не закроется. Eidos никогда не запускает инструмент сам.

## DLL, нужные инструменту, выбираются по его ИМЕНИ

Это самая неожиданная часть, поэтому стоит сказать прямо: **название, которое вы
даёте инструменту, решает, какие runtime-зависимости Eidos ему предоставит.**
Совпадение - это подстрока названия без учёта регистра.

| Если название содержит | Eidos запрашивает |
|---|---|
| `bodyslide`, `outfit` | `d3dx9_43`, `d3dcompiler_47` |
| `dyndolod`, `texgen`, `xlodgen` | `d3dcompiler_47`, `d3dx9_43`, `d3dx11_43`, `dotnet10` |
| `cathedral`, `cao` | `vcrun2022`, `d3dcompiler_47`, `d3dx11_43` |
| `synthesis` | `dotnetsdk10`, `vcrun2022` |
| `pandora` | `dotnet10` |
| `fnis` | `dotnet48` |
| `nemesis`, `loot` | `vcrun2022` |
| что угодно другое | ничего |

Так что инструмент, зарегистрированный как **`BodySlide`**, получает свои
DirectX-DLL; тот же исполняемый файл, зарегистрированный как **`BS`**, не
получает ничего и может не запуститься с ошибкой, в которой про DLL нет ни
слова. Называйте инструменты по имени программы.

Список лежит в `default_prereqs` (`crates/eidos-instance/src/tools.rs`), а поле
`Prereqs` в диалоге Executables можно править - определение это значение по
умолчанию, а не правило.

Заголовок точно так же решает и **аргументы** - для единственного инструмента,
которому нужен такой, какой никто не угадает: заголовок, содержащий `pgpatcher`
(или `parallaxgen`, прежнее имя), получает `--ignore-mo2vfscheck`. Почему и
почему это не по желанию - [ниже](#почему-pgpatcher-требует---ignore-mo2vfscheck).

### Три вида зависимостей

**Уровень 1 - встроенные DLL** (`d3dx9_43`, `d3dcompiler_47`, `d3dcompiler_43`,
`d3dx11_43`). Eidos поставляет их и копирует в префикс при запуске.
Делать ничего не нужно, сеть не нужна.

**Уровень 2 - verbs winetricks** (`vcrun2022`, `dotnet8`, `dotnetdesktop8`,
`dotnet48`, `xact`...). Они пишут ключи реестра, GAC и хосты CLR, поэтому их
нельзя перенести копированием файлов. Они **скачиваются с серверов Microsoft**.

**Уровень 3 - runtime** (`dotnet10`, `dotnetsdk10`). Современный runtime .NET - это 193 файла,
которые живут в собственном каталоге и находятся через `DOTNET_ROOT`: никогда не
регистрируются, вообще никогда не устанавливаются в префикс, так что ни один из
двух других уровней не может его нести. Eidos скачивает его сам, сверяет с
контрольной суммой, встроенной в бинарник, и кэширует в
`~/.local/share/Colony/Eidos/runtimes/` - **вне любой инстанции**, потому что
78 МБ не зависят ни от игры, ни от профиля.

`dotnetsdk10` - это .NET 10 SDK: 301 МБ на загрузку, 808 МБ после распаковки. Он
нужен Synthesis для компиляции патчеров, а для их сборки и запуска Synthesis
вызывает голый `dotnet`, поэтому инструмент, который объявляет `dotnetsdk10`,
получает ещё и папку SDK в `WINEPATH`, а также
`NUGET_CERT_REVOCATION_MODE=offline`, `DOTNET_GENERATE_ASPNET_CERTIFICATE=false`
и `DOTNET_CLI_TELEMETRY_OPTOUT=1`.
Сборка патчера оставила бы работающими узлы MSBuild и сервер VBCSCompiler, а под
Wine они не дают завершиться wineserver префикса, поэтому инструмент получает
ещё `MSBUILDDISABLENODEREUSE=1`, `DOTNET_CLI_USE_MSBUILD_SERVER=0` и
`UseSharedCompilation=false`. `DOTNET_ROLL_FORWARD=Major` позволяет патчеру,
собранному под .NET 8 (Mutagen до 0.54), работать в среде выполнения .NET 10 из
SDK, если среда выполнения .NET 8 не найдена.
Запись Synthesis в `tools.ini`, где всё ещё
стоит старое значение по умолчанию `dotnet8`, `vcrun2022`, получает
`dotnetsdk10`, `vcrun2022`, когда Eidos её читает.

NuGet проверяет подпись каждого восстанавливаемого пакета по хранилищу корневых
сертификатов Windows, а в префиксе Wine нет корневых сертификатов для подписи
кода и меток времени, которые SDK поставляет как
`sdk/10.0.403/trustedroots/codesignctl.pem` и `timestampctl.pem`. Без них
восстановление `Mutagen.Bethesda.Synthesis` 0.36.6 завершается ошибками `NU3018`
и `NU3028`. Поэтому перед запуском инструмента, объявляющего `dotnetsdk10`, если
SDK уже скачан, Eidos добавляет 385 сертификатов из обоих файлов в хранилище
корневых сертификатов текущего пользователя в префиксе игры, тем же импортом
через `regedit`, который записывает путь к игре (см. ниже). Если какой-то из них
пропадёт, Eidos импортирует их снова. После этого каждая программа Windows в
этом префиксе доверяет этим корневым сертификатам. С ними в новом префиксе и с
пустым кэшем NuGet то же восстановление и сборка проходят с системным Wine 11.21
и с GE-Proton11-9.

Ничто на уровнях 2 и 3 не выполняется молча:

```sh
eidos prereqs skyrimse            # show what the registered tools need, and their state
eidos prereqs skyrimse --install  # fetch what is missing (downloads)
```

В GUI те же состояния находятся под полем Prereqs, а недостающие - это кнопки.
Verb, который не встроенный, не runtime и не известный winetricks verb,
показывается как вероятная опечатка, а не предлагается к скачиванию.

### Почему DynDOLOD нужен `dotnet10`

DynDOLOD не строит object LOD сам: он вызывает LODGen, и их в комплекте три.
`LODGenx64.exe` собран под .NET Framework 4.8, который под Proton направляется в
Wine Mono - а инициализатор `System.Uri` там вызывает метод, которого в Mono нет.
Он умирает раньше первой строки работы, оставляя лог с одним баннером версии и
ничем больше, и диалог DynDOLOD, где сказано только «failed for one or more
worlds».

Установка настоящего .NET Framework это не чинит: Proton заменяет `mscoree.dll`
- загрузчик, который бы его нашёл - символической ссылкой в собственное дерево и
делает это заново при каждом обновлении префикса.

Работает сборка `LODGenx64Win10.exe`, собранная под современный .NET и не
трогающая `mscoree`. Направьте `DOTNET_ROOT` на runtime .NET 10, и она
запускается. Именно это и обеспечивает `dotnet10`, а Eidos выставляет переменную
при запуске любого инструмента, который его объявляет.

Eidos запускает системный `winetricks` поверх собственного `wine` от Proton и
префикса игры, что обходит контейнер pressure-vessel от Steam и несовместимость
protontricks + Proton-GE. Инструмент, объявляющий неустановленный verb уровня 2,
всё равно запускается - с предупреждением, называющим verb и команду для
исправления: возможно, он есть у пользователя из другого источника.

### Почему PGPatcher требует `--ignore-mo2vfscheck`

PGPatcher переписывает меши и плагины так, чтобы имеющиеся у вас моды текстур -
vanilla, parallax, complex material, PBR - использовали правильный шейдер на
каждой поверхности. Он справедливо отказывается работать вне менеджера модов:
патчить голую папку игры было бы разрушительно.

Беда в том, КАК он это проверяет: он ищет **usvfs**, слой перехвата DLL, который
MO2 внедряет в игру под Windows. У Eidos его нет и не будет - объединённое
представление это монтирование FUSE, в которое Wine заходит, не зная о его
существовании, - поэтому проверка ничего не находит и инструмент немедленно
завершается с

```
Please verify that you are launching PGPatcher from MO2, VFS not detected.
```

называя программу, которую пользователь вовсе не запускал, ещё до начала работы.
Ответ самого автора на два сообщения с Linux ([#716][pg716] и [#725][pg725], оба
из Fluorine, линуксового форка MO2, построенного на FUSE по той же причине) -
флаг, пропускающий проверку.

Поэтому Eidos подставляет его сам. Найденный в пуле модов PGPatcher приходит с
уже выставленным аргументом, а ввод `PGPatcher` в поле заголовка диалога
Executables заполняет поле Arguments так же. То, что вы ввели, всегда побеждает:
подставляется только оставленное пустым поле, ровно как у требований выше.

Список находится в `default_args` (`crates/eidos-instance/src/tools.rs`), рядом с
`default_prereqs`. В нём одна запись, и одной достаточно, чтобы оправдать
функцию: флаг угадать невозможно, а ошибка, которую он предотвращает, называет
не ту программу.

Во время работы он ничего не требует, что необычно для инструмента на .NET: он
несёт собственную среду (`dotnetlib/`, с `runtimeconfig.json`, объявляющим
`includedFrameworks`) и кладёт библиотеки CRT от Microsoft рядом с исполняемым
файлом. Оставьте Prereqs пустым.

### PGPatcher и PGLite в режиме Mod Organizer 2

Когда Mod Manager стоит на `None`, PGPatcher видит одну объединённую папку
`Data` и не может определить, из какого мода пришли меш или текстура, поэтому ему
нечего показать в конфликтах и не на какой порядок модов опереться. Режим
`Mod Organizer 2` читает сам экземпляр: `modlist.txt` профиля, включённые моды в
порядке приоритета и файлы в папке каждого мода. PGLite, внутриигровая версия,
читает экземпляр так же. У экземпляра Eidos уже есть структура MO2 (`mods/`,
`profiles/<name>/modlist.txt`, `overwrite/`), поэтому этот режим с ним работает.

В лаунчере PGPatcher:

1. Установите **Mod Manager** в `Mod Organizer 2`.
2. Установите **MO2 Options -> Instance Location** на папку экземпляра Eidos,
   записанную как путь Windows на диске `Z:` в Wine, который соответствует `/`.
   Переносной экземпляр в `/mnt/Games/Eidos-Skyrim` записывается как
   `Z:\mnt\Games\Eidos-Skyrim`; глобальный как
   `Z:\home\<you>\.local\share\Colony\Eidos\instances\<game id>`.
3. Оставьте `--ignore-mo2vfscheck` в аргументах инструмента. В этом режиме
   PGPatcher ищет usvfs и останавливается, если его нет.

PGPatcher принимает папку, только если в ней есть `modorganizer.ini`, поэтому
Eidos записывает `ModOrganizer.ini` в корень экземпляра при каждом запуске игры
или инструмента, для запускаемого профиля. Файл перезаписывается, только когда
меняется его содержимое. В нём есть:

- в `[General]`: `gameName` (название игры в MO2, то есть `New Vegas` для Fallout: New Vegas), `gamePath` (папка установки игры в виде пути `Z:`)
  и `selected_profile`;
- в `[Settings]`: `mod_directory`, `profiles_directory` и
  `overwrite_directory` как абсолютные пути `Z:`, а также `download_directory`,
  если у экземпляра есть папка `downloads/`.

Его первая строка это комментарий о том, что файл записал Eidos. Файл
`ModOrganizer.ini` без этой строки, с любым регистром букв в имени, никогда не
изменяется и не удаляется: экземпляр MO2, открытый вами в Eidos, сохраняет свой,
и PGPatcher читает этот файл как есть. MO2 отбрасывает комментарии, когда
сохраняет свои настройки, поэтому файл, поверх которого сохранил MO2, с этого
момента принадлежит MO2. Пустой файл считается файлом Eidos.

В таком файле указан профиль, который MO2 выбрал последним, и PGPatcher
использует этот профиль, а не тот, который запускает Eidos. Если они
различаются, Eidos при запуске пишет предупреждение в журнал. Выберите тот же
профиль в MO2 или переименуйте либо удалите файл, чтобы Eidos записал свой.

Eidos записывает свой файл только при запуске чего-либо, поэтому между запусками в
нём указан профиль последнего. Инструмент, запущенный Eidos, находит там
свой профиль.

PGPatcher останавливается с ошибкой, когда в профиле нет ни одного включённого
мода, и когда его папка вывода совпадает с папкой включённого мода, так же как
под MO2.

## Путь к игре в префиксе

Windows-инструменты находят игру, читая
`HKLM\Software\Bethesda Softworks\<game>` `installed path` - ключ, который пишет
собственный установщик игры и который Steam под Proton никогда не запускает. Без
него xEdit, Wrye Bash и DynDOLOD открываются на пустом пути. Eidos пишет его
перед запуском инструмента: идемпотентно, только добавляя, и пропуская, если
префикс не инициализирован или занят.

## Как добраться до инструмента: скрыть, закрепить и ярлык

Умолчания для игры включают инструменты, которыми вы можете никогда не
воспользоваться, а список из восьми записей ради второй - это список, который
никто не читает. В диалоге Executables:

- **Pin to top** ставит запись в начало списка Run.
- **Hide from picker** убирает её оттуда, не удаляя.
- **Desktop shortcut** пишет `.desktop` в
  `~/.local/share/applications` - туда, где лаунчеру и место на
  freedesktop-системе, поэтому он появляется в меню приложений и в поиске, а не
  на рабочем столе. Он напрямую выполняет `eidos tool <instance> run <title>`, а
  значит инструмент поднимается **через объединённый вид с профилем этой
  инстанции**, при том что окно Eidos вообще не открыто.

Скрытие и закрепление касаются того, как до инструмента *добираются*, а не того,
что он запускает, поэтому они применимы и к умолчаниям для игры, и к вашим
собственным записям.

У загрузчика script extender, лаунчера и бинарника игры нет кнопки Desktop
shortcut. Они запускают игру, а игра всегда запускается через свой магазин, и
это уже делает ярлык самого магазина. Ярлык, созданный для одного из них в
Eidos 1.22 или раньше, продолжает работать: как и команда
`eidos tool <instance> run <title>`, набранная в терминале, он просит магазин
запустить игру, так же как Run в окне, которое не открывал ни один магазин. Если
настройки в магазине нет, команда ничего не запускает и выводит, что задать.
Ярлык не показывает никакого сообщения, поэтому запустите ту же команду в
терминале, чтобы его прочитать.

## Инструмент, который сам себе приложение Steam

Creation Kit - отдельное приложение Steam и хочет собственный AppID; несколько
других инструментов моддинга, распространяемых через Steam, устроены так же.
Задайте **Steam AppID** в записи, и Eidos запустит её под этим id вместо
игрового.

В Windows это означает другой лаунчер. Здесь это две переменные окружения в
запуске, который и так уже собирался - `SteamAppId` и `SteamGameId`, обе, потому
что Proton читает одну, а собственные библиотеки Steam - другую, и инструмент,
видящий их расхождение, падает странно, а не понятно. `eidos tool ... --print`
показывает ровно то, что получит настоящий запуск.

## Переменные окружения и инструменты без Proton

У трёх ключей `<instance>/tools.ini` пока нет поля в диалоге Executables, так
что впишите их в секцию инструмента вручную. Каждая строка `env=NAME=value`
задаёт одну переменную только для запусков этого инструмента:

```ini
[Tool/BodySlide]
exe=Data/CalienteTools/BodySlide/BodySlide x64.exe
env=PROTON_LOG=1
env=WINEDEBUG=-all
```

Eidos применяет эти строки после всего, что задаёт сам, поэтому значение,
указанное здесь, заменяет его собственное. Это касается и `WINEDLLOVERRIDES`,
который Eidos собирает из DLL, поставляемых вашими модами: инструмент, который
его задаёт, должен перечислить в нём каждую нужную ему DLL. Имя состоит из букв,
цифр и `_` и не начинается с цифры. Строка с любым другим именем пропускается.

`runner=native` запускает сам `exe`, без Proton. Объединённый вид монтируется
как для любого инструмента, а строки `arg0=`, `arg1=` становятся его
аргументами. Это нужно для программы под Linux или для инструмента к копии,
которой не управляет Steam и для которой Heroic не записал раннер: `exe` - это
Wine этой копии, программа для Windows идёт первым аргументом, а префикс
задаётся через `env=`.

```ini
[Tool/SSEEdit (GOG)]
exe=/opt/wine-ge/bin/wine
arg0=/home/me/Games/Skyrim/SSEEdit.exe
workdir=/home/me/Games/Skyrim
runner=native
env=WINEPREFIX=/home/me/Games/Heroic/Prefixes/default/Skyrim
```

`exe` должен быть абсолютным путём. Рабочий каталог по умолчанию - папка, в
которой лежит `exe`, здесь папка раннера, поэтому задайте `workdir=`. На
объединённый путь переписывается только `exe`: для программы Windows внутри мода
укажите её путь в папке `Data` игры, где её показывает объединённый вид.
Нативный инструмент пропускает шаги Proton: ключ реестра, описанный выше, кэш
шейдеров Steam, пустые корни .NET и удаление оверлея Steam из `LD_PRELOAD`.

Для копии из GOG или Epic, установленной через Heroic, такая запись
инструментам не нужна, если в настройках игры в Heroic
(`GamesConfig/<appName>.json`) указана сборка Wine или Proton: Eidos запускает
их этой сборкой в префиксе Heroic для игры, а `eidos prereqs <instance> --install`
передаёт её winetricks. У копии, установленной только через Legendary, настроек
Heroic нет.

`slr=1` запускает инструмент, и импорт в реестр перед ним, внутри контейнера
Steam Linux Runtime, который указывает Proton инструмента (`require_tool_appid`
в его `toolmanifest.vdf`), так же, как Steam запускает игру. Эта среда
выполнения должна быть установлена в одной из библиотек Steam; если её нет,
запуск останавливается и называет приложение Steam, которое нужно установить.
`eidos prereqs` по-прежнему запускает winetricks на хосте, а инструмент с
`runner=native` этот ключ игнорирует. Контейнер видит вашу домашнюю папку и
библиотеку Steam с игрой. Инструменту, моду или среде выполнения в другом месте,
например на другом диске, нужен `env=STEAM_COMPAT_MOUNTS=/этот/путь` (несколько
путей разделяются `:`). Proton, установленный в
`/usr/share/steam/compatibilitytools.d`, скорее всего, не будет работать с
`slr=1`, потому что `/usr` внутри контейнера принадлежит среде выполнения.
Запуск инструмента внутри контейнера ещё не проверялся.

`eidos tool <instance> run <title> --print` показывает итоговую команду и каждую
переменную, которую запуск задаёт поверх унаследованного окружения, включая эти
строки.

## BethINI Pie

Eidos не поставляет BethINI Pie. Положите скачанную со страницы на Nexus версию в `mods/` этого экземпляра или в вашу папку инструментов, и `Bethini.exe` появится в списке инструментов. Запущенный через Eidos, он правит копию INI-файлов игры, принадлежащую профилю. Перед каждым запуском Eidos сохраняет копию этих INI; **Backups -> INIs** возвращает одну из них. INI, которого не было при копировании, остаётся как есть.

## Собственные настройки инструмента остаются его собственными

Eidos кладёт инструмент в нужное место с нужными DLL. Что инструмент дальше
делает со своей конфигурацией - это между вами и им, и сбой обычно молчаливый.

Разобранный пример, потому что иначе он стоит часа: **Game Data Path** в
настройках BodySlide должен указывать на каталог `Data` игры, а не на папку игры
выше него. Если задать на уровень выше, batch build отчитается «All sets
processed successfully» и запишет 1439 мешей туда, где игра их никогда не будет
искать. Eidos их ловит - они попадают в `Overwrite/Root/`, а не в вашу
установку - но с точки зрения игры всё в порядке, кроме того что ваши тела не
собраны.

Вывод инструментов принадлежит Overwrite. Когда запуск производит что-то
стоящее, **Overwrite -> Create mod...** превращает это в обычный мод, который
можно упорядочивать, отключать и удалять, как любой другой.
