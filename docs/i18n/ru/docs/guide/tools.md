# Инструменты: xEdit, BodySlide, DynDOLOD, FNIS

Инструмент, запущенный через Eidos, видит **объединённый вид**, внутри
собственного Proton-префикса игры. Он читает то, что прочитает игра - все
включённые моды, в порядке приоритета - а всё, что он пишет, попадает в
Overwrite, откуда одним щелчком превращается в настоящий мод.

## Те, которые Eidos находит сам

Некоторые инструменты названы достаточно однозначно, чтобы их можно было найти,
а не объявлять, и xEdit - очевидный случай: `FO4Edit.exe` для Fallout 4,
`SSEEdit.exe` для Skyrim SE, `TES5Edit.exe` для оригинала и так далее - вместе с
их близнецами **QuickAutoClean**, то есть той самой кнопкой для грязных правок,
о которых постоянно предупреждает LOOT. Eidos ищет их по имени файла в:

- папке установки игры и деревьях `Root/` включённых модов;
- **`mods/` этой инстанции**, куда инструменты ставят пользователи MO2;
- **папке инструментов**, заданной в настройках (Tools -> Tools folder), для
  каталога, общего для нескольких инстанций - `/mnt/Games/Tools` и тому подобное.

Список зависит от игры, так что инстанции Skyrim никогда не предложат редактор
Fallout. Поиск останавливается на четвёртом уровне вложенности, потому что пул
модов - это сотни тысяч файлов, а это выполняется при каждом построении списка
инструментов, и он не идёт по символическим ссылкам. Найденный так инструмент
настраивается ровно так же, как введённый вручную: его runtime-зависимости
выводятся из имени по тому же правилу, что и всё описанное ниже.

Если инструмент лежит где-то ещё или нужны другие аргументы, добавьте его
вручную - пользовательская запись с тем же названием перекрывает всё найденное
автоматически.

## Как добавить

В GUI: **Tools -> Executables**, затем Add. Из командной строки:

```sh
eidos tool skyrimse add BodySlide "<path>/CalienteTools/BodySlide/BodySlide.exe"
eidos tool skyrimse                       # list what is registered
eidos tool skyrimse run BodySlide         # run it through the merged view
eidos tool skyrimse run BodySlide --print # show the command without running it
```

Расширитель скриптов, бинарник игры и лаунчер определяются автоматически;
регистрировать нужно только дополнительные инструменты.

### Указывайте на настоящий файл, где бы он ни лежал

Регистрируйте исполняемый файл там, где он реально находится. Если инструмент
установлен как мод, это внутри папки мода:

```
~/.local/share/eidos/skyrimse/mods/BodySlide.../CalienteTools/BodySlide/BodySlide.exe
```

(это путь глобальной инстанции - для портативной то же правило действует внутри
её собственной папки, `<instance>/mods/...`; учтите, что такой абсолютный путь -
единственное, что не переживёт ПЕРЕМЕЩЕНИЯ портативной папки в будущем).

Eidos переписывает этот путь на путь в объединённом виде перед запуском, поэтому
инструмент работает из `<game>/Data/CalienteTools/BodySlide/` и видит там же
файлы всех остальных модов. Это важнее, чем кажется: BodySlide поставляется с
**пустым** каталогом `SliderSets`, а все тела, которые он умеет собирать,
приходят из CBBE и модов на одежду. Запущенный из своей собственной папки мода
он не находит ничего и выглядит сломанным.

MO2 делает то же самое переписывание и по той же причине - в его собственном
комментарии назван FNIS.

Инструмент в **выключенном** моде переписать нельзя, потому что его файлов нет и
в виде. Eidos сообщает об этом и запускает его из его собственной папки, а не
делает вид, что всё в порядке.

## Вывод инструмента в его собственный мод

Генератор - FNIS, Nemesis, BodySlide, DynDOLOD, Synthesis - пишет сотни файлов.
По умолчанию они попадают в Overwrite вместе со всем остальным. Задайте
**Capture output into** в редакторе Executables, и вывод этого запуска пойдёт в
указанный мод:

```
Tools -> Executables -> (your tool) -> Capture output into: FNIS Output
```

Мод создаётся, если его нет. Переносятся только файлы, созданные ЭТИМ запуском;
всё, что уже было в Overwrite, там и остаётся, поэтому два инструмента с целями
захвата не крадут вывод друг у друга. Запуск, ничего не записавший, не оставляет
после себя пустого мода.

Это делается после запуска, а не переводом слоя записи на мод, как поступает
MO2. Перевод слоя записи на мод поднял бы его на верхний приоритет на весь
запуск - перевернув каждый конфликт с его участием и перевернув их обратно
потом - и писал бы прямо поверх собственных файлов мода без copy-up. Захват
приводит к тому же итоговому состоянию без того и другого.

Если целевой мод выключен, вывод всё равно записывается, но игра его не увидит,
поэтому при следующем запуске инструмент сгенерирует те же файлы заново. Eidos
предупреждает, когда это так.

## DLL, нужные инструменту, выбираются по его ИМЕНИ

Это самая неожиданная часть, поэтому стоит сказать прямо: **название, которое вы
даёте инструменту, решает, какие runtime-зависимости Eidos ему предоставит.**
Совпадение - это подстрока названия без учёта регистра.

| Если название содержит | Eidos запрашивает |
|---|---|
| `bodyslide`, `outfit` | `d3dx9_43`, `d3dcompiler_47` |
| `dyndolod`, `texgen`, `xlodgen` | `d3dcompiler_47`, `d3dx9_43`, `d3dx11_43`, `dotnet10` |
| `cathedral`, `cao` | `vcrun2022`, `d3dcompiler_47`, `d3dx11_43` |
| `synthesis` | `dotnet8`, `vcrun2022` |
| `pandora` | `dotnetdesktop8` |
| `fnis` | `dotnet48` |
| `nemesis`, `loot` | `vcrun2022` |
| что угодно другое | ничего |

Так что инструмент, зарегистрированный как **`BodySlide`**, получает свои
DirectX-DLL; тот же исполняемый файл, зарегистрированный как **`BS`**, не
получает ничего и может не запуститься с ошибкой, в которой про DLL нет ни
слова. Называйте инструменты по имени программы.

Список лежит в `default_prereqs` (`crates/eidos-instance/src/tools.rs`), а поле
`Prereqs` в диалоге Executables можно править - определение это значение по
умолчанию, а не правило.

### Три вида зависимостей

**Уровень 1 - встроенные DLL** (`d3dx9_43`, `d3dcompiler_47`, `d3dx11_43`).
Eidos поставляет их и копирует в префикс при запуске. Делать ничего не нужно,
сеть не нужна.

**Уровень 2 - verbs winetricks** (`vcrun2022`, `dotnet8`, `dotnetdesktop8`,
`dotnet48`, `xact`...). Они пишут ключи реестра, GAC и хосты CLR, поэтому их
нельзя перенести копированием файлов. Они **скачиваются с серверов Microsoft**.

**Уровень 3 - runtime** (`dotnet10`). Современный runtime .NET - это 193 файла,
которые живут в собственном каталоге и находятся через `DOTNET_ROOT`: никогда не
регистрируются, вообще никогда не устанавливаются в префикс, так что ни один из
двух других уровней не может его нести. Eidos скачивает его сам, сверяет с
контрольной суммой, встроенной в бинарник, и кэширует в
`~/.local/share/Colony/Eidos/runtimes/` - **вне любой инстанции**, потому что
78 МБ не зависят ни от игры, ни от профиля.

Ничто на уровнях 2 и 3 не выполняется молча:

```sh
eidos prereqs skyrimse            # show what the registered tools need, and their state
eidos prereqs skyrimse --install  # fetch what is missing (downloads)
```

В GUI те же состояния находятся под полем Prereqs, а недостающие - это кнопки.
Verb, который не встроенный, не runtime и не известный winetricks verb,
показывается как вероятная опечатка, а не предлагается к скачиванию.

### Почему DynDOLOD нужен `dotnet10`

DynDOLOD не строит object LOD сам: он вызывает LODGen, и их в комплекте три.
`LODGenx64.exe` собран под .NET Framework 4.8, который под Proton направляется в
Wine Mono - а инициализатор `System.Uri` там вызывает метод, которого в Mono нет.
Он умирает раньше первой строки работы, оставляя лог с одним баннером версии и
ничем больше, и диалог DynDOLOD, где сказано только «failed for one or more
worlds».

Установка настоящего .NET Framework это не чинит: Proton заменяет `mscoree.dll`
- загрузчик, который бы его нашёл - символической ссылкой в собственное дерево и
делает это заново при каждом обновлении префикса.

Работает сборка `LODGenx64Win10.exe`, собранная под современный .NET и не
трогающая `mscoree`. Направьте `DOTNET_ROOT` на runtime .NET 10, и она
запускается. Именно это и обеспечивает `dotnet10`, а Eidos выставляет переменную
при запуске любого инструмента, который его объявляет.

Eidos запускает системный `winetricks` поверх собственного `wine` от Proton и
префикса игры, что обходит контейнер pressure-vessel от Steam и несовместимость
protontricks + Proton-GE. Инструмент, объявляющий неустановленный verb уровня 2,
всё равно запускается - с предупреждением, называющим verb и команду для
исправления: возможно, он есть у пользователя из другого источника.

## Путь к игре в префиксе

Windows-инструменты находят игру, читая
`HKLM\Software\Bethesda Softworks\<game>` `installed path` - ключ, который пишет
собственный установщик игры и который Steam под Proton никогда не запускает. Без
него xEdit, Wrye Bash и DynDOLOD открываются на пустом пути. Eidos пишет его
перед запуском инструмента: идемпотентно, только добавляя, и пропуская, если
префикс не инициализирован или занят.

## Как добраться до инструмента: скрыть, закрепить и ярлык

Умолчания для игры включают инструменты, которыми вы можете никогда не
воспользоваться, а список из восьми записей ради второй - это список, который
никто не читает. В диалоге Executables:

- **Pin to top** ставит запись в начало списка Run.
- **Hide from picker** убирает её оттуда, не удаляя.
- **Desktop shortcut** пишет `.desktop` в
  `~/.local/share/applications` - туда, где лаунчеру и место на
  freedesktop-системе, поэтому он появляется в меню приложений и в поиске, а не
  на рабочем столе. Он напрямую выполняет `eidos tool <instance> run <title>`, а
  значит инструмент поднимается **через объединённый вид с профилем этой
  инстанции**, при том что окно Eidos вообще не открыто.

Скрытие и закрепление касаются того, как до инструмента *добираются*, а не того,
что он запускает, поэтому они применимы и к умолчаниям для игры, и к вашим
собственным записям.

## Инструмент, который сам себе приложение Steam

Creation Kit - отдельное приложение Steam и хочет собственный AppID; несколько
других инструментов моддинга, распространяемых через Steam, устроены так же.
Задайте **Steam AppID** в записи, и Eidos запустит её под этим id вместо
игрового.

В Windows это означает другой лаунчер. Здесь это две переменные окружения в
запуске, который и так уже собирался - `SteamAppId` и `SteamGameId`, обе, потому
что Proton читает одну, а собственные библиотеки Steam - другую, и инструмент,
видящий их расхождение, падает странно, а не понятно. `eidos tool ... --print`
показывает ровно то, что получит настоящий запуск.

## Собственные настройки инструмента остаются его собственными

Eidos кладёт инструмент в нужное место с нужными DLL. Что инструмент дальше
делает со своей конфигурацией - это между вами и им, и сбой обычно молчаливый.

Разобранный пример, потому что иначе он стоит часа: **Game Data Path** в
настройках BodySlide должен указывать на каталог `Data` игры, а не на папку игры
выше него. Если задать на уровень выше, batch build отчитается «All sets
processed successfully» и запишет 1439 мешей туда, где игра их никогда не будет
искать. Eidos их ловит - они попадают в `Overwrite/Root/`, а не в вашу
установку - но с точки зрения игры всё в порядке, кроме того что ваши тела не
собраны.

Вывод инструментов принадлежит Overwrite. Когда запуск производит что-то
стоящее, **Overwrite -> Create mod...** превращает это в обычный мод, который
можно упорядочивать, отключать и удалять, как любой другой.
