# Инструменты: xEdit, BodySlide, DynDOLOD, PGPatcher, FNIS

Инструмент, запущенный через Eidos, видит объединённый вид внутри Wine-префикса
игры (Proton-префикса Steam или префикса, который настроил Heroic). Он читает то,
что прочитает игра (все включённые моды, в порядке приоритета), а всё, что он
пишет, попадает в Overwrite, откуда одним щелчком превращается в настоящий мод.
Инструмент с `runner=native` работает без Proton; см.
[ниже](#переменные-окружения-и-инструменты-без-proton).

## Те, которые Eidos находит сам

Некоторые инструменты названы достаточно однозначно, чтобы их можно было найти, а
не объявлять, и xEdit - очевидный случай: `FO4Edit.exe` для Fallout 4,
`SSEEdit.exe` для Skyrim SE, `TES5Edit.exe` для оригинала и так далее. К каждому
прилагается запись QuickAutoClean, которая чистит грязные правки, о которых
предупреждает LOOT. `PGPatcher.exe` находится так же во всех играх Bethesda, кроме
Morrowind, и приходит с аргументом, без которого не может работать (см.
[ниже](#почему-pgpatcher-требует---ignore-mo2vfscheck)). Eidos ищет их по имени
файла в:

- `Overwrite/Root/`, папке игры, с которой работает инстанция (установка из
  магазина или её копия игры), и деревьях `Root/` включённых модов;
- `mods/` этой инстанции, куда инструменты ставят пользователи MO2;
- папке инструментов, заданной в Preferences (General -> Tools), для каталога,
  общего для нескольких инстанций, например `/mnt/Games/Tools`.

Распространённые генераторы находятся так же, каждый для игр, которые он
поддерживает: Pandora, Nemesis, FNIS, BodySlide, DynDOLOD, TexGen, xLODGen и
Synthesis. Так же находится BethINI Pie (`Bethini.exe`), для тех же игр, что и
PGPatcher; см. [BethINI Pie](#bethini-pie). В Stardew Valley так же находится SMAPI
(`StardewModdingAPI.exe`). Он же служит загрузчиком расширителя скриптов этой игры,
поэтому запускает игру через магазин, как описано в разделе
[Как добраться до инструмента](#как-добраться-до-инструмента-скрыть-закрепить-ярлык-на-рабочем-столе).

Список зависит от игры, так что инстанции Skyrim никогда не предложат редактор
Fallout. Поиск останавливается на четвёртом уровне вложенности, потому что пул
модов - это сотни тысяч файлов, а поиск выполняется при каждом построении списка
инструментов; по символическим ссылкам он не идёт. Найденный так инструмент
настраивается ровно так же, как введённый вручную: его prerequisites, его
аргументы (`--ignore-mo2vfscheck` у PGPatcher) и мод для перехвата вывода
берутся из названия по правилам ниже.

Если инструмент лежит где-то ещё или нужны другие аргументы, добавьте его вручную.
Пользовательская запись с тем же названием перекрывает всё найденное
автоматически.

## Очистка плагина, который LOOT помечает как грязный

После сортировки LOOT вкладка Diagnostics перечисляет плагины, которые LOOT
помечает как грязные (dirty), для игр, у которых есть и xEdit, и данные LOOT об
очистке (Skyrim LE, SE и VR, Enderal SE, Fallout 3, New Vegas, Fallout 4 и 4 VR,
Oblivion, Starfield). Если Eidos находит xEdit, зарегистрированный в Executables
или лежащий в любом месте инстанции, где Eidos ищет инструменты, на карточке
есть Clean all, а у каждого грязного плагина в меню его строки есть Clean with
QuickAutoClean; иначе карточка предлагает добавить xEdit в Executables. Eidos не
скачивает xEdit. Он запускает режим QuickAutoClean программы xEdit на одном
плагине за раз, через объединённый вид, с `-qac -autoexit -autoload`. xEdit
сохраняет очищенный плагин поверх загруженного, а в объединённом виде это новый
файл в Overwrite; Eidos переносит его в мод с именем `Cleaned plugins`, который
создаётся включённым в конце списка, где он выигрывает все конфликты. В плагин в
его собственном моде или в папке Data игры ничего не записывается. Чтобы
отменить очистку, отключите `Cleaned plugins` или скройте в нём один файл.
Плагин, лежащий в Overwrite, не очищается, потому что xEdit переписал бы этот
файл сам; сначала превратите Overwrite в мод.

Резервные копии, кэш и журнал xEdit попадают в `<instance>/logs/qac-<time>/`, за
пределы объединённого вида, а строка состояния показывает числа из этого
журнала. После удачной очистки Eidos удаляет эту папку, после неудачной
оставляет её. Размер и дату плагина, из которого сделана каждая копия, Eidos
записывает в `Cleaned plugins/meta.ini`. Когда этот плагин меняется, вкладка
Diagnostics показывает Out-of-date copy of <plugin> с кнопкой, которая скрывает
старую копию.

## Как добавить

В GUI: Tools в строке меню или Executables на панели инструментов, затем Add. Из
командной строки:

```sh
eidos tool skyrimse add BodySlide "<path>/CalienteTools/BodySlide/BodySlide.exe"
eidos tool skyrimse                       # list what is registered
eidos tool skyrimse run BodySlide         # run it through the merged view
eidos tool skyrimse run BodySlide --print # show the command without running it
eidos tool skyrimse rm BodySlide          # remove an entry you added
eidos tool skyrimse run --exe "<path>/GenerateFNISforUsers.exe"   # запустить exe один раз, не регистрируя его
eidos tool skyrimse run "SSEEdit QuickAutoClean" --output-mod "Cleaned plugins" -- -qac -autoexit -autoload Dawnguard.esm
```

`--output-mod <mod>` собирает вывод этого запуска в `mods/<mod>`, что бы ни
говорила собственная настройка инструмента. `rm` удаляет только записи, которые
вы добавили; запись по умолчанию для игры можно скрыть, но не удалить.

Exe, запущенный через `--exe`, чьё имя файла Eidos знает для этой игры (без учёта
регистра), получает название этого инструмента, а с ним prerequisites, аргументы и
мод для перехвата, описанные ниже. `GenerateFNISforUsers.exe` - это FNIS, поэтому
строка с `--exe` выше запрашивает `dotnet48` и перехватывает вывод в
`FNIS Output`. Любой другой exe получает в качестве названия своё имя файла. Во
вкладке Data у строки `.exe` есть Add tool, который открывает диалог Executables с
уже заполненной записью, и Run, который запускает файл один раз, как `--exe`. Оба
называют файл одинаково.

Для команды, которая не является инструментом Windows, `eidos shell skyrimse`
открывает ваш `$SHELL` (`/bin/sh`, если он не задан) в папке игры со
смонтированным объединённым видом. Всё, что пишет оболочка, попадает в Overwrite, а
выход из оболочки размонтирует вид. `eidos shell skyrimse -- <command>` выполняет
вместо этого одну команду. Ctrl+C в интерактивной оболочке останавливает набранную
команду и оставляет оболочку открытой. Оболочка работает без Proton; программа
Windows запускается через `eidos tool`.

В окне Stop завершает зависший запуск инструмента: нажмите его дважды, и Eidos
завершит программы запуска, а затем обработает его файлы, как после любого выхода.
Если включено Notify the desktop when a long job ends (Preferences, General,
Running a game), запуск инструмента, закончившийся, пока окно в фоне, отправляет
уведомление рабочего стола.

Расширитель скриптов, бинарный файл игры и лаунчер определяются автоматически;
регистрировать нужно только дополнительные инструменты. В инстанции, которая
работает с копией игры, они определяются в копии; см.
[Инструменты на копии игры](#инструменты-на-копии-игры).

### Указывайте на настоящий файл, где бы он ни лежал

Регистрируйте исполняемый файл там, где он реально находится. Если инструмент
установлен как мод, это внутри папки мода:

```
~/.local/share/Colony/Eidos/instances/skyrimse/mods/BodySlide.../CalienteTools/BodySlide/BodySlide.exe
```

Это путь глобальной инстанции. Для портативной то же правило действует внутри её
собственной папки, `<instance>/mods/...`. Такой абсолютный путь - единственное,
что не переживёт перемещения портативной папки позже.

Eidos переписывает этот путь на путь в объединённом виде перед запуском, поэтому
инструмент работает из `<game>/Data/CalienteTools/BodySlide/` и видит там же
файлы всех остальных модов. BodySlide поставляется с пустым каталогом
`SliderSets`, а все тела, которые он умеет собирать, приходят из CBBE и модов на
одежду. Запущенный из своей собственной папки мода, он не находит ничего и
выглядит сломанным.

MO2 делает то же самое переписывание и по той же причине: в его собственном
комментарии назван FNIS.

Инструмент в выключенном моде переписать нельзя, потому что его файлов нет и в
виде. Eidos сообщает об этом и запускает его из его собственной папки.

## Инструменты из списка Mod Organizer 2

Список Wabbajack или другая инстанция MO2, открытая как инстанция Eidos, хранит
свой `ModOrganizer.ini`, и настроенные там исполняемые файлы можно скопировать в
`tools.ini`:

```sh
eidos tool /path/to/list import-mo2           # показать, что будет добавлено
eidos tool /path/to/list import-mo2 --write   # добавить
```

В окне в диалоге Executables есть Import from ModOrganizer.ini с флажком у каждой
записи, который можно снять. Add selected помещает отмеченные записи в список, и
пока вы не нажмёте Save, ничего не сохраняется. Учитывается только
`ModOrganizer.ini`, который Eidos не писал; о том, который пишет Eidos, см.
[PGPatcher и PGLite](#pgpatcher-и-pglite-в-режиме-mod-organizer-2).

Пути на `Z:` - это пути Linux, и они остаются как есть. Путь на другой букве диска
переносится в папку списка, если называет эту папку
(`D:\Lists\MyList\tools\SSEEdit.exe` становится `<list>/tools/SSEEdit.exe`), в
исполняемом файле, рабочем каталоге и аргументах. Загрузчик расширителя скриптов,
лаунчер и бинарный файл игры становятся простыми именами, поэтому запускаются из
папки игры, поверх которой Eidos монтирует вид, как встроенные записи. `hide` из
MO2 становится Hide from picker, а `steamAppID` становится Steam AppID. Записи,
указывающие в другое место (системная программа Windows, инструмент вне списка),
показываются как пропущенные с причиной, а название, которое уже есть в
`tools.ini`, никогда не заменяется.

Импортированная запись сохраняет название и аргументы из MO2, а Eidos ничего не
заполняет по названию: ни prerequisites, ни дополнительного аргумента, ни мода для
перехвата. Задайте их в диалоге Executables. У записи PGPatcher из списка,
сделанного в Windows, обычно нет `--ignore-mo2vfscheck`; добавьте его (см.
[ниже](#почему-pgpatcher-требует---ignore-mo2vfscheck)).

Импортированный путь, указывающий в папку `Stock Game` списка, переносится на
установку из магазина во время запуска только тогда, когда инстанция работает с
этой копией; см. следующий раздел.

## Инструменты на копии игры

Когда инстанция работает с копией игры (папка `Stock Game` или `Game Root` списка
либо замороженная копия; см.
[Файлы игры](usage.md#файлы-игры-установка-из-магазина-или-копия)), инструмент
видит файлы копии, а не установки из магазина. Объединённый вид по-прежнему
смонтирован на установку из магазина: в корневом виде копия лежит внизу, а вид
Data читает `Data` копии. Eidos ищет расширитель скриптов, лаунчер, бинарный файл
игры и известные инструменты в копии, а не в установке из магазина.

Путь инструмента, аргумент или рабочий каталог, указывающие в копию, переносятся
на установку из магазина перед запуском. Он может быть записан как путь Linux или
как путь Wine `Z:`: `-D:"Z:\...\Stock Game\Data"` становится тем же путём под
установкой из магазина. Записям, импортированным из `ModOrganizer.ini` списка, это
нужно. Когда инстанция работает с установкой из магазина, ничего не переносится,
так что такая запись читает голую копию без ваших модов.

`installed path` игры в реестре префикса и `gamePath` в `ModOrganizer.ini`, который
пишет Eidos, по-прежнему называют установку из магазина, где смонтирован
объединённый вид. Если папки копии нет или в ней нет бинарного файла игры, запуск
инструмента останавливается, как и запуск игры, а сообщение называет
`eidos stock-game <instance> store`, чтобы вернуться к установке из магазина.

`eidos stock-game <instance>` показывает, какие файлы игры использует инстанция и
на какие копии она может переключиться. `use <folder>` и `store` переключают их, а
`freeze --yes` копирует установку из магазина в папку `Stock Game` инстанции и
запускается из неё. Карточка Game files во вкладке Diagnostics делает то же; см.
[Файлы игры](usage.md#файлы-игры-установка-из-магазина-или-копия).

## Вывод инструмента в его собственный мод

Генератор (FNIS, Nemesis, BodySlide, DynDOLOD, Synthesis) пишет сотни файлов. По
умолчанию они попадают в Overwrite вместе со всем остальным. Задайте Capture
output into в редакторе Executables, и вывод этого запуска пойдёт в указанный
мод:

```
Executables -> (your tool) -> Capture output into: FNIS Output
```

Pandora, Nemesis, FNIS, BodySlide и Synthesis появляются с уже заданным модом для
перехвата: `Pandora Output`, `Nemesis Output`, `FNIS Output`, `BodySlide Output` и
`Synthesis Output`. DynDOLOD, TexGen и xLODGen появляются без него, потому что
пишут в выходную папку, которую вы им укажете.

Мод создаётся, если его нет. Переносятся только файлы, созданные этим запуском;
всё, что уже было в Overwrite, там и остаётся, поэтому два инструмента с целями
перехвата не забирают вывод друг у друга. Запуск, ничего не записавший, не
оставляет после себя пустого мода.

Eidos переносит файлы после запуска. MO2 вместо этого направляет слой записи на
мод, что поднимает этот мод на верхний приоритет на весь запуск: каждый конфликт с
его участием переворачивается, а потом переворачивается обратно. Записи при этом
идут прямо поверх собственных файлов мода, без copy-up. Перехват приходит к тому
же итоговому состоянию без того и другого.

Если целевой мод отключён, вывод всё равно записывается, но игра его не увидит, и
инструмент при следующем запуске сгенерирует те же файлы заново. Eidos
предупреждает, когда так и есть.

### Когда вывод устарел

Eidos записывает, из каких модов, порядка плагинов и профиля сделан вывод
инструмента, размер и дату исполняемого файла инструмента, а также путь и
аргументы записи в `tools.ini`. Когда что-то из этого меняется, вкладка
Diagnostics показывает Generated output inputs changed, а на карточке есть кнопка
Run <tool> again, которая запускает инструмент с его нынешними настройками.

Для генератора, чей устаревший вывод ломает игру, такого как Pandora или Nemesis,
добавьте `check_before_play=1` в его запись в `tools.ini` или включите для него
Ask before playing when its output is out of date в диалоге Executables. Тогда Run
сначала спрашивает: запустить инструмент или играть как есть. Выбор Play anyway
запоминается, пока моды, плагины или профиль снова не изменятся или пока не
закроется окно. Eidos никогда не запускает инструмент сам. Если включено Start the
game at once when a store opens Eidos, такой вопрос оставляет окно открытым вместо
запуска игры.

## Prerequisites и аргументы берутся из названия

Название, которое вы дали инструменту, определяет, какие prerequisites времени
выполнения Eidos подготавливает для него. Совпадение - это подстрока названия без
учёта регистра.

| Если название содержит | Eidos запрашивает |
|---|---|
| `bodyslide`, `outfit` | `d3dx9_43`, `d3dcompiler_47` |
| `dyndolod`, `texgen`, `xlodgen` | `d3dcompiler_47`, `d3dx9_43`, `d3dx11_43`, `dotnet10` |
| `cathedral`, `cao` | `vcrun2022`, `d3dcompiler_47`, `d3dx11_43` |
| `synthesis` | `dotnetsdk10`, `vcrun2022` |
| `pandora` | `dotnet10` |
| `fnis` | `dotnet48` |
| `nemesis`, `loot` | `vcrun2022` |
| что-либо другое | ничего |

Так что инструмент, зарегистрированный как `BodySlide`, получает свои DLL DirectX;
тот же исполняемый файл, зарегистрированный как `BS`, не получает ничего и может
не запуститься с ошибкой, в которой о DLL ни слова. Называйте инструменты по имени
программы.

Список лежит в `default_prereqs` (`crates/eidos-instance/src/tools.rs`), а поле
`Prereqs` в диалоге Executables редактируемо: название лишь заполняет значение по
умолчанию.

Название так же определяет аргументы, для единственного инструмента, которому
нужен аргумент, который никто не угадает: название с `pgpatcher` (или
`parallaxgen`, его прежним именем) получает `--ignore-mo2vfscheck`. Почему, и
почему он не необязателен, см.
[ниже](#почему-pgpatcher-требует---ignore-mo2vfscheck). Мод для перехвата тоже
берётся из названия (см. [выше](#вывод-инструмента-в-его-собственный-мод)).

### Три вида prerequisites

Уровень 1 - встроенные DLL: `d3dx9_43`, `d3dcompiler_47`, `d3dcompiler_43` и
`d3dx11_43`. Eidos носит их внутри своих бинарных файлов и копирует в префикс при
запуске. В 64-разрядном префиксе, как в Proton по умолчанию, 64-разрядная сборка
идёт в `system32`, а 32-разрядная в `syswow64`. Делать ничего не нужно, сеть не
нужна. Каждая сборка хранится сжатой gzip, поэтому восемь файлов занимают в каждом
бинарном файле 7,9 МБ вместо 17,9 МБ, а распаковывается только копируемая (не
больше 4,7 МБ).

Уровень 2 - установщики: `vcrun2022`, `dotnet6`, `dotnet7`, `dotnet8`,
`dotnetdesktop6`, `dotnetdesktop8`, `dotnet48`, `xact` и `xact_x64`. Они пишут
ключи реестра, GAC и хосты CLR, поэтому их нельзя просто скопировать как файлы.
Три из них Eidos ставит без winetricks: `vcrun2022` запускает
`VC_redist.x86.exe` и `VC_redist.x64.exe` от Microsoft, а `dotnet8` и
`dotnetdesktop8` запускают установщик .NET 8.0.12 Desktop Runtime, который несёт и
среду .NET. Набор релиза (`eidos-linux-bundle.tar.gz`) поставляет эти установщики в
своей папке `runtimes/`, а `install.sh` копирует их в
`~/.local/share/Colony/Eidos/runtimes/` для пользователя, который его запускает, в
том числе с `--system`. Eidos ищет каждый файл сначала там, затем в папке
`runtimes/` рядом с бинарным файлом `eidos` (распакованный набор, запущенный на
месте). Без обеих копий (единый файл `eidos-linux`, сборка из исходников или другой
пользователь общесистемной установки) Eidos скачивает их с сайта Microsoft
(`download.visualstudio.microsoft.com`) в `~/.local/share/Colony/Eidos/runtimes/` и
хранит там. В обоих случаях файл отклоняется, если его SHA-256 не совпадает с
зашитым в Eidos, и запускается без окна (`/install /quiet /norestart`) в префиксе
игры, со сборкой Proton или Wine, которая запускает инструменты игры. Как и
winetricks, `vcrun2022` сначала задаёт для DLL Visual C++ в переопределениях DLL
префикса `native,builtin`. После этого, со сборкой Proton, Eidos проверяет, что
среда C++ префикса не наполовину от Microsoft и не наполовину от Proton. Если это
так, установка завершается неудачей: сообщение называет пары DLL из разных сборок и
говорит поставить `vcrun2022` через winetricks, который сам заменяет
`msvcp140.dll`. Ставится только 64-разрядный .NET 8; инструменту с 32-разрядным
.NET 8 по-прежнему нужен `winetricks dotnetdesktop8`.

Остальные шесть глаголов проходят через системный `winetricks`, который должен
быть в `PATH`. Eidos запускает его с `wine` той сборки Proton или Wine, которая
запускает инструменты игры, против префикса игры, что обходит контейнер
pressure-vessel Steam и несовпадение protontricks + Proton-GE. Некоторым глаголам
winetricks нужен `cabextract`, и Eidos предупреждает, когда его нет. Инструмент,
который объявляет не установленный глагол уровня 2, всё равно запускается, с
предупреждением, называющим глагол и команду для исправления, потому что вы могли
поставить его иначе.

Глагол уровня 2 считается выполненным, когда его перечисляет собственный
`winetricks.log` префикса, кто бы ни запускал winetricks или protontricks, или
когда Eidos установил его в этот же префикс. Свои установки Eidos записывает в
`prereqs.done` в инстанции, привязывая их к пути и inode префикса, так что
пересозданный префикс снова показывает свои глаголы как ожидающие. Rebuild
prefix, действие Diagnostics для копии Steam, переименовывает `compatdata/<appid>`
в `<appid>.eidos-backup-<time>` и ничего не удаляет; Steam создаёт новый префикс
при следующем запуске игры.

Уровень 3 - среды выполнения, `dotnet10` и `dotnetsdk10`. Современная среда .NET -
это 193 файла, которые лежат в собственном каталоге и находятся через
`DOTNET_ROOT`. Она никогда не регистрируется и не устанавливается в префикс,
поэтому ни один из двух других уровней не может её нести. Eidos хранит её вне любой
инстанции, потому что 78 МБ - это не на игру и не на профиль: каждая среда
распаковывается в `~/.local/share/Colony/Eidos/runtimes/<verb>-<version>/`
(`dotnet10-10.0.10`, `dotnetsdk10-10.0.403`). Eidos ищет zip среды под его именем
для скачивания в тех же двух папках, что и установщики уровня 2, и распаковывает
копию, которую поставляет набор релиза (`dotnet-runtime-10.0.10-win-x64.zip`, только
для `dotnet10`), либо скачивает её. Набор не поставляет
`dotnet-sdk-10.0.403-win-x64.zip` для SDK, но копия, положенная туда вручную,
используется и экономит скачивание. Eidos отклоняет любой из файлов, если его
SHA-256 не совпадает с зашитым в Eidos. Zip распаковывается через `7z`, тот же
7-Zip, что используется для архивов модов.

`dotnetsdk10` - это .NET 10 SDK, загрузка в 301 МБ, которая распаковывается в
808 МБ. Он нужен Synthesis для компиляции патчеров, и тот вызывает голый `dotnet`,
чтобы собирать и запускать их, поэтому инструмент, объявляющий `dotnetsdk10`,
получает также папку SDK в `WINEPATH`, а ещё `NUGET_CERT_REVOCATION_MODE=offline`,
`DOTNET_GENERATE_ASPNET_CERTIFICATE=false` и `DOTNET_CLI_TELEMETRY_OPTOUT=1`.
Сборка патчера оставила бы запущенными узлы MSBuild и сервер VBCSCompiler, а под
Wine они держат wineserver префикса живым, поэтому инструмент получает также
`MSBUILDDISABLENODEREUSE=1`, `DOTNET_CLI_USE_MSBUILD_SERVER=0` и
`UseSharedCompilation=false`. `DOTNET_ROLL_FORWARD=Major` позволяет патчеру,
собранному под .NET 8 (Mutagen до 0.54), работать на среде .NET 10 из SDK, когда
среда .NET 8 не найдена. Запись Synthesis в `tools.ini`, где всё ещё указан старый
вариант по умолчанию, `dotnet8`, `vcrun2022`, получает `dotnetsdk10`, `vcrun2022`,
когда Eidos её читает.

NuGet проверяет подпись каждого восстанавливаемого пакета по корневому хранилищу
Windows, а в префиксе Wine нет корневых сертификатов подписи кода и меток времени,
которые SDK поставляет как `sdk/10.0.403/trustedroots/codesignctl.pem` и
`timestampctl.pem`. Без них восстановление `Mutagen.Bethesda.Synthesis` 0.36.6
завершается с `NU3018` и `NU3028`. Поэтому перед запуском инструмента, объявляющего
`dotnetsdk10`, после скачивания SDK Eidos добавляет 385 сертификатов из обоих
файлов в корневое хранилище текущего пользователя в префиксе игры, тем же
импортом `regedit`, который пишет путь к игре (см. ниже). Он импортирует их снова,
если один пропал. Тогда каждая программа Windows в этом префиксе доверяет этим
корням. С ними, в свежем префиксе с пустым кэшем NuGet, то же восстановление и
сборка проходят на системном Wine 11.21 и на GE-Proton11-9.

Eidos ничего из уровней 2 и 3 не устанавливает, пока вы не попросите:


```sh
eidos prereqs skyrimse            # show what the registered tools need, and their state
eidos prereqs skyrimse --install  # install what is missing (the bundle's copies first, then downloads)
```

В GUI те же состояния показаны под полем Prereqs, а отсутствующие - это кнопки.
Глагол, который не встроен, не относится к средам выполнения и не относится к
глаголам уровня 2, сообщается как вероятная опечатка, а не предлагается для
скачивания.

`eidos prereqs <instance> --install` отказывается, пока игра, Steam или инструмент
всё ещё держат префикс. Среды уровня 3 устанавливаются даже до появления
префикса. Установщикам, которые запускает сам Eidos, нужен существующий префикс:
пока магазин не запустил игру хотя бы раз, они останавливаются с сообщением
«start the game once through its store, then install again». Глаголы уровня 2
ставятся по одному, и каждый успех записывается, так что после сбоя та же команда
продолжает с места остановки. Для копии из GOG или Epic без настроек Heroic
`--install` копирует встроенные DLL и затем останавливается перед глаголами уровня
2: он говорит использовать winetricks самого этого раннера и читает
`winetricks.log` префикса при следующей проверке.

### Почему DynDOLOD нужен `dotnet10`

DynDOLOD не строит LOD объектов сам: он вызывает LODGen, и поставляет их три.
`LODGenx64.exe` нацелен на .NET Framework 4.8, который под Proton направляется на
Mono из Wine, а инициализатор `System.Uri` в Mono вызывает метод, которого Mono не
реализует. LODGen умирает до первой строки работы, оставляя журнал с баннером
версии и ничем больше, и диалог DynDOLOD, который говорит лишь «failed for one or
more worlds».

Установка настоящего .NET Framework этого не лечит: Proton заменяет `mscoree.dll`,
загрузчик, который его нашёл бы, символической ссылкой в собственное дерево и
делает это снова при каждом обновлении префикса.

Рабочая сборка - `LODGenx64Win10.exe`, нацеленная на современный .NET и никогда не
трогающая `mscoree`. Направьте `DOTNET_ROOT` на среду .NET 10, и она запускается.
Это и подготавливает `dotnet10`, а Eidos задаёт переменную при запуске любого
инструмента, который его объявляет.

### Почему Pandora нужен `dotnet10`

Pandora - приложение на Avalonia, а не на WPF, и со времён Pandora 4.1.0 оно нацелено
на `net10.0`, так что одной среды .NET 10 достаточно для его запуска. Когда оно не
находит среды, оно предлагает установить .NET Desktop Runtime. Это общий текст,
который лаунчер .NET показывает любой GUI-программе, не нашедшей среды, и
`dotnetdesktop8` этого не исправляет.

Eidos 1.21.0 и старше давали Pandora `dotnetdesktop8`, а запись хранит свою строку
`prereqs=`. Когда Eidos читает запись Pandora, в которой по-прежнему указан только
`dotnetdesktop8`, а `.runtimeconfig.json` рядом с её исполняемым файлом называет
`net10.0`, запись получает вместо него `dotnet10`. Pandora 2.x нацелен на .NET 8 и
сохраняет то, что есть.

### Почему PGPatcher требует `--ignore-mo2vfscheck`

PGPatcher переписывает меши и плагины так, чтобы любые ваши моды текстур
(ванильные, parallax, complex material, PBR) использовали нужный шейдер на каждой
поверхности. Он отказывается работать вне менеджера модов, потому что патчить
голую папку игры было бы разрушительно.

PGPatcher проверяет наличие usvfs, слоя перехвата DLL Windows, который MO2 вводит в
игру. В Eidos его нет: объединённый вид - это монтирование FUSE, в которое Wine
заходит, не зная о его существовании. Поэтому проверка ничего не находит, и
инструмент сразу завершается с

```
Please verify that you are launching PGPatcher from MO2, VFS not detected.
```

называя программу, которую пользователь не запускает, до начала какой-либо
работы. Ответ его автора на два сообщения об этом из Linux ([#716][pg716] и
[#725][pg725], оба от Fluorine, форка MO2 для Linux, который по той же причине
основан на FUSE) - флаг, пропускающий проверку.

Поэтому Eidos подставляет его сам. PGPatcher, найденный в пуле модов, приходит с
уже заданным аргументом, а ввод `PGPatcher` в качестве названия в диалоге
Executables заполняет поле Arguments так же. То, что вы вводите, всегда
побеждает: подстановка заполняет только поле, которое вы оставили пустым, в
точности как prerequisites выше.

Список лежит в `default_args` (`crates/eidos-instance/src/tools.rs`), рядом с
`default_prereqs`.

Его среде ничего не нужно, что необычно для инструмента на .NET: он несёт свою
собственную (`dotnetlib/`, с `runtimeconfig.json`, объявляющим
`includedFrameworks`) и поставляет DLL CRT от Microsoft рядом со своим
исполняемым файлом. Оставьте Prereqs пустым.

[pg716]: https://github.com/hakasapl/PGPatcher/issues/716
[pg725]: https://github.com/hakasapl/PGPatcher/issues/725

### PGPatcher и PGLite в режиме Mod Organizer 2

Когда Mod Manager установлен в `None`, PGPatcher видит одну объединённую папку
`Data` и не может сказать, из какого мода пришёл меш или текстура, так что ему
нечего показывать в конфликтах и нет порядка модов, которому следовать. Его режим
`Mod Organizer 2` читает саму инстанцию: `modlist.txt` профиля, включённые моды в
порядке их приоритета и файлы в папке каждого мода. PGLite, внутриигровая версия,
читает инстанцию так же. У инстанции Eidos уже есть структура MO2 (`mods/`,
`profiles/<name>/modlist.txt`, `overwrite/`), так что этот режим на ней работает.

В лаунчере PGPatcher:

1. Установите Mod Manager в `Mod Organizer 2`.
2. Установите MO2 Options -> Instance Location в папку инстанции Eidos, записанную
   как путь Windows на диске Wine `Z:`, который равен `/`. Портативная инстанция в
   `/mnt/Games/Eidos-Skyrim` - это `Z:\mnt\Games\Eidos-Skyrim`; глобальная -
   `Z:\home\<you>\.local\share\Colony\Eidos\instances\<game id>`.
3. Оставьте `--ignore-mo2vfscheck` в аргументах инструмента. В этом режиме
   PGPatcher ищет usvfs и останавливается, когда его нет.

PGPatcher принимает папку, только если в ней есть `modorganizer.ini`, поэтому Eidos
пишет `ModOrganizer.ini` в корне инстанции каждый раз, когда запускает игру или
инструмент, для запускаемого профиля. Файл переписывается, только когда его
содержимое меняется. В нём:

- в `[General]`: `gameName` (имя игры в MO2, то есть `New Vegas` для Fallout: New
  Vegas), `gamePath` (папка установки игры из магазина как путь `Z:`, и в инстанции,
  которая работает с копией игры) и `selected_profile`;
- в `[Settings]`: `mod_directory`, `profiles_directory` и `overwrite_directory` как
  абсолютные пути `Z:`, а также `download_directory`, когда у инстанции есть папка
  `downloads/`.

Его первая строка - комментарий о том, что файл написал Eidos. `ModOrganizer.ini`
без этой строки, при любом написании имени, никогда не меняется и не удаляется:
инстанция MO2, которую вы открыли в Eidos, сохраняет свой файл, а PGPatcher читает
этот файл как есть. MO2 при сохранении настроек теряет комментарии, так что файл,
поверх которого сохранил MO2, с этого момента принадлежит MO2. Пустой файл
считается файлом Eidos.

Такой файл называет профиль, который MO2 выбрал последним, а PGPatcher использует
этот профиль, а не тот, который запускает Eidos. Когда они различаются, Eidos при
запуске пишет в журнал предупреждение. Выберите тот же профиль в MO2 либо
переименуйте или удалите файл, чтобы Eidos записал свой.

Инструменты в режиме Mod Organizer 2 также читают игру из `gamePath` этого файла.
Когда он называет не папку игры, с которой работает инстанция, и не установку из
магазина, вкладка Diagnostics показывает ModOrganizer.ini points tools at another
game folder с этим путём и папкой игры, с которой работает эта инстанция. Измените
`gamePath` в файле или удалите файл, чтобы Eidos записал свой.

Eidos пишет свой файл только при запуске чего-либо, поэтому между запусками он
называет профиль последнего из них. Инструмент, который запускает Eidos, находит
там свой профиль.

PGPatcher останавливается с ошибкой, когда в профиле нет включённых модов и когда
его выходная папка - это папка включённого мода, как и под MO2.

## Собственные программы Wine в префиксе игры

Меню File запускает четыре программы Wine в префиксе игры: winecfg, regedit,
файловый проводник Wine и деинсталлятор. Они запускаются как любой инструмент, со
сборкой Proton или Wine, которая запускает инструменты игры, со смонтированными
модами, а окно ждёт их. Prefix drive_c открывает диск `C:` префикса в вашем
файловом менеджере. Строка остаётся серой, пока в префиксе нет этой программы, что
случается при первом запуске игры магазином. Из терминала то же делает
`eidos tool <instance> run winecfg`, а также `regedit`, `explorer` и
`uninstaller`, когда ни один инструмент в списке не имеет такого названия.

Изменение `installed path` игры, сделанное в regedit, возвращается при следующем
запуске инструмента; см. следующий раздел.

## Путь к игре в префиксе

Инструменты Windows находят свою игру, читая
`HKLM\Software\Bethesda Softworks\<game>` `installed path`, ключ, который пишет
собственный установщик игры. Steam под Proton этот установщик никогда не запускает.
Без ключа xEdit, Wrye Bash и DynDOLOD открываются с пустым путём.

Перед запуском инструмента Eidos пишет ключ импортом `regedit` в префикс игры, если
только более ранний импорт не записал тот же путь и префикс всё ещё его хранит.
Ключ называет установку из магазина, и в инстанции, которая работает с копией игры,
потому что объединённый вид смонтирован там. Для инструмента, объявляющего
`dotnetsdk10`, тот же импорт добавляет корни подписи NuGet (см.
[выше](#три-вида-prerequisites)). Инструмент с `runner=native` этот шаг
пропускает. Когда префикса ещё нет или его держит другая программа, инструмент всё
равно запускается, а Eidos печатает предупреждение, называющее магазин, из
которого нужно один раз запустить игру, или программу, которую нужно закрыть.
Когда ключ называет папку, отличную от установки из магазина, вкладка Diagnostics
показывает Windows tools cannot find <game>, пока следующий запуск инструмента не
запишет его снова.

## Как добраться до инструмента: скрыть, закрепить, ярлык на рабочем столе

В набор по умолчанию для игры входят инструменты, которыми вы можете никогда не
пользоваться. В диалоге Executables:

- Pin to top ставит запись в начало списка Run.
- Hide from picker убирает запись, не удаляя её.
- Desktop shortcut пишет `.desktop` в `~/.local/share/applications`, так что он
  появляется в меню приложений и в поиске, а не на рабочем столе. Он запускает
  `eidos tool <instance> run <title>` напрямую, так что инструмент поднимается через
  объединённый вид с профилем этой инстанции, без открытого окна Eidos.

Скрытие и закрепление меняют только способ добраться до инструмента, поэтому они
работают и на записях по умолчанию для игры, и на ваших собственных.

У загрузчика расширителя скриптов, лаунчера и бинарного файла игры кнопки Desktop
shortcut нет. Они запускают игру, которая всегда стартует через свой магазин, а
собственный ярлык магазина уже это делает. Ярлык, созданный для одного из них в
Eidos 1.22 или старше, продолжает работать: как и `eidos tool <instance> run
<title>`, набранная в терминале, он просит магазин запустить игру, как Run в окне,
которое не открывал магазин. Когда настройки магазина нет, команда ничего не
запускает и печатает, что нужно задать. Ярлык не показывает сообщения, так что
выполните ту же команду в терминале, чтобы его прочитать.

Eidos передаёт магазину любую запись таким способом, когда имя файла её
исполняемого файла совпадает (без учёта регистра) с загрузчиком расширителя
скриптов, лаунчером или бинарным файлом игры: запись по умолчанию, добавленную
вами, импортированную из MO2 или запуск `--exe`. Сначала он отмечает эту
инстанцию как последнюю использованную, так что окно, которое открывает магазин,
показывает эту инстанцию, затем выполняет `steam -applaunch <id>`,
`xdg-open heroic://launch?appName=<app>&runner=<runner>` для Heroic или
`legendary launch <app>`. С `--print` он печатает эту команду магазина и ничего не
запускает. Команда `steam` должна быть в `PATH`: Flatpak Steam её туда не
кладёт, поэтому запуск не удаётся, а сообщение говорит запустить игру из Steam.

Запись запускается напрямую через объединённый вид, как любой инструмент, когда
процесс запустил магазин: задана одна из `SteamGameId`, `SteamAppId`,
`HEROIC_APP_NAME`, `HEROIC_APP_RUNNER` или `EIDOS_STORE_STARTED`. Без одной из них
Eidos сам игру через Proton не запускает. Когда в инстанции нет загрузчика
расширителя скриптов (в папке игры, с которой она работает, в `Root/` включённого
мода или в `Overwrite/Root/`), ничего не запускается, а строка говорит сначала
установить расширитель скриптов. Для копии из GOG вне Heroic или идентификатора
магазина, который Eidos не может передать, она говорит запустить игру из этого
магазина.

У профиля может быть свой ярлык для игры. Щёлкните профиль правой кнопкой и
выберите Desktop shortcut: запись запускает
`eidos tool <instance> run "<game>" --profile <name>`, что делает этот профиль
активным, как выбор его в окне, а затем просит магазин запустить игру. Окно Eidos,
которое открывает магазин, показывает этот профиль. `--profile` работает с любым
`eidos tool ... run` и выбирает профиль до запуска инструмента; с `--print` он
ничего не выбирает.

## Инструмент, который сам является приложением Steam

Creation Kit - это отдельное приложение Steam, и ему нужен собственный AppID;
несколько других инструментов для модов, поставляемых через Steam, такие же.
Задайте Steam AppID в записи, и Eidos запустит его под этим идентификатором, а не
под идентификатором игры.

В Windows это означает другой лаунчер. Здесь это две переменные окружения в том
же запуске, `SteamAppId` и `SteamGameId`. Eidos задаёт обе, потому что Proton
читает одну, а собственные библиотеки Steam читают другую, а инструмент, который
видит их расхождение, падает без внятной ошибки. `eidos tool ... --print` показывает
в точности то, что получил бы настоящий запуск.

## Переменные окружения и инструменты без Proton

Три ключа `<instance>/tools.ini` пока не имеют поля в диалоге Executables, так что
добавляйте их в секцию инструмента вручную. Каждая строка `env=NAME=value` задаёт
одну переменную только для запусков этого инструмента:

```ini
[Tool/BodySlide]
exe=Data/CalienteTools/BodySlide/BodySlide x64.exe
env=PROTON_LOG=1
env=WINEDEBUG=-all
```

Eidos применяет эти строки после всего, что задаёт сам, и после переменных из
`launch-env.ini` профиля, так что значение здесь заменяет оба. Это включает
`WINEDLLOVERRIDES`, который Eidos собирает из DLL, поставляемых вашими модами:
инструмент, который задаёт его, должен перечислить в нём каждую нужную ему DLL.
Обёртки профиля идут вокруг команды инструмента так же, как вокруг команды игры;
см. [Переменные и обёртки по профилям](usage.md#переменные-и-обёртки-по-профилям).
Имя состоит из букв, цифр и `_` и не начинается с цифры. Строка с любым другим
именем игнорируется.

`runner=native` запускает сам `exe`, без Proton. Объединённый вид монтируется, как
для любого инструмента, а строки `arg0=`, `arg1=` - это его аргументы.
Используйте его для программы Linux или для инструмента на копии, которой Steam не
управляет и для которой Heroic не записал раннер: `exe` - это Wine этой копии,
программа Windows - первый аргумент, а префикс берётся из `env=`.

```ini
[Tool/SSEEdit (GOG)]
exe=/opt/wine-ge/bin/wine
arg0=/home/me/Games/Skyrim/SSEEdit.exe
workdir=/home/me/Games/Skyrim
runner=native
env=WINEPREFIX=/home/me/Games/Heroic/Prefixes/default/Skyrim
```

`exe` должен быть абсолютным путём. Рабочий каталог по умолчанию - папка, где лежит
`exe`, здесь это папка раннера, поэтому задайте `workdir=`. Переписывается на путь
в объединённом виде только `exe`: для программы Windows внутри мода укажите её путь
под папкой игры `Data`, где её показывает объединённый вид. Нативный инструмент
пропускает шаги Proton: ключ реестра выше, кэш шейдеров Steam, пустые корни .NET и
удаление оверлея Steam из `LD_PRELOAD`.

На копии из GOG или Epic, установленной через Heroic, инструментам такая запись не
нужна, когда настройки Heroic игры (`GamesConfig/<appName>.json`) называют сборку
Wine или Proton: Eidos запускает их с этой сборкой в префиксе Heroic игры, а
`eidos prereqs <instance> --install` использует её для установщиков и для
winetricks. У копии, установленной одним Legendary, настроек Heroic нет.

`slr=1` запускает инструмент, и импорт реестра перед ним, внутри контейнера Steam
Linux Runtime, который называет сборка Proton инструмента (`require_tool_appid` в
её `toolmanifest.vdf`), так, как Steam запускает игру. Эта среда должна быть
установлена в библиотеке Steam; если нет, запуск останавливается и называет
приложение Steam, которое нужно установить. `eidos prereqs` по-прежнему запускает
свои установщики и winetricks на хосте, а инструмент с `runner=native` этот ключ
игнорирует. Контейнер видит вашу домашнюю папку и библиотеку Steam игры.
Инструменту, моду или среде где-либо ещё, например на другом диске, нужен
`env=STEAM_COMPAT_MOUNTS=/that/path` (несколько путей через `:`). Сборка Proton,
установленная в `/usr/share/steam/compatibilitytools.d`, вероятно, непригодна с
`slr=1`, потому что `/usr` внутри контейнера принадлежит самой среде. Ни один
запуск инструмента внутри контейнера пока не проверялся.

`eidos tool <instance> run <title> --print` показывает итоговую команду и каждую
переменную, которую запуск задаёт поверх унаследованного окружения, включая эти
строки. Для записи, которая запускает игру, он печатает вместо этого команду
магазина (см.
[Как добраться до инструмента](#как-добраться-до-инструмента-скрыть-закрепить-ярлык-на-рабочем-столе)).

## BethINI Pie

Eidos не поставляет BethINI Pie. Положите релиз, скачанный с его страницы на Nexus,
в `mods/` этой инстанции или в папку инструментов, и `Bethini.exe` появится в
списке инструментов, для тех же игр, что и PGPatcher. Запущенный через Eidos, он
правит копию игровых INI из профиля. Перед каждым запуском инструмента, чьё
название содержит `bethini`, Eidos сохраняет точку восстановления этих INI;
Backups на панели инструментов, затем INIs возвращает одну из них. INI, которого не
было, когда делалась копия, остаётся как есть. Диалог хранит 10 новейших точек
восстановления каждого вида, а при восстановлении одной сначала делается резервная
копия INI в их нынешнем виде, так что ошибочный выбор можно отменить.

## Собственные настройки инструмента остаются его собственными

Eidos не проверяет большинство настроек инструментов; неверная обычно приводит к
сбою без ошибки.

Game Data Path в BodySlide (Settings) должен указывать на каталог игры `Data`, а не
на папку игры выше него. Если задан на уровень выше, пакетная сборка сообщает «All
sets processed successfully» и записывает 1439 мешей туда, где игра никогда их не
ищет. Eidos ловит их в `Overwrite/Root/`, так что установка вашей игры не
затронута, а единственный признак в игре - тела не собраны.

Перед запуском BodySlide или Outfit Studio строка состояния предупреждает, когда
`GameDataPath` или `OutputDataPath` в победившем
`CalienteTools/BodySlide/Config.xml` во время запуска не ведёт в папку игры `Data`,
а вкладка Diagnostics показывает то же предупреждение как карточку со значением,
которое нужно задать. `eidos check <instance>` тоже сообщает об этом. Путь `S:`
читается так, как Eidos сопоставляет `S:` для инструмента, с папкой библиотеки
Steam. `OutputDataPath` внутри папки `mods/` инстанции, для мода вывода,
допускается. Diagnostics показывает карточку и тогда, когда `Overwrite/Root/`
содержит папку `meshes` или `textures`.

Вывод инструмента принадлежит Overwrite. Когда запуск создаёт что-то, что стоит
сохранить, Overwrite -> Create mod... превращает это в обычный мод, который можно
упорядочивать, отключать и удалять, как любой другой.
