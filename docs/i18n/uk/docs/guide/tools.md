# Інструменти: xEdit, BodySlide, DynDOLOD, PGPatcher, FNIS

Інструмент, запущений через Eidos, бачить об'єднаний вигляд усередині Wine-префікса
гри (Proton-префікса Steam або префікса, який створив Heroic). Він читає те, що
читатиме гра (усі увімкнені моди в порядку пріоритету), а все, що він пише,
потрапляє в Overwrite, де один клац перетворює це на справжній мод. Інструмент із
`runner=native` працює без Proton; див.
[нижче](#змінні-середовища-та-інструменти-без-proton).

## Ті, що Eidos знаходить сам

Деякі інструменти названі достатньо унікально, щоб їх можна було знайти, а не
оголошувати, і xEdit - очевидний випадок: `FO4Edit.exe` для Fallout 4,
`SSEEdit.exe` для Skyrim SE, `TES5Edit.exe` для оригіналу і так далі. Кожен
приходить із записом QuickAutoClean, який чистить брудні правки, про які
попереджає LOOT. `PGPatcher.exe` знаходиться так само в кожній грі Bethesda,
крім Morrowind, і приходить з аргументом, без якого не може працювати (див.
[нижче](#чому-pgpatcher-потребує---ignore-mo2vfscheck)). Eidos шукає їх за іменем
файлу в:

- `Overwrite/Root/`, теці гри, з якої працює екземпляр (інсталяція з магазину або
  її копія гри), та деревах `Root/` увімкнених модів;
- `mods/` цього екземпляра, куди інструменти встановлюють користувачі MO2;
- теці інструментів, яку ви задали в Preferences (General -> Tools), для каталогу,
  спільного між екземплярами, як-от `/mnt/Games/Tools`.

Поширені генератори знаходяться так само, кожен для ігор, які він підтримує:
Pandora, Nemesis, FNIS, BodySlide, DynDOLOD, TexGen, xLODGen і Synthesis. Так
само й BethINI Pie (`Bethini.exe`), у тих самих іграх, що й PGPatcher; див.
[BethINI Pie](#bethini-pie). У Stardew Valley так само знаходиться SMAPI
(`StardewModdingAPI.exe`). Він же є завантажувачем script extender для цієї гри,
тож запускає гру через магазин, як описано в
[Як дістатися інструмента](#як-дістатися-інструмента-приховати-закріпити-і-ярлик-на-робочому-столі).

Список складається окремо для кожної гри, тож екземплярові Skyrim ніколи не
запропонують редактор Fallout. Пошук зупиняється на четвертому рівні, бо пул
модів - це сотні тисяч файлів, а це виконується щоразу, коли будується список
інструментів, і він не йде за симлінками. Знайдений так інструмент налаштований
точно як той, що ви вписали руками: його передумови, його аргументи
(`--ignore-mo2vfscheck` для PGPatcher) і його мод для перехоплення визначаються з
його назви, за правилами нижче.

Якщо інструмент лежить деінде або ви хочете інші аргументи, додайте його
руками. Запис користувача з тією самою назвою перекриває будь-що знайдене
автоматично.

## Очищення плагіна, який LOOT позначає як брудний

Після сортування LOOT вкладка Diagnostics показує плагіни, які LOOT позначає як
брудні (dirty), для ігор, що мають і xEdit, і дані LOOT про очищення (Skyrim LE,
SE і VR, Enderal SE, Fallout 3, New Vegas, Fallout 4 і 4 VR, Oblivion,
Starfield). Коли Eidos знаходить xEdit, зареєстрований у Executables або будь-де
в екземплярі, де Eidos шукає інструменти, на картці є Clean all, а кожен брудний
плагін має Clean with QuickAutoClean у меню свого рядка; інакше картка радить
додати xEdit в Executables. Eidos не завантажує xEdit. Він запускає режим
QuickAutoClean програми xEdit на одному плагіні за раз, через об'єднаний вигляд,
з `-qac -autoexit -autoload`. xEdit зберігає очищений плагін поверх
завантаженого, а в об'єднаному вигляді це новий файл в Overwrite; Eidos
переносить його в мод з назвою `Cleaned plugins`, який створюється увімкненим у
кінці списку, де він виграє кожен конфлікт. У плагін у його власному моді чи в
теці Data гри нічого не записується. Щоб скасувати очищення, вимкніть `Cleaned
plugins` або сховайте в ньому один файл. Плагін, що лежить в Overwrite, не
чиститься, бо xEdit переписав би сам цей файл; спершу перетворіть Overwrite на
мод.

Резервні копії, кеш і журнал xEdit потрапляють у `<instance>/logs/qac-<time>/`,
поза об'єднаний вигляд, а рядок стану показує числа з цього журналу. Після
вдалого очищення Eidos видаляє цю теку, після невдалого залишає її. Розмір і
дату плагіна, з якого зроблено кожну копію, Eidos записує в `Cleaned
plugins/meta.ini`. Коли цей плагін змінюється, вкладка Diagnostics показує
**Out-of-date copy of <plugin>** з кнопкою, що ховає стару копію.

## Як додати

У GUI: Tools у рядку меню або Executables на панелі інструментів, далі Add. З
командного рядка:

```sh
eidos tool skyrimse add BodySlide "<path>/CalienteTools/BodySlide/BodySlide.exe"
eidos tool skyrimse                       # list what is registered
eidos tool skyrimse run BodySlide         # run it through the merged view
eidos tool skyrimse run BodySlide --print # show the command without running it
eidos tool skyrimse rm BodySlide          # remove an entry you added
eidos tool skyrimse run --exe "<path>/GenerateFNISforUsers.exe"   # запустити exe один раз, не реєструючи його
eidos tool skyrimse run "SSEEdit QuickAutoClean" --output-mod "Cleaned plugins" -- -qac -autoexit -autoload Dawnguard.esm
```

`--output-mod <mod>` збирає вивід цього запуску в `mods/<mod>`, що б не казало
власне налаштування інструмента. `rm` видаляє лише записи, які ви додали;
типовий запис гри можна сховати, але не видалити.

Exe, запущений через `--exe`, чия назва файлу відома Eidos для цієї гри (без
урахування регістру), отримує назву цього інструмента, а з нею й передумови,
аргументи та мод для перехоплення нижче. `GenerateFNISforUsers.exe` - це FNIS, тож
рядок `--exe` вище просить `dotnet48` і збирає вивід у `FNIS Output`. Будь-який
інший exe отримує назву за іменем файлу. На вкладці Data рядок `.exe` має Add
tool, який відкриває діалог Executables із заповненим записом, і Run, який
запускає файл один раз, як це робить `--exe`. Обидві називають файл однаково.

Для команди, яка не є інструментом Windows, `eidos shell skyrimse` відкриває ваш
`$SHELL` (`/bin/sh`, якщо його не задано) у теці гри з змонтованим об'єднаним
виглядом. Усе, що пише оболонка, потрапляє в Overwrite, а вихід з оболонки
демонтує вигляд. `eidos shell skyrimse -- <command>` виконує натомість одну
команду. Ctrl+C в інтерактивній оболонці зупиняє набрану команду й лишає оболонку
відкритою. Оболонка працює без Proton; програма Windows іде через `eidos tool`.

У вікні Stop завершує запуск інструмента, що завис: натисніть його двічі, і
Eidos завершить програми цього запуску, а тоді обробить його файли, як після
будь-якого виходу. З увімкненим Notify the desktop when a long job ends
(Preferences, General, Running a game) запуск інструмента, що завершується, поки
вікно у фоні, надсилає сповіщення робочого столу.

Завантажувач script extender, бінарний файл гри та лаунчер визначаються
автоматично; реєструвати треба лише додаткові інструменти. В екземплярі, що
працює з копії гри, вони визначаються в копії; див.
[Інструменти на копії гри](#інструменти-на-копії-гри).

### Вказуйте на справжній файл, хоч би де він був

Реєструйте виконуваний файл там, де він насправді лежить. Якщо інструмент був
встановлений як мод, то це всередині теки мода:

```
~/.local/share/Colony/Eidos/instances/skyrimse/mods/BodySlide.../CalienteTools/BodySlide/BodySlide.exe
```

Це шлях глобального екземпляра. Для портативного екземпляра діє те саме правило
під його власною текою, `<instance>/mods/...`. Абсолютний шлях на кшталт цього -
єдине, що не переживає переміщення портативної теки згодом.

Eidos переписує цей шлях на об'єднаний перед запуском, тож інструмент
виконується з `<game>/Data/CalienteTools/BodySlide/` і бачить там файли всіх
інших модів теж. BodySlide постачає порожній каталог `SliderSets`, а кожне тіло,
яке він може зібрати, походить із CBBE та модів на одяг. Запущений із власної
теки мода, він не знаходить нічого й має вигляд зламаного.

MO2 робить те саме переписування з тієї самої причини: його власний коментар
називає FNIS.

Інструмент у вимкненому моді переписати неможливо, бо його файлів у вигляді теж
немає. Eidos про це каже і запускає його з власної теки.

## Інструменти зі списку Mod Organizer 2

Список Wabbajack або інший екземпляр MO2, відкритий як екземпляр Eidos, зберігає
свій `ModOrganizer.ini`, і виконувані файли, налаштовані там, можна скопіювати в
`tools.ini`:

```sh
eidos tool /path/to/list import-mo2           # показати, що буде додано
eidos tool /path/to/list import-mo2 --write   # додати
```

У вікні діалог Executables має Import from ModOrganizer.ini з прапорцем біля
кожного запису, який можна зняти. Add selected додає позначені записи до списку, і
нічого не зберігається, доки ви не натиснете Save. Враховується лише
`ModOrganizer.ini`, який Eidos не записував; про той, що пише Eidos, див.
[PGPatcher і PGLite](#pgpatcher-і-pglite-у-режимі-mod-organizer-2).

Шляхи на `Z:` - це шляхи Linux, і вони лишаються як є. Шлях на іншій літері диска
переноситься в теку списку, якщо називає цю теку
(`D:\Lists\MyList\tools\SSEEdit.exe` стає `<list>/tools/SSEEdit.exe`), у
виконуваному файлі, робочому каталозі та аргументах. Завантажувач script
extender, лаунчер і виконуваний файл гри стають простими іменами, тож
запускаються з теки гри, поверх якої Eidos монтує вигляд, як і вбудовані записи.
`hide` у MO2 стає Hide from picker, а `steamAppID` стає Steam AppID. Записи, що
вказують деінде (системна програма Windows, інструмент поза списком), показано як
пропущені з причиною, а назва, яка вже є в `tools.ini`, ніколи не замінюється.

Імпортований запис зберігає назву й аргументи з MO2, а Eidos нічого не заповнює з
його назви: ні передумов, ні додаткового аргумента, ні мода для перехоплення.
Задайте їх у діалозі Executables. У записі PGPatcher зі списку, зробленого на
Windows, зазвичай бракує `--ignore-mo2vfscheck`; додайте його (див.
[нижче](#чому-pgpatcher-потребує---ignore-mo2vfscheck)).

Імпортований шлях, що вказує в теку `Stock Game` списку, переноситься на
інсталяцію з магазину під час запуску лише тоді, коли екземпляр працює з цієї
копії; див. наступний розділ.

## Інструменти на копії гри

Коли екземпляр працює з копії гри (тека `Stock Game` або `Game Root` зі списку чи
заморожена копія; див.
[Файли гри](usage.md#файли-гри-встановлення-з-магазину-або-копія)), інструмент
бачить файли копії, а не інсталяції з магазину. Об'єднаний вигляд і далі змонтовано
на інсталяції з магазину: кореневий вигляд має копію внизу, а вигляд Data читає
`Data` копії. Eidos шукає script extender, лаунчер, бінарний файл гри та відомі
інструменти в копії замість інсталяції з магазину.

Шлях інструмента, аргумент чи робочий каталог, що вказує в копію, переноситься на
інсталяцію з магазину перед запуском. Його можна записати як шлях Linux або як
шлях Wine `Z:`: `-D:"Z:\...\Stock Game\Data"` стає тим самим шляхом під
інсталяцією з магазину. Записам, імпортованим із `ModOrganizer.ini` списку, це
потрібне. Коли екземпляр працює з інсталяції з магазину, нічого не переноситься,
тож такий запис читає голу копію без ваших модів.

`installed path` гри в реєстрі префікса і `gamePath` у `ModOrganizer.ini`, який
пише Eidos, і далі називають інсталяцію з магазину, де змонтовано об'єднаний
вигляд. Якщо теки копії немає або в ній немає бінарного файлу гри, запуск
інструмента зупиняється, як і запуск гри, а повідомлення називає
`eidos stock-game <instance> store`, щоб повернутися до інсталяції з магазину.

`eidos stock-game <instance>` показує, які файли гри запускає екземпляр і на які
копії він міг би перемкнутися. `use <folder>` і `store` перемикають їх, а
`freeze --yes` копіює інсталяцію з магазину в теку `Stock Game` екземпляра й
запускає з неї. Картка Game files на вкладці Diagnostics робить те саме; див.
[Файли гри](usage.md#файли-гри-встановлення-з-магазину-або-копія).

## Як спрямувати вивід інструмента у власний мод

Генератор (FNIS, Nemesis, BodySlide, DynDOLOD, Synthesis) пише сотні файлів.
Типово вони потрапляють в Overwrite разом з усім іншим. Задайте Capture output
into у редакторі Executables, і вивід цього запуску піде натомість у той мод:

```
Executables -> (ваш інструмент) -> Capture output into: FNIS Output
```

Pandora, Nemesis, FNIS, BodySlide і Synthesis з'являються з уже заданим модом для
перехоплення: `Pandora Output`, `Nemesis Output`, `FNIS Output`,
`BodySlide Output` і `Synthesis Output`. DynDOLOD, TexGen і xLODGen з'являються
без нього, бо пишуть у вихідну теку, яку ви їм вкажете.

Мод створюється, якщо його немає. Переміщуються лише файли, які створив цей
запуск; усе, що вже було в Overwrite, там і лишається, тож два інструменти з
цілями захоплення не крадуть вивід одне в одного. Запуск, який нічого не
написав, не лишає по собі порожнього мода.

Eidos переміщує файли після запуску. MO2 натомість наводить шар запису на мод, що
піднімає цей мод на найвищий пріоритет на весь запуск: кожен конфлікт, у якому він
бере участь, перевертається, а потім перевертається назад. Записи також ідуть
просто крізь власні файли мода без copy-up. Захоплення досягає того самого
кінцевого стану без жодного з цих наслідків.

Якщо цільовий мод вимкнено, вивід усе одно запишеться, але гра його не побачить,
тож інструмент згенерував би ті самі файли наступного разу. Eidos попереджає,
коли це так.

### Коли його вивід застарів

Eidos записує, з яких модів, порядку плагінів і профілю зроблено вивід
інструмента, розмір і дату виконуваного файлу інструмента, а також шлях і
аргументи запису в `tools.ini`. Коли щось із цього змінюється, вкладка
Diagnostics показує **Generated output inputs changed**, а на картці є кнопка
**Run <tool> again**, яка запускає інструмент з його теперішніми налаштуваннями.

Для генератора, чий застарілий вивід ламає гру, як-от Pandora чи Nemesis, додайте
`check_before_play=1` до його запису в `tools.ini` або ввімкніть **Ask before
playing when its output is out of date** для нього в діалозі Executables. Тоді Run
спершу спитає: запустити інструмент чи все одно грати. Вибір Play anyway
пам'ятається, доки моди, плагіни чи профіль знову не зміняться або доки вікно не
закриється. Eidos ніколи не запускає інструмент сам. З увімкненим **Start the
game at once when a store opens Eidos** таке запитання тримає вікно відкритим
замість запуску гри.

## Передумови й аргументи беруться з назви

Назва, яку ви даєте інструментові, вирішує, які передумови середовища виконання
Eidos для нього надасть. Збіг - підрядок назви без урахування регістру.

| Якщо назва містить | Eidos запитує |
|---|---|
| `bodyslide`, `outfit` | `d3dx9_43`, `d3dcompiler_47` |
| `dyndolod`, `texgen`, `xlodgen` | `d3dcompiler_47`, `d3dx9_43`, `d3dx11_43`, `dotnet10` |
| `cathedral`, `cao` | `vcrun2022`, `d3dcompiler_47`, `d3dx11_43` |
| `synthesis` | `dotnetsdk10`, `vcrun2022` |
| `pandora` | `dotnet10` |
| `fnis` | `dotnet48` |
| `nemesis`, `loot` | `vcrun2022` |
| будь-що інше | нічого |

Тож інструмент, зареєстрований як `BodySlide`, отримує свої DLL DirectX; той самий
виконуваний файл, зареєстрований як `BS`, не отримує нічого і може не запуститися
з помилкою, яка нічого не каже про DLL. Називайте інструменти за іменем програми.

Список - у `default_prereqs` (`crates/eidos-instance/src/tools.rs`), а поле
`Prereqs` у діалозі Executables редаговане: назва лише заповнює типове значення.

Назва так само вирішує й аргументи, для єдиного інструмента, якому потрібен такий,
що ніхто не вгадає: назва, що містить `pgpatcher` (або `parallaxgen`, попереднє
ім'я), отримує `--ignore-mo2vfscheck`. Чому і чому це не на вибір - [нижче](#чому-pgpatcher-потребує---ignore-mo2vfscheck).
Мод для перехоплення теж береться з назви (див.
[вище](#як-спрямувати-вивід-інструмента-у-власний-мод)).

### Три різновиди передумов

Рівень 1 - вбудовані DLL: `d3dx9_43`, `d3dcompiler_47`, `d3dcompiler_43` і
`d3dx11_43`. Eidos несе їх усередині своїх бінарних файлів і копіює в префікс під
час запуску. У 64-бітному префіксі, типовому для Proton, 64-бітна збірка йде в
`system32`, а 32-бітна в `syswow64`. Робити нічого не треба, мережа не потрібна.
Кожна збірка зберігається стисненою gzip, тож вісім файлів займають 7,9 МБ
кожного бінарного файла замість 17,9 МБ, а розпаковується лише той, що
копіюється (щонайбільше 4,7 МБ).

Рівень 2 - інсталятори: `vcrun2022`, `dotnet6`, `dotnet7`, `dotnet8`,
`dotnetdesktop6`, `dotnetdesktop8`, `dotnet48`, `xact` і `xact_x64`. Вони пишуть
ключі реєстру, GAC і хости CLR, тож їх неможливо просто скопіювати файлами. Три
з них Eidos встановлює без winetricks: `vcrun2022` запускає `VC_redist.x86.exe` і
`VC_redist.x64.exe` від Microsoft, а `dotnet8` і `dotnetdesktop8` запускають
інсталятор .NET 8.0.12 Desktop Runtime, який містить і саме середовище виконання
.NET. Пакет випуску (`eidos-linux-bundle.tar.gz`) постачає ці інсталятори в теці
`runtimes/`, а `install.sh` копіює їх до `~/.local/share/Colony/Eidos/runtimes/`
для користувача, який його запускає, так само й з `--system`. Eidos спершу
шукає кожен файл там, потім у теці `runtimes/` поруч із бінарним файлом `eidos`
(розпакований пакет, запущений на місці). Без жодної з цих копій (окремий файл
`eidos-linux`, збірка з джерельних кодів чи інший користувач системного
встановлення) Eidos завантажує їх від Microsoft
(`download.visualstudio.microsoft.com`) до `~/.local/share/Colony/Eidos/runtimes/`
і тримає там. В обох випадках файл відхиляється, якщо його SHA-256 не збігається
з вбудованим в Eidos, і запускається без вікна (`/install /quiet /norestart`) у
префіксі гри тією збіркою Proton або Wine, яка запускає інструменти гри. Як і
winetricks, `vcrun2022` спершу ставить DLL Visual C++ у `native,builtin` у
перевизначеннях DLL префікса. Потім, зі збіркою Proton, Eidos перевіряє, що
середовище виконання C++ у префіксі не наполовину від Microsoft і наполовину від
Proton. Якщо так, встановлення завершується невдачею: повідомлення називає пари
DLL, що походять із різних збірок, і радить натомість установити `vcrun2022`
через winetricks, який сам замінює `msvcp140.dll`. Встановлюється лише 64-бітний
.NET 8; 32-бітному інструменту для .NET 8 і далі потрібен
`winetricks dotnetdesktop8`.

Решта шість verbs ідуть через системний `winetricks`, який має бути в `PATH`.
Eidos запускає його з `wine` тієї збірки Proton чи Wine, що запускає інструменти
гри, проти префікса гри, що обходить контейнер pressure-vessel від Steam і
невідповідність protontricks + Proton-GE. Деякі verbs winetricks потребують
`cabextract`, і Eidos попереджає, коли його немає. Інструмент, який оголошує
невстановлений verb Рівня 2, усе одно запускається, з попередженням, яке називає
verb і команду для виправлення, бо ви могли встановити його іншим способом.

Verb Рівня 2 вважається виконаним, коли власний `winetricks.log` префікса його
перелічує, хто б не запускав winetricks чи protontricks, або коли Eidos
установив його в цей самий префікс. Власні встановлення Eidos записує в
`prereqs.done` в екземплярі, прив'язане до шляху й inode префікса, тож
перебудований префікс знову показує свої verbs як незавершені. **Rebuild prefix**,
дія Diagnostics для копії зі Steam, перейменовує `compatdata/<appid>` на
`<appid>.eidos-backup-<time>` і нічого не видаляє; Steam створює новий префікс
під час наступного запуску гри.

Рівень 3 - середовища виконання, `dotnet10` і `dotnetsdk10`. Сучасне середовище
виконання .NET - це 193 файли, які живуть у власному каталозі й знаходяться через
`DOTNET_ROOT`. Воно ніколи не реєструється й ніколи не встановлюється у префікс,
тож жоден з інших рівнів його не понесе. Eidos тримає його поза будь-яким
екземпляром, бо 78 МБ не є ані на гру, ані на профіль: кожне середовище
виконання розпаковується в `~/.local/share/Colony/Eidos/runtimes/<verb>-<version>/`
(`dotnet10-10.0.10`, `dotnetsdk10-10.0.403`). Eidos шукає zip середовища
виконання під його іменем завантаження в тих самих двох теках, що й інсталятори
Рівня 2, і розпаковує копію, яку постачає пакет випуску
(`dotnet-runtime-10.0.10-win-x64.zip`, лише для `dotnet10`), або завантажує її.
Пакет не постачає `dotnet-sdk-10.0.403-win-x64.zip` для SDK, але копія, покладена
туди вручну, використовується й заощаджує завантаження. Eidos відхиляє будь-який
із файлів, якщо його SHA-256 не збігається з вбудованим в Eidos. Він розпаковує
zip через `7z`, той самий 7-Zip, що й для архівів модів.

`dotnetsdk10` - це .NET 10 SDK: 301 МБ на завантаження, 808 МБ після
розпакування. Він потрібен Synthesis для компіляції патчерів, а для їх збирання
і запуску Synthesis викликає голий `dotnet`, тож інструмент, що оголошує
`dotnetsdk10`, отримує ще й теку SDK у `WINEPATH`, а також
`NUGET_CERT_REVOCATION_MODE=offline`, `DOTNET_GENERATE_ASPNET_CERTIFICATE=false`
і `DOTNET_CLI_TELEMETRY_OPTOUT=1`.
Збирання патчера залишило б запущеними вузли MSBuild і сервер VBCSCompiler, а
під Wine вони не дають завершитися wineserver префікса, тож інструмент отримує
ще `MSBUILDDISABLENODEREUSE=1`, `DOTNET_CLI_USE_MSBUILD_SERVER=0` і
`UseSharedCompilation=false`. `DOTNET_ROLL_FORWARD=Major` дозволяє патчеру,
зібраному під .NET 8 (Mutagen до 0.54), працювати в середовищі виконання .NET 10
із SDK, якщо середовище виконання .NET 8 не знайдено.
Запис Synthesis у `tools.ini`, де досі стоїть старе типове значення `dotnet8`,
`vcrun2022`, отримує `dotnetsdk10`, `vcrun2022`, коли Eidos його читає.

NuGet перевіряє підпис кожного пакета, який відновлює, за сховищем кореневих
сертифікатів Windows, а в префіксі Wine немає кореневих сертифікатів для підпису
коду та міток часу, які SDK постачає як
`sdk/10.0.403/trustedroots/codesignctl.pem` і `timestampctl.pem`. Без них
відновлення `Mutagen.Bethesda.Synthesis` 0.36.6 завершується помилками `NU3018`
і `NU3028`. Тому перед запуском інструмента, що оголошує `dotnetsdk10`, якщо SDK
уже завантажено, Eidos додає 385 сертифікатів з обох файлів до сховища кореневих
сертифікатів поточного користувача в префіксі гри, тим самим імпортом через
`regedit`, який записує шлях до гри (див. нижче). Якщо якийсь із них зникне,
Eidos імпортує їх знову. Після цього кожна програма Windows у цьому префіксі
довіряє цим кореневим сертифікатам. З ними в новому префіксі та з порожнім кешем
NuGet те саме відновлення і збирання проходять із системним Wine 11.21 і з
GE-Proton11-9.

Eidos нічого не встановлює з рівнів 2 чи 3, доки ви не попросите:

```sh
eidos prereqs skyrimse            # show what the registered tools need, and their state
eidos prereqs skyrimse --install  # install what is missing (the bundle's copies first, then downloads)
```

У GUI ті самі стани розташовані під полем Prereqs, а відсутні є кнопками. Verb,
який не є ані вбудованим, ані середовищем виконання, ані verb Рівня 2,
повідомляється як ймовірна одруківка, а не пропонується до завантаження.

`eidos prereqs <instance> --install` відмовляє, поки гра, Steam чи інструмент
досі тримають префікс. Середовища виконання Рівня 3 встановлюються навіть до
появи префікса. Інсталятори, які Eidos запускає сам, потребують існуючого
префікса: поки магазин не запустив гру один раз, вони зупиняються з «start the
game once through its store, then install again». Verbs Рівня 2 встановлюються по
одному, і кожен успіх записується, тож після невдачі та сама команда
продовжує. Для копії з GOG чи Epic без налаштувань Heroic `--install` копіює
вбудовані DLL і зупиняється перед verbs Рівня 2: він радить скористатися
winetricks цього раннера і читає `winetricks.log` префікса під час наступної
перевірки.

### Чому DynDOLOD потребує `dotnet10`

DynDOLOD не будує object LOD сам: він викликає LODGen, і постачає їх три.
`LODGenx64.exe` націлений на .NET Framework 4.8, який під Proton скеровується на
Mono від Wine, чий ініціалізатор `System.Uri` викликає метод, якого Mono не
реалізує. LODGen помирає до першого рядка роботи, лишаючи журнал із банером версії
і більш нічим, та діалог DynDOLOD, який каже лише "failed for one or more worlds".

Встановлення справжнього .NET Framework цього не виправляє: Proton замінює
`mscoree.dll` - завантажувач, який його знайшов би - симлінком у власне дерево, і
робить це знову при кожному оновленні префікса.

Збірка, яка працює, - це `LODGenx64Win10.exe`, націлена на сучасний .NET, яка
ніколи не торкається `mscoree`. Наведіть `DOTNET_ROOT` на середовище виконання
.NET 10 - і вона запрацює. Саме це надає `dotnet10`, і Eidos встановлює змінну
під час запуску будь-якого інструмента, який її оголошує.

### Чому Pandora потребує `dotnet10`

Pandora - це застосунок на Avalonia, а не на WPF, і вона націлена на `net10.0`
від Pandora 4.1.0, тож її запускає саме середовище виконання .NET 10. Коли вона
не знаходить середовища виконання, то радить установити .NET Desktop Runtime. Це
загальний текст, який показує лаунчер .NET для будь-якої GUI-програми, що не
знайшла середовища виконання, і `dotnetdesktop8` цього не виправляє.

Eidos 1.21.0 і старіші давали Pandora `dotnetdesktop8`, а запис зберігає свій
рядок `prereqs=`. Коли Eidos читає запис Pandora, що досі перелічує лише
`dotnetdesktop8`, а `.runtimeconfig.json` поруч із її виконуваним файлом називає
`net10.0`, запис отримує натомість `dotnet10`. Pandora 2.x націлена на .NET 8 і
лишає те, що має.

### Чому PGPatcher потребує `--ignore-mo2vfscheck`

PGPatcher переписує меші та плагіни так, щоб наявні у вас моди текстур (vanilla,
parallax, complex material, PBR) використовували правильний шейдер на кожній
поверхні. Він відмовляється працювати поза менеджером модів, бо латати голу теку
гри було б руйнівно.

PGPatcher шукає usvfs, шар перехоплення DLL, який MO2 впроваджує в гру під
Windows. В Eidos його немає: об'єднаний вигляд - це монтування FUSE, у яке Wine
заходить, не знаючи про його існування. Тож перевірка нічого не знаходить і
інструмент негайно завершується з

```
Please verify that you are launching PGPatcher from MO2, VFS not detected.
```

називаючи програму, якої користувач не запускав, ще до будь-якої роботи.
Відповідь самого автора на два повідомлення з Linux ([#716][pg716] і
[#725][pg725], обидва з Fluorine, лінуксового форку MO2, побудованого на FUSE з
тієї самої причини) - прапорець, що пропускає перевірку.

Тому Eidos підставляє його сам. Знайдений у пулі модів PGPatcher приходить із
уже виставленим аргументом, а введення `PGPatcher` у полі назви діалогу
Executables заповнює поле Arguments так само. Те, що ви ввели, завжди перемагає:
підставляється лише залишене порожнім поле, точно як у передумовах вище.

Список у `default_args` (`crates/eidos-instance/src/tools.rs`), поряд із
`default_prereqs`.

Його середовище виконання нічого не вимагає, що незвично для інструмента на .NET:
він несе власне (`dotnetlib/`, з `runtimeconfig.json`, що оголошує
`includedFrameworks`) і кладе бібліотеки CRT від Microsoft поряд із виконуваним
файлом. Залиште Prereqs порожнім.

[pg716]: https://github.com/hakasapl/PGPatcher/issues/716
[pg725]: https://github.com/hakasapl/PGPatcher/issues/725

### PGPatcher і PGLite у режимі Mod Organizer 2

Коли Mod Manager має значення `None`, PGPatcher бачить одну об'єднану теку
`Data` і не може визначити, з якого мода походить меш чи текстура, тож йому
нічого показати в конфліктах і немає порядку модів, якого слід дотримуватися.
Його режим `Mod Organizer 2` читає сам екземпляр: `modlist.txt` профілю,
увімкнені моди в порядку пріоритету та файли в теці кожного мода. PGLite, версія
всередині гри, читає екземпляр так само. Екземпляр Eidos уже має структуру MO2
(`mods/`, `profiles/<name>/modlist.txt`, `overwrite/`), тому цей режим із ним
працює.

У лаунчері PGPatcher:

1. Встановіть **Mod Manager** на `Mod Organizer 2`.
2. Встановіть **MO2 Options -> Instance Location** на теку екземпляра Eidos,
   записану як шлях Windows на диску `Z:` у Wine, яким є `/`. Портативний
   екземпляр у `/mnt/Games/Eidos-Skyrim` записується як
   `Z:\mnt\Games\Eidos-Skyrim`; глобальний як
   `Z:\home\<you>\.local\share\Colony\Eidos\instances\<game id>`.
3. Залиште `--ignore-mo2vfscheck` в аргументах інструмента. У цьому режимі
   PGPatcher шукає usvfs і зупиняється, якщо його немає.

PGPatcher приймає теку, лише якщо в ній є `modorganizer.ini`, тому Eidos
записує `ModOrganizer.ini` у корінь екземпляра щоразу, коли запускає гру або
інструмент, для профілю, що запускається. Файл перезаписується, лише коли
змінюється його вміст. Він містить:

- у `[General]`: `gameName` (назва гри в MO2, тобто `New Vegas` для Fallout: New
  Vegas), `gamePath` (теку встановлення гри з магазину як шлях `Z:`, так само й
  для екземпляра, що працює з копії гри) і `selected_profile`;
- у `[Settings]`: `mod_directory`, `profiles_directory` і
  `overwrite_directory` як абсолютні шляхи `Z:`, а також `download_directory`,
  якщо екземпляр має теку `downloads/`.

Його перший рядок - коментар про те, що файл записав Eidos. Файл
`ModOrganizer.ini` без цього рядка, з будь-яким написанням назви, ніколи не
змінюється й не видаляється: екземпляр MO2, який ви відкрили в Eidos,
зберігає свій, і PGPatcher читає цей файл як є. MO2 відкидає коментарі, коли
зберігає свої налаштування, тож файл, поверх якого зберіг MO2, відтоді належить
MO2. Порожній файл вважається файлом Eidos.

У такому файлі вказано профіль, який MO2 вибрав останнім, і PGPatcher
використовує цей профіль, а не той, що запускає Eidos. Якщо вони відрізняються,
Eidos під час запуску пише попередження в журнал. Виберіть той самий профіль у
MO2 або перейменуйте чи видаліть файл, щоб Eidos записав свій.

Інструменти в режимі Mod Organizer 2 також читають гру з `gamePath` цього файла.
Коли він не називає ні теку гри, з якої працює екземпляр, ні інсталяцію з
магазину, вкладка Diagnostics показує **ModOrganizer.ini points tools at another
game folder** із цим шляхом і текою гри, яку запускає цей екземпляр. Змініть
`gamePath` у файлі або видаліть файл, щоб Eidos записав власний.

Eidos записує свій файл лише під час запуску чогось, тож між запусками в ньому
вказано профіль останнього. Інструмент, який запускає Eidos, знаходить
там свій профіль.

PGPatcher зупиняється з помилкою, коли в профілі немає жодного увімкненого мода,
і коли його тека виводу є текою увімкненого мода, так само як під MO2.

## Власні програми Wine у префіксі гри

Меню File запускає чотири програми Wine в префіксі гри: winecfg, regedit,
файловий менеджер Wine і програму видалення. Вони стартують як будь-який
інструмент, зі збіркою Proton або Wine, яка запускає інструменти гри, за
змонтованих модів, а вікно чекає на їх завершення. **Prefix drive_c** відкриває
диск `C:` префікса у вашому файловому менеджері. Рядок залишається сірим, доки в
префіксі немає цієї програми, що стається, коли магазин уперше запускає гру. З
термінала `eidos tool <instance> run winecfg` робить те саме, так само як `regedit`,
`explorer` і `uninstaller`, коли жоден інструмент у списку не має такої назви.

Зміна `installed path` гри, зроблена в regedit, повертається на місце під час
наступного запуску інструмента; див. наступний розділ.

## Шлях до гри у префіксі

Windows-інструменти знаходять свою гру, читаючи
`HKLM\Software\Bethesda Softworks\<game>` `installed path` - ключ, який пише
власний інсталятор гри. Steam під Proton ніколи не запускає цей інсталятор. Без
ключа xEdit, Wrye Bash і DynDOLOD відкриваються на порожньому шляху.

Перед запуском інструмента Eidos пише ключ імпортом через `regedit` у префіксі
гри, якщо тільки попередній імпорт уже не записав той самий шлях і префікс усе
ще його тримає. Ключ називає інсталяцію з магазину, так само й для екземпляра, що
працює з копії гри, бо об'єднаний вигляд змонтовано там. Для інструмента, що
оголошує `dotnetsdk10`, той самий імпорт додає кореневі сертифікати підпису
NuGet (див. [вище](#три-різновиди-передумов)). Інструмент із `runner=native`
пропускає цей крок. Коли префікса ще немає або його тримає інша програма,
інструмент усе одно запускається, а Eidos виводить попередження, яке називає
магазин, з якого один раз запустити гру, або програму, яку треба закрити. Коли
ключ називає теку, відмінну від інсталяції з магазину, вкладка Diagnostics показує
**Windows tools cannot find <game>**, доки наступний запуск інструмента не запише
його знову.

## Як дістатися інструмента: приховати, закріпити і ярлик на робочому столі

Типовий набір гри містить інструменти, якими ви, можливо, ніколи не
скористаєтесь. У діалозі Executables:

- **Pin to top** ставить запис на початок списку Run.
- **Hide from picker** прибирає запис, не видаляючи його.
- **Desktop shortcut** пише `.desktop` у `~/.local/share/applications`, тож він
  з'являється у меню програм і в пошуку, а не на робочому столі. Він виконує
  `eidos tool <instance> run <title>` напряму, тож інструмент піднімається через
  об'єднаний вигляд із профілем цього екземпляра, і вікно Eidos відкривати не
  потрібно.

Приховування і закріплення стосуються лише того, як інструмент дістають, тож вони
застосовні і до типових наборів для кожної гри, і до ваших власних записів.

У завантажувача script extender, лаунчера та бінарного файла гри немає кнопки
Desktop shortcut. Вони запускають гру, а гра завжди запускається через свій
магазин, і це вже робить ярлик самого магазину. Ярлик, створений для одного з
них в Eidos 1.22 або раніше, і далі працює: як і команда
`eidos tool <instance> run <title>`, набрана в терміналі, він просить магазин
запустити гру, так само як Run у вікні, яке не відкривав жоден магазин. Якщо
налаштування в магазині немає, команда нічого не запускає і виводить, що задати.
Ярлик не показує жодного повідомлення, тож запустіть ту саму команду в терміналі,
щоб його прочитати.

Eidos передає магазину будь-який запис таким чином, коли назва файлу його
виконуваного файла збігається (без урахування регістру) з завантажувачем script
extender, лаунчером чи бінарним файлом гри: типовий запис, доданий вами, імпортований
із MO2 або запуск `--exe`. Спершу він позначає цей екземпляр як останній
використаний, щоб вікно, яке відкриє магазин, показало цей екземпляр, потім
виконує `steam -applaunch <id>`,
`xdg-open heroic://launch?appName=<app>&runner=<runner>` для Heroic або
`legendary launch <app>`. З `--print` він друкує цю команду магазину й нічого не
запускає. Команда `steam` має бути в `PATH`: Flatpak Steam її туди не кладе, тож
запуск не вдається, а повідомлення радить запустити гру зі Steam.

Запис запускається напряму через об'єднаний вигляд, як будь-який інструмент, коли
процес запустив магазин: задано одну зі змінних `SteamGameId`, `SteamAppId`,
`HEROIC_APP_NAME`, `HEROIC_APP_RUNNER` або `EIDOS_STORE_STARTED`. Без жодної з
них Eidos сам не запускає гру через Proton. Коли в екземпляра немає завантажувача
script extender (у теці гри, з якої він працює, у `Root/` увімкненого мода чи в
`Overwrite/Root/`), нічого не запускається, а рядок радить спершу встановити
script extender. Для копії з GOG поза Heroic або ідентифікатора магазину, який
Eidos не може передати, він радить запустити гру з цього магазину.

Профіль може мати власний ярлик для гри. Клацніть профіль правою кнопкою миші й
виберіть **Desktop shortcut**: ярлик запускає
`eidos tool <instance> run "<game>" --profile <name>`, і ця команда робить
профіль активним, як вибір у вікні, а потім просить магазин запустити гру. Вікно
Eidos, яке відкриває магазин, показує цей профіль. `--profile` працює з
будь-якою командою `eidos tool ... run` і вибирає профіль до запуску
інструмента; з `--print` він нічого не вибирає.

## Інструмент, який сам є застосунком Steam

Creation Kit - окремий застосунок Steam і хоче власний AppID; кілька інших
інструментів моддингу, що постачаються через Steam, такі самі. Задайте
**Steam AppID** у записі, і Eidos запустить його під цим id замість
ідентифікатора гри.

На Windows це означало б інший лаунчер. Тут це дві змінні середовища на тому
самому запуску, `SteamAppId` і `SteamGameId`. Eidos задає обидві, бо Proton читає
одну, а власні бібліотеки Steam читають іншу, і інструмент, який бачить їхню
розбіжність, ламається без зрозумілої помилки. `eidos tool ... --print` показує
точно те, що отримав би справжній запуск.

## Змінні середовища та інструменти без Proton

Три ключі `<instance>/tools.ini` поки не мають поля в діалозі Executables, тож
допишіть їх у секцію інструмента вручну. Кожен рядок `env=NAME=value` задає одну
змінну лише для запусків цього інструмента:

```ini
[Tool/BodySlide]
exe=Data/CalienteTools/BodySlide/BodySlide x64.exe
env=PROTON_LOG=1
env=WINEDEBUG=-all
```

Eidos застосовує ці рядки після всього, що задає сам, і після змінних із
`launch-env.ini` профілю, тож значення, вказане тут, замінює обидва. Це стосується
й `WINEDLLOVERRIDES`, який Eidos складає з DLL, що їх постачають ваші моди:
інструмент, який його задає, мусить перелічити в ньому кожну потрібну йому DLL.
Обгортки профілю огортають команду інструмента так само, як команду гри; див.
[Змінні та обгортки для профілю](usage.md#змінні-та-обгортки-для-профілю). Ім'я
складається з літер, цифр і `_` і не починається з цифри. Рядок з будь-яким іншим
ім'ям пропускається.

`runner=native` запускає сам `exe`, без Proton. Об'єднаний вигляд монтується як
для будь-якого інструмента, а рядки `arg0=`, `arg1=` стають його аргументами. Це
потрібно для програми під Linux або для інструмента до копії, якою не керує
Steam і для якої Heroic не записав ранер: `exe` - це Wine цієї копії, програма
для Windows іде першим аргументом, а префікс задається через `env=`.

```ini
[Tool/SSEEdit (GOG)]
exe=/opt/wine-ge/bin/wine
arg0=/home/me/Games/Skyrim/SSEEdit.exe
workdir=/home/me/Games/Skyrim
runner=native
env=WINEPREFIX=/home/me/Games/Heroic/Prefixes/default/Skyrim
```

`exe` має бути абсолютним шляхом. Робочий каталог за замовчуванням - тека, в
якій лежить `exe`, тут тека раннера, тому задайте `workdir=`. На об'єднаний
шлях переписується лише `exe`: для програми Windows усередині мода вкажіть її
шлях у теці `Data` гри, де її показує об'єднаний вигляд. Нативний інструмент
пропускає кроки Proton: ключ реєстру, описаний вище, кеш шейдерів Steam,
порожні корені .NET і вилучення оверлея Steam з `LD_PRELOAD`.

Для копії з GOG або Epic, встановленої через Heroic, такий запис інструментам не
потрібен, якщо в налаштуваннях гри в Heroic (`GamesConfig/<appName>.json`)
вказано збірку Wine або Proton: Eidos запускає їх цією збіркою в префіксі Heroic
для гри, а `eidos prereqs <instance> --install` використовує її для інсталяторів
і для winetricks. Копія, встановлена лише через Legendary, не має налаштувань
Heroic.

`slr=1` запускає інструмент, і імпорт у реєстр перед ним, усередині контейнера
Steam Linux Runtime, який указує Proton інструмента (`require_tool_appid` у його
`toolmanifest.vdf`), так само, як Steam запускає гру. Це середовище виконання
має бути встановлене в одній із бібліотек Steam; якщо його немає, запуск
зупиняється й називає застосунок Steam, який треба встановити. `eidos prereqs` і
далі запускає свої інсталятори та winetricks на хості, а інструмент із
`runner=native` ігнорує цей ключ. Контейнер бачить вашу домашню теку та
бібліотеку Steam із грою. Інструменту, моду чи середовищу виконання деінде,
наприклад на іншому диску, потрібен `env=STEAM_COMPAT_MOUNTS=/цей/шлях` (кілька
шляхів розділяються `:`). Proton, встановлений у
`/usr/share/steam/compatibilitytools.d`, імовірно, не працюватиме з `slr=1`, бо
`/usr` усередині контейнера належить середовищу виконання. Запуск інструмента
всередині контейнера ще не перевірявся.

`eidos tool <instance> run <title> --print` показує остаточну команду і кожну
змінну, яку запуск задає поверх успадкованого середовища, разом із цими рядками.
Для запису, що запускає гру, він друкує натомість команду магазину (див.
[Як дістатися інструмента](#як-дістатися-інструмента-приховати-закріпити-і-ярлик-на-робочому-столі)).

## BethINI Pie

Eidos не постачає BethINI Pie. Покладіть завантажену зі сторінки на Nexus версію в
`mods/` цього екземпляра або у вашу теку інструментів, і `Bethini.exe` з'явиться в
списку інструментів, у тих самих іграх, що й PGPatcher. Запущений через Eidos, він
змінює копію INI-файлів гри, що належить профілю. Перед кожним запуском
інструмента, чия назва містить `bethini`, Eidos зберігає точку відновлення цих
INI; Backups на панелі інструментів, потім INIs, повертає одну з них. INI, якого
не було під час копіювання, лишається як є. Діалог тримає 10 найновіших точок
відновлення кожного виду, а відновлення спершу робить резервну копію поточних INI,
тож хибний вибір можна скасувати.

## Власні налаштування інструмента однаково лишаються його власними

Eidos не перевіряє більшість налаштувань інструментів; хибне зазвичай
призводить до збою без помилки.

Game Data Path у BodySlide (Settings) має вказувати на каталог `Data` гри, а не
на теку гри над ним. Задайте на рівень вище - і пакетна збірка звітує "All sets
processed successfully" та пише 1439 мешів туди, де гра ніколи не шукатиме. Eidos
їх ловить в `Overwrite/Root/`, тож вашу інсталяцію гри не зачеплено, а єдина ознака
в грі - що ваші тіла не зібрані.

Перед запуском BodySlide або Outfit Studio рядок стану попереджає, якщо
`GameDataPath` або `OutputDataPath` у переможному
`CalienteTools/BodySlide/Config.xml` під час запуску не веде до теки `Data` гри,
а вкладка Diagnostics показує те саме попередження як картку зі значенням, яке
треба задати. `eidos check <instance>` теж про це повідомляє. Шлях на `S:`
читається так, як Eidos зіставляє `S:` для інструмента, тобто з текою бібліотеки
Steam. `OutputDataPath` усередині теки `mods/` екземпляра, для мода виводу,
приймається. Diagnostics також показує картку, коли `Overwrite/Root/` містить
теку `meshes` або `textures`.

Вивід інструментів належить Overwrite. Коли запуск дає щось варте збереження,
Overwrite -> Create mod... перетворює це на звичайний мод, який можна
впорядковувати, вимикати і видаляти, як будь-який інший.
