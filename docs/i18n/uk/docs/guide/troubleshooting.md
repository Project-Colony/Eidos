# Діагностика та усунення несправностей

Усе на той день, коли гра бачить щось, із чим файлова система не згодна: перемикачі
середовища, читання лічильників операцій, відомі проблеми з їхньою історією та
історія passthrough.

### Діагностика VFS

На випадок, коли гра бачить щось, із чим файлова система не згодна, є дві змінні
середовища:

```sh
EIDOS_FUSE_STATS=1                  # лічильники операцій, скидаються при демонтуванні
EIDOS_FUSE_NO_CACHE=1               # усі кеші з боку ядра вимкнено
EIDOS_FUSE_NO_CACHE=attr,neg,keep,dir   # або назвати їх поіменно
```

Саме деталізована форма знайшла описаний нижче виліт: вимкнути всі чотири - це
відповідь на питання «чи це кешування?», а назвати їх поіменно - відповідь на
питання «яке саме». Лічильники відповідають на другу половину: завантаження, що
показує `read 0`, - це завантаження, де `FUSE_PASSTHROUGH` віддав кожен байт у ядрі,
а отже все, що ви збиралися налаштовувати на шляху читання, уже безкоштовне.

## Змонтувати об'єднання вручну

Перша `--layer` перемагає в конфлікті; остання - ваші недоторкані дані гри.
Монтуванню потрібні лише `/dev/fuse` і `fusermount3` (без overlayfs, без Wine):

```sh
eidos-fuse --layer mod_b --layer mod_a --layer game_data /mnt/point
# ... читайте й пишіть через /mnt/point ...
fusermount3 -u /mnt/point
```

Записи потрапляють до `--overwrite <dir>` (тимчасова тека, якщо не вказано), тож
самі шари лишаються недоторканими навіть тут.

#### Чому passthrough вимкнений типово

Passthrough передає ядру справжній файл-основу, тож читання цілком оминають
цього демона. Вимір A/B нижче зроблено з попередньою версією демона, до зміни,
описаної далі у відомій проблемі «FUSE passthrough не дає грі завантажити
жодного вмісту модів». Ця зміна оминає найімовірнішу причину, але в грі її ще не
виміряно заново, тож passthrough типово лишається вимкненим, доки цього не
зроблять. Виміряно A/B на Skyrim SE 1.6.1170, proton-cachyos 11.0, ядро 7.1.4,
той самий порядок завантаження з 82 додатків; єдина змінна - чи несе двійковий
файл цю здатність:

| passthrough | відмови `NtCreateFile` зі `STATUS_ACCESS_VIOLATION` |
|-------------|------------------------------------------------------|
| увімкнено   | 152 - 75 `.bsa`, 65 `.esl`, 10 `.esm`, 2 `.esp`     |
| вимкнено    | 0                                                    |

З увімкненим гра не відкривала жодного власного архіву чи додатка, що в грі
проявлялося як моди, яких немає, - без помилки, без рядка в журналі. З вимкненим
той самий порядок завантаження доходив до гри з живими додатками, архівами та
скриптами Papyrus.

Відмова була невидима зсередини демона, що й зробило її дорогою в пошуку:
власний `open` демона був успішний щоразу, і ядро жодного разу не відмовило у
файлі-основі (перевірено на цілій невдалій сесії з `EIDOS_FUSE_TRACE=open`: нуль
`open FAILED`, нуль `passthrough refused`). Помилка виникала після того, як
демон відповів `opened_passthrough`, тож жодне журналювання з боку демона не
могло її побачити. Вона й не залежала від розширення - била по архівах і
додатках однаково, тобто по файлах, які гра тримає відкритими весь час роботи.

`EIDOS_FUSE_PASSTHROUGH=1` вмикає його назад, щоб виміряти вигоду або перевірити
механізм ще раз. Попередження про здатність у лаунчері та у вкладці Diagnostics
з'являються лише тоді, коли ви її попросили.

Щоб запустити саму гру через Eidos, задайте її параметр запуску в Steam:

```
eidos play skyrimse -- %command%
```

Префікс `WINEDLLOVERRIDES` не потрібен. Коли увімкнений мод імпортує
`d3dcompiler_47`, Eidos розгортає свою вбудовану копію в префікс, примусово
робить її рідною і зливає це з будь-якими перевизначеннями DLL, які постачає мод
(завантажувачі ENB/ReShade/`.asi`).

### Чи справді використовується індекс шарів?

`LayerStack::new` будує або повну карту шарів лише для читання, або жодної.
Без карти кожен запит обходить шари, як раніше: відповіді ті самі, завантаження
збереження триває приблизно втричі довше, а більше нічого зовні не змінюється.

Коли індекс вимкнено, монтування один раз під час старту повідомляє причину:

```
eidos-fuse: layer index off (<reason>); every lookup walks all layers
```

Причина називає нечитабельний каталог, шар глибший за 64 каталоги, понад
4 000 000 записів або `EIDOS_NO_INDEX`. Рядок потрапляє в журнал запуску: у
`logs/run-*.log` екземпляра під час запуску з вікна, у консоль Steam під час
запуску через Steam. З `EIDOS_FUSE_STATS=1` звіт під час розмонтування також має
рядок `layer index:`, і ненульовий лічильник `unindexed` на звичайному монтуванні
означає, що індекс був вимкнений.

Приклади нижче перевіряють те саме офлайн, на теках екземпляра, без монтування:

```sh
cargo run --release -p eidos-core --example index_health -- <mods-dir> <overwrite-dir>
cargo run --release -p eidos-core --example index_agrees -- <mods-dir> <overwrite-dir>
cargo run --release -p eidos-core --example listing_cost -- <mods-dir> <overwrite-dir>
```

`index_health` розв'язує справжні шляхи з індексом і без нього та порівнює обходи
тек. `index_agrees` перевіряє, що обидва відповідають ТЕ САМЕ, на кожному шляху й
кожному переліку реального екземпляра. `listing_cost` вимірює, що карта об'єднаних
нащадків заощаджує на `readdir`.

`EIDOS_NO_INDEX=1` примусово вмикає обхід - на випадок, коли зневаджують саме
різницю між двома відповідями.

## Відомі проблеми

### DLSS чи генерація кадрів мовчки нічого не робить

Три окремі причини, кожна без жодного повідомлення про помилку: NVAPI не увімкнений
у параметрах запуску, ексклюзивний повноекранний режим або застаріла стеля FPS у
Reflex. Повний перелік - у [graphics.uk.md](graphics.md).

**Мод, що пише одну теку двома способами, втрачав усе під другим написанням.**
Виправлено. ext4 розрізняє `meshes/` і `Meshes/`; об'єднаний вигляд не має, а
справжні моди постачають обидва - у XP32 Maximum Skeleton анімації та файл поведінки
FNIS лежать під написанням з великої літери, а `character assets` - під іншим.

Розв'язувач брав точний збіг регістру для кожного складника шляху й тримався за
нього: заходив у `meshes/`, не знаходив там решти шляху й кидав УВЕСЬ ШАР. Кожен
файл під іншим написанням був невидимий для гри - без помилки, без журналу, без
нічого в жодній діагностиці. На реальному екземплярі з 50 шарів це були 74 файли.

Складник, що збігся, тепер кандидат, а не рішення; точний регістр і далі пробується
першим, і лише коли решта під ним не знаходиться, обхід шукає сусідів, рівних із
точністю до регістру. Переліки мали ту саму ваду текою вище й тепер читають кожну
таку теку в кожному шарі.

**LODGen від DynDOLOD помирає, лишаючи порожній журнал.** Виправлено за допомогою
`dotnet10`; див. [tools.md](tools.md). Симптом ні з чим не сплутати:
`LODGen_SSE_<world>_log.txt` із банером версії, рядком `.NET Version:` і більш
нічим - для кожного світу, плюс діалог, що каже лише «failed to generate object LOD
for one or more worlds». Причина - Mono з Wine, який відповідає замість .NET
Framework, і жодне встановлення .NET Framework цього не лікує: Proton замінює
`mscoree.dll` символічним посиланням у власне дерево під час кожного оновлення
префікса.

**Wine не міг зрозуміти, що монтування згортає регістр.** Виправлено, і саме це
мало значення.

`get_dir_case_sensitivity` у Wine спершу питає теку через `FS_IOC_GETFLAGS`,
потім винюхує маркер, який CIOPFS лишає в теках, що їх обслуговує. Якщо немає ні
того, ні іншого, Wine вважає файлову систему ЧУТЛИВОЮ до регістру, і кожен
пошук, чиє написання не збігається побайтово, відкочується до читання ЦІЛОЇ теки
заради нечутливого до регістру збігу. Ігри Bethesda просять
`data/ccbgssse001-fish.bsa`, тоді як файл зветься `ccBGSSSE001-Fish.bsa`, тож це
спрацьовувало майже на кожному ресурсі: 4471 проба маркера і 2236 повних
перечитувань теки за вісім секунд та 195796 перелічень `Data` за дев'яносто.
Skyrim SE так і не доходив до головного меню - він сидів на 240 МБ резидентної
пам'яті, поки демон спалював 92 % ядра.

Eidos згортав регістр у `resolve_read` від самого початку. Уся ціна була в тому,
що він ніколи про це не казав. Тепер `lookup` відповідає `.ciopfs`; `readdir` і
далі його не перелічує. `ioctl` також відповідає на `FS_IOC_GETFLAGS` для тек
прапором casefold, який нинішній Wine запитує перед пошуком маркера.

Дві речі зробили це смертельним, а не просто повільним. Ціна росте з розміром теки,
тож встановлення вмісту Anniversary (`Data` з 37 файлів до 177) переважило шальку. І
`opendir` жадібно будував об'єднаний перелік, що є чистим марнуванням, коли Wine
відкриває теку лише заради `stat` того маркера всередині, - знімок тепер робиться на
першому `readdir`.

Після: головне меню, 2,1 ГБ резидентної пам'яті, демон на 0 % CPU.

`EIDOS_FUSE_TRACE=opendir` - це те, що його знайшло, і воно постачається. Лічильники
операцій кажуть «скільки»; 195796 перелічень однієї теки в загальній сумі невидимі.

**Те, що гра переписувала `plugins.txt` порожнім**, найімовірніше було тим самим:
`Data`, який вона не могла перелічити за розумний час, звідки й висновок, що там
нічого немає, - і збереження цього висновку. Не доведено й варте перевірки. Хай там
як, захист захоплення (захоплення, що повністю спорожняє активний набір,
відхиляється за будь-якого розміру) означає, що пошкодити профіль це більше не може.

**`FOPEN_KEEP_CACHE` вимкнений.** Виправлено, і варто знати чому. Він валив
Skyrim SE на розіменуванні нуля через лічені секунди після головного меню,
детерміновано, без жодного встановленого мода; решту трьох кешів з боку ядра
відсікали по одному бісекцією, і значення мав лише цей. Ця бісекція йшла з
увімкненим `FUSE_PASSTHROUGH`, а ядро завершує з EIO відкриття через
passthrough, що несе `FOPEN_KEEP_CACHE`, тож з цим прапорцем кожне відкриття
через passthrough провалювалося. Можливо, саме ці невдалі відкриття й валили
гру, а сам прапорець при вимкненому passthrough жодного разу не перевіряли.
Відповіді через passthrough його більше не несуть. Його втрату тоді виміряли як
безкоштовну, але з увімкненим passthrough демон обслуговує *нуль* читань
(`EIDOS_FUSE_STATS` повідомляв `read 0` за повне завантаження), тож при
passthrough, типово вимкненому (нижче), справжня ціна не виміряна. Увімкніть
`EIDOS_FUSE_KEEP_CACHE=1`, щоб випробувати його окремо.

### FUSE passthrough не дає грі завантажити жодного вмісту модів

Демон тепер оминає найімовірнішу причину (нижче), але в грі це ще не виміряно
заново, тож passthrough типово лишається вимкненим; `EIDOS_FUSE_PASSTHROUGH=1`
вмикає його. До цієї зміни з увімкненим passthrough Skyrim SE не міг відкрити
152 власні файли (75 `.bsa`, 65 `.esl`, 10 `.esm`, 2 `.esp`) зі
`STATUS_ACCESS_VIOLATION` проти 0 при вимкненому, на ядрі 7.1.4, - тобто вміст
модів не завантажувався, мовчки. Ядро підіймало помилку після того, як демон
відповів `opened_passthrough`, тож власні журнали демона показували чистий
прогін (нуль невдалих відкриттів, нуль відхилених файлів-основ).

Ядро прив'язує до кожного inode один файл-основу (`fs/fuse/iomode.c`).
Відкриття, що приносить другий ідентифікатор файла-основи для inode, який його
вже має, завершується з EIO, як і звичайне відкриття (без `FOPEN_PASSTHROUGH`)
inode, що має файл-основу. Відкриття через passthrough, що несе
`FOPEN_KEEP_CACHE`, теж завершується з EIO. Демон раніше реєстрував новий
ідентифікатор при кожному відкритті, тож друге відкриття файла, який гра вже
тримала відкритим, провалювалося. Wine повідомляє EIO як
`STATUS_ACCESS_VIOLATION`; це та сама помилка 152 невдалих відкриттів. Це
правило взято з вихідного коду ядра, і воно збігається з цими 152 відмовами,
тому саме воно найімовірніша причина.

Тепер демон реєструє один файл-основу на inode, спільний для всіх його
відкриттів через passthrough, і ніколи не ставить `FOPEN_KEEP_CACHE` на
відкриття через passthrough. Passthrough стосується лише відкриттів тільки для
читання у файлів із шарів гри та модів розміром від 1 MiB або із закінченням
`.dll`, `.exe` чи `.asi`. Щойно цей файл-основу зареєстровано, його використовує
кожне відкриття файла тільки для читання, а поки файл має звичайні відкриття,
нові читачі теж отримують звичайні відкриття. Файл з Overwrite ніколи не йде
через passthrough, а монтування, яке проєктує часові позначки додатків, взагалі
його не використовує. Відкриття на запис файла, який тримають читачі через
passthrough, отримує ETXTBSY (у Wine: `STATUS_SHARING_VIOLATION`) до будь-якого
copy-up, тож відкриття з `O_TRUNC` не може залишити в Overwrite порожню копію,
яка сховала б файл мода.

### Кнопка Mod Manager Download нічого не робить

У розділі Налаштування > Завантаження показано, яка програма отримує посилання `nxm://`. Якщо це не Eidos, програми немає або жодну не задано, на сторінці Стан з'являється картка. Кнопка Зареєструвати записує `eidos-nxm.desktop` і робить його обробником за замовчуванням для `x-scheme-handler/nxm`. У терміналі те саме робить `eidos nxm --register`.

Якщо в стані вже вказано Eidos, а кнопка досі нічого не робить, браузер міг зберегти попередній вибір. Очистьте збережений вибір для посилань nxm у налаштуваннях браузера, щоб він запитав знову. Браузер із Flatpak не може запускати програми хоста й передає посилання через портал робочого столу, який читає обробник, зареєстрований на хості.
