# Діагностика та усунення несправностей

Перемикачі середовища, читання лічильників операцій, Health-картки вкладки
Diagnostics, пошук мода, що стоїть за збоєм, що додати до звіту про ваду та відомі
проблеми з їхньою історією.

## Діагностика VFS

На випадок, коли гра бачить щось, із чим файлова система не згодна, є дві змінні
середовища:

```sh
EIDOS_FUSE_STATS=1                  # лічильники операцій, скидаються при демонтуванні
EIDOS_FUSE_NO_CACHE=1               # усі кеші з боку ядра вимкнено
EIDOS_FUSE_NO_CACHE=attr,neg,keep,dir   # або назвати їх поіменно
```

Саме деталізована форма знайшла виліт `FOPEN_KEEP_CACHE`, описаний у відомих
проблемах: вимкнути всі чотири - це відповідь на питання «чи це кешування?», а
назвати їх поіменно - відповідь на питання «яке саме». Лічильники відповідають на
другу половину. З увімкненим passthrough (типово він вимкнений) завантаження, що
показує `read 0`, - це завантаження, де `FUSE_PASSTHROUGH` віддав кожен байт у
ядрі, а отже все, що ви збиралися налаштовувати на шляху читання, уже безкоштовне.

Ще кілька перемикачів звужують пошук вади:

```sh
EIDOS_FUSE_TRACE=open,opendir       # журналювати кожен open / opendir (1 = усі канали)
EIDOS_FUSE_THREADS=1                # один потік демона (типово: кількість CPU, не більше 4)
EIDOS_FUSE_OPENDIR=1                # тримати дескриптори opendir, навіть коли ядро може їх пропустити
EIDOS_NO_INDEX=1                    # обходити шари замість індексу шарів
EIDOS_NO_OW_INDEX=1                 # те саме для індексу складу Overwrite
EIDOS_FUSE_KEEP_CACHE=1             # FOPEN_KEEP_CACHE знову ввімкнено, див. Відомі проблеми
```

Для запуску зі Steam поставте їх перед командою в параметрі запуску, наприклад
`EIDOS_FUSE_STATS=1 ~/.local/bin/eidos-gui %command%`. Вивід іде в журнал
запуску: `logs/run-*.log` екземпляра для запуску з вікна, консоль Steam для запуску
зі Steam.

Щоб подивитися на сам об'єднаний вигляд, `eidos shell <instance>` відкриває
оболонку в теці гри такою, якою її бачить гра, а
`eidos shell <instance> -- ls Data/meshes` виконує там одну команду; усе записане
потрапляє в Overwrite
([usage.md](usage.md#оболонка-в-обєднаному-вигляді)). Кнопка Save tree на вкладці
Data записує все об'єднане дерево `Data` у текстовий файл, по одному файлу на
рядок із модом, з якого він походить, із прихованою домашньою текою.

## Змонтувати об'єднання вручну

`eidos-fuse` постачається з пакетом Arch і зі збірками з джерельних кодів:
`just build` збирає його, а `just install` чи `install.sh` копіює, коли він є.
Пакет випуску і `eidos-linux` його не містять. Рядок використання:

```
eidos-fuse --layer <dir> [--layer <dir> ...] [--overwrite <dir>] <mountpoint>
```

Перша `--layer` перемагає в конфлікті; остання - ваші недоторкані дані гри.
Монтуванню потрібні лише `/dev/fuse` і `fusermount3` (без overlayfs, без Wine):

```sh
eidos-fuse --layer mod_b --layer mod_a --layer game_data /mnt/point
# ... читайте й пишіть через /mnt/point ...
fusermount3 -u /mnt/point
```

Записи потрапляють до `--overwrite <dir>` (тимчасова тека, якщо не вказано), тож
самі шари лишаються недоторканими навіть тут.

## Чому passthrough вимкнений типово

Passthrough передає ядру справжній файл-основу, тож читання цілком оминають
цього демона. Вимір A/B нижче зроблено з попередньою версією демона, до зміни,
описаної далі у відомій проблемі «FUSE passthrough не дає грі завантажити
жодного вмісту модів». Ця зміна оминає найімовірнішу причину, але в грі її ще не
виміряно заново, тож passthrough типово лишається вимкненим, доки цього не
зроблять. Виміряно A/B на Skyrim SE 1.6.1170, proton-cachyos 11.0, ядро 7.1.4,
той самий порядок завантаження з 82 додатків; єдина змінна - чи несе двійковий
файл цю здатність:

| passthrough | відмови `NtCreateFile` зі `STATUS_ACCESS_VIOLATION` |
|-------------|------------------------------------------------------|
| увімкнено   | 152 - 75 `.bsa`, 65 `.esl`, 10 `.esm`, 2 `.esp`     |
| вимкнено    | 0                                                    |

З увімкненим гра не відкривала жодного власного архіву чи додатка, що в грі
проявлялося як моди, яких немає, - без помилки, без рядка в журналі. З вимкненим
той самий порядок завантаження доходив до гри з живими додатками, архівами та
скриптами Papyrus.

Відмова була невидима зсередини демона: власний `open` демона був успішний щоразу,
і ядро жодного разу не відмовило у файлі-основі (перевірено на цілій невдалій
сесії з `EIDOS_FUSE_TRACE=open`: нуль `open FAILED`, нуль `passthrough refused`).
Помилка виникала після того, як демон відповів `opened_passthrough`, тож жодне
журналювання з боку демона не могло її побачити. Вона й не залежала від
розширення - била по архівах і додатках однаково, тобто по файлах, які гра тримає
відкритими весь час роботи.

`EIDOS_FUSE_PASSTHROUGH=1` вмикає його назад, щоб виміряти вигоду або перевірити
механізм ще раз. Попередження про здатність у лаунчері та у вкладці Diagnostics
з'являються лише тоді, коли ви його попросили.

## Чи справді використовується індекс шарів?

`LayerStack::new` будує або повну карту шарів лише для читання, або жодної.
Без карти кожен запит обходить шари, як раніше: відповіді ті самі, завантаження
збереження триває приблизно втричі довше, а більше нічого зовні не змінюється.

Коли індекс вимкнено, монтування один раз під час старту повідомляє причину:

```
eidos-fuse: layer index off (<reason>); every lookup walks all layers
```

Причина називає нечитабельний каталог, шар глибший за 64 каталоги, понад
4 000 000 записів або `EIDOS_NO_INDEX`. Рядок потрапляє в журнал запуску: у
`logs/run-*.log` екземпляра під час запуску з вікна, у консоль Steam під час
запуску через Steam. З `EIDOS_FUSE_STATS=1` звіт під час розмонтування також має
рядок `layer index:`, і ненульовий лічильник `unindexed` на звичайному монтуванні
означає, що індекс був вимкнений.

Приклади нижче перевіряють те саме офлайн, на теках екземпляра, без монтування:

```sh
cargo run --release -p eidos-core --example index_health -- <mods-dir> <overwrite-dir>
cargo run --release -p eidos-core --example index_agrees -- <mods-dir> <overwrite-dir>
cargo run --release -p eidos-core --example listing_cost -- <mods-dir> <overwrite-dir>
```

`index_health` розв'язує справжні шляхи з індексом і без нього та порівнює обходи
тек. `index_agrees` перевіряє, що обидва відповідають ТЕ САМЕ, на кожному шляху й
кожному переліку реального екземпляра. `listing_cost` вимірює, що карта об'єднаних
нащадків заощаджує на `readdir`.

`EIDOS_NO_INDEX=1` примусово вмикає обхід - на випадок, коли зневаджують саме
різницю між двома відповідями.

## Запуск гри через CLI

Щоб запустити гру через CLI `eidos`, а не через вікно, задайте в її параметрі
запуску Steam абсолютний шлях до `eidos`, наприклад:

```
~/.local/bin/eidos play skyrimse -- %command%
```

Префікс `WINEDLLOVERRIDES` не потрібен. Коли увімкнений мод імпортує
`d3dcompiler_47`, Eidos розгортає свою вбудовану копію в префікс, примусово
робить її рідною і зливає це з будь-якими перевизначеннями DLL, які постачає мод
(завантажувачі ENB/ReShade/`.asi`).

Eidos сам ніколи не запускає гру через Proton. `eidos tool <instance> run <title>`
із записом, що запускає гру (завантажувач script extender, лаунчер чи двійковий
файл гри), просить запустити її магазин, якому належить копія, так само як Run у
вікні, яке не відкрив жоден магазин, і друкує, що задати, коли налаштування
магазину не запускає Eidos. `--print` друкує команду магазину замість її
виконання.

## Гра чи інструмент, що не закривається

Поки гра чи інструмент працює, кнопка Run стає кнопкою Stop, і на картці
блокування теж є кнопка Stop. Натисніть її двічі. Друге натискання завершує всі
програми, запущені цим запуском: спершу SIGTERM, потім через 10 секунд SIGKILL
для всього, що лишилося. Усе, що гра не зберегла, втрачається. Далі Eidos робить
те саме, що й після будь-якого виходу: зміни INI та плагінів повертаються в
профіль, вивід інструментів записується, а моди відмонтовуються. Запуск
записується з кодом виходу 143, що б не повернула програма, тож
`eidos sessions <instance> diff` ніколи не бере його за останній вдалий. Unlock
працює інакше: повертає вікно й лишає програму запущеною. З термінала
`kill <pid>` для процесу `eidos` (pid є на картці блокування) робить те саме, що
Stop.

## Пошук того, що зламалося

Щоб знайти, яка зміна зламала гру:

- `eidos sessions <instance> diff` перелічує, що змінилося з останнього запуску
  гри, який завершився з кодом 0: моди, версії, порядок плагінів, INI і
  виконуваний файл гри ([usage.md](usage.md#що-змінилося-з-останнього-вдалого-запуску)).
- Test run поруч із Run грає з модами профілю, без модів або з вибраними модами, які ввімкнено,
  і майстрами, яких вони потребують, і спрямовує все, що гра пише, до
  `<instance>/test-run/`. Після запуску ви залишаєте або викидаєте кожну групу
  файлів: збереження, зміни INI, стан плагінів, вивід Overwrite і журнали
  ([usage.md](usage.md#тестові-запуски)).
- Find the mod behind a problem на вкладці Diagnostics запускає тестові запуски з
  половиною підозрюваних, що лишилися, щоразу й питає, чи проблема була. 200
  підозрюваних вимагають близько 8 запусків, а пошук переживає закриття Eidos
  ([usage.md](usage.md#як-знайти-мод-що-спричиняє-проблему)).

Зупинений запуск ніколи не підставляє Yes у цьому пошуку наперед, бо він
записується з кодом виходу 143 (див. вище).

## Health-картки

Вкладка Diagnostics показує Health-картку для кожної знайденої проблеми, з її
причиною і, для деяких, кнопкою, що її виправляє. Картки параметра запуску описано
в [install.md](install.md), картки NVAPI, повноекранного режиму й ENB - у
[graphics.md](graphics.md), а картки Proton і префікса - у наступному розділі.
`eidos check <instance>` друкує висновки, яким не потрібне вікно
([usage.md](usage.md#перевірки-стану-з-термінала) їх перелічує), зокрема картки
префікса, реєстру й диска `S:`. Лише вікно показує картку Proton з її варіантами
для Flatpak, невідомої та старішої збірки, порядок патчів, скрипти розширювача,
архіви, які не завантажує жоден додаток, вимоги Nexus, застарілі копії додатків і
картку Display.

### Система

- «vm.max_map_count is <value>» з'являється нижче 1048576 - типового значення в
  Arch Linux, Fedora 39 і новіших та Ubuntu 24.04 і новіших. Деякі ігри під Proton
  відображають більше областей пам'яті й тоді падають без помилки. Поставте
  `vm.max_map_count = 1048576` у файл під `/etc/sysctl.d`, наприклад
  `80-gamecompatibility.conf`, потім виконайте `sudo sysctl --system`.
- «The open files limit is <value>» з'являється, коли жорстка межа нижча за 524288,
  яких потребує esync у Proton; нижче неї ігри можуть не запускатися або падати.
  systemd 240 і новіші її задають. У старішій конфігурації задайте
  `DefaultLimitNOFILE=524288` у `/etc/systemd/system.conf` і
  `/etc/systemd/user.conf`, потім увійдіть знову.
- «Game files on a Windows file system» називає теку гри, префікс або корінь
  екземпляра, коли вони на `ntfs`, `ntfs3`, `fuseblk` (ntfs-3g, exfat-fuse),
  `exfat` або `vfat`. Proton потребує символічних посилань, прав Unix і назв, чутливих
  до регістру. Перенесіть гру, її префікс і екземпляр на файлову систему Linux,
  як-от ext4, btrfs чи xfs.

### Файли гри

Картка Game files угорі вкладки показує, чи екземпляр запускає інсталяцію з
магазину, чи копію гри всередині екземпляра
([usage.md](usage.md#файли-гри-встановлення-з-магазину-або-копія)). Запуски
відхиляються, з карткою, що каже причину, у трьох випадках:

- «The game copy '<folder>' is missing»: екземпляр запускає копію, якої вже немає.
  Поверніть її на місце або поверніться до версії з магазину.
- «'<folder>' has no <binary>»: тека, яку запускає екземпляр, не містить
  виконуваного файлу гри, тож це не копія гри.
- «<game> cannot run from a copy yet»: Morrowind, а також Oblivion з
  `bUseMyGamesDirectory=0` тримають список додатків у теці гри.

«ModOrganizer.ini points tools at another game folder» з'являється, коли
власний `ModOrganizer.ini` зі списку, не записаний Eidos, має `gamePath`, що
відрізняється від файлів гри, які запускає екземпляр. Інструменти в режимі Mod
Organizer 2, як-от PGPatcher, читають гру звідти. Змініть `gamePath` у цьому
файлі або видаліть файл, щоб Eidos записав власний.

### Порядок завантаження

- «sTestFile lines make the game ignore plugins.txt» з'являється для Fallout 4,
  Fallout 4 VR і Starfield, коли в `Fallout4Custom.ini` чи `StarfieldCustom.ini`
  профілю є рядки `sTestFile1`-`sTestFile10` у `[General]`. Поки один із них
  задано, гра завантажує ці додатки, а порядок завантаження, який пише Eidos, не
  має сили. Fix прибирає рядки з копії профілю й зберігає попередній файл як
  `<ini>.pre-fix`.
- Starfield: увімкнені додатки `.esp` без прапорця master отримують картку, бо
  Starfield не вміє сортувати їх серед `.esm` і додатків із прапорцем master та
  тримає частину їхніх записів завантаженими всю сесію. Випуск автора у вигляді
  `.esm` уникає обох проблем.
- Starfield: «Invalid blueprint plugins» перелічує додатки, що мають частину, але не
  всі з трьох ознак blueprint: прапорець, назву, що починається з `BlueprintShips-`,
  і розширення `.esm`. «Blueprint plugins without their main plugin» перелічує ті,
  чий основний додаток не ввімкнено: `BlueprintShips-Example.esm` потребує
  `Example.esm`, `.esp` або `.esl`.
- «<patch> loses <n> file(s) to <master>» з'являється, коли додаток в одному моді
  потребує майстра з іншого мода, а той інший мод має вищий пріоритет, тож його
  копії файлів, які постачають обидва, перемагають. Патч зазвичай ставлять нижче
  за мод, який він патчить, і кнопка Move на картці ставить його туди. Лишіть
  порядок, якщо патч мусить програвати ці файли.
- «Out-of-date copy of <plugin>» з'являється, коли мод містить очищену або з
  прапорцем light копію додатка, чий оригінал відтоді змінився (оновлення мода чи
  гри). Гра завантажує стару копію. Сховайте її, потім очистьте чи позначте новий
  додаток знову.

### Список модів

- «Order rules of the collection <name> that no longer hold» з'являється, коли
  моди встановленої колекції більше не стоять у порядку, якого вимагають її
  правила. Restore collection order повертає лише моди цієї колекції, а Ctrl+Z
  скасовує це.
- «<mod> requires <mod>, which is not installed» (або «which is disabled») походить
  із вимог Nexus, які читає Check for updates. Open on Nexus веде на сторінку
  потрібного мода, Download main file завантажує його з premium-акаунта, а Ignore
  ховає вимогу, яку вже задовольняє інший мод. Вимога DLC - лише порада: Eidos
  шукає додаток з назвою DLC.
- «fontconfig.txt names a font library that is missing» (рушії Skyrim) називає
  шрифти, яких не має жоден шар і жоден архів, та мод, чий
  `Interface/fontconfig.txt` перемагає. Текст меню може показуватися квадратиками,
  доки шрифт не встановлено або рядок не видалено.
- «BA2 archive stores audio compressed» (Fallout 4 і Fallout 4 VR) рахує файли
  `.wav` і `.xwm`, які BA2 мода зберігає стисненими. Гра може впасти, коли їх
  відтворює. Перепакуйте архів з нестисненим аудіо.

### Script extender і оновлення гри

- «<loader> is not installed» з'являється, коли додатки script extender
  встановлені (у `SKSE/Plugins`, `F4SE/Plugins` тощо), а завантажувача немає в
  жодному увімкненому моді й у теці гри. Гра стартує без них.
- «The script extender does not match game version <version>» з'являється, коли
  завантажувач встановлено, а DLL середовища виконання для запущеної версії гри
  немає, наприклад `skse64_1_6_1170.dll`. Завантажувач зупиняється з помилкою.
  Зазвичай це йде після оновлення гри. Ця й попередня картки мають кнопки Open the
  download page для сайту розширювача та Install the downloaded archive, яка кладе
  завантажувач у теку `Root/` мода.
- «<game> changed since the last clean launch» з'являється, коли виконуваний файл
  гри або, для копії зі Steam, її build id змінилися з останнього запуску через
  Eidos, що завершився без помилки. Оновлення Steam, яке лишає виконуваний файл як
  був, її не викликає. Додатки script extender, зібрані під стару версію, можуть
  перестати завантажуватися, а картки нижче називають ті, що її декларують. Щоб
  зберегти версію гри, на якій збирали список, заморозьте її в екземпляр кнопкою
  Freeze this version на картці Game files або командою
  `eidos stock-game <instance> freeze --yes` після того, як лише `freeze` показав
  розмір: пізніші оновлення магазину змінюють інсталяцію з магазину, а не копію.
- «<mod> replaces <n> <extender> script(s)» з'являється, коли мод із вищим
  пріоритетом, ніж script extender, має вільні копії `.pex` власних скриптів
  розширювача. Стара копія ламає функції, які вона декларує, а гра не показує
  помилки. Перемістіть розширювач нижче за цей мод (кнопка Move на картці робить
  це, коли обидва є модами) або сховайте ці файли в моді. Коли скрипти розширювача
  лежать вільно в `Data` гри, встановіть розширювач як мод, щоб його можна було
  впорядкувати. Архіви не перевіряються, лише вільні файли.

### Вивід інструментів

- «Overwrite/Root holds meshes» (або textures) означає, що інструмент, чий шлях
  даних вказував на теку гри, записав ці теки туди, де гра їх ніколи не читає.
  Виправте шлях інструмента, видаліть теки й запустіть інструмент знову. Кнопка
  Open folder відкриває `Overwrite/Root`.
- «BodySlide's GameDataPath is not the game's Data folder» (або
  `OutputDataPath`): див.
  [Інструменти](tools.md#власні-налаштування-інструмента-однаково-лишаються-його-власними).

### Збій в останній сесії

«The game crashed in the last session» з'являється, коли реєстратор збоїв записав
лог під час останнього запуску. Картка називає виняток, а також DLL і додатки з
логу, які встановлюють ваші моди чи Overwrite. Вважайте їх зачіпками: мод,
названий у логу збою, часто лише місце, де збій проявився, а не його причина.
Коли лог не називає жодного файла з ваших модів, картка про це каже. Open the log
відкриває лог, а Copy the log (home path hidden) копіює його з прихованою
домашньою текою.

### Розмір вікна

Для Skyrim SE, Enderal SE і Fallout 4 картка Display показує розмір і режим вікна,
з якими профіль запускає гру, і каже «No window size set for this profile», коли
його не задає ні Prefs INI профілю, ні Prefs INI префікса. Apply записує розмір і
режим у копію профілю та, коли вікно задає SSE Display Tweaks, у копію INI цього
мода в Overwrite ([usage.md](usage.md#діагностика)).

## Який Proton запускає гру, і зламаний префікс

Вкладка Diagnostics має картку Proton: збірка, яку Eidos і Steam використовують
для гри, власне налаштування Steam і збірка, що востаннє запускала префікс. Якщо
префікс востаннє підготував новіший Proton, ніж вибраний, картка стає порадою, бо
старіший Proton на новішому префіксі може скинути його файли Wine або не
запуститися. Виберіть збірку не старішу у Properties гри, Compatibility в Steam,
або перебудуйте префікс.

Інші картки Proton і префікса:

- «Proton comes from the Flatpak Steam install»: цей Proton тримає своє середовище
  виконання й бібліотеки steamclient усередині пісочниці Flatpak, тож запуск із
  хоста може не вдатися. Eidos не запускає його через `flatpak run`, бо це
  помістило б гру в пісочницю, поза об'єднаний вигляд. Установіть Proton у
  `~/.steam/root/compatibilitytools.d/` і виберіть його для гри.
- «Eidos cannot tell which Proton runs this game»: `config.vdf` у Steam не називає
  для неї інструмента сумісності, а префікс не записує жодної встановленої збірки.
  Інструменти не стартують, доки його не вибрано в Steam (Properties гри,
  Compatibility).
- «<game> has no Proton prefix yet»: запустіть гру один раз через Steam, потім
  натисніть F5. Якщо Steam не створює префікс, перевірте, що тека гри під
  `steamapps/compatdata` доступна для запису; порожня тека, що належить root,
  блокує це без повідомлення.
- «Windows tools cannot find <game>»: запис префікса про шлях встановлення
  неправильний або відсутній, а xEdit, DynDOLOD, Wrye Bash і Creation Kit його
  читають. Eidos запише правильний шлях під час наступного запуску інструмента.
- «The prefix's S: drive points outside the Steam library»: `S:` не збігається ні з
  коренем бібліотеки, куди Eidos скеровує його для інструмента, ні з
  `<library>/steamapps`, куди Steam скеровує його для гри. Імовірно, бібліотеку
  переміщено або префікс прийшов з іншої машини. Кожен шлях відносно `S:`, збережений
  у префіксі, нікуди не веде, доки наступний запуск через Eidos чи Steam не
  скерує його знову.
- «<store> installation: started through its store» - картка копії з GOG чи Epic.
  Run просить Heroic або Legendary запустити гру, коли Eidos там є обгорткою гри, а
  інструменти запускаються зі збіркою Wine чи Proton, яку Heroic записав для
  копії.

Меню File запускає winecfg, regedit, провідник файлів Wine та програму видалення
в префіксі гри з тим Proton, що запускає інструменти гри
([tools.md](tools.md#власні-програми-wine-у-префіксі-гри)). Їхні рядки лишаються
сірими, доки в префіксі немає цих програм.

Кнопка Rebuild prefix на картці Proton призначена для префікса, який більше не
працює. Натисніть її двічі. Eidos нічого не видаляє: він перейменовує
`steamapps/compatdata/<appid>` на `<appid>.eidos-backup-<date>-<time>` у тій
самій теці, і Steam створює новий префікс під час наступного запуску гри зі
Steam. Він відмовляє, поки префікс використовує гра, інструмент або будь-яка
програма Wine. Доки нового префікса немає, Run у вікні не може передати гру
Steam і показує параметр запуску, тож натисніть Play у Steam. Збереження й
налаштування, що є лише в старому префіксі, лишаються в перейменованій теці:
скопіюйте назад те, що потрібно, і видаліть цю теку самі, коли вона стане
непотрібна.

## Що додати до звіту про ваду

- Copy report на вкладці Diagnostics копіює версію Eidos, гру, збірку Proton, чи
  Steam є Flatpak, стан passthrough, тип сесії, дистрибутив, ядро,
  `vm.max_map_count`, межу відкритих файлів, чи є `/dev/fuse` і `fusermount3`,
  назви змінних запуску й програм-обгорток профілю та кожну Health-картку. Ваша
  домашня тека показана як `~`, а ім'я для входу як `<user>`.
  `eidos check <instance>` друкує той самий заголовок у терміналі, а `--json`
  дає його як JSON.
- Журнал запуску, `<instance>/logs/run-*.log`, починається з точної команди, яку
  виконав Eidos. File, Eidos logs відкриває теку власних журналів Eidos,
  `~/.local/share/Colony/Eidos/logs`.
- Copy the log (home path hidden) на картці збою копіює лог збою.
- Save tree на вкладці Data зберігає об'єднане дерево `Data` із джерелом кожного
  файла.

## Відомі проблеми

### DLSS чи генерація кадрів мовчки нічого не робить

Три окремі причини, кожна без жодного повідомлення про помилку: NVAPI не увімкнений
у параметрах запуску, ексклюзивний повноекранний режим або застаріла стеля FPS у
Reflex. Повний перелік - у [graphics.md](graphics.md).

### Run нічого не робить із Flatpak Steam

У вікні, яке не відкрив жоден магазин, Run просить Steam запустити гру командою
`steam -applaunch <appid>`. Flatpak Steam не кладе `steam` у `PATH` хоста, тож
рядок стану каже «Could not start Steam» з помилкою. Натисніть Play у Steam.

### Збереження з іншого пристрою не з'являється

Збереження, що потрапляє в префікс повз Eidos, наприклад завантаження Steam Cloud
зі Steam Deck, лишається прихованим, поки збереження профілю змонтовано. Ніщо його
не видаляє. Вкладка Saves рахує такі збереження під своїм заголовком, а Import
копіює їх у профіль, не замінюючи збереження профілю
([usage.md](usage.md#збереження-належать-профілю)).

### Мод, що пише одну теку двома способами, втрачав усе під другим написанням

Виправлено. ext4 розрізняє `meshes/` і `Meshes/`; об'єднаний вигляд не має, а
справжні моди постачають обидва - у XP32 Maximum Skeleton анімації та файл поведінки
FNIS лежать під написанням з великої літери, а `character assets` - під іншим.

Розв'язувач брав точний збіг регістру для кожного складника шляху й тримався за
нього: заходив у `meshes/`, не знаходив там решти шляху й кидав УВЕСЬ ШАР. Кожен
файл під іншим написанням був невидимий для гри - без помилки, без журналу, без
нічого в жодній діагностиці. На реальному екземплярі з 50 шарів це були 74 файли.

Складник, що збігся, тепер кандидат, а не рішення; точний регістр і далі пробується
першим, і лише коли решта під ним не знаходиться, обхід шукає сусідів, рівних із
точністю до регістру. Переліки мали ту саму ваду текою вище й тепер читають кожну
таку теку в кожному шарі.

Індекс шляхів ніколи не мав цієї вади, бо обходить кожну теку, яку знаходить. Тож
якийсь час індекс повертав файли, яких не міг повернути запасний шлях, хоча саме
запасна відповідь мала бути ніколи не хибною.

### LODGen від DynDOLOD помирає, лишаючи порожній журнал

Виправлено за допомогою `dotnet10`; див. [tools.md](tools.md). `LODGen_SSE_<world>_log.txt`
кожного світу містить банер версії, рядок `.NET Version:` і більш нічого, а
діалог каже лише «failed to generate object LOD for one or more worlds». Причина -
Mono з Wine, який відповідає замість .NET Framework, і жодне встановлення .NET
Framework цього не лікує: Proton замінює `mscoree.dll` символічним посиланням у
власне дерево під час кожного оновлення префікса. Пакет випуску постачає
середовище виконання .NET 10; інші встановлення завантажують його один раз.

### Wine не міг зрозуміти, що монтування згортає регістр

Виправлено.

`get_dir_case_sensitivity` у Wine спершу питає теку через `FS_IOC_GETFLAGS`,
потім винюхує маркер, який CIOPFS лишає в теках, що їх обслуговує. Якщо немає ні
того, ні іншого, Wine вважає файлову систему ЧУТЛИВОЮ до регістру, і кожен
пошук, чиє написання не збігається побайтово, відкочується до читання ЦІЛОЇ теки
заради нечутливого до регістру збігу. Ігри Bethesda просять
`data/ccbgssse001-fish.bsa`, тоді як файл зветься `ccBGSSSE001-Fish.bsa`, тож це
спрацьовувало майже на кожному ресурсі: 4471 проба маркера і 2236 повних
перечитувань теки за вісім секунд та 195796 перелічень `Data` за дев'яносто.
Skyrim SE так і не доходив до головного меню - він сидів на 240 МБ резидентної
пам'яті, поки демон спалював 92 % ядра.

Eidos згортав регістр у `resolve_read` від самого початку. Уся ціна була в тому,
що він ніколи про це не казав. Тепер `lookup` відповідає `.ciopfs`; `readdir` і
далі його не перелічує. `ioctl` також відповідає на `FS_IOC_GETFLAGS` для тек
прапором casefold, який нинішній Wine запитує перед пошуком маркера.

Дві речі зробили це смертельним, а не просто повільним. Ціна росте з розміром теки,
тож встановлення вмісту Anniversary (`Data` з 37 файлів до 177) переважило шальку. І
`opendir` жадібно будував об'єднаний перелік, що є чистим марнуванням, коли Wine
відкриває теку лише заради `stat` того маркера всередині, - знімок тепер робиться на
першому `readdir`.

Після: головне меню, 2,1 ГБ резидентної пам'яті, демон на 0 % CPU.

`EIDOS_FUSE_TRACE=opendir` - це те, що його знайшло, і воно постачається. Лічильники
операцій кажуть «скільки»; 195796 перелічень однієї теки в загальній сумі невидимі.

### Гра переписала `plugins.txt` порожнім

Найімовірніше, це те саме, що й згортання регістру вище: `Data`, який вона не могла
перелічити за розумний час, звідки й висновок, що там нічого немає, - і збереження
цього висновку. Не доведено й варте перевірки. Хай там як, захист захоплення
(захоплення, що повністю спорожняє активний набір, відхиляється за будь-якого
розміру) означає, що пошкодити профіль це більше не може.

### `FOPEN_KEEP_CACHE` вимкнений

Виправлено. Він валив Skyrim SE на розіменуванні нуля через лічені секунди після
головного меню, детерміновано, без жодного встановленого мода; решту трьох кешів з
боку ядра відсікали по одному бісекцією, і значення мав лише цей. Ця бісекція йшла
з увімкненим `FUSE_PASSTHROUGH`, а ядро завершує з EIO відкриття через
passthrough, що несе `FOPEN_KEEP_CACHE`, тож з цим прапорцем кожне відкриття
через passthrough провалювалося. Можливо, саме ці невдалі відкриття й валили
гру, а сам прапорець при вимкненому passthrough жодного разу не перевіряли.
Відповіді через passthrough його більше не несуть. Його втрату тоді виміряли як
безкоштовну, але з увімкненим passthrough демон обслуговує *нуль* читань
(`EIDOS_FUSE_STATS` повідомляв `read 0` за повне завантаження), тож при
passthrough, типово вимкненому, справжня ціна не виміряна. Увімкніть
`EIDOS_FUSE_KEEP_CACHE=1`, щоб випробувати його окремо.

### FUSE passthrough не дає грі завантажити жодного вмісту модів

Демон тепер оминає найімовірнішу причину (нижче), але в грі це ще не виміряно
заново, тож passthrough типово лишається вимкненим; `EIDOS_FUSE_PASSTHROUGH=1`
вмикає його. До цієї зміни з увімкненим passthrough Skyrim SE не міг відкрити
152 власні файли зі `STATUS_ACCESS_VIOLATION`, тож вміст модів не завантажувався,
мовчки. Вимір і причина, чому власні журнали демона показували чистий прогін, - у
розділі «Чому passthrough вимкнений типово» вище.

Ядро прив'язує до кожного inode один файл-основу (`fs/fuse/iomode.c`).
Відкриття, що приносить другий ідентифікатор файла-основи для inode, який його
вже має, завершується з EIO, як і звичайне відкриття (без `FOPEN_PASSTHROUGH`)
inode, що має файл-основу. Відкриття через passthrough, що несе
`FOPEN_KEEP_CACHE`, теж завершується з EIO. Демон раніше реєстрував новий
ідентифікатор при кожному відкритті, тож друге відкриття файла, який гра вже
тримала відкритим, провалювалося. Wine повідомляє EIO як
`STATUS_ACCESS_VIOLATION`; це та сама помилка 152 невдалих відкриттів. Це
правило взято з вихідного коду ядра, і воно збігається з цими 152 відмовами,
тому саме воно найімовірніша причина.

Тепер демон реєструє один файл-основу на inode, спільний для всіх його
відкриттів через passthrough, і ніколи не ставить `FOPEN_KEEP_CACHE` на
відкриття через passthrough. Passthrough стосується лише відкриттів тільки для
читання у файлів із шарів гри та модів розміром від 1 MiB або із закінченням
`.dll`, `.exe` чи `.asi`. Щойно файл має файл-основу, його використовує
кожне відкриття цього файла тільки для читання, а поки файл має звичайні відкриття,
нові читачі теж отримують звичайні відкриття. Файл з Overwrite ніколи не йде
через passthrough, а монтування, яке проєктує часові позначки додатків, взагалі
його не використовує. Відкриття на запис файла, який тримають читачі через
passthrough, отримує ETXTBSY (у Wine: `STATUS_SHARING_VIOLATION`) до будь-якого
copy-up, тож відкриття з `O_TRUNC` не може залишити в Overwrite порожню копію,
яка сховала б файл мода.

### Кнопка Mod Manager Download нічого не робить

Preferences, Nexus, Downloads показує, яка програма отримує посилання `nxm://`.
Health-картка з'являється, коли ця програма не Eidos, її немає або не задано жодної.
Кнопка Register записує `eidos-nxm.desktop` і робить його обробником за
замовчуванням для `x-scheme-handler/nxm`. У терміналі те саме робить
`eidos nxm --register`.

Якщо в стані вже вказано Eidos, а кнопка досі нічого не робить, браузер міг
зберегти попередній вибір. Очистьте збережений вибір для посилань nxm у
налаштуваннях браузера, щоб він запитав знову. Браузер із Flatpak не може
запускати програми хоста й передає посилання через портал робочого столу, який
читає обробник, зареєстрований на хості.
