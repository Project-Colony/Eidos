# 문제 해결과 진단

게임이 파일 시스템과 말이 맞지 않는 무언가를 보는 날을 위한 모든 것: 환경 스위치,
연산 카운터를 읽는 법, 알려진 문제와 그 내력, 그리고 패스스루 이야기.

### VFS 진단하기

게임이 파일 시스템과 말이 맞지 않는 무언가를 볼 때를 위한 환경 변수가 둘 있습니다:

```sh
EIDOS_FUSE_STATS=1                  # 연산 카운터, 언마운트 때 덤프
EIDOS_FUSE_NO_CACHE=1               # 커널 쪽 캐시를 전부 끄기
EIDOS_FUSE_NO_CACHE=attr,neg,keep,dir   # 또는 하나씩 이름을 대기
```

아래에 설명된 크래시를 찾아낸 것이 이 세분화된 형태입니다. 넷을 모두 끄면 "캐싱
때문인가?"에 답하고, 이름을 대야만 "어느 것인가"에 답합니다. 카운터는 나머지 절반에
답합니다 - `read 0`을 보여주는 로드는 `FUSE_PASSTHROUGH`가 모든 바이트를 커널
안에서 제공한 로드이므로, 읽기 경로에서 손보려던 것은 이미 공짜입니다.

## 유니온을 손으로 마운트하기

충돌하면 첫 번째 `--layer`가 이깁니다. 마지막은 손대지 않은 게임 데이터입니다.
마운트에 필요한 것은 `/dev/fuse`와 `fusermount3`뿐입니다(overlayfs도, Wine도
필요 없습니다):

```sh
eidos-fuse --layer mod_b --layer mod_a --layer game_data /mnt/point
# ... /mnt/point를 통해 읽고 쓰기 ...
fusermount3 -u /mnt/point
```

쓰기는 `--overwrite <dir>`에 떨어지므로(생략하면 임시 디렉터리), 여기서도 레이어
자체는 손대지 않은 채로 남습니다.


#### 패스스루가 기본으로 꺼져 있는 이유

패스스루는 커널에 실제 백킹 파일을 넘겨주어 읽기가 이 데몬을 통째로 건너뛰게 합니다.
처리량에서는 이득이지만 여기서는 정확성을 대가로 치릅니다. Skyrim SE 1.6.1170,
proton-cachyos 11.0, 커널 7.1.4, 동일한 82개 플러그인 로드 순서에서, 실행 파일이 그
능력을 지녔는지만을 변수로 두고 A/B로 측정한 결과입니다:

| 패스스루 | `STATUS_ACCESS_VIOLATION`으로 끝난 `NtCreateFile` 실패 |
|-------------|--------------------------------------------------------|
| 켬          | 152 - `.bsa` 75, `.esl` 65, `.esm` 10, `.esp` 2        |
| 끔          | 0                                                      |

켜 두면 게임은 자기 아카이브도 플러그인도 하나 열지 못하며, 이는 게임 안에서 그저
존재하지 않는 모드로 드러납니다 - 오류도, 로그 한 줄도 없이. 꺼 두면 같은 로드
순서가 플러그인과 아카이브와 Papyrus 스크립트를 살린 채 플레이에 도달합니다.

이 실패는 데몬 안에서는 보이지 않고, 그래서 찾아내는 데 비용이 컸습니다. 우리 쪽
`open`은 매번 성공하고 커널은 백킹 파일을 결코 거부하지 않습니다(실패한 세션 전체를
`EIDOS_FUSE_TRACE=open`으로 확인: `open FAILED` 0건, `passthrough refused` 0건).
오류는 데몬이 `opened_passthrough`라고 답한 뒤에 만들어지므로, 데몬 쪽의 어떤 로깅도
그것을 볼 수 없습니다. 확장자를 가리지도 않습니다 - 아카이브와 플러그인을 똑같이
덮치며, 곧 게임이 실행 내내 열어 두는 파일들입니다.

`EIDOS_FUSE_PASSTHROUGH=1`이 그것을 다시 켭니다. 무엇을 벌어들이는지 측정하거나
메커니즘을 다시 시험하기 위한 것입니다. 런처와 Diagnostics 탭의 능력 경고는 그것을
요청했을 때에만 나타납니다.

게임 자체를 Eidos를 통해 실행하려면 Steam 실행 옵션을 이렇게 설정하세요:

```
eidos play skyrimse -- %command%
```

셰이더 컴파일에 Proton이 네이티브 d3dcompiler를 필요로 한다면 앞에
`WINEDLLOVERRIDES="d3dcompiler_47=n"`을 붙이세요. Eidos는 그것을 모드가 함께 담아
오는 DLL 오버라이드(ENB/ReShade/`.asi` 로더)와 병합합니다.


### 레이어 인덱스가 실제로 쓰이고 있는가?

인덱스는 전부 아니면 전무이고 조용히 만들어집니다. `LayerStack::new`는 읽기 전용
레이어의 완전한 맵을 얻거나 `None`을 얻으며, 후자면 모든 조회는 예전과 똑같이
레이어를 훑습니다. 세션 로그의 어떤 것도 둘을 구별해 주지 않으므로, 조용히 폴백한
스택은 제대로 동작하는 스택과 똑같아 보입니다 - 옛 비용을 치르면서 말입니다.

```sh
cargo run --release -p eidos-core --example index_health -- <mods-dir> <overwrite-dir>
cargo run --release -p eidos-core --example index_agrees -- <mods-dir> <overwrite-dir>
cargo run --release -p eidos-core --example listing_cost -- <mods-dir> <overwrite-dir>
```

`index_health`는 인덱스가 있을 때와 없을 때 실제 경로를 해석하고 디렉터리 스캔을
비교합니다. `index_agrees`는 실제 인스턴스의 모든 경로와 모든 목록에서 둘이 똑같은
답을 내는지 확인합니다. `listing_cost`는 병합된 자식 맵이 `readdir`에서 무엇을
아껴 주는지 측정합니다.

`EIDOS_NO_INDEX=1`은 훑기를 강제합니다. 두 답의 차이 자체가 디버깅 대상일 때를 위한
것입니다.

## 알려진 문제

### DLSS나 프레임 생성이 조용히 아무 일도 하지 않음

원인이 셋으로 갈리고 어느 것도 오류 메시지를 내지 않습니다. 실행 옵션에서 NVAPI가
켜지지 않았거나, 독점 전체 화면이거나, 예전 값으로 남은 Reflex FPS 상한입니다. 점검
목록 전체는 [graphics.ko.md](graphics.md)에 있습니다.

**한 디렉터리를 두 가지로 적은 모드가 두 번째 철자 아래의 모든 것을 잃었습니다.**
고쳐졌습니다. ext4는 `meshes/`와 `Meshes/`를 별개로 두지만 병합된 뷰는 그래서는 안
되고, 실제 모드는 둘 다 담아 배포합니다 - XP32 Maximum Skeleton은 애니메이션과 FNIS
동작 파일을 대문자 쪽에, `character assets`를 다른 쪽에 둡니다.

리졸버는 경로 요소마다 대소문자가 정확히 맞는 것을 택하고 거기에 매달렸습니다.
`meshes/`로 들어갔다가 나머지 경로를 거기서 찾지 못하자 레이어 전체를 포기한
것입니다. 다른 철자 아래의 모든 파일이 게임에게는 보이지 않았습니다 - 오류도, 로그도,
어떤 진단에도 아무것도 없었습니다. 실제 50레이어 인스턴스에서 그것은 74개
파일이었습니다.

이제 맞아떨어지는 요소는 결정이 아니라 후보입니다. 정확한 대소문자를 여전히 먼저
시도하고, 그 아래에서 나머지가 실패했을 때에만 스캔이 대소문자를 접었을 때 같아지는
형제를 찾습니다. 목록 조회에도 한 디렉터리 위에서 같은 결함이 있었고, 이제 레이어마다
대소문자를 접었을 때 같아지는 디렉터리를 모두 읽습니다.

이 일의 모양새로 알아둘 만한 것이 있습니다. 경로 인덱스에는 이 버그가 없었습니다.
찾아낸 디렉터리를 모두 훑기 때문입니다. 인덱스는 폴백이 내놓지 못하는 파일을 조용히
돌려주고 있었는데, 이는 앞뒤가 뒤바뀐 것입니다 - 결코 틀리지 않아야 하는 답은
폴백 쪽입니다.

**DynDOLOD의 LODGen이 빈 로그를 남기고 죽습니다.** `dotnet10`으로 해결됩니다.
[tools.ko.md](tools.md)를 보세요. 증상은 오해할 여지가 없습니다. 모든 월드마다
`LODGen_SSE_<world>_log.txt`에 버전 배너와 `.NET Version:` 줄만 있고 그 밖에는
아무것도 없으며, "failed to generate object LOD for one or more worlds"만 적힌 대화
상자가 뜹니다. 원인은 Wine의 Mono가 .NET Framework 행세를 하는 것이고, .NET
Framework를 아무리 설치해도 고쳐지지 않습니다 - Proton은 프리픽스를 갱신할 때마다
`mscoree.dll`을 자기 트리 안으로 향하는 심링크로 바꿔 놓습니다.

**Wine은 마운트가 대소문자를 접는다는 것을 알 수 없었습니다.** 고쳐졌고, 이것이
중요한 문제였습니다.

"이 파일 시스템은 대소문자를 구분하지 않는가"를 묻는 API는 없어서, Wine의
`get_dir_case_sensitivity`는 CIOPFS가 자기가 제공하는 디렉터리에 남기는 표식을
킁킁거립니다. 그것이 없으면 Wine은 대소문자를 구분한다고 가정하고, 철자가 바이트
단위로 맞지 않는 모든 조회는 대소문자 무시 일치를 찾으려 디렉터리 전체를 읽는 쪽으로
물러섭니다. Bethesda 게임은 파일이 `ccBGSSSE001-Fish.bsa`인데도
`data/ccbgssse001-fish.bsa`를 요구하므로, 이는 거의 모든 에셋에서 발동했습니다. 8초
동안 표식 탐침 4471회와 디렉터리 전체 재읽기 2236회, 90초 동안 `Data` 열거 195796회.
Skyrim SE는 메인 메뉴에 끝내 이르지 못했습니다 - 상주 메모리 240 MB에 앉아 있는 동안
데몬은 코어 하나의 92%를 태웠습니다.

Eidos는 처음부터 `resolve_read`에서 대소문자를 접고 있었습니다. 그 모든 비용은
그렇다고 말하지 않은 데서 왔습니다. 이제 `lookup`이 `.ciopfs`에 답합니다. `readdir`은
여전히 그것을 나열하지 않습니다.

이것을 그저 느린 정도가 아니라 치명적으로 만든 것은 둘입니다. 비용이 디렉터리 크기에
비례해서 커지므로 Anniversary 콘텐츠 설치(`Data`가 37개 파일에서 177개로)가 저울을
넘겼습니다. 그리고 `opendir`이 병합된 목록을 미리 만들었는데, Wine이 디렉터리를 여는
이유가 그 안의 표식을 `stat`하기 위해서일 뿐일 때 이는 순전한 낭비입니다 - 이제
스냅숏은 첫 `readdir`에서 찍힙니다.

그 뒤: 메인 메뉴 도달, 상주 메모리 2.1 GB, 데몬 CPU 0%.

이것을 찾아낸 것은 `EIDOS_FUSE_TRACE=opendir`이고, 그대로 배포됩니다. 연산 카운터는
몇 번인지 말해 줍니다. 한 디렉터리를 195796번 열거한 것은 총합 안에서는 보이지
않습니다.

**게임이 `plugins.txt`를 비워서 다시 쓰는 것**도 거의 확실히 같은 일이었습니다 -
어떤 합리적인 시간 안에도 열거할 수 없는 `Data`를 두고, 거기에 아무것도 없다고
결론짓고 그것을 저장한 것입니다. 증명되지는 않았고 다시 확인해 볼 만합니다. 어느
쪽이든 캡처 가드(활성 집합을 통째로 비우는 캡처는 크기와 무관하게 거부됩니다) 덕분에
이제 그것이 프로필을 망가뜨릴 수는 없습니다.

**`FOPEN_KEEP_CACHE`는 꺼져 있습니다.** 고쳐졌고, 그 이유를 알아둘 만합니다. 모드를
하나도 설치하지 않은 상태에서 메인 메뉴 몇 초 뒤에 널 역참조로 Skyrim SE를
결정론적으로 죽였습니다. 나머지 커널 쪽 캐시 셋은 하나씩 이분해서 배제했고 이것만이
문제였습니다. 그것을 잃는 비용은 그때 공짜로 측정되었지만, 그 측정은
`FUSE_PASSTHROUGH`가 켜진 상태에서 이루어졌습니다. 그때 데몬은 읽기를 *하나도*
제공하지 않으며(`EIDOS_FUSE_STATS`는 전체 로드에 대해 `read 0`을 보고했습니다)
커널은 이미 백킹 파일에 대해 그 페이지들을 캐시하고 있었습니다. 패스스루는 이제
기본으로 꺼져 있으므로(아래 참고) 그 논거는 더 이상 성립하지 않고 실제 비용은
측정되지 않은 상태입니다 - 어쨌든 크래시만으로도 꺼 둘 이유는 충분합니다. 조사하려면
`EIDOS_FUSE_KEEP_CACHE=1`로 다시 켜세요. 두 플래그는 더 이상 얽혀 있지 않으므로 이제
따로 시험할 수 있습니다.

### FUSE 패스스루가 게임이 모드 콘텐츠를 하나도 로드하지 못하게 함

꺼서 해결했습니다. `EIDOS_FUSE_PASSTHROUGH=1`이 되돌립니다. 패스스루를 켜면 커널
7.1.4에서 Skyrim SE가 자기 파일 152개(`.bsa` 75, `.esl` 65, `.esm` 10, `.esp` 2)를
`STATUS_ACCESS_VIOLATION`으로 열지 못하고, 끄면 0개입니다 - 그래서 모드 콘텐츠가
조용히 하나도 로드되지 않습니다. 커널은 데몬이 `opened_passthrough`라고 답한 뒤에
오류를 올리므로, 데몬 자신의 로그는 깨끗한 실행을 보여줍니다(실패한 open 0건, 거부된
백킹 파일 0건). 커널 경로에서의 근본 원인은 밝혀지지 않았습니다. 다시 시험할 수
있도록, 그리고 이미지 매핑이 그것을 필요로 하는 것으로 드러날 경우 패스스루를 DLL로만
좁힐 수 있도록 스위치는 남겨 둡니다.
