# Eidos 사용하기

실용 설명서: CLI, GUI, Steam 실행 옵션, 소스에서 빌드하기, 그리고 개념 증명
스크립트. 뭔가 잘못돼 보일 때 무엇을 해야 하는지는
[troubleshooting.ko.md](troubleshooting.md)를 보세요.

## 써보기 (CLI)

```sh
eidos games                       # 여기 설치된 지원 게임들 (MO2의 목록처럼)
eidos init skyrimse               # 모딩 인스턴스 만들기
# ...각 모드를 폴더째로 <instance>/mods/ 에 넣으세요 (전역 인스턴스는
#    ~/.local/share/eidos/skyrimse 에 있습니다; `eidos init`이 여러분 것을 알려줍니다)...
eidos install skyrimse mod.7z     # 또는 내려받은 압축 파일 설치 (Simple / FOMOD)
eidos import skyrimse <mo2-profile>  # 기존 MO2 프로필의 순서 + 플러그인 상태 가져오기
eidos sort skyrimse               # 플러그인 로드 순서를 LOOT로 정렬
eidos play skyrimse               # 무엇이 마운트될지 보기
eidos play skyrimse -- <command>  # 게임 위에 모드를 마운트한 채 <command> 실행
eidos collection skyrimse <link>  # Nexus 컬렉션을 제작자가 만든 그대로 설치하기
eidos pack skyrimse backup.eidos  # 인스턴스 전체를 파일 하나로, 다른 곳으로 옮기려고
eidos unpack backup.eidos <folder>   # 다른 기계에서 되돌려 놓기
```

`eidos tool`, `eidos prereqs`, `eidos nexus`, `eidos nxm`, `eidos export`가 나머지를
채웁니다; 전체 목록은 인수 없이 `eidos`를 실행하세요.

### 인스턴스: 전역과 휴대용

위의 모든 명령은 인스턴스를 대상으로 합니다. `skyrimse`는 **전역** 인스턴스를
가리킵니다 - `~/.local/share/eidos/skyrimse`에 중앙 집중식으로 저장되고 Eidos가
관리합니다. 다른 한 종류는 **휴대용**입니다: 원하는 곳 어디에나 두는 자족적인
폴더(두 번째 드라이브, 게임용 파티션)로, 옮길 수 있고 격리되어 있으며, MO2의
휴대용 인스턴스와 똑같습니다. 게임 id를 받는 명령은 어디서든 휴대용 인스턴스의
폴더도 받습니다:

```sh
eidos init skyrimse /mnt/games/EidosSkyrim   # 거기에 휴대용 인스턴스 만들기
eidos install /mnt/games/EidosSkyrim mod.7z  # 모든 명령이 폴더를 받습니다
eidos play /mnt/games/EidosSkyrim -- %command%
```

폴더는 스스로를 설명합니다(그 안의 `eidos-instance.ini`가 게임 이름을 담고
있습니다). 그래서 더 필요한 것은 없습니다 - 그리고 환경 변수
`EIDOS_INSTANCE=<folder>`는 게임 id를 그 폴더로 돌리는데, Steam 실행 옵션에서
요긴합니다. 여러분이 만들었거나 열어본 휴대용 인스턴스는
`~/.config/Colony/Eidos/instances.ini`에 (가장 최근에 쓴 것부터) 기억됩니다.
GUI의 환영 화면이 한 번의 클릭으로 열 수 있게 이들을 나열하고, Steam 실행은
마지막으로 플레이한 것으로 들어가며, `nxm://` 처리기는 그 안으로 내려받습니다.
알아둘 만한 단서 둘: 휴대용 폴더를 손으로 옮기면 예전 위치를 절대 경로로 등록해 둔
도구 항목을 빼고 모든 것이 유지되고(아래의 `eidos pack` / `eidos unpack`이 그것들을
대신 고쳐 줍니다; 그냥 `mv`로는 안 됩니다), 공유 런타임
캐시(`~/.local/share/Colony/Eidos/runtimes/`)는 의도적으로 기계 전역으로
남습니다 - 78 MB짜리 .NET 호스트는 인스턴스마다 둘 것이 아닙니다.

Eidos는 자기 파일을 `Colony/Eidos` 아래에 둡니다. Colony 계열의 모든 프로그램이
쓰는 배치입니다: 여러분이 고른 것(설정, Nexus 세션, 인스턴스 목록, 여러분이 쓴
게임과 애드온 정의)은 `~/.config/Colony/Eidos/`에, 세션 로그는
`~/.local/state/Colony/Eidos/logs/`에, Eidos가 내려받은 것은
`~/.local/share/Colony/Eidos/`에 들어갑니다. 예전의 Eidos는 이것들을
`~/.config/eidos/`와 `~/.local/state/eidos/`에 두었습니다. 업그레이드 후 첫
실행이 이들을 **복사해** 옮기고 로그에 그렇게 적습니다. 옛 디렉터리는 있던 그대로
남습니다 - 아무것도 지우지 않으므로 잘못된 업그레이드가 로그인을 앗아갈 수
없습니다 - 그리고 만족스러우면 직접 지우면 됩니다.

여러분의 모드는 거기에 속하지 않습니다. 전역 인스턴스는 여전히
`~/.local/share/eidos/<game>/`에, 휴대용 인스턴스는 여러분이 둔 곳에 있습니다.
그 경로들은 인스턴스 목록에, 어쩌면 Steam 실행 옵션에까지 적혀 있기 때문입니다:
옮기면 Eidos가 양쪽 끝을 다 쥐고 있지 않은 연결이 끊어집니다.

한 곳만은 딱 잘라 거부합니다: **게임 설치 폴더 안**(MO2 경험자의 반사
행동입니다). 그 트리는 Steam의 것이고 - 업데이트, "파일 무결성 확인",
제거가 그것을 다시 쓰거나 지우면서 여러분의 설정 전체를 가져갈 수 있습니다 -
게다가 Eidos는 게임 루트 위에 마운트하므로, 그 안의 인스턴스는 자기 자신의 마운트
대상 안에 앉게 됩니다. 마법사도, `eidos init`도, `eidos play`도 모두 거부합니다.
대신 폴더를 게임 옆에 두세요(같은 드라이브의 형제 폴더면 편의는 똑같습니다).

`play`는 인스턴스의 모드를 게임 자신의 `Data` 디렉터리 위에(바인드 스태시를 거쳐
마운트하므로 데몬은 여전히 원본 파일을 읽습니다) 비공개 네임스페이스 안에서
마운트하고, 그 뷰를 통해 명령을 실행합니다. 쓰기(세이브, 다시 생성된 설정)는
인스턴스의 `overwrite/` 레이어에 떨어지고, 게임 설치본과 모든 모드 원본은
바이트 단위로 원래 그대로 남습니다.

### 권한이 필요한 단계는 없습니다

Eidos는 완전히 rootless로 동작합니다. 비공개 user + mount 네임스페이스 안에서
마운트하므로 setuid 도우미도, 데몬도, 부여할 것도 없습니다.

`sudo setcap cap_sys_admin+ep "$(command -v eidos)"`는 **선택**이며 딱 한 가지를
좌우합니다: 커널 FUSE 패스스루. 게임을 망가뜨리기 때문에 기본값은 꺼짐입니다
(아래 참고). 이 능력이 있으면 Eidos는 user 네임스페이스 대신 평범한 mount
네임스페이스를 씁니다. 모드 배치는 어느 쪽이든 동일합니다.


예전의 `setcap` 안내가 사라진 이유와 FUSE 패스스루가 꺼진 채로 배포되는 이유는
[troubleshooting.ko.md](troubleshooting.md#패스스루가-기본으로-꺼져-있는-이유)에
설명되어 있습니다.

## Nexus 컬렉션 설치하기

```sh
eidos collection skyrimse nxm://skyrimspecialedition/collections/rqhcxy/revisions/latest
eidos collection skyrimse rqhcxy --dry-run     # 읽어서 무슨 일이 일어날지 말해주기
```

창 안에서: 링크를 **File -> Open a Nexus collection...**에 붙여넣고 *Install this
collection*을 누르세요.

### 이것이 "이 모드들을 내려받기"가 아닌 이유

컬렉션은 장바구니 목록이 아니라 **레시피**이고, 그 레시피의 거의 아무것도 Nexus
API에서는 보이지 않습니다. 설치 순서, 모드마다의 스크립트 설치 프로그램에 제작자가
준 답, 파일 충돌에서 어느 모드가 이기는지, 어느 플러그인이 어디에 로드되는지,
바이너리 패치까지 - 전부 컬렉션 자신의 압축 파일 안 `collection.json`에 들어
있습니다. 같은 모드들을 내려받아 기본 옵션으로 설치하면 다른 게임이 나옵니다.

그래서 Eidos는 압축 파일을 내려받고, 레시피를 읽고, 그것을 적용합니다:

| 컬렉션이 말하는 것 | Eidos가 하는 일 |
| --- | --- |
| `phase` | 그 순서대로 설치하고, 선택 구성 항목은 맨 마지막에 |
| `choices` | 각 FOMOD에 제작자가 준 답을 재생하고, 그럴 수 없을 때는 그렇다고 말합니다 |
| `modRules` | 각 파일에서 옳은 모드가 이기도록 모드 목록을 다시 정렬합니다 |
| `plugins` / `pluginRules` | LOOT 규칙을 여러분의 userlist에 병합하고 정렬합니다 |
| `INI Tweaks/` | 그것들을 그 자체로 하나의 모드로 설치합니다 |
| `tools` | 어떤 도구를 기대하는지 알려줍니다; 아무것도 만들지 않습니다 |

상태는 **모든** 구성 항목마다
`<instance>/collections/<slug>-<revision>/state.json`에 쓰이므로, 200개 중
147번째에서 끊긴 설치는 147번부터 이어집니다. 같은 명령을 다시 실행하세요.

### 척하지 않는 것

**무료 Nexus 계정으로는 구성 항목 모드들을 받아올 수 없습니다.** Nexus는 API를
통해 무료 계정에는 내려받기 링크를 발급하지 않습니다; 파일마다 사이트 자체의 "Mod
Manager Download" 버튼이 필요합니다. 컬렉션 **압축 파일**은 무료 계정에서도 잘
내려받아지므로 - 그래서 레시피 전체를 읽을 수 있습니다 - 각 구성 항목은 여러분이
직접 받아올 수 있도록 정확한 페이지 URL과 함께 보고됩니다. 이것은 Nexus의 사업
규칙이고, 아무리 재시도해도 그것을 넘어설 수는 없습니다.

아직 적용되지 않으며, 그냥 넘어가는 대신 보고서에 이름이 적히는 것: **바이너리
패치**, 그리고 파일이 컬렉션 압축 파일 안에 실려 오는 구성 항목(`bundle`).
컬렉션이 여러분더러 손으로 받아오라고 기대하는 구성 항목(`browse`, `manual`)은
제작자 자신의 지침을 보고서까지 그대로 전달합니다.

### 보고서

보고서의 핵심은 "설치됨"이 믿을 값어치가 있다는 것입니다. 설치 프로그램 응답을
전부 재생할 수는 없었던 구성 항목은 **설치되었지만, 컬렉션이 요구하는 방식은
아님**입니다 - 겉보기에 닮은 성공들과 분리된 자기만의 줄로요, 디스크 위의 파일이
제작자의 것과 다르기 때문입니다. 컬렉션 안의 아무것도 가리키지 못한 순서 규칙,
서로 모순되는 규칙의 고리에 걸린 모드, 존재하지 않는 LOOT 그룹, 그리고 이 버전의
Eidos가 이해하지 못하는 매니페스트의 어떤 부분이든 모두 함께 나열됩니다.

그 대안은 - 그런 것을 로그에 적고 설치가 끝났다고 부르는 것은 - 컬렉션이 아무도
찾아낼 수 없는 이유로 잘못 돌아가게 되는 경로입니다.

## 인스턴스를 다른 기계로 옮기기

`eidos pack`은 인스턴스 전체를 - 모든 모드, 로드 순서, 모든 프로필, 여러분의
세이브가 들어 있는 Overwrite, 그리고 모든 것이 설치되어 나온 압축 파일들까지 -
파일 하나에 씁니다. `eidos unpack`은 그것을 되돌려 놓습니다:

```sh
eidos pack skyrimse ~/backup.eidos                  # 또는 폴더를 주세요: 게임 이름과 날짜로 이름이 붙습니다
eidos unpack ~/backup.eidos /mnt/games/EidosSkyrim  # 다른 기계에서
```

`eidos pack --dry-run`은 무엇이 들어가고 무엇이 들어가지 않으며 그 이유는
무엇인지, 그리고 자리가 얼마나 필요한지를 아무것도 쓰지 않은 채 정확히
나열합니다. `eidos unpack --info`는 이미 가지고 있는 파일에 대해 같은 일을 합니다.

7-Zip이 무언가를 읽지 못했더라도 압축 파일은 그대로 쓰이고 이름도 붙습니다 -
가지고 있을 값어치는 있으니까요 - 하지만 `eidos pack`은 **1**로 끝나며 무엇이
빠졌는지 말해줍니다. 불완전한 백업은 성공이 아니고, 이것은 사람들이 `&&` 앞에
두는 명령입니다.

`.eidos` 파일은 자기 이름을 쓴 7-Zip 압축 파일입니다. 위장이 아니라 선택입니다:
모드를 설치하려면 어차피 7-Zip이 필요하므로 의존성이 하나도 늘지 않고, 언젠가
Eidos를 잃어버려도 백업은 여러분이 가진 아무 압축 프로그램에서나 열립니다.
**비솔리드**이므로 70 GB짜리 백업에서 앞쪽 전부를 풀지 않고도 파일 하나만 꺼낼 수
있고, LZMA2 `-mx1`로 압축됩니다 - 텍스처가 많은 목록에서 원본의 약 43%이고,
`-mx9`가 몇 점 더 줄이려고 쓰는 시간의 몇 분의 일밖에 걸리지 않습니다. 텍스처와
메시는 이미 압축된 형식이라, 더 큰 사전이 찾아낼 것이 거의 남아 있지 않습니다.
여러분 콘텐츠에서는 생각이 다르다면 `--level`(0, 1, 3, 5, 7, 9)이 그것을
덮어쓰고, `--no-downloads`는 `downloads/`를 빼놓습니다.

패킹은 인스턴스 잠금을 잡으므로 게임이나 다른 Eidos가 그 인스턴스에 쓰고 있는
동안에는 돌아가지 않습니다 - 백업은 스냅숏이지 번진 자국이 아닙니다. 백업은
`.part` 이름으로 쓰인 뒤 마지막에 이름이 바뀌므로, 도중에 끊긴 pack은 완성된 것처럼
보이지만 실은 아닌 `.eidos` 파일 대신 딱 봐도 덜 끝난 것을 남깁니다.

### 안에 들어가지 않는 것, 그리고 그 이유

| 빠지는 것 | 이유 |
| --- | --- |
| Proton 프리픽스 | 기계에 맞춰진 모양(드라이브 매핑, *이* 파일 시스템의 `Z:` 뷰)이고, Eidos가 `eidos prereqs <instance> --install`로 1분이면 다시 만듭니다. 이걸 지고 가면 다른 기계가 어차피 다시 만들어야 할 것을 보내자고 압축 파일이 대략 두 배가 됩니다. |
| 게임 | 인스턴스는 자기가 담고 있지 않은 게임을 모딩합니다. 그쪽에서 Steam으로 설치하세요. |
| 인스턴스 바깥의 도구 | xEdit, DynDOLOD 같은 것들은 자체 설치 프로그램을 가진 서드파티 바이너리입니다. 압축 파일 안에 **이름은** 적히므로, unpack이 새 기계에 어느 것들이 없는지 정확히 알려줍니다. |
| `logs/`, `.eidos.lock`, `prereqs.done`, `prereqs.log` | 백업을 만든 기계의 기록입니다. 특히 `prereqs.done`은 있지도 않은 프리픽스에 런타임 라이브러리가 이미 설치되어 있다고 주장하게 됩니다. |
| `loot/`, 단 `userlist.yaml`은 제외 | Eidos가 필요할 때 다시 받아오는 마스터리스트 캐시입니다. 여러분 자신의 LOOT 규칙은 캐시가 아니고 - 그것을 다시 받아오는 사람은 아무도 없으니 - 그 파일 하나는 함께 실려 갑니다. |
| `.base/`, `.base-root/` | 세션 동안 게임 자신의 파일이 치워져 있는 빈 마운트 지점입니다. |
| 쓰다 만 파일 | 멈춰 둔 내려받기(`*.unfinished`), 진행 중인 원자적 쓰기(`*.eidos-tmp*`). |
| 심볼릭 링크 | 7-Zip은 링크를 따라가 그것이 가리키는 것을 복사할 텐데, 절대 링크라면 남의 트리를 백업 안으로 끌어들인다는 뜻입니다. 대신 보고만 합니다. |

이들 하나하나가 그 이유와 함께 압축 파일 루트의 `eidos-backup.ini`에 들어갑니다 -
그래서 "여기 뭐가 안 들어 있지?"에 대한 답은 짐작이 아니라 `cat`입니다. 같은
파일이 인스턴스가 예전에 어디 있었는지, 어느 프로필이 활성이었는지, 풀면 얼마나
커지는지, 새 기계가 어떤 도구를 필요로 할지를 기록합니다.

내려받기 기록(`downloads/*.meta`)은 `url=` 줄이 **비워진** 채 들어갑니다. 그 URL은
서명된 Nexus 링크입니다: 몇 시간이면 동작을 멈추고, 그 파일을 내려받은 계정의
`user_id`를 담고 있습니다. 백업은 남에게 건네주라고 만드는 것이므로 그것을 지고
가지 않습니다. 내려받기를 다시 찾아낼 수 있게 해주는 것 - 모드 id, 파일 id,
버전 - 은 그대로 남습니다.

### 창 안에서

둘 다 **File** 메뉴에 있습니다: *Pack this instance...* 와 *Unpack a backup...*.
unpack은 환영 화면에도, 인스턴스 목록 아래에 있습니다. 그것이 가장 필요한 기계는
아직 인스턴스가 하나도 없는 기계이니까요.

Pack 대화 상자는 저지르기 전에 미리 보여줍니다: 파일이 몇 개인지, 얼마나 큰지,
그중 `downloads/`가 얼마나 되는지, 압축 파일이 대략 얼마가 될지, 그리고 이름은
적히지만 실려 가지는 않는 도구가 무엇인지. Unpack 대화 상자는 여러분이 파일을
고르는 순간 백업의 매니페스트를 읽으므로, 그 백업이 어느 게임을 담고 있는지, 언제
만들어졌는지, 예전에 어디 있었는지, 그 도구들 중 무엇이 여기 없는지를 말해줄 수
있습니다 - 여러분이 폴더를 주기도 전에.

둘 다 진행 표시줄과 함께 워커 스레드에서 돌아가므로 일하는 동안에도 창은 계속
응답하고, 끝나면 그 표시줄이 곧 보고가 됩니다. 패킹은 실행 내내 인스턴스 잠금을
잡고 있습니다: 읽히는 동안에는 다른 무엇도 그 인스턴스를 건드릴 수 없으며, 그것이
바로 백업을 번진 자국이 아니라 스냅숏으로 만들어 주는 것입니다.

### unpack이 고쳐주는 것

폴더를 그냥 복사하면 모든 도구 버튼이 옛 기계의 경로를 가리킨 채로 남습니다.
`eidos unpack`은 옛 인스턴스 루트를 가리키는 값들만, 오직 그것들만 다시 씁니다:
`tools.ini`의 `exe`, `workdir`, 번호가 붙은 `arg` 키들, 그리고 각 모드
`meta.ini`의 `installationFile`. 애초에 인스턴스 안에 있던 적이 없는
도구(`/opt/xedit/SSEEdit.exe`)는 있던 그대로 두고 다시 설치할 것으로 나열합니다 -
남의 xEdit가 어디로 갔는지 짐작하는 것은 수리가 아니라 창작이니까요. 인스턴스가
스스로를 중앙 집중식이라 하는지 휴대용이라 하는지도 바로잡아, 이후의 명령이 지금
있는 자리에서 찾도록 합니다.

unpack은 비어 있지 않은 폴더(덮어쓸 작정이라면 `--force`를 주세요), 매니페스트
자신이 말하는 크기에 못 미치는 디스크, 여러분 것보다 새로운 Eidos가 만든 압축
파일, 그리고 여러분이 고른 폴더 *바깥*에 쓰이게 될 항목을 담은 압축 파일은
거부합니다.

그다음:

```sh
eidos prereqs /mnt/games/EidosSkyrim --install   # Proton 프리픽스 다시 만들기
eidos play /mnt/games/EidosSkyrim
```

## GUI

```sh
cargo run -p eidos-gui
```

Colony의 양피지 / 버건디 외양을 한 MO2식 첫 실행 마법사: 환영 -> 인스턴스
종류(휴대용 / 전역) -> 게임 -> 이름과 위치 -> 요약 -> 생성 -> 메인 화면. 환영
화면은 알려진 기존 인스턴스도 모두(전역과 휴대용, 최근에 쓴 것부터) 나열해 한
번의 클릭으로 열게 해줍니다 - 인스턴스 전환기 역할도 겸합니다 - 그리고 이미
인스턴스가 들어 있는 폴더를 마법사에 가리키면 그 위에 새로 만들지 않고 있는
그대로 입양합니다(폴더가 다른 게임의 것이면 딱 잘라 거부합니다).

두 창(pane)짜리 메인 창도 만들어져 있습니다: 프로필 선택기(전환하거나, 현재
것을 복사해 새로 만들기), 거르고 선택하고 순서를 바꾸고 구분자로 묶고 카테고리로
좁히고 오른쪽 클릭으로 동작을 부를 수 있는 모드 목록, 그리고 Data / Plugins /
Conflicts / Overwrite / Saves / Downloads / Diagnostics 탭과 실행 대상 선택기가
달린 Run 버튼.

순서 바꾸기는 맨 위/맨 아래로 보내기만이 아닙니다: MO2의 조준된 이동도 여기
있습니다 - 첫 번째로 충돌하는 모드 위로 보내기, 마지막 것 아래로, 명시한
우선순위로, 또는 구분자의 그룹 안으로. 모두 하나의 공유 이동 헬퍼를 거치므로,
행을 지우고 다시 넣을 때 생기는 오프바이원은 다섯 곳이 아니라 한 곳에만
있습니다.

### 열, 정렬, 그룹

목록은 기본으로 네 개의 열을 그리고 여덟 개를 제공합니다: Category, Content,
Version, Author, Installed, Nexus id, Game, Flags. View 메뉴에서 체크하세요.
기본이 여덟 개 전부가 아닌 데에는 이유가 있습니다 - 모든 열을 켠 목록에는
정작 여러분이 읽고 있는 열인 NAME이 들어갈 자리가 남지 않습니다.

아무 머리글이나 클릭하면 그것으로 정렬합니다. 다시 클릭하면 역순, 세 번째
클릭이면 **로드 순서**로 돌아옵니다. 이건 들리는 것보다 중요합니다: 로드 순서는
목록을 끌어다 놓을 수 있는 유일한 순서입니다. 삽입 간격은 진짜 목록을 가리키는데,
정렬된 행은 전혀 다른 곳에 있기 때문입니다. 정렬이 켜져 있는 동안에는 삽입 띠를
그리지 않고, 아무도 겨냥하지 않은 곳에 떨어뜨리는 대신 끌기를 거부합니다 - MO2가
하는 것과 같은 일이고, 이유도 같습니다. View 메뉴가 그렇다고 말해주고 돌아가는
길도 제공합니다.

View 메뉴는 목록 전체를 카테고리별로 또는 출처별로(Nexus에서 온 것, 손으로 설치한
것) **그룹**으로 묶을 수도 있습니다. 그룹 머리글은 구분자가 아닙니다: 이름을
바꾸거나 색을 칠하거나 옮길 것이 뒤에 없고, 접히며, 접혀도 개수는 머리글에
남습니다. 구분자는 정렬이나 그룹 아래에서 목록을 떠납니다 - 구분자는 로드 순서상
뒤따르는 행들의 머리에 서는데, 정렬과 그룹은 둘 다 그 행들을 옮겨버렸으니까요.

### 마우스와 키보드

모드를 더블 클릭하면 Information, Ctrl+더블 클릭이면 그 폴더, Shift+더블
클릭이면 Nexus 페이지가 열립니다. Ctrl+F는 필터 상자에 캐럿을 놓습니다. 글자를
치면 그 글자로 시작하는 다음 모드로 뛰고, 다시 누르면 첫 번째에 붙어 있는 대신
나머지를 훑습니다. 어느 것도 필터나 접힌 구분자나 접힌 그룹이 감춘 행에는 내려
앉을 수 없습니다 - 보이지 않는 강조 표시를 옮기는 것이야말로 다음 Space가 보고
있지도 않던 모드를 켜고 끄게 되는 경로입니다.

구분자 메뉴의 "Collapse others"는 그것 하나만 빼고 모든 그룹을 접습니다. 끌기
도중에 접힌 그룹 위에 머무르면 그 그룹이 열려서, 끌기를 먼저 포기하지 않고도 모드를
그 안에 떨어뜨릴 수 있습니다 - 스쳐 지나는 것이 아니라 머무르는 것입니다.

### 목록이 모드에 대해 알려주는 것

권고성 플래그가 둘, 둘 다 글리프이며 설명은 마우스를 올리면 나옵니다. **No valid
game data**는 모드 최상단의 어떤 것도 이 게임이 로드하는 것처럼 보이지 않는다는
뜻입니다. 폴더를 한 단계 위로 올려야 할 수도 있고, 이 게임의 모드가 아닐 수도
있습니다. **Another game**은 모드 자신의 `meta.ini`가 다른 게임을 가리킨다는
뜻입니다. 둘 다 아무것도 막지 않고 - 모드는 그대로 배치됩니다 - 행 메뉴의 "Mark
as valid"가 어느 쪽이든 잠재웁니다. MO2 자신의 `validated=` 키를 통해서이므로,
한쪽 관리자에서 보증한 모드는 다른 쪽에도 조용히 도착합니다.

배치 검사는 일부러 너그럽습니다: `Root/` 트리도 인정하고, 읽을 수 없는 폴더도
인정하고, 빈 폴더도 인정합니다. 오백 행짜리 목록에서 잘못된 경고는 빠진 경고보다
나쁩니다.

### 손대기 전에 모드 백업하기

"Back up this mod"는 모드 폴더를 `<name>_backup`으로(그다음은 `_backup2`, 이런
식으로 - 백업이 이전 것을 대체하는 일은 없습니다) 옆에 복사합니다. 그 사본은
**비활성**입니다: 모드가 아니고, 체크박스는 아무 일도 하지 않으며, 병합된 뷰에
아무것도 보태지 않습니다. 체크하면 한 모드의 사본 둘이 서로 위에 배치될 테니까요.
"Restore this backup over the mod"는 두 번의 클릭으로 되돌립니다. 현재 내용물을
먼저 옆으로 옮겨두고, 사본이 성공한 뒤에야 버립니다.

**Data**는 병합된 뷰의 진짜 트리입니다. 한 번에 한 단계씩 펼쳐지므로 노드를 여는
비용은 활성화된 모드 전부를 재귀적으로 훑는 것이 아니라 그 노드를 가진 레이어마다
디렉터리 읽기 한 번입니다. 마운트가 서비스하는 것과 같은 레이어 스택이
답하므로 화이트아웃과 숨긴 파일이 존중되고, 이 탭이 게임이 보게 될 것과 어긋날 수
없습니다. 이름으로 거르고, 다투는 파일만으로 좁히고, Size와 Modified 열로 무엇이
어디 있는지 가려내고, 아무 행이나 파일 관리자에서 Reveal 하세요. **Plugins**는
ESP/ESM/ESL 로드 순서입니다(켜고 끄기, 손으로 순서 바꾸기, 또는 LOOT로 정렬한 뒤
정렬 후 보고서 읽기 - 그 안의 조언 링크는 브라우저에서 열립니다).
**Conflicts**는 파일별 승자와 패자를 설명합니다. **Overwrite**는 게임이 쓴 것을
한 단계로 진짜 모드로 만듭니다. **Saves**는 각 세이브의 헤더를 파싱해 - 캐릭터,
레벨, 위치, 플레이 시간 - 거기 구워진 플러그인 목록을 현재 것과 비교하고,
필요한 모드를 켜주는 버튼을 답니다. 이름만 대고 나머지를 여러분에게 떠넘기는 것은
지루한 쪽 절반이니까요.

"Information..."은 모드별 대화 상자를 엽니다: 일반, 충돌, 파일 트리, INI 조정,
메모. 파일 트리에서(그리고 Data 트리에서) 어떤 파일이든 **숨길** 수 있습니다 -
`<name>.mohidden`으로 이름이 바뀌어 지우지 않은 채로 가상 뷰에서 빠지므로, 한
모드의 어긋난 메시 세 개를 우선순위를 건드리지 않고 억누를 수 있습니다. 파일
트리는 평범한 파일 조작도 합니다: 새 폴더, 이름 바꾸기, 삭제, 열기. 모두 하나의
리졸버를 거치는데, 그 모드 안의 평범한 경로가 아닌 것은 무엇이든 거부합니다 -
`..`도, 절대 경로도, 심볼릭 링크인 구성 요소도 안 됩니다. 링크를 따라가면 삭제가
모드 폴더 바깥으로 나가버릴 테니까요. 이름 바꾸기는 마지막 구성 요소만 바꾸므로
결코 이동이 될 수 없고, 이미 쓰이고 있는 이름은 그 파일을 조용히 대체하는 대신
거부합니다. 삭제는 두 번의 클릭을 요구합니다. 여기서 다시 클릭해도 되돌릴 수 없는
유일한 동작입니다.

파일 트리나 Data 트리의 아무 행에서나 **View**는 파일을 미리 보여줍니다: 이미지와
텍스트. DDS나 NIF는 아닙니다 - 이 트리에 없는 블록 디코더와 렌더러가 필요합니다 -
하지만 빈 상자를 보여주는 대신 그렇다고 말하고 Reveal을 가리킵니다. 텍스트는
64 KB까지 읽고 어디서 멈췄는지 말해줍니다. 미리 보기는 한 번 훑어보는 것이고
Papyrus 로그는 백 메가바이트가 될 수 있으니까요. **INI Tweaks**는 모드가 자기
`INI Tweaks/` 폴더에 담아 온 조각들을 나열합니다. 켜진 것들은 실행 시 우선순위
순서대로 프로필의 게임 INI에 병합되고, 실행분의 INI가 캡처될 때 다시 떼어집니다 -
그러지 않으면 조정 하나가 슬그머니 설정이 되어버려 꺼도 아무 일이 없게 됩니다.

**Downloads 목록에서 모드 목록의 어떤 위치로 내려받은 것을 끌어다 놓으면** 그
우선순위로 설치되고, 파일 관리자에서 창 위로 떨어뜨린 압축 파일이나 폴더도
설치됩니다(그쪽 절반은 X11 또는 XWayland 세션이 필요합니다 - winit은 파일
떨구기를 X11에만 구현했습니다). 내려받기 자체도 멈추고 이어받을 수 있습니다:
멈추면 전송이 서고 받다 만 것은 남으며, Resume은 새 링크를 다시 확인하고 멈춘
곳부터 이어갑니다.

Downloads 탭은 전송 대기열이 아니라 압축 파일 **서고**입니다. 이름으로
거르고(친숙한 모드 이름으로도 되므로 "skyui"가
`SkyUI_5_2_SE-12604-5-2SE.7z`를 찾아냅니다), 최신순 · 이름 · 크기 · 상태로
정렬하고, 다 쓴 압축 파일은 **숨기세요** - 파일은 남기고 행만 없애므로, 책을
치우는 것이 태우는 것이 되지는 않습니다. "Show hidden"이 되돌려주고, 같은 버튼이
다시 숨김을 풉니다. "Remove N installed"는 이미 설치한 모드의 압축 파일을 두 번의
클릭으로 지우는데, **화면에 보이는** 것만 지웁니다: 필터가 곧 여러분이 어느 것을
뜻했는지 말한 방식입니다.

### Nexus 컬렉션

컬렉션 링크를 붙여넣거나 - 사이트에서 하나 클릭하면 - Eidos가 그 리비전의 구성
항목들을 나열하고, 각각을 이 인스턴스와 맞춰 봅니다: 설치됨, 내려받음, 없음.
컬렉션을 **읽기만** 합니다. 설치하지는 않고, 그 창이 그렇다고 말합니다. 여기서
설치 기능을 정직하지 못하게 만드는 것은 단순히 어렵기 때문이 아니라 네 가지
때문입니다: 구성 항목들은 평범한 Nexus 파일이라 파일마다 키가 필요한데 그 키는
사이트 자체의 버튼 밖에서는 프리미엄 계정만 발급할 수 있습니다. 전체 설치는 이
클라이언트가 초과 지출을 거부하는 예산 대비 구성 항목당 세 번의 API 호출입니다.
매니페스트의 단계, 규칙, 재생되는 FOMOD 응답은 실제로 공개된 Bethesda 컬렉션에
대고 검증할 수 없었고, 추측은 맞아 보이지만 맞지 않는 로드 순서를 만들어냅니다.
읽기는 요청 한 번이면 되고 정확합니다.

컬렉션은 **자기 게임에** 대고만 읽을 수 있습니다. Fallout 4 인스턴스를 올려둔 채
Skyrim 컬렉션을 열면, 구성 항목들을 엉뚱한 모드 목록에 맞춰 보는 대신 이름을 대며
거부합니다. 그랬다면 모든 "설치됨"과 모든 "없음"이 답의 모양을 뒤집어쓴 잡음일
테니까요.

### 오프라인 모드

**Settings -> Nexus -> Offline**은 Eidos가 Nexus에 접촉하는 일을 아예 멈춥니다.
업데이트 확인, 로그인, 내려받기, 컬렉션은 연결 오류로 실패하는 대신 그렇다고
말합니다. 켜지 않는 한 꺼져 있습니다 - 예전 Eidos가 쓴 설정 파일에는 그런 키가
없고, 없는 것을 "켜짐"으로 읽으면 업그레이드하는 모두의 네트워크를 끊게 됩니다.

**Preferred servers**는 내려받기가 선호할 CDN 노드를 좋은 것부터 줄 세웁니다.
고를 미러를 하나보다 많이 받는 것은 프리미엄 계정뿐이므로, 나머지 모두에게는
Nexus가 고르고 이 설정은 아무것도 바꾸지 않습니다. 이것은 필터가 아니라
순서입니다: 여러분이 지정한 것이 오늘 하나도 제공되지 않아도 내려받기는 그대로
일어납니다, Nexus가 처음 내놓은 노드에서.

**Categories**는 보여주기만 하는 것이 아니라 편집할 수 있습니다: 한 모드에나 선택
전체에 지정하고, 같은 대화 상자에서 카탈로그 자체를 고치고, 게임의 공식 카테고리
목록을 Nexus에서 가져오세요. 카탈로그 파일 둘 다 MO2 자신의
것(`categories.dat`과 `nexuscatmap.dat`)이므로, 공유된 인스턴스는 카탈로그
하나를 유지합니다.

**View -> INI editor**는 프로필의 게임 INI를 편집합니다 - 실행할 때마다 덮어쓰이는
Proton 프리픽스 속에 파묻힌 것이 아니라 남아 있는 사본 쪽입니다. **View ->
Log**는 세션 로그를 읽습니다. **View -> Extensions**는 여러분 자신의 애드온을
나열합니다. [extensions.ko.md](extensions.md)를 보세요.

설치는 무엇이든 받습니다: Simple과 FOMOD 경로, 여기에 Wrye Bash **BAIN**
패키지(하위 패키지를 체크하면 순서대로 병합됩니다)와, 어떤 휴리스틱도 배치를
알아보지 못할 때 압축 파일 트리를 보여주고 데이터 루트를 직접 가리키게 해주는
**수동** 선택기까지. 거부되는 압축 파일은 없습니다.

**Diagnostics**는 실시간 상태 검사를 돌립니다: 무엇보다 위의 실행 능력, 빠진
마스터(단 하나로 가장 믿을 만한 크래시 예측 지표), 활성 플러그인 중 아무도 로드하지
않을 아카이브, 모드 목록이 여전히 모드 폴더와 맞는지, 그리고 - 한 번 실행한
뒤에는 - 스크립트 익스텐더 자신의 로그가 각 플러그인 DLL에 대해 뭐라고 하는지.
"내 SKSE 플러그인이 로드됐나?"를 추론에서 증거로 바꿔줍니다.

GUI를 통해 게임을 실행하려면 게임의 Steam 실행 옵션을 실행 파일의 절대 경로로
설정하세요(Steam은 PATH의 `~/.cargo/bin`을 보지 못합니다):

```
~/.cargo/bin/eidos-gui %command%
```

Eidos는 그 게임의 인스턴스로 열립니다 - 마지막으로 쓴 것이므로 휴대용 인스턴스도
전역 인스턴스와 똑같이 다시 찾아집니다. Run을 클릭하면 병합된 뷰를 통해
실행됩니다. (Steam 밖에서 Run을 누르면 이 줄을 그대로, 실행 중인 바이너리의 실제
경로로 보여줍니다.)

Bethesda 타이틀의 Steam `%command%`는 보통 `<Game>Launcher.exe`를 가리킵니다.
Eidos는 그것을 결코 실행하지 않습니다: 그 런처는 `Data`를 다시 훑고
`plugins.txt`를 다시 쓰는 별개의 설정 앱이라, 방금 배치한 로드 순서를 되돌려
버립니다. Eidos는 스크립트 익스텐더의 로더가 설치되어 있으면 그것으로, 아니면 게임
바이너리로 바꿔 넣고, 물러설 수밖에 없었을 때는 그렇다고 말합니다 - 모든 SKSE
모드가 죽은 채로 시작하는 게임은 시작하지 않는 게임보다 나쁩니다.

여기 있던 예전 지침은 `WINEDLLOVERRIDES="d3dcompiler_47=n"`을 강요했습니다. 그것은
이제 필요 없고, 애초에 그리 정확하지도 않았습니다: *native*로의 오버라이드는 진짜
`d3dcompiler_47.dll`이 이미 프리픽스에 있을 때에만 도움이 됩니다. 이제 Eidos는
활성화된 모드의 DLL import를 훑고, 진짜 Microsoft DLL을 직접 배치한 다음에야
오버라이드를 설정합니다.

## 개념 증명 해보기

게임은 필요 없습니다. user 네임스페이스 안의 비특권 OverlayFS만으로(Linux >=
5.11) 합집합 + copy-on-write + 무접촉 + 네임스페이스별 범위를 증명합니다:

```sh
./scripts/poc-overlay.sh
```

## 도구

xEdit, BodySlide, DynDOLOD 같은 것들은 게임의 Proton 프리픽스 안에서 병합된 뷰를
통해 실행됩니다:

```sh
eidos tool skyrimse add BodySlide "<path>/CalienteTools/BodySlide/BodySlide.exe"
eidos tool skyrimse run BodySlide
eidos prereqs skyrimse            # 등록된 도구들이 필요로 하는 것과 그 상태
eidos prereqs skyrimse --install  # 빠진 것을 가져오기
```

도구 이름을 짓기 전에 알아둘 것 하나: **제목이 Eidos가 그 도구에 어떤 런타임
DLL을 준비해 줄지 결정합니다** - `BodySlide`는 DirectX 라이브러리를 받고, `BS`는
아무것도 받지 못합니다. GUI에서는 Executables 대화 상자가 각 선행 요건의 실제
상태를 입력란 아래에 보여주고, 빠진 것들은 버튼입니다.

표, 세 가지 선행 요건 등급, DynDOLOD가 winetricks로는 설치할 수 없는 .NET 런타임을
필요로 하는 이유, 그리고 모드로 설치된 도구가 자기 폴더가 아니라 병합된 경로에서
실행되는 이유는 [tools.ko.md](tools.md)에 있습니다.

소스에서 빌드하는 법과 저장소 배치는
[../internals/contributing.md](../../../../internals/contributing.md)에 있습니다.

## 확장

Eidos는 다시 빌드하지 않고도 확장할 수 있습니다: `~/.config/Colony/Eidos/addons/`에
둔 TOML 매니페스트가 Extensions 목록에 도구를, 또는 Health 탭에 검사를 더합니다.
Eidos 안으로 로드되는 것은 아무것도 없습니다 - 확장은 Eidos가 실행하는
프로그램입니다. [extensions.ko.md](extensions.md)를 보세요.
