# 拡張

拡張は Eidos の一部にならずに Eidos へ項目を足します。実体は、あるプログラムを
指す TOML マニフェストと、せいぜいそのプログラムだけです。

マニフェストは `~/.config/Colony/Eidos/addons/` に置き、拡張ごとに `.toml` を
一つ。View -> Extensions -> Open folder でフォルダを開き、Reload を
押します - 再起動は要りません。

`id`、`kind`、`exec` は必須で、`name` を省くと id が使われます。`exec` は
プログラムを指します。`/` を含まない名前は `PATH` から探します。プログラムが
見つからないと Eidos はその拡張をスキップし、View -> Extensions の行に理由が
出ます(`<exec> is not on PATH` または `<exec> is not there`)。`games` は拡張を
指定したゲーム id に限ります。省くとすべてのゲームに適用され、別のゲームでは
行に "not for this game" と出ます。

Eidos が拒否したマニフェストは、理由付きで先頭に並びます。拒否される場合は、
読めないファイル、TOML として不正または必須フィールドの欠落、空の `id` または
空白を含む `id`、空の `exec`、先のマニフェストがすでに使った `id`(ファイルは
名前順に読まれます)、Eidos が知らない `kind`、そして `protocol = 1` とファイル名
`extensions` を欠いたインストーラー、プレビュー、セーブ情報の kind です。

## なぜ Eidos の中に何も読み込まないのか

Mod Organizer 2 はプラグインを共有ライブラリとして読み込み、Python のものは Qt
経由で動かします。どちらもここには持ち込めません。Rust に安定した ABI はなく、
別のコンパイラ - あるいは別の最適化フラグ、共有依存の別の機能セット - で
ビルドされた共有ライブラリは未定義動作になり、バージョン不一致としては何も
報告されません。しかも
Eidos のウィジェットはコンパイル時ジェネリックなので、仮に ABI が安定していても
ライブラリが返すウィジェットを組み立てることはできません。

拡張は、あなたのアカウントが持つファイルシステムへのアクセス権で Eidos が実行するプログラムです。信頼できるヘルパーだけをインストールしてください。プロセスの分離と応答の検証は、OS のサンドボックスを提供するものではありません。

## ツール

```toml
id = "wrye-bash"
name = "Wrye Bash"
kind = "tool"
exec = "/opt/wrye/wrye-bash"
args = ["--data", "{data}"]
games = ["skyrimse"]        # すべてのゲームに出すなら省略
description = "Bashed patch builder."
author = "you"
version = "1.0"
```

View -> Extensions に Run ボタン付きで現れ、切り離されて起動します - Eidos は
待たず、ステータス行に pid が出ます。出力は捨てられます。`workdir` がなければ、
Eidos 自身を起動したフォルダで始まります。

## チェック

```toml
id = "esl-count"
name = "ESL budget"
kind = "diagnose"
exec = "/home/me/bin/esl-count.sh"
args = ["{profile_dir}/plugins.txt"]
```

更新のたびに、`workdir` の指定がなければインスタンスのルートで実行され、
1 行につき 1 件の所見を出力します:

```
level<TAB>title<TAB>detail
```

`level` は `problem`、`advice`、`ok` のいずれか。detail は任意で、title のない
行は捨てられます。既知のレベルで始まらないものはすべて無視されるので、進捗出力や
紛れ込んだ警告が Eidos 自身のチェックのような行を立てることはできません。所見は
Diagnostics タブに `<name> - <title>` として、prefix と Nexus のカードの後、
ほかの Health カードの前に並びます。

チェックの持ち時間は 3 秒。超えたものは停止され、それ自身に対する問題として
報告されます - クリックのたびに続く同じ更新の中で走るので、固まったチェックは
ウィンドウを凍らせてしまうからです。時計はチェックが終了して出力パイプが閉じる
まで進むので、パイプを握ったままの子プロセスが残っていると、その分も 3 秒に
数えられます。エラー終了して何も出力しなかったチェックも同じように報告され、
その際はエラー出力の最初の行が付きます。どちらかの出力が 1 MiB を超えた場合も
同様です。いずれの場合も Reload を押すまで再実行されず、行には "It will not be
retried until you press Reload." と出ます。チェックの標準入力は空です。

## プレースホルダ

`args` と `workdir` はどちらも次を展開します:

| プレースホルダ  | 何であるか                                   |
| --------------- | -------------------------------------------- |
| `{instance}`    | インスタンスのルート                         |
| `{mods}`        | `<instance>/mods`                            |
| `{downloads}`   | `<instance>/downloads`                       |
| `{overwrite}`   | `<instance>/overwrite`                       |
| `{profile}`     | 有効なプロファイル名                         |
| `{profile_dir}` | 有効なプロファイルのディレクトリ             |
| `{game}`        | ゲーム id、たとえば `skyrimse`               |
| `{game_name}`   | ゲームの表示名                               |
| `{install}`     | インスタンスが動かすゲームフォルダ           |
| `{data}`        | そのフォルダの `Data` ディレクトリ           |

`{install}` はストアのインストール先です。インスタンスがゲームのコピー(凍結した
`Stock Game` や、リスト自身のゲームフォルダ)で動くときは、そのコピーを指します
([usage.md](usage.md#ゲームファイル-ストアのインストールかコピーか)を参照)。`{data}` も
それに従います。

チェックにはさらに、マニフェストのあるフォルダを指す `{addon_dir}` が使えます。
下のプロトコル 1 の拡張も同じです。ツールでは使えません。

未知のプレースホルダは空にしません。空にすると `--out {typo}` が
`--out --next-flag` に化けてしまうからです。Eidos は、プレースホルダを
すべて解決できないツールやチェックの実行を拒否し、足りないものを告げます。
ツールならステータス行、チェックなら Diagnostics タブのそのチェックの行です。

## 拡張にできないこと

拡張は Eidos をコールバックしたり、アーカイブから自分自身を登録したり、独自のウィジェットを描画したりすることはできません。プロトコル 1 の構造化インストーラーは、検証されたファイル計画と選択の質問を返せます。レビュー、一時領域での準備、公開は Eidos が管理します。FOMOD と BAIN は引き続きネイティブのインストーラーです。プレビューやセーブ情報の拡張も、応答に上限を設けた同じホストを使います。照合の優先順位、記録済みの CLI 回答、制限、再実行時の同一性検証については、[プロトコル仕様と実行可能な例](../../../../guide/examples/extensions/README.md)を参照してください。
