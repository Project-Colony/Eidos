# トラブルシューティングと診断

ゲームがファイルシステムと食い違うものを見てしまった日のための一式です。
環境スイッチ、操作カウンタの読み方、既知の問題とその経緯、そしてパススルーの
話。

### VFS を診断する

ゲームがファイルシステムと食い違うものを見ているとき用に、環境変数が二つ
あります。

```sh
EIDOS_FUSE_STATS=1                  # op counters, dumped at unmount
EIDOS_FUSE_NO_CACHE=1               # every kernel-side cache off
EIDOS_FUSE_NO_CACHE=attr,neg,keep,dir   # or name them individually
```

troubleshooting.md に書いたクラッシュを見つけたのは、細かく指定できるほうの
形です。四つ全部を切れば「キャッシュのせいか?」に答えが出て、個別に名指しして
初めて「どれか」に答えが出ます。カウンタは残りの半分に答えます - `read 0` が
出るロードは `FUSE_PASSTHROUGH` が全バイトをカーネル内で処理したもので、
read パスで調整しようとしていたことはすでに無料で済んでいます。

## ユニオンを手でマウントする

衝突したときは最初の `--layer` が勝ち、最後があなたの手つかずのゲームデータ
です。マウントに要るのは `/dev/fuse` と `fusermount3` だけです(overlayfs も
Wine も不要):

```sh
eidos-fuse --layer mod_b --layer mod_a --layer game_data /mnt/point
# ... read and write through /mnt/point ...
fusermount3 -u /mnt/point
```

書き込みは `--overwrite <dir>`(省略時は一時ディレクトリ)へ落ちるので、ここ
でもレイヤ自体は手つかずのままです。


#### なぜパススルーは既定で無効なのか

パススルーは実体のバッキングファイルをカーネルへ渡すので、読み取りはこの
デーモンを完全に飛ばします。スループットの勝ちですが、ここでは正しさを犠牲に
します。Skyrim SE 1.6.1170、proton-cachyos 11.0、カーネル 7.1.4、同じ 82
プラグインのロード順で、バイナリがその capability を持つかどうかだけを変数に
して A/B を実測しました:

| パススルー | `STATUS_ACCESS_VIOLATION` を伴う `NtCreateFile` の失敗 |
|-------------|--------------------------------------------------------|
| 有効        | 152 - `.bsa` 75、`.esl` 65、`.esm` 10、`.esp` 2        |
| 無効        | 0                                                      |

有効にするとゲームは自分の書庫もプラグインも一つも開けず、ゲーム内では MOD が
ただ存在しないという形で表れます - エラーもログ行もありません。無効なら同じ
ロード順が、プラグインも書庫も Papyrus スクリプトも生きたままゲームプレイに
届きます。

この失敗はデーモンの内側からは見えず、それが発見を高くつかせました。こちらの
`open` は毎回成功し、カーネルがバッキングファイルを拒むこともありません
(失敗するセッション一回分を `EIDOS_FUSE_TRACE=open` で通して確認: `open
FAILED` ゼロ、`passthrough refused` ゼロ)。エラーはデーモンが
`opened_passthrough` と返したあとに生まれるので、デーモン側のどんなログにも
映りません。拡張子に固有でもなく、書庫もプラグインも等しく襲います。つまり
ゲームが実行中ずっと開いたままにするファイルです。

`EIDOS_FUSE_PASSTHROUGH=1` で戻せます。何が得られるかを測るため、あるいは
仕組みを再検証するためです。ランチャーと Diagnostics タブに出る capability の
警告は、こちらから求めたときにしか現れません。

ゲーム自体を Eidos 越しに起動するには、Steam の起動オプションをこうします:

```
eidos play skyrimse -- %command%
```

シェーダのコンパイルに Proton がネイティブの d3dcompiler を要るなら、前に
`WINEDLLOVERRIDES="d3dcompiler_47=n"` を付けてください。Eidos はそれを MOD が
同梱する DLL オーバーライド(ENB/ReShade/`.asi` ローダ)と統合します。


### レイヤのインデックスは本当に使われているのか?

インデックスは全か無かで、しかも黙って作られます。`LayerStack::new` は読み取り
専用レイヤの完全なマップを得るか `None` を得るかで、後者ならすべての問い合わせ
は以前とまったく同じようにレイヤを歩きます。セッションログに両者を見分けるもの
は何もないので、黙ってフォールバックしたスタックは動いているものと見分けが
つきません - 昔のコストを払いながら。

```sh
cargo run --release -p eidos-core --example index_health -- <mods-dir> <overwrite-dir>
cargo run --release -p eidos-core --example index_agrees -- <mods-dir> <overwrite-dir>
cargo run --release -p eidos-core --example listing_cost -- <mods-dir> <overwrite-dir>
```

`index_health` はインデックスあり/なしで実パスを解決し、ディレクトリ走査を
比べます。`index_agrees` は実インスタンスのすべてのパスとすべての一覧に
ついて、両者が同じものを返すか確かめます。`listing_cost` は統合済みの children
マップが `readdir` で何を節約するかを測ります。

`EIDOS_NO_INDEX=1` は歩くほうを強制します。二つの答えの差そのものをデバッグ
しているとき用です。

## 既知の問題

### DLSS やフレーム生成が黙って何もしない

原因は三つあり、どれもエラーメッセージを出しません。起動オプションで NVAPI が
有効になっていない、排他的フルスクリーン、古い Reflex の FPS 上限。チェック
リスト全体は [graphics.ja.md](graphics.md) にあります。

**一つのディレクトリを二通りに綴った MOD が、二つ目の下にあるものをすべて
失っていた。** 修正済み。ext4 は `meshes/` と `Meshes/` を別物として扱います。
統合ビューはそうであってはならず、実際の MOD は両方を同梱します - XP32
Maximum Skeleton はアニメーションと FNIS の behaviour ファイルを大文字のほう
に、`character assets` をもう一方に置いています。

リゾルバはパスの各要素について大小が完全に一致するものを取り、それに賭けて
いました。`meshes/` に入り、そこで残りのパスを見つけられず、レイヤ丸ごとを
捨てていたのです。もう一方の綴りの下にあるファイルはすべてゲームから見えません
でした - エラーもログもなく、どの診断にも出ません。実際の 50 レイヤの
インスタンスでは 74 ファイルでした。

一致した要素はいまや決定ではなく候補です。大小の完全一致はいまも先に試され、
その下で残りが失敗したときにだけ、走査は大小を畳み込んで等しい兄弟を探します。
一覧のほうも一つ上のディレクトリで同じ欠陥を抱えており、いまはレイヤごとに大小
を畳み込んで等しいディレクトリをすべて読みます。

形として知っておく価値があること: パスインデックスにこのバグはありませんでし
た。見つけたディレクトリをすべて歩くからです。フォールバックが返せないファイル
を黙って返していたわけで、これは逆です - フォールバックこそ決して間違えない
はずの答えです。

**DynDOLOD の LODGen が空のログを残して死ぬ。** `dotnet10` で修正、
[tools.ja.md](tools.md) を参照。症状は紛れもありません。すべてのワールドに
ついて `LODGen_SSE_<world>_log.txt` にバージョンのバナーと `.NET Version:` の
行だけがあって他は何もなく、ダイアログは「failed to generate object LOD for one
or more worlds」とだけ言います。原因は Wine の Mono が .NET Framework の代わり
に応答することで、.NET Framework をいくら入れても直りません - Proton は
プレフィックスを更新するたびに `mscoree.dll` を自分のツリーへのシンボリック
リンクで置き換えます。

**Wine はマウントが大小を畳み込むと分からなかった。** 修正済み、そしてこれが
効いた一件です。

「このファイルシステムは大小を区別しないか」を問う API はないので、Wine の
`get_dir_case_sensitivity` は CIOPFS が自分の配下のディレクトリに残すマーカーを
嗅ぎに行きます。無ければ Wine は大小を区別すると仮定し、綴りがバイト単位で
一致しないルックアップはすべて、大小無視の一致を探すためにディレクトリ丸ごとの
読み取りへ落ちます。Bethesda のゲームはファイルが `ccBGSSSE001-Fish.bsa` である
のに `data/ccbgssse001-fish.bsa` を求めるので、ほぼすべてのアセットで発火しま
した。八秒で 4471 回のマーカー探査と 2236 回のディレクトリ全読み直し、九十秒で
`Data` の列挙 195796 回。Skyrim SE はメインメニューに一度も届かず、常駐 240 MB
のままでデーモンはコアの 92% を焼いていました。

Eidos は最初から `resolve_read` で大小を畳み込んでいました。コストのすべては、
そう言わなかったことにありました。`lookup` はいま `.ciopfs` に答えます。
`readdir` はいまもそれを一覧しません。

これを単に遅いではなく致命的にしたものが二つあります。コストはディレクトリの
大きさに比例するので、Anniversary のコンテンツを入れたこと(`Data` が 37
ファイルから 177 へ)が均衡を崩しました。そして `opendir` が統合済みの一覧を
先回りして作っていたこと。Wine がディレクトリを開くのは中のマーカーを `stat`
するためだけ、という場合には純粋な無駄です - スナップショットはいまは最初の
`readdir` で取られます。

その後: メインメニュー、常駐 2.1 GB、デーモンは CPU 0%。

見つけたのは `EIDOS_FUSE_TRACE=opendir` で、これは同梱されています。操作
カウンタは数を教えます。一つのディレクトリの 195796 回の列挙は、合計の中では
見えません。

**ゲームが `plugins.txt` を空に書き直す件**も、ほぼ同じことでしょう - まともな
時間で列挙しきれない `Data` を前に、そこには何もないと結論して、それを保存した。
証明はされておらず、確かめ直す価値があります。いずれにせよキャプチャのガード
(有効なセットを丸ごと消すキャプチャは、大きさによらず拒まれる)があるので、
これがプロファイルを壊すことはもうありません。

**`FOPEN_KEEP_CACHE` は無効。** 修正済み、そして理由を知っておく価値があり
ます。MOD を一つも入れていない状態で、メインメニューの数秒後に Skyrim SE を
null 参照で決定論的に落としました。カーネル側の残り三つのキャッシュは個別に
二分探索で除外され、効いていたのはこれだけでした。失っても無料だと当時は実測
されましたが、その測定は `FUSE_PASSTHROUGH` が有効な状態で取られたもので、
そこではデーモンは読み取りを*一つも*処理せず(`EIDOS_FUSE_STATS` はロード一回分
で `read 0` を報告)、カーネルはすでにバッキングファイルに対してそのページを
キャッシュしていました。パススルーはいまは既定で無効(下記)なので、その論拠は
もう通らず、本当のコストは未測定です - どのみちクラッシュだけで無効のままに
する理由には十分です。調べるなら `EIDOS_FUSE_KEEP_CACHE=1` で戻せます。二つの
フラグはもう絡み合っていないので、いまは単独で試せます。

### FUSE パススルーがあるとゲームは MOD の中身を一切読み込まない

無効にすることで修正、`EIDOS_FUSE_PASSTHROUGH=1` で戻ります。パススルーが有効
だと Skyrim SE はカーネル 7.1.4 で自分のファイル 152 個(`.bsa` 75、`.esl` 65、
`.esm` 10、`.esp` 2)を `STATUS_ACCESS_VIOLATION` で開けず、無効なら 0 です -
つまり MOD の中身が黙って一つも読み込まれません。カーネルはデーモンが
`opened_passthrough` と返したあとにエラーを上げるので、デーモン自身のログは
きれいな実行を映します(失敗した open ゼロ、拒まれたバッキングファイルゼロ)。
カーネル側の経路における根本原因は特定できていません。再検証できるように、
そしてイメージのマッピングに必要だと判明した場合にパススルーを DLL のみへ
絞れるように、スイッチは残してあります。
