# Eidos の使い方

Eidos の使い方です。インスタンスとゲームのコピー、コマンドライン、Test run、ウィンドウ、
Nexus のコレクションと更新、インスタンスの別マシンへの移動、ツールと拡張を扱います。
問題が起きたときは [troubleshooting.md](troubleshooting.md) を、ソースからのビルドと
リポジトリの構成は [../internals/contributing.md](../../../../internals/contributing.md) を
参照してください。

## インスタンス: グローバルとポータブル

インスタンスを取るコマンドは、ゲーム ID かポータブルインスタンスのフォルダを受け取り
ます。`skyrimse` が指すのはグローバルインスタンスで、Eidos は
`~/.local/share/Colony/Eidos/instances/skyrimse` に置きます。ポータブルインスタンスは、
好きな場所(二台目のドライブ、ゲーム用のパーティション)に置ける自己完結した
フォルダで、MO2 のポータブルインスタンスと同じように移動できます:

```sh
eidos init skyrimse /mnt/games/EidosSkyrim   # そこにポータブルインスタンスを作る
eidos install /mnt/games/EidosSkyrim mod.7z  # どのコマンドもフォルダを受け取る
eidos play /mnt/games/EidosSkyrim -- %command%
```

フォルダの `eidos-instance.ini` がゲーム名を持つので、フォルダには他に何も要りません。
環境変数の `EIDOS_INSTANCE=<folder>` はゲーム ID をそのフォルダへ振り向けます。Steam の
起動オプションなどで使えます。作ったり開いたりしたポータブルインスタンスは
`~/.config/Colony/Eidos/instances.ini` に(最近使った順で)記憶されます。ウィンドウの
ようこそ画面はそれらを一覧し、Steam からの起動は最後に遊んだものに着地し、`nxm://`
ハンドラはそこへダウンロードします。

ポータブルフォルダを手で移動しても、古い場所への絶対パスで登録したツールの項目を
除いて、すべて残ります。`eidos pack` と `eidos unpack`
([後述](#インスタンスを別のマシンへ移す))はそれを直しますが、素の `mv` は直しません。
`~/.local/share/Colony/Eidos/runtimes/` のランタイムキャッシュはマシン上のすべての
インスタンスで共有されるので、78 MB の .NET ホストが各インスタンスにコピーされる
ことはありません。

一箇所だけは拒否されます。ゲームのインストールフォルダの中です。MO2 の利用者がよく
インスタンスを置く場所ですが、あの木は Steam のものです。更新、「整合性の確認」、
アンインストールがそれを書き換えたり消したりして、あなたの環境ごと持っていきます。
また Eidos はゲームのルートに重ねてマウントするので、その中のインスタンスは自分の
マウント先の内側に座ることになります。ウィザードも `eidos init` も `eidos play` も
`eidos shell` も断ります。フォルダはゲームの隣に置いてください。同じドライブの
兄弟フォルダなら、手軽さは変わりません。

### Eidos が自分のファイルを置く場所

Eidos は自分のファイルを `Colony/Eidos` の下に置きます。Colony 系のどのプログラムも
使う配置です。あなたが選んだもの(設定、Nexus のセッション、インスタンス一覧、自分で
書いたゲームとアドオンの定義)は `~/.config/Colony/Eidos/`、グローバルインスタンス
(`instances/`)、ダウンロードしたランタイム、セッションログ(`logs/`)は
`~/.local/share/Colony/Eidos/`、LOOT のマスターリストは `~/.cache/Colony/Eidos/` で、
無くなればいつでも再ダウンロードされます。

古い Eidos のレイアウト(`~/.config/eidos/`、`~/.local/share/eidos/`、
`~/.local/state/`)のファイルが見つかると、更新後の初回起動がそれらをコピーし、ログに
そう書きます。グローバルインスタンスはバイト単位のコピーではなくハードリンクで移す
ので、MOD は余分な容量を使わず、ツールの項目は新しいフォルダを指すよう書き換えられ
ます。古いディレクトリのものは変更も削除もされません。新しい配置が動くのを確かめたら、
自分で消してください。コピーができない場合(ディスクが一杯か読み取り専用、古い
インスタンスフォルダが別のドライブにある、そこからゲームがまだ動いている)、Eidos は
古い場所を使い続け、次回の起動で再び試みます。古いインスタンスフォルダを指したままの
Steam の起動オプションは、移動後のインスタンスを開きます。

ハードリンクで容量が節約されるのは最初だけです。移動後に削除や再インストールをした
MOD やダウンロードは、古いインスタンスフォルダを通じて古いコピーがディスクに残り
続けるので、その容量を取り戻すには `~/.local/share/eidos/<game>/` を削除してください。

ポータブルインスタンスは決して移動しません。置いた場所にそのまま残ります。

## コマンドライン

```sh
eidos games                                # ここに入っている対応ゲーム(MO2 の一覧と同じ)
eidos init skyrimse [folder]               # インスタンスを作る。フォルダを渡せばポータブル
eidos init skyrimse --game-path <folder>   # 複数インストールされているとき、<folder> のコピーを使う
eidos install skyrimse mod.7z [name]       # 書庫をインストールする(Simple、FOMOD、BAIN、OMOD)
eidos install skyrimse mod.7z --replace --backup  # MOD に上書きして再インストールする(--merge はそのファイルの上に入れる)
eidos import skyrimse <mo2-profile>        # MO2 プロファイルの MOD の順序とプラグインの状態を引き継ぐ
eidos sort skyrimse [--dry-run]            # ロード順を LOOT で並べ替える(--update-masterlist で先に更新)
eidos play skyrimse                        # 何がマウントされるかを表示する
eidos play skyrimse -- <command>           # MOD をゲームに重ねた状態で <command> を実行する
eidos shell skyrimse                       # 統合ビューのシェル。書き込みは Overwrite に入る
eidos check skyrimse [--json]              # ウィンドウなしの Health チェック
eidos sessions skyrimse                    # 記録されたゲームとツールの実行を新しい順に表示
eidos sessions skyrimse diff [<id>]        # 終了コード 0 で終わった直近の実行から何が変わったか
eidos stock-game skyrimse                  # インスタンスが使うゲームファイル。コピーを凍結するか切り替える
eidos tool skyrimse                        # ツールを一覧する(add、rm、run は下の「ツール」を参照)
eidos tool skyrimse run --exe <path>       # exe を統合ビュー越しに一度だけ実行する
eidos tool skyrimse import-mo2 [--write]   # ModOrganizer.ini の実行ファイル。--write で追加する
eidos prereqs skyrimse [--install]         # ツールが必要とするもの。--install で足りないものを取得する
eidos collection skyrimse <link>           # Nexus のコレクションをインストールする(--dry-run、--no-optional)
eidos nexus status                         # 保存された Nexus のサインインを確認する
eidos nexus update skyrimse [--apply]      # MOD の更新を確認する。--apply でインストールする
eidos nxm <link>                           # Mod Manager Download のリンクをダウンロードする
eidos nxm --register                       # サイトの Mod Manager Download ボタンが Eidos を開くようにする
eidos export skyrimse -o mods.csv --active # MO2 の CSV 形式。--active は有効な MOD だけ
eidos pack skyrimse backup.eidos           # インスタンス丸ごとを一つのファイルに
eidos unpack backup.eidos [folder]         # フォルダなしならグローバルインスタンスは元の場所に戻る
eidos --version                            # バージョンを表示する
```

引数なしの `eidos` はコマンドの一覧を表示します。ほとんどのコマンドは、引数が足りない
ときに自分のオプションを表示し、`eidos tool --help` はツールのサブコマンドを一覧します。
`eidos pack` は `--dry-run`、`--level`、`--no-downloads`、`--no-recovery`、`--force` を
取り、`eidos unpack` は `--info` と `--force` を取ります。どちらも
[後述](#インスタンスを別のマシンへ移す)します。`eidos stock-game` は
[ゲームファイル](#ゲームファイル-ストアのインストールかコピーか)で説明します。

### 統合ビュー越しにゲームを実行する

`eidos play` は、プライベートな名前空間の中で、インスタンスの MOD をゲーム自身の
`Data` ディレクトリに重ねてマウントし、そのビュー越しにコマンドを実行します。ゲーム
自身のファイルは先に bind-stash されるので、デーモンは元のファイルをそのまま読めます。
書き込み(セーブ、再生成された設定)はインスタンスの `overwrite/` レイヤーに落ちます。
ゲームのインストール先も MOD のフォルダも、一バイトも変わりません。

Eidos に root は要りません。setuid のヘルパーもシステムサービスも与える権限もなく、
プライベートな user + mount 名前空間の中でマウントします。`eidos` バイナリへの任意の
capability は FUSE パススルーを許しますが、`EIDOS_FUSE_PASSTHROUGH=1` を設定しない限り
無効のままです。[install.md](install.md#任意-fuse-パススルー)を参照してください。
capability があると、Eidos は user 名前空間ではなく素の mount 名前空間を使います。
MOD の展開はどちらでも同じです。

### 統合ビューでのシェル

`eidos shell <instance>` は、ゲームから見える状態のゲームフォルダで `$SHELL`(なければ `/bin/sh`)を起動します。有効な MOD はすべて `Data` に重ねられ、Root MOD はゲームのルートに重ねられ、そこへ書き込まれたものはすべて Overwrite に入ります。`eidos shell <instance> -- <command>` は代わりにコマンドを 1 つだけ実行します。たとえば `eidos shell skyrimse -- ls Data/meshes` や、NifSkope のようなネイティブツールです。この実行はゲームのセッションと同じくインスタンスのロックを保持するので、終了するまでウィンドウは変更を保存できず、`eidos sessions` には `shell` という名前で記録され、ゲームの起動としては記録されません。コマンド実行中の Ctrl+C は Stop と同じように実行を止めます。Eidos がコマンドを終了させ、セッションを回収し、アンマウントします。対話シェルでは Ctrl+C は通常どおりシェルのものです。実行を終えるには `exit` と入力します。

### ターミナルからの Health チェック

`eidos check <instance>` は、ウィンドウを要しない Health チェックを実行します。SSH 越しや
Game Mode でも動かせ、バグ報告にも貼れます:

- Proton プレフィックスとそのレジストリ;
- プラグインの診断と欠けたマスター;
- スクリプトエクステンダとそのプラグイン;
- 前回の正常な起動以降のゲームの更新;
- Steam の起動オプション;
- グラフィックスの設定(NVAPI、フルスクリーン、ENB);
- 直近の実行のクラッシュログ;
- プロファイルの INI にある `sTestFile` の行;
- Starfield の `.esp` と blueprint プラグイン;
- `vm.max_map_count` と open files の上限;
- インスタンスが動かすゲームのコピーと、リストの `ModOrganizer.ini` にある別の
  ゲームフォルダを指す `gamePath`;
- もう成り立たないコレクションの順序規則;
- NTFS、exFAT、FAT 上のゲームファイル;
- BodySlide のデータパス;
- `Overwrite/Root` に残った `Data` フォルダ;
- `Interface/fontconfig.txt` が名指しするが、どの MOD も提供しないフォントライブラリ;
- Fallout 4 と Fallout 4 VR の MOD の BA2 アーカイブに含まれる圧縮された音声。

一部のカードは、Diagnostics タブで、ウィンドウだけが計算します。パッチの順序、MOD が
置き換えるエクステンダのスクリプト、どれも読み込まないアーカイブ、Nexus の要件、LOOT が
dirty と示すプラグイン、ゲームを動かす Proton のビルド、Display カード、入力より古い
ツールの出力です。

コマンドは Copy report と同じシステムの行を出力し、続いて検出ごとに 1 行を出力します。
ホームフォルダは `~`、ログイン名は `<user>` に置き換えて表示します。終了コードは、問題が
見つからなければ 0(助言だけなら 0 のまま)、問題が 1 つ以上見つかれば 1、Eidos が
チェックできなかったとき(引数の誤り、開けないインスタンス、検出できないゲーム)は 2 です。

`eidos check <instance> --json` は代わりに JSON オブジェクトを 1 つ出力します。最上位のフィールドは `eidos`(バージョン)、`game`、`instance`、`system`(`proton`、`flatpak_steam`、`passthrough`、`session`、`distro`、`kernel`、`dev_fuse`、`fusermount3`、`max_map_count`、`open_files_hard`)、`findings` です。`max_map_count` と `open_files_hard` は数値で、Eidos が読み取れなかったときは `null` です。各検出は `code`、`level`(`problem` または `advice`)、その `args` からなり、各コードの説明文は Diagnostics タブに表示されます。

### 前回の正常な実行から何が変わったか

`eidos play`、`eidos shell`、`eidos tool run` による実行は、ウィンドウ、ターミナル、Steam のどこから始めても、`<instance>/logs/sessions/` に記録を書き込みます。内容は、プロファイル、有効な各 MOD とそのバージョンおよび Nexus のファイル ID、プラグインの順序、各プロファイル INI のチェックサム、ゲーム実行ファイルのバージョン、Eidos のバージョン、終了コード、その実行で作られたセーブです。新しい 50 件が残り、`logs/` はパックしたインスタンスに含まれません。`eidos sessions <instance> diff` は、終了コード 0 で終わった直近のゲーム実行を現在の状態と比べます。`diff <id>` で一覧から別の記録を選べます。一覧では [Test run](#テスト実行) が `test` と表示され、Test run が最後の正常な実行として選ばれることはありません。停止した実行は終了コード 143 を記録するので、これも選ばれません。Eidos はここではまだクラッシュを検出せず、Proton 上でクラッシュしたゲームも終了コード 0 で終わることがあります。選ばれた実行がそれに当たる場合は、`diff <id>` でより前の記録を指定してください。

## MOD 一覧

MO2 と同じく、プロファイルはそれぞれ自分の `modlist.txt`(どの MOD が有効で、
どの優先度か)を持ち、MOD のフォルダ自体はインスタンスで共有の `mods/` に
あります。手で `mods/` に置いたフォルダはまだ一覧に載っていません。それは
最高の優先度で無効として現れます。ウィンドウの一覧の末尾、MO2 と同じ場所です。
だから有効にすれば、競合ではそれが勝ちます。

フォルダは共有なので、MOD を削除したり改名したりすると、すべてのプロファイルが
変わります。その行はどのプロファイルの `modlist.txt` からも消され、あるいは
そこで改名され、それ以外については各プロファイルが自分の状態と順序を保ちます。
MOD が一つも残らなかったプロファイルは、`modlist.txt` そのものを持ちません。

ウィンドウは MOD 一覧とロード順の自分用の写しをもとに動きます。開いている間に
別の Eidos プロセスがそのどちらかを書くと(端末での `eidos install` や
`eidos sort`、コレクション、Steam が始めたセッション、二つ目のウィンドウ)、
ウィンドウの次の編集は、その作業を上書きする代わりに拒否されます。ウィンドウは
ディスクから読み直し、
*Not saved: another Eidos process changed the mod list. It has been reloaded - redo the change.*
と告げます(ロード順の場合も同様です)。失われるのはその一クリックだけなので、もう一度やってください。
Rename、New mod、Add separator、Remove、そして Overwrite を MOD に変える操作は、
`mods/` に触る前に確認を行うので、拒否された編集はディスク上の何も変えません。
INI エディタも同じく、開いた後に変わったファイルの上へ保存することを拒みます。

## セーブはプロファイルのもの

プロファイルはそれぞれ自分のセーブを `profiles/<name>/saves/` に持ち、実行して
いる間はそのフォルダが Proton プレフィックスの中のゲームのセーブフォルダに重ねて
マウントされます。プロファイルの初回起動は、プレフィックスにすでにあるセーブを
そこへ一度だけコピーするので、後でプロファイルから消したセーブは消えたままです。
実行が終わるたびに、プロファイルの最新のセーブが Steam Cloud のためにプレフィックス
へコピーし戻されます。Eidos が置いたのではないプレフィックスのセーブは、まず
プロファイルに `orphan-<time>-<name>` として保管され、上書きされることは決して
ありません。

最初のコピーの後に Eidos を通らずにプレフィックスへ入ってきたセーブ(Steam Deck
からの Steam Cloud のダウンロード、Eidos を使わない起動)は、プロファイルの
セーブがマウントされている間は隠れたままです。それを消すものは何もありません。
起動時に実行のログでその名前が挙げられます(ウィンドウからの起動ならインスタンスの
`logs/run-*.log`、Steam からの起動なら Steam のコンソール)。挙げられるのは、
そのファイルの組が変わるたびに一度だけです。Saves タブは、見出しの下の行でこれらの
セーブを数えます。それで遊ぶには、Saves タブの Import を押してください。Import は
そのセーブをコセーブと一緒にプロファイルへコピーし、プロファイルのセーブを置き換える
ことはありません。プロファイルがすでに使っている名前のセーブは、
`orphan-<time>-<name>` として取り込まれます。

## テスト実行

Run の隣にある Test run ボタンは Run と同じようにゲームを起動しますが、ゲームが書き込むものはすべて、プロファイル、Overwrite、プレフィックスではなく `<instance>/test-run/` に入ります。対象は、新しいセーブと変更されたセーブ、INI の変更、`plugins.txt`、Data やゲームフォルダに書かれたファイル、そして `Documents/My Games/<game>` のログです。テストは、プロファイルの MOD のまま、MOD なし、またはリストで選択した MOD のうち有効なものと、そのプラグインがマスターとして必要とする MOD だけ、のいずれかで行えます。

ゲームが終了すると、Eidos はそれらのファイルを 5 つのグループ(セーブ、INI の変更、プラグインの状態、Overwrite への出力、ログ)に分けて一覧にし、グループごとに残すか捨てるかを尋ねます。Apply は、ファイルのある全グループに答えが出るまで待ちます。プラグインの状態は、その実行がプロファイルとは別の MOD の組を使った場合には提示されません。セーブを残しても、プロファイルのセーブが消えることはありません。実行中にゲームが消したセーブも同じです。Overwrite への出力を残すと、ゲームが消したファイルも Overwrite から取り除かれ、一覧は先にその数を示します。何かを捨てるには 2 回目の押下が必要です。Decide later は一覧を閉じてファイルを `test-run/` に残し、次にインスタンスを開いたときか F5 を押したときに一覧が再び開きます。テスト実行中に Eidos やコンピューターが止まった場合も、ファイルはそこに残り、一覧は同じように開きます。

ウィンドウがゲームのストアから起動されたものでない場合、Test run は Run と同じようにゲームをそのストア(Steam、Heroic、Legendary)に渡し、ストアが始めた実行がテスト実行になります。ストアがゲームを起動しなかった場合、依頼は待機したままになります。そのプロファイルの次のゲーム実行が、Run からでもストアからでも、テスト実行になります。Cancel the waiting test run はそれを取り下げます。テスト実行が扱うのは上に挙げたフォルダだけです。Wine のレジストリなど、ゲームのそれ以外の書き込みはいつもの場所に行きます。テスト実行のセーブが Steam Cloud に届くのは、それを残してから通常の実行をプレイした後だけです。

### 問題の原因になっている MOD を見つける

Diagnostics にある Find the mod behind a problem ボタンは、再現できる問題(特定の場所でのクラッシュなど)を起こしている MOD を探します。各ステップは、残っている容疑の MOD の半分、それらが必要とするマスター、常にオンにしておく MOD(開始時にリストで選択していた有効な MOD と、スクリプトエクステンダを提供する MOD)によるテスト実行です。実行のたびに、問題が起きたかどうかを答えます。Not sure は容疑の MOD を別の分け方で分け直し、Run it again はそのステップをやり直します。回答または Run it again は、2 回目の押下でそのステップが書いたファイルを捨てます。その一部を残したい場合は、先に See the files を押してください。テスト実行の後と同じ一覧が開きます。ゲームがクラッシュしてクラッシュロガーがログを書いた場合、またはゲームがエラーコードで終了した場合、Eidos は Yes をありそうな答えとして示します。容疑の MOD が 200 個なら、実行は約 8 回です。

探索は `<instance>/bisect.json` に保存されるので、ステップの合間に Eidos を閉じてもかまいません。探索は開始したプロファイルに属します。Stop the search は 2 回目の押下で探索を破棄します。結果は、その MOD か、互いのマスターを必要とする MOD の組を示し、`<instance>/logs/bisect-<time>.txt` に残ります。生成された MOD(Nemesis や DynDOLOD の出力、Bashed Patch)は完全なリスト向けに作られているため、その半分では失敗することがあります。常にオンにしておくか、探索のあいだずっとオフにしておいてください。

## Wabbajack リスト

Eidos には Wabbajack のインストーラーはありません。リストは Eidos の外で CLF3 または Jackify を使ってインストールし、ウィザードでそのインストール先フォルダをポータブルインスタンスとして選んでください。Eidos はフォルダを MO2 の構成として読みます。`mods/`、`profiles/<name>/modlist.txt`、プラグインリストです。インストーラーが書いた `ModOrganizer.ini` は保持され、上書きされることはないので、リスト自身の実行ファイルの登録はそのまま残ります。

多くのリストは、改変したゲームのコピーを入れた `Stock Game` または `Game Root` フォルダを作り、MO2 はそこからゲームを起動します。ウィザードまたは `eidos init` がリストのフォルダを初めて取り込むとき、そのフォルダにゲームの実行ファイルがあれば、インスタンスもそこからゲームを起動します。起動は引き続き Steam、またはそのゲームを持つストアを通して行われるので、何も移動する必要はありません。Eidos はリストの `ModOrganizer.ini` にある `gamePath` から、またはこの 2 つの名前からフォルダを見つけます。以前の Eidos で取り込んだインスタンスは、切り替えるまでストアのインストールを使い続けます(次の節を参照)。その `gamePath` がインスタンスの動かさないゲームフォルダを指している場合、Diagnostics がそう告げます。PGPatcher のような Mod Organizer 2 モードのツールは、ゲームをそこから読むからです。CLF3 は BSA と DDS のファイルを独自のツールで作り直すため、結果が Wabbajack のインストールと異なることがあり、リストの作者もそのサポートはしません。

## ゲームファイル: ストアのインストールかコピーか

既定では、ゲームはストアのインストール、つまり Steam、Heroic、Legendary がゲームを置いているフォルダから動きます。代わりに、インスタンス内に置いたそのフォルダのコピーから動かすこともできます。MOD はコピーの上に重なり、ストアのインストールは Eidos が結果をマウントする場所でしかなくなります。ゲームを起動するのは引き続きストアなので、Steam のオーバーレイ、シェーダーキャッシュ、クラウドセーブはそのまま使えます。

Diagnostics タブの一番上にある Game files カードは、インスタンスが使っているファイルを、コピーとストアのインストールそれぞれのゲームバージョンとともに示し、それらを切り替えます。ターミナルでは `eidos stock-game <instance>` が同じ内容を表示し、`use <folder>`、`store`、`freeze`、`delete --yes` がカードのボタンと同じことをします。`freeze` はサイズとコピーの種類を表示し、`freeze --yes` がコピーします。

**Freeze this version** はストアのインストールを `<instance>/Stock Game` にコピーし、そこからゲームを起動します。ストアの更新が変えるのはストアのインストールでありコピーではないので、更新でスクリプトエクステンダのプラグインが壊れなくなります。1 回目の押下でサイズと、ファイルシステムがそれをどう扱うかを表示し、2 回目でコピーします。btrfs や XFS のようにブロックを共有できるファイルシステム(reflink)では、ストアがファイルを変えるまでコピーはほとんど容量を使いません。ext4 の場合や、ゲームとインスタンスが別のファイルシステムにある場合は、ゲームフォルダと同じ大きさの完全なコピーになります。Eidos は次の場合に拒否します。Steam がゲームを使用中または完全にはインストールされていないと報告している間、インスタンスのゲームやツールが動いている間、インスタンスにすでにリストのゲームのコピー、凍結したコピー、未完成のコピーがある場合、そしてファイルシステムの空きが完全なコピーに必要な分に足りない場合です。Heroic と Legendary のコピーは、進行中の更新を確認されません。Stop、失敗、コピー中のゲームの Steam 更新のあとには `Stock Game.eidos-tmp` が残り、カードがその削除を提案します。このフォルダが使われることはありません。

コピーは、作成後にストアがゲームフォルダで追加、変更、削除したファイルをすべて隠します。新しい Creation Club ファイル、新しい実行ファイル、新しい DLL などです。ゲーム、プラグインリスト、LOOT、Health のチェックはどれもコピーを読みます。ゲームフォルダの外で起きることは隠せません。更新により次回の起動時に Proton プレフィックスへランタイムがインストールされることはありますし、Steam がゲームを別の Proton に切り替えることもあります。

**Return to the store version** は、2 回目の押下で次回の起動からコピーを外します。コピーはディスクに残り、**Delete the copy** で削除できます。こちらも 2 回目の押下が必要です。インスタンスがまだそのコピーを動かしている間は、Delete は拒否されます。Eidos がリスト自身の `Stock Game` や `Game Root` フォルダを削除することはありません。コピーのフォルダがなくなる、またはゲームの実行ファイルがなくなると起動は拒否され、Diagnostics がそのフォルダ名を示すので、ストア版が知らないうちに起動することはありません。

Morrowind と、`bUseMyGamesDirectory=0` の Oblivion はプラグインリストをゲームフォルダに置くため、Eidos はまだこれらをコピーから起動しません。

## Nexus のコレクションをインストールする

```sh
eidos collection skyrimse nxm://skyrimspecialedition/collections/rqhcxy/revisions/latest
eidos collection skyrimse rqhcxy --dry-run      # 読んで、何が起きるかを言う
eidos collection skyrimse rqhcxy --no-optional  # 任意とされた構成要素を飛ばす
```

ウィンドウでは、リンクを File -> Open a Nexus collection... に貼り付けるか、サイトで
コレクションをクリックします。Eidos はそのリビジョンの構成要素を一覧し、それぞれをこの
インスタンスと照合します。インストール済み、ダウンロード済み、または不足です。
*Install this collection* はレシピ全体をワーカースレッドで実行し、pack と unpack の
ジョブと同じプログレスバーを使い、終わるとそのバーが報告になります。ウィンドウと
`eidos collection` は同じインストールを実行します。

リンクなしで File -> Open a Nexus collection... を開くと、Browse タブで開きます。
開いているインスタンスのゲーム向けに公開されたコレクションを 20 件ずつ、ダウンロード
数順、最近の更新順、新着順のいずれかで並べて一覧し、検索ボックスは名前または説明文が
一致するコレクションに絞り込みます。各行には作者、最新のリビジョン、MOD の数、
ダウンロード数、日付が出ます。View はそのコレクションの最新リビジョンを Link タブで
開き、リンクを貼り付けたのと同じです。成人向けと指定されたコレクションは、Nexus
アカウントで成人向けコンテンツを表示する設定でない限り除外され、評価のないコレク
ションは常に除外され、一覧の下の行が両方を数えます。閲覧には、このペインのほかの
機能と同じく、サインイン済みの Nexus アカウントが必要です。

コレクションは、自分のゲームのインスタンスに対してだけ開けます。Fallout 4 の
インスタンスが読み込まれているときに Skyrim のコレクションを開くと、構成要素を誤った
MOD 一覧と照合する代わりに、名前を挙げて拒否されます。

### コレクションから Eidos が読むもの

コレクションのほとんどは Nexus の API からは見えません。インストールの順序、各 MOD の
スクリプトインストーラに作者が与えた回答、ファイルの競合でどの MOD が勝つか、どの
プラグインがどこに読み込まれるか、バイナリのパッチ。その全部が、コレクション自身の
書庫の中の `collection.json` にあります。同じ MOD を落としてきて既定のオプションの
ままインストールしても、出来上がるのは別のゲームです。

Eidos は書庫を落とし、`collection.json` を読み、それを適用します:

| コレクションが言うこと | Eidos がすること |
| --- | --- |
| `phase` | その順にインストールし、任意の構成要素は最後に回す |
| `choices` | 各 FOMOD への作者の回答を再生し、できないときはそう言う |
| `modRules` | 各ファイルで正しい MOD が勝つように MOD 一覧を並べ替える |
| `plugins` / `pluginRules` | LOOT のルールをあなたの userlist へ統合して並べ替える |
| `INI Tweaks/` | それ自体を一つの MOD としてインストールする |
| `tools` | どのツールを前提としているかを伝える。何も作らない |

構成要素はインストールされるそばから有効になります。入る場所は MOD 一覧の末尾、
インストールの順序のままで、`modRules` が動かす前です。一覧に載らない構成要素は
読み込まれず、レポートにもそれは出てこないからです。

状態は構成要素一つごとに `<instance>/collections/<slug>-<revision>.state.json` へ
書かれます。そのリビジョンのフォルダの中ではなくその隣に置かれるので、コレクションが
自分の状態ファイルを同梱することはできず、200 個中 147 個目で中断したインストールは
147 個目から続きます。書き込みは一時的な名前で行い、そこから所定の名前へ付け替える
ので、中断が残すのは古い記録か新しい記録のどちらかで、どちらかの半分ということは
ありません。もし読めなくなったときは、Eidos はコレクション全体を最初からやり直す
代わりに、そこで止まってそう言います。同じコマンドをもう一度実行してください。

すでに持っているコレクションの新しいリビジョンをインストールすると、前の
リビジョンのフォルダを引き継ぎます。変わっていない構成要素はその場で検証され、
作者がファイルを更新した構成要素は古いフォルダの中で置き換えられ、新しい
リビジョンが外した構成要素はインストールされたまま残り、無効にするか削除するかを
あなたが決められるようレポートに名前が出ます。別のプロファイルが有効にしている
フォルダは決して引き継ぎません。mods フォルダは共有なので、そのプロファイルが
知らないうちに変わってしまうからです。代わりに新しいリビジョンは自分の写しを
その隣にインストールし、レポートは古いほうをこのプロファイルで無効にするよう
求めます。削除しろとは決して言いません。古いリビジョンへ戻るときも同じように
そのフォルダを引き取り直し、引き取れないものは新しい写しをインストールします。
このように構成要素を置き換えるとき、そのフォルダの中であなたがファイルを変更または追加していた場合は、古いフォルダを先に `<name>_backup` として隣に残します。これはゲームに読み込まれることはなく、レポートにその名前が出ます。

前のリビジョンの残りが有効のままだと、そのインストールは作者が組んだとおりの
ものとは数えられません。それを無効にすればその注記は消えます。`--no-optional`
で飛ばした構成要素は引き継がれず、同じように名前が出ます。引き継ぎそのものが
失敗したときは、実行は *previous revision: its folders could not be taken over*
とその理由を示して止まります。それを直して、同じコマンドをもう一度実行して
ください。

### 無料アカウントと、自分で取ってくる構成要素

無料の Nexus アカウントでは構成要素の MOD を取ってこられません。Nexus は API
経由では無料会員にダウンロードのリンクを発行しません。どのファイルにもサイト自身の
「Mod Manager Download」ボタンが要ります。コレクションの書庫そのものは無料会員でも
落とせるので、レシピは丸ごと読めますが、構成要素はそれぞれ、自分で取ってくるための
ページの URL を正確に添えて報告され、何度やり直しても変わりません。サイト自身の
ボタンで取ってきて、同じコマンドをもう一度実行してください。そうした構成要素は実行の
たびに `downloads/` の中を探されるので、あなたが渡したぶんだけコレクションは仕上がって
いきます。

ウィンドウでは、無料アカウントだとコレクションのペインにまとめての取得の代わりに
*Fetch the N missing required files, one by one* が出ます。これは足りない必須
ファイルの最初の一つの Nexus ページを開き、そのファイルが `downloads/` に届くのを
待ってから次を開きます。各ファイルでページのダウンロードボタンを押すのは、今まで
どおりあなたです。ペインには進み具合(*3 of 12*)と *Skip*、*Stop* が出ます。
代わりに同じ MOD の別のファイルが届いた場合は、ペインが両方のファイル ID を示し、
指定されたほうを待ち続けます。任意の構成要素はこの対象に入らず、それぞれの *Open*
ボタンが残ります。

Eidos はまた、バイナリのパッチ(それぞれ記録された CRC と照合します)、ファイルの上書き(指定されたファイルは MO2 と同じく `.mohidden` で隠します)、そしてファイルがコレクションの書庫の中を一緒に運ばれてくる構成要素(`bundle`)も適用します。コレクションが手で取ってくることを前提にしている構成要素(`browse`、`manual`)は、作者自身の指示をそのままレポートまで運びます。名前がすでにあなたの MOD と同じ構成要素は、その上にではなく、空いている名前を取ってその隣にインストールされ、どれがそうだったかはレポートが言います。

### レポート

インストーラへの回答を全部は再生できなかった構成要素には、作者が組んだとおりに
インストールされた構成要素とは別に、*installed, but not the way the collection asks*
という独立した行が付きます。ディスク上のファイルが作者のものと違うからです。
レポートにはほかに、コレクションの中の何も名指ししていなかった順序のルール、矛盾する
ルールの輪に捕まった MOD、存在しない LOOT のグループ、そしてこのバージョンの Eidos が
理解しないマニフェストの部分も並びます。

### コレクションの順序を保つ

Eidos は、インストールしたコレクションのルールをインストール後も保持します。あとで
そのうち 2 つの MOD を before または after の規則に反するように動かすと、Diagnostics
タブにそのコレクション用のカードが 1 枚出て、そうした最初の組を名指しし、成り立たなく
なった規則の数を数えます。数えるのは現在のプロファイルで有効な MOD だけで、ループに
捕まった規則は、どんな順序でも守れないので飛ばされます。Restore collection order は、
コレクションの MOD を、すべての規則を守る順序に戻し、規則が許す限りあなた自身の順序を
保ち、コレクションにない MOD はそのままにします。Ctrl+Z で取り消せます。`eidos check`
は同じ所見を `collection_order_broken` として一覧します。この確認は `collections/` の
そのリビジョンのレシピを読むので、キャッシュしたレシピが削除されたコレクションは
確認されません。

## インスタンスを別のマシンへ移す

`eidos pack` はインスタンスを丸ごと(MOD の一つ残らず、ロード順、プロファイル全部、
セーブの入った Overwrite、そして全部のインストール元になった書庫まで)一つの
ファイルに書き出します。`eidos unpack` はそれを元に戻します:

```sh
eidos pack skyrimse ~/backup.eidos                  # フォルダを渡してもよい。ゲーム名と日付から名前が付く
eidos unpack ~/backup.eidos /mnt/games/EidosSkyrim  # 向こうのマシンで
```

`eidos pack --dry-run` は、何が入り、何が入らず、それはなぜか、そしてどれだけの
空きが要るかを、何も書かずに並べます。手元にすでにあるファイルについては
`eidos unpack --info` が同じことをします。

7-Zip が読めなかったものがあっても、あるいはバックアップに入っているはずのものを
走査が飛ばさざるを得なかったとしても(シンボリックリンク、読めなかったフォルダ、
7-Zip に安全には渡せない名前)、書庫はあなたが選んだ名前で書き出されますが、
`eidos pack` は 1 で終了し、何が欠けているかを告げます。そのため `eidos pack ... && ...`
を実行するスクリプトはそこで止まります。

`.eidos` ファイルは独自の拡張子を付けた 7-Zip の書庫です。MOD を一つ入れるだけでも
7-Zip はすでに必須なので依存は増えませんし、バックアップは 7-Zip を読めるどの書庫
ソフトでも Eidos なしで開けます。圧縮は LZMA2 の `-mx1` で、テクスチャの多い構成で
元の約 43% になります。`-mx9` は時間がはるかにかかり、縮むのは数ポイントだけです。
テクスチャもメッシュもすでに圧縮された形式で、辞書を大きくしても見つかるものはほとんど
残っていません。`--level`(0、1、3、5、7、9)で別のレベルを選べ、`--no-downloads` は
`downloads/` を外します。

既定のレベル 1 では、ファイルは最大 16 MB のソリッドブロックに収められます。
70 GB のバックアップからファイル一つを取り出しても、デコードされるのはせいぜいそ
のファイルが入っているブロックだけで、前に並ぶものを全部展開することはありませ
ん。ゲームのデータの pack も、ファイルを一つずつ圧縮する場合に比べて 2 - 5 倍、
展開は 2 - 4 倍速くなります。代わりに損傷に弱くなります。壊れた 1 バイトがそのブ
ロックのファイルをすべて巻き込み、最大 16 MB 分の隣のファイルを失うことがありま
す。この場合に備えるのが、後で説明する修復データです。ほかのレベルはすべて非ソ
リッドのままです。ファイルはそれぞれ独立したストリームになり、壊れた 1 バイトで
失うのはそのファイル一つです。レベル 0 はファイルを圧縮せずに格納します。レベル
3 以上では LZMA2 がもともと 16 MB 以上の単位で処理するので、ソリッドブロックにす
ると計測では遅くなりました。レベル 5 では、メッシュの pack に 1.4 倍、テクスチャ
の展開に 6.8 倍の時間がかかりました。

pack はインスタンスのロックを取るので、ゲームや別の Eidos がそのインスタンスへ書
いている間は走れず、読んでいる最中にインスタンスを変えるものもありません。書き込みは
`.part` の名前で行われ、ディスクへ確実に書き出されたあと、あなたが選んだ名前を得る前に
`7z t` で丸ごと読み戻されます。この検査はすべてのブロックをデコードし、すべての
チェックサムを照合します。もう一台のマシンで展開するときと同じ作業です。これで分かるのは書き込み直後にディスクが返した内容であって、ドライブがそれを保ち続けることではありません。そのために後で説明する修復データがあります。検査に失敗すると `.part` は削除され、あなたの選んだ名前では
何も書かれず、`eidos pack` は 7-Zip が損傷を見つけた行を示します。中断または失敗
した pack が残すのは `.part` ファイルか何もないかのどちらかで、完成したように見えて
実はそうでない `.eidos` ファイルではありません。

par2cmdline がインストールされていれば(Arch では `sudo pacman -S par2cmdline`、
Debian と Ubuntu では `sudo apt install par2`、Fedora では
`sudo dnf install par2cmdline`)、`eidos pack` は書庫の隣に PAR2 の修復データも書
きます。`backup.eidos.par2` といくつかの `backup.eidos.volNN+MM.par2` ファイルで、
合計は書庫の 5% と小さな索引です。これらは書き込まれたときの名前のまま `.eidos` ファイルと同じフォルダに置き、一緒にコピーしてください。修復データなしで移したバックアップには直す材料がなく、修復データは書庫の名前を記録しているので、名前を変えたバックアップとはもう合いません。`eidos unpack` は名前でこれらを見つけ、何かを展開する前に書庫を照合します。末尾が切れて 7-Zip が開けなくなったバックアップも対象です。数バイトが壊れていれば、par2 が先に書庫を修復し、壊れたコピーを
`backup.eidos.1` として残します。このため、書庫のフォルダに書庫と同じ大きさの空き容量が要ります。5% で補えない損傷なら、ファイルを一つも書かない
うちに展開を止めます。同じ名前の古いバックアップのものなど、書庫に合わない修復ファイルは、7-Zip が書庫を読んで無傷だと確認できれば使われず、展開時にその旨が表示されます。par2 のないマシンでも展開は行われ、修復データを使わなかっ
たという警告が出ます。`--no-recovery` を付けると修復データなしで pack し、
`eidos pack --dry-run` は修復データを書くかどうかを表示します。`--force` は同じ名前の
既存ファイルを置き換えます。

### 入らないもの、そしてその理由

| 入らないもの | 理由 |
| --- | --- |
| Proton プレフィックス | あれはマシンの形をしています(ドライブの割り当て、このマシンのファイルシステムを映した `Z:`)。しかも Eidos は `eidos prereqs <instance> --install` で一分もあれば作り直します。運んだところで、向こうのマシンがどのみち作り直すもののために書庫がおよそ倍になるだけです。 |
| ゲーム本体 | インスタンスは、自分の中に含まないゲームに MOD を当てるものです。向こうでは Steam から入れてください。 |
| インスタンスの外にあるツール | xEdit、DynDOLOD といった面々は、それぞれ独自のインストーラを持つ第三者のバイナリです。書庫にはその名前が入るので、unpack すれば新しいマシンにどれが足りないのかがそのまま分かります。 |
| `logs/`、`.eidos.lock`、`prereqs.done`、`prereqs.log` | バックアップを作ったマシンの記録です。とくに `prereqs.done` は、そこに無いプレフィックスにランタイムのライブラリがもう入っていると言い張ることになります。 |
| `loot/`、ただし `userlist.yaml` を除く | Eidos が必要に応じて取り直すマスターリストのキャッシュです。自分で書いた LOOT のルールは取り直せないので、`userlist.yaml` 一つだけは入ります。 |
| `.base/`、`.base-root/` | セッションの間ゲーム自身のファイルを退避しておく、空のマウントポイントです。 |
| `test-run/`、`bisect.json` | レビュー待ちの [Test run](#テスト実行) と、2 つのステップの間にある問題の原因 MOD の探索です。どちらもこのマシンでの実行に属します。 |
| 書きかけのファイル | 一時停止したダウンロード(`*.unfinished`)、進行中のアトミックな書き込み(`*.eidos-tmp*`)。 |
| シンボリックリンク | 7-Zip はリンクを辿って指す先をコピーしてしまいます。絶対リンクなら、よそのディレクトリ木をバックアップへ引き込むということです。代わりに報告し、バックアップは不完全とみなされます。別のドライブへリンクされた `mods/` や `downloads/` は書庫に入りません。リンクされた `downloads/` を意図して外してバックアップするなら、`--no-downloads` を渡してください(ウィンドウなら *Include downloads/* のチェックを外します)。意図した除外は欠落には数えられません。 |

インスタンス内のゲームのコピー(`Stock Game`)はほかのフォルダと同じように pack されるので、凍結したインスタンスのバックアップはおよそゲームの大きさの分だけ大きくなります。未完成のコピー(`Stock Game.eidos-tmp`)は入りません。

これらはどれも、書庫のルートの `eidos-backup.ini` に理由付きで載るので、そのファイルを
読めば何が入っていないかが分かります。同じファイルは、インスタンスが以前どこにあったか、
どのプロファイルが有効だったか、展開するとどれだけの大きさになるか、そして新しい
マシンでどのツールが要るかも記録します。

ダウンロードの記録(`downloads/*.meta`)は、`url=` の行を空にして入ります。
あの URL は署名付きの Nexus のリンクで、数時間で効かなくなり、ファイルを落とした
アカウントの `user_id` を含んでいます。バックアップは誰かに渡すこともあるからです。
MOD の id、ファイルの id、バージョンは残るので、ダウンロードをもう一度見つけられます。

### ウィンドウの中では

どちらも File メニューにあります。*Pack this instance...* と *Unpack a backup...* です。
unpack はようこそ画面の、インスタンスの一覧の下にもあるので、まだインスタンスを
持っていないマシンでも展開できます。

Pack のダイアログは、何かを書く前に、ファイルが何個で、どれだけの大きさで、そのうち
どれだけが `downloads/` で、書庫はおおよそどれくらいになり、どのツールが名前だけ載って
運ばれないのかを見せます。*Write recovery data* のチェックボックスは、par2 が
インストールされていればオンになり、なければインストールすべきパッケージ名とともに
灰色になります。Unpack のダイアログはファイルを選んだその場でバックアップのマニフェスト
を読むので、それがどのゲームのものか、いつ作られたか、以前どこにあったか、そのツールの
どれがここに足りないのかを、フォルダを選ぶ前に教えます。

どちらもプログレスバー付きのワーカースレッドで走り、終わればそのバーがそのまま報告に
なります。

### unpack が直すもの

フォルダをただコピーしただけでは、ツールのボタンはどれも古いマシンのパスを指した
ままになります。`eidos unpack` は、古いインスタンスのルートを名指ししている値だけを
書き換えます。`tools.ini` の `exe`、`workdir`、番号付きの `arg` キー、そして各 MOD の
`meta.ini` の `installationFile` です。そもそもインスタンスの中になかったツール
(`/opt/xedit/SSEEdit.exe`)はそのままの姿で残され、入れ直すものとして一覧に出ます。
新しいマシンでそのツールがどこにあるかを Eidos が当てることはありません。インスタンスが
自分を集約型と名乗るかポータブルと名乗るかも直すので、後のコマンドは今ある場所を探します。

unpack は次のものを断ります。空でないフォルダ(上書きするつもりなら `--force` を渡して
ください)、マニフェスト自身の数字に足りないディスク、自分より新しい Eidos が作った
書庫、そして選んだフォルダの外に書き出されるエントリを持つ書庫。フォルダを渡さない
場合、グローバルインスタンスのバックアップはそのゲームの中央の場所へ戻り、ポータブルの
ものにはフォルダが必要です。

その後は:

```sh
eidos prereqs /mnt/games/EidosSkyrim --install   # Proton プレフィックスを作り直す
eidos play /mnt/games/EidosSkyrim
```

## ウィンドウ

`eidos-gui`、または Colony がインストールする `eidos-linux` ファイルを起動します。

初回起動は MO2 風のウィザードを開きます。ようこそ、インスタンスの種類(ポータブルか
グローバル)、ゲーム、名前と場所、概要、そしてメインウィンドウです。ようこそ画面は既知の
インスタンスもすべて(グローバルもポータブルも、最後に使った順に)一覧して一クリックで
開けるので、インスタンスの切り替え役も兼ねます。すでにインスタンスがあるフォルダを
ウィザードに指すと、上から作り直すのではなくそのまま開き、別のゲームのフォルダは拒否します。

メインウィンドウは二つのペインでできています。MOD 一覧と、Data、Plugins、Conflicts、
Overwrite、Archives、Saves、Downloads、Diagnostics のタブです。Run ボタン、Test run
ボタン([テスト実行](#テスト実行))、実行対象の選択もあります。MOD 一覧は、絞り込み、選択、
並べ替え、セパレータでのグループ化、カテゴリでの絞り込み、右クリックからの操作ができます。
先頭や末尾へ送るだけでなく、MOD のメニューには MO2 の狙いを定めた移動があります。最初に
競合する MOD の上へ、最後の下へ、指定した優先度へ、あるいはセパレータのグループの中へ。

プロファイルの選択でプロファイルを切り替えます。プロファイルを右クリックすると、Rename、
Copy to new...、Desktop shortcut、Import from MO2...、そして削除があります。削除は 2 回の
クリックが必要で、有効なプロファイルと最後のプロファイルは拒否されます。Import from
MO2... は MO2 プロファイルの MOD の順序とロード順を引き継ぎます。Desktop shortcut は
`eidos tool <instance> run "<game>" --profile <name>` を実行するデスクトップエントリを
書きます。それはそのプロファイルをアクティブにして、ストアにゲームの起動を頼みます
(詳細は [tools.md](tools.md#ツールに手を伸ばす-隠す固定するデスクトップショートカット))。

File メニューは、ゲームのプレフィックスで winecfg、regedit、Wine のファイルエクスプローラー、
アンインストーラーも実行し、Prefix drive_c はプレフィックスの `C:` ドライブを開きます。
[tools.md](tools.md#ゲームのプレフィックスで動く-wine-自身のプログラム)を参照してください。
*Instances...* は Eidos が知っているインスタンスを一覧し、Forget はそのうち 1 つを一覧から
外しますが、ディスク上は何も触りません。*Export the mod list...* は、`eidos export` と同じ
ように MO2 の CSV 形式で一覧を書き出します。

### Preferences

左上の Eidos をクリックすると、二つのペインの代わりに Preferences が開き、もう一度
クリックする(または Close を押す)と元に戻ります。Colony のどのプログラムとも同じく、
General、Appearance、Accessibility が先に並び、そのあとに Mod list、Nexus、About が
続きます。変更はすべてその場で適用され、保存されます。Save ボタンはありません。

- General: Eidos が開くゲーム、ウィンドウの大きさ、インターフェースの言語、ツール
  フォルダ、ゲームの実行方法。Lock the window while a game runs は既定でオンです。
  Start the game at once when a store opens Eidos と、ウィンドウが背面にある間に長い処理が
  終わったことを知らせるデスクトップ通知は、既定ではオフです。ウィンドウは英語と
  フランス語に対応しています。System は `LC_ALL`、`LC_MESSAGES`、`LANG` に従い、
  変更はその場で反映されます。`eidos` のコマンドラインは常に英語で応答します。
- Appearance: テーマ(26 のファミリ、59 のパレット、既定は Eidos の羊皮紙)、アクセント
  カラー、文字の大きさ、エフェクト、そしてライブプレビュー。
- Accessibility: ハイコントラスト、ディスレクシアに配慮したフォント、モーションの
  軽減、そして Appearance の文字サイズに掛け合わされる読書用の文字サイズ。
- Mod list: MOD を一覧の上端または下端へドラッグしているときの自動スクロールの速さ。
- Nexus: サインイン、ダウンロードフォルダ、`nxm://` ハンドラとその Register ボタン、
  優先サーバー、Install downloads when they finish、Offline mode。
- About: ファイルの場所、キーボードショートカット、バージョン、リリース確認。

見た目とインターフェースの言語は `~/.config/Colony/Eidos/preferences.json` に保存されます。
コマンドラインも読むそのほかの設定(既定のゲーム、ツールフォルダ、Nexus のサーバー、
Offline mode など)はその隣の `settings.ini` に、Nexus のセッションは `nexus.ini` に
保存されます。以前の Eidos が `settings.ini` に保存していたテーマは、初回に引き継がれます。

About -> Version にはリリース確認があり、既定で有効です。起動時に、1 日 1 回まで、Eidos は
GitHub に `Project-Colony/Eidos` の最新リリースを問い合わせます。実行中のコピーより新しければ、メニューバーの Help の後ろに `Eidos <version> is available: release notes` が表示され、そのリンクで変更履歴の載ったリリースページが開きます。Eidos が自分自身をダウンロードしたり置き換えたりすることはありません。オフラインモードでは確認を行いません。パッケージマネージャーが `/usr` 以下に入れたコピーでは無効で、更新はパッケージマネージャーが行います。`install.sh --system` が Eidos を置く `/usr/local` は、自分で入れたものとして扱います。

### 列、並べ替え、グループ化

一覧は最初から四列(MO2 が出す Category、Content、Version、Flags)を描き、八列を
用意しています。Category、Content、Version、Author、Installed、Nexus id、Game、Flags。
View メニューでチェックを入れてください。八列全部を出すと、名前の列の余地がほとんど
残りません。

見出しをクリックすればその列で並べ替わります。もう一度で逆順、三度目でロード順に
戻ります。一覧をドラッグできるのはロード順のときだけです。ドロップ位置は本物の一覧を
指すのに、並べ替えられた行の画面上の位置はその一覧での位置と違うからです。並べ替えが
効いている間は挿入の帯を描かず、ドラッグを拒否します。MO2 と同じです。View メニューは
そう告げ、戻る道も出します。

View メニューは一覧全体をグループ化もできます。カテゴリ別か、出所別(Nexus からか、
手で入れたか)。グループの見出しはセパレータではありません。名前を変えたり色を付けたり
動かしたりできません。折りたためて、折りたたんでも件数は見出しに残ります。並べ替えや
グループ化が効いている間は、セパレータは隠れます。セパレータはロード順で後ろに続く
行の頭に立つものですが、どちらも画面上のその順序を変えてしまうからです。

### マウスとキーボード

MOD をダブルクリックで Information、Ctrl+ダブルクリックでそのフォルダ、
Shift+ダブルクリックで Nexus のページ。Ctrl+F でカーソルが絞り込み欄に入ります。
文字を打つとその文字で始まる次の MOD へ飛び、もう一度押せば最初のものに留まらず
残りを順に辿ります。どれも、絞り込みや折りたたんだセパレータ・折りたたんだ
グループが隠している行には着地しないので、次の Space が見えない MOD を切り替える
ことはありません。

セパレータのメニューの「Collapse others」は、そのグループ以外を全部折りたたみます。
ドラッグ中に折りたたんだグループの上でポインタを止めると開くので、MOD を中へ落とせます。
通り過ぎるだけでは開きません。

Ctrl+Z は MOD 一覧またはロード順への直前の変更(チェック、移動、一括無効化、LOOT による
並べ替え)を取り消します。Ctrl+Shift+Z でやり直します。ウィンドウは 50 ステップを保持し、
F5、ゲームやツールの実行終了、プロファイルの切り替え、別の Eidos プロセスによる一覧の
変更のときに履歴を破棄します。MOD のインストール、名前の変更、削除はディスク上の
フォルダを変えるため、それより前に戻る取り消しは拒否されます。

### 一覧を絞り込む

Filters ボタンを押すと、条件ごとに 1 行が並びます。有効、競合あり、更新あり、
カテゴリなし、Nexus で推奨済み(endorsed)、追跡中(tracked)、Nexus id あり、
隠しファイルあり、有効なゲームデータなし、別のゲーム用、メモあり、そして内容の
種類ごとに 1 行(プラグイン、BSA または BA2 の書庫、テクスチャ、メッシュ、
スクリプト、スクリプトエクステンダのプラグイン、インターフェースのファイル、
サウンド、FaceGen)です。行をクリックするたびに、オフ、「only」、「except」の
順に切り替わります。一番上の行は、オンにした条件をすべて満たす MOD と、どれか 1 つを
満たす MOD とを切り替えます。名前の欄とカテゴリの一覧は、どちらのときも結果をさらに
絞ります。隠しファイルの行は有効な MOD だけを見ます。

### 一覧が MOD について教えること

助言のフラグが二つあり、どちらも字形で、ホバーすると説明が出ます。No valid game data は、
MOD の一番上にこのゲームが読み込むものらしきものが何もない、という意味です。フォルダを
一階層上げる必要があるのかもしれませんし、このゲーム向けの MOD ではないのかもしれません。
Another game は、MOD 自身の `meta.ini` が別のゲームを指している、という意味です。どちらも
何も止めません。MOD はそのまま展開されます。行のメニューの「Mark as valid」は、MO2 自身の
`validated=` キーを通してどちらも黙らせるので、片方のマネージャで有効と印を付けた MOD は
もう片方でもフラグが付きません。

配置の判定は確かなときだけ MOD にフラグを付けます。`Root/` の木も、読めないフォルダも、
空のフォルダも、有効なゲームデータとして数えます。

### セーブや他の MOD が使っている MOD を無効にするとき

MOD を無効にする前、または削除する前に、Eidos はプロファイルの最新のセーブ 3 つの
プラグイン一覧を読みます。そのどれかがその MOD のプラグインを使っていると、一覧の上に
バーが出てプラグイン名を挙げ、「Disable anyway」か「Cancel」を待ちます(Esc でも取り消せ
ます)。Remove は、もう一度クリックするよう求めるメッセージに同じ名前を加えます。読むのは
Skyrim と Fallout 4 のセーブだけで、ほかのゲームでは確認なしに無効になります。

MOD の Information の General タブには、その MOD が必要とする MOD と、その MOD を必要とする MOD が、有効なプラグインのマスターから読み取って一覧されます。ほかの MOD が必要とする MOD を無効にすると同じバーが出て、「Disable them too」ならそれを必要とするすべての MOD と、さらにそれらを必要とする MOD も無効にし、「Keep them enabled」なら対象だけを無効にします。Diagnostics タブの不足マスターカードには "Enable what provides them" があります。不足している各マスターを含む MOD を有効にし、存在するのにチェックが外れているマスタープラグインにチェックを入れます。

### 触る前に MOD を控えておく

「Back up this mod」はそのフォルダを `<name>_backup` として脇にコピーします
(次は `_backup2`、以下同様。控えが前の控えを置き換えることはありません)。
コピーは MOD ではありません。チェックボックスは何もせず、統合ビューにも何も足しません。
チェックを入れれば同じ MOD の複製二つを重ねて展開することになるからです。「Restore this
backup over the mod」は二クリックで元に戻します。今の中身がまず脇へ退けられ、コピーが
成功してから初めて捨てられます。

ツールバーの Backups は、プロファイルの MOD 一覧、ロード順(`plugins.txt` と
`loadorder.txt` を一緒に)、ゲームの INI の復元ポイントを、それぞれ 10 個まで
`<profile>/backups/` に保持します。Back up now は 1 つ追加し、Restore は先に現在の状態を
バックアップするので、選び間違いも取り消せます。Eidos は BethINI の実行のたびにも、その前に
INI の復元ポイントを残します([tools.md](tools.md#bethini-pie)を参照)。

### タブ

Data は統合ビューの木で、一階層ずつ展開します。フォルダを開くと、そのフォルダを持つ
レイヤーごとにそのフォルダを読むだけで、有効な MOD 全部を一度に読むことはありません。
マウントが供給するのと同じレイヤースタックから作られるので、whiteout や隠しファイルも
尊重され、このタブはゲームが見るものを示します。名前で絞り込み、争っているファイルだけに
絞り、Size と Modified の列で何がどこにあるかを整理し、どの行でもファイルマネージャで
Reveal できます。ファイルにカーソルを合わせると、それを同梱しているほかの MOD が一覧に
出ます。MOD の最上位にある `meta.ini`、`readme.txt`、`fomod/`、`Root/` は、このタブでも
マウントでも Data に含まれません。最初の三つは MOD マネージャ用で、`Root/` は代わりに
ゲームフォルダへ入ります。ゲームやツールがこれらの名前で書いたファイルは Overwrite に入り、
表示されたままです。

Data の `.exe` の行には Add tool と Run があります。Add tool はそのファイルを入力済みの状態で Executables エディターを開きます(Save を押すまで何も保存されません)。Run は登録済みのツールと同じように、統合ビューを通してそのファイルを一度だけ実行します([ツール](#ツール))。Save tree は、統合された Data ツリー全体を、ファイルごとに 1 行、提供元の MOD とともにテキストファイルへ書き出します。ホームフォルダとユーザー名は取り除かれ、バグ報告に使えます。

Plugins は ESP/ESM/ESL のロード順です。切り替え、手での並べ替え、あるいは LOOT での
並べ替えと、その後のレポートの閲覧ができ、レポートの助言のリンクはブラウザで開きます。
ヘッダには、有効なプラグインの数がインデックス空間ごとにゲームの上限と並んで表示され
(例: `full 231/254, light 512/4096`)、どれかが満杯になるとオレンジ色になります。
フィルターボックスは名前で一覧を絞ります。Space、Ctrl+A、Shift による範囲選択、そして
行メニューの Activate all shown と Deactivate all shown は、表示されている行だけに作用し、
ドラッグはフィルターを消すまで拒否されます。プラグインを選ぶと、そのマスターがプラグイン
一覧で、それを同梱する MOD が MOD 一覧で色付けされます。LOOT が dirty と示したプラグインには
Diagnostics のカードが出て、xEdit でクリーニングできます
([tools.md](tools.md#loot-が-dirty-と判定したプラグインをクリーニングする))。

LOOT で並べ替えたあと、新規レコードがすべて light の範囲に収まる full プラグインは、
ホバーでそのことを表示し、行のメニューに Flag as light が出ます。Eidos は light フラグを
立てたコピーを `<plugin> (light)` という新しい MOD に書き込み、MOD 一覧のいちばん下(最も
高い優先度)に置き、元のプラグインには触れないので、その MOD を無効にすれば元に戻ります。
プロファイルの最新のセーブ 3 つのどれかがそのプラグインを full プラグインとして読み込んで
いる場合は拒否します。読めるのは Skyrim と Fallout 4 のセーブだけなので、Starfield では
セーブを確認しません。LOOT が調べるのはレコードの範囲だけです。セルやワールドスペースを
追加するプラグインは、フラグを立てる前に xEdit で確認してください。

プラグインにカーソルを合わせると、入手元、作者、ヘッダーとフォームのバージョン、説明の先頭 300 文字、マスター、そして LOOT で並べ替えた後は LOOT のメッセージが表示されます。Skyrim、Skyrim SE、Skyrim VR、Enderal SE では、読み込まれたプラグインと同名の INI もゲームが読み込みます。INI 列はそのプラグインに印を付け、クリックするとそのファイルを読み取り専用で開きます。

Conflicts はファイルごとの勝ち負けを説明します。Overwrite はゲームが書いたものを一手で
本物の MOD に変えます。

Archives は、有効な MOD が同梱するすべての BSA または BA2 を、それが来た MOD と、それが
読み込まれる理由(同名の有効なプラグイン、または INI が登録している)とともに一覧します。
何も読み込まないものは、無駄な重さとして印が付きます。同名のアーカイブを同梱する別の
MOD が競合に勝つ場合、その行はその MOD を名指しします。Extract は、アーカイブを拡張子を
除いた名前の新しい MOD(`Foo.ba2` は `Foo (extracted)`)に展開し、アーカイブはその MOD に
残します。ルーズファイルは、MOD の順序にかかわらず、どのアーカイブ内のファイルにも勝ちます。

Saves は各セーブのヘッダ(キャラクター、レベル、場所、プレイ時間)を読み、そこに保存された
プラグイン一覧を現在のものと突き合わせ、必要な MOD を有効にするボタンを添えます。Eidos を
通らずにプレフィックスへ届いたセーブは、[セーブはプロファイルのもの](#セーブはプロファイルのもの)
で説明しています。

Downloads と Diagnostics には、下にそれぞれの節があります。

### MOD の information

「Information...」は MOD ごとのダイアログを開きます。General、Conflicts、Filetree、
INI Tweaks、Notes、Nexus files、Nexus page のタブがあります。filetree から(そして Data の
木から)どのファイルも隠せます。`<name>.mohidden` に改名され、削除せずに統合ビューから
外れるので、ある MOD の迷子のファイルを、優先度に触らずに黙らせられます。filetree は
普通のファイル操作もします。新規フォルダ、改名、削除、開く。どれも、その MOD の中の
素直なパスでないものは拒否します。`..` も、絶対パスも、途中にシンボリックリンクがある
パスも、です。辿ってしまえば削除が MOD フォルダの外に出てしまうからです。改名は最後の
構成要素だけを置き換えるので、ファイルを移動することは決してなく、すでに使われている名前は
拒否します。削除は二クリックで、取り消せません。

filetree でも Data の木でも、行の View はそのファイルをプレビューします。画像、テキスト、
DDS テクスチャ(mip、レイヤー、面、チャンネルを選べます)、そして拡散テクスチャ付きの
静的な NIF モデルです。NIF プレビューには `eidos-nif-preview` が Eidos の隣か `PATH` 上に
必要です。リリースバンドル、Arch パッケージ、ソースビルドには入っていますが、
`eidos-linux` には入っていません。テキストは 64 KB まで読み、どこで止めたかを言います。

INI Tweaks は、MOD が `INI Tweaks/` フォルダで配っている断片を一覧します。有効なものは
起動時に優先度順でプロファイルのゲーム INI へ統合され、その回の INI を取り込むときに
外されるので、tweak を無効にすればその設定も消えます。

Nexus files タブは、Nexus 上の MOD のファイルを新しい順に並べ、ここにインストールされて
いるものと、それを置き換えるものに印を付けます。後者の行には Update ボタンがあります。
[MOD の更新](#mod-の更新)を参照してください。

Nexus page タブには、MOD の説明と、ページ上の各ファイルバージョンの変更履歴が新しい順に表示されます。Eidos は初めてタブを開いたときに両方を Nexus の GraphQL API から読み込みます。この API は 1 時間あたりのリクエスト上限に数えられません。読み込んだ内容は Eidos を閉じるか Refresh を押すまで保持されます。表示はプレーンテキストです。BBCode と HTML の書式は取り除かれ、リンクのアドレスはそのテキストの後ろに書かれ、画像と動画は省かれます。テキストの上にある Endorse と Track は、MOD の右クリックメニューと同じ働きをします。アダルト MOD のページは、Nexus アカウントでアダルトコンテンツを表示する設定にしていない限り隠されたままで、レーティングのないページはどの場合でも隠されます。

### ダウンロード

Downloads の一覧から MOD 一覧の位置へダウンロードをドラッグすれば、その優先度で
インストールできます。ファイルマネージャからウィンドウへ落とした書庫やフォルダも
インストールされます。ファイルのドロップには X11 か XWayland のセッションが要ります。
winit がファイルのドロップを実装しているのは X11 だけです。ダウンロードは一時停止と
再開ができます。一時停止は転送を止めて途中のファイルを残し、Resume は Nexus から新しい
リンクを取り直して止まったところから続けます。

Downloads タブは、ダウンロードした書庫を保持します。名前で絞り込み(親しみやすい MOD 名
でも通るので、「skyui」で `SkyUI_5_2_SE-12604-5-2SE.7z` が見つかります)、新しい順・
名前・サイズ・状態で並べ替え、用の済んだ書庫は隠せます。ファイルは残して行だけを落とします。
「Show hidden」で戻り、同じボタンで隠しを解きます。「Remove N installed」は、すでに
インストールした MOD の書庫を二クリックで削除します。消えるのは絞り込みが表示している
ものだけです。

Preferences -> Nexus -> Install downloads when they finish は初期状態でオフです。オンにすると、ウィンドウを開いている間に終わった Nexus のダウンロードは、Downloads タブを開かなくてもインストールされます。通常のインストールと同じで、FOMOD ならインストーラーが開き、MOD 一覧にすでにある名前なら対応を尋ねられます。ウィンドウを開く前、またはオプションをオンにする前から `downloads/` にあったアーカイブには手を付けません。インストールを取り消したダウンロードも同じです。コレクションのペインでコレクションを開いている間は、ダウンロードが自動ではインストールされず、その間に終わったものも、あとから自動ではインストールされません。そのコレクションの構成要素はコレクションがインストールします。保留中の Update が待っているファイルは、その Update がインストールします。この方法でインストールされるのは Nexus のダウンロードだけで、Downloads のフィルターが隠しているものは、フィルターを解除するまで待ちます。ドラッグの最中や、ゲームまたは別の Eidos がインスタンスを握っている間は、インストールを待ちます。

### MOD の更新

ツールバー右端近くの更新ボタンは、Nexus id を持つすべての MOD を確認します。MOD のページが、インストール済みのバージョンを示していれば、それ以上は何も尋ねません。そうでなければ、Eidos は MOD のファイル一覧を読み(もう 1 回のリクエストで、確認の間は保持されます)、MOD の `meta.ini` が記録しているファイル ID から更新の連鎖をたどります。作者は新しいアップロードを古いものの後継として印を付け、MO2 も同じ連鎖を読みます。その連鎖にある、より新しいファイルが更新です。連鎖が後継を挙げず、インストール済みのファイルがページにまだ載っているときは、ページが別のバージョンを示していても、その MOD は最新と数えられます。ページのバージョンが決め手になるのは、ファイル ID が記録されていないとき、インストール済みのファイルが削除またはアーカイブされたとき、Nexus がファイル一覧を送ってこなかったときだけです。

各 MOD は、インスタンスのものではなく、その MOD 自身の `meta.ini` が名指しするゲーム(`gameName`)の Nexus ドメインを使います。更新の確認、Endorse、Track、Visit on Nexus はすべてそこへ向かいます。Enderal SE は `skyrimspecialedition` の MOD も受け付けるので、Enderal SE のインスタンスにインストールした Skyrim SE の MOD は、その Skyrim SE のページで確認されます。Mod Manager Download のリンクは、そのゲームがリンクのドメインを受け付けるなら、最後に使ったインスタンスへ行きます。そうでなければ、そのドメインが自分自身のものであるゲームのインスタンスへ、それを受け付けるだけのゲームのインスタンスより先に行きます。`EIDOS_INSTANCE=<folder>` はどちらも上書きします。

MOD の右クリックメニューにある Track と Untrack は、その MOD を Nexus の追跡中 MOD に加えたり外したりします。これでサイトの通知が、ここで追跡しているものと一致します。同じメニューの Endorse と Abstain は、Nexus でその MOD を推薦したり推薦を取り下げたりします。更新ボタンの隣の endorse ボタンは、選択した MOD を推薦します。更新の確認のたびに、Eidos は Nexus からあなたの推薦(endorsement)と追跡中 MOD も読み込み(リクエスト 2 回)、各 MOD の Endorsed と Tracked のフラグを、その MOD 自身の Nexus ドメインで合わせます。両者が食い違うときは Nexus が優先されます。どちらかのリストを読めなかったときは、確認がそのことを伝え、それらのフラグは元のままにします。

「Information...」の Nexus files タブにある Update ボタンは、新しいファイルをインストールします。プレミアムアカウントなら Eidos がファイルを自分でダウンロードします。無料アカウントならファイルのページを開き、そこで Mod Manager Download がファイルを送り返し、書庫が `downloads/` に届いた時点でインストールが始まります。その先はいつものインストールです。FOMOD は MOD をインストールしたときの答えで開き、続く確認では「Keep a backup of the existing mod」にチェックが入った状態で Replace を選べます。前回の確認で何を選んでいても同じです。Replace は MOD の優先度と、有効かどうかを保ちます。

Replace が MOD のフォルダを入れ替える前に、Eidos は古いフォルダと新しいフォルダをファイル名とサイズで比べ、両方のプラグインのヘッダーを読みます。対象は Update、コレクションの更新、インストール時の確認で選んだ Replace です。そのあとステータス行に、追加・削除・サイズ変更のファイル数と、新しい版だけが必要とするマスターの名前が出ます。「Information...」の General タブの末尾には Last update 欄があり、バージョン、追加または削除されたプラグイン、追加または不要になったマスター、ESM・ESL・ESH フラグが変わったプラグイン、この MOD が新たにファイルを共有するようになった、または共有しなくなった MOD、そしてファイルが並びます。同じサイズで書き換えられたファイルは載りません。レポートはインスタンス内の `logs/updates/<mod>.json` に保存され、`eidos pack` はこれを含めません。新規インストールやフォルダへの Merge で削除されます。`eidos install --replace` は同じ件数を `changes:` の行に出力します。

複数の Nexus ファイルを抱えるフォルダ(メインファイルにオプションのファイルを混ぜ込んだ
ものなど)は断ります。新しいメインファイルで置き換えると、ほかのファイルが失われる
からです。それらは手で更新してください。

`eidos nexus update skyrimse --apply` は同じ確認をしたうえで、プレミアムアカウントなら
新しいファイルをそれぞれダウンロードし、`--replace --backup` でそのフォルダの上に
インストールします。無料アカウントでは代わりに、ファイルのページごとに `OPEN <url>`
を表示します。複数のファイルをまとめたフォルダは理由を添えて飛ばします。保存された
回答のない FOMOD の MOD(Eidos が回答を残す前にインストールしたものなど)は、
インストーラーの既定値では再インストールしません。その更新は失敗し、一度ウィンドウから
MOD を更新するよう伝えるメッセージを出します。ウィンドウでの更新が回答を保存します。
選ぶものが何もないインストーラーの FOMOD は、いつも通りインストールします。
どれかの更新が失敗すればコマンドは 1 で終わります。

### コレクションの更新

Check for updates を実行すると、Eidos はこのインスタンスにインストール済みの各コレクションの最新リビジョンも Nexus に問い合わせます。MOD 一覧の上の 1 行に、新しいリビジョンがあるコレクションと、追加(+)、更新(~)、除外(-)された MOD の数が表示されます。カーソルを重ねると MOD 名が見られます。インストール済みリビジョンのレシピがキャッシュに残っていない場合、数は表示されません。Update を押すと新しいリビジョンがコレクションのペインで開き、*Install this collection* で実行できます。この一覧は確認のたびに作り直され、保存されません。

### Nexus の設定

Preferences -> Nexus -> Offline は Eidos が Nexus に接続すること自体をやめさせ、
GitHub への 1 日 1 回のリリース確認も省きます。更新確認、サインイン、ダウンロード、
コレクションは、接続エラーで失敗する代わりにそう言います。既定では無効です。

Preferred servers はダウンロードが好む CDN のノードに順位を付けます。良いものから
先に。選べる複数のミラーが渡されるのはプレミアム会員だけなので、それ以外の人には
Nexus が選び、この設定は何も変えません。挙げたノードがどれも出てこなくても、
ダウンロードは Nexus が最初に出したノードから行われます。

### カテゴリ

カテゴリは MOD 一つにも選択全体にも割り当てられ、同じダイアログからカタログ自体を編集
でき、ゲームの公式カテゴリ一覧を Nexus から取ってこられます。カタログのファイルはどちらも
MO2 のもの(`categories.dat` と `nexuscatmap.dat`)なので、共有したインスタンスは
カタログを一つに保ちます。Nexus からダウンロードした MOD は、Fetch from Nexus でカタログの
対応付けが済んでいれば、インストール時にカテゴリが付きます。

### INI エディタ、ログ、拡張

View -> INI editor はプロファイルのゲーム INI を、Eidos が保持する写しとして編集します。
Proton プレフィックスの中の写しは、起動のたびに上書きされます。最後のタブはプロファイルの
`launch-env.ini` です([プロファイルごとの変数とラッパー](#プロファイルごとの変数とラッパー))。
View -> Log はセッションログを読みます。View -> Extensions は自分のアドオンを一覧します。
[extensions.md](extensions.md) を参照してください。

起動時にゲームのメイン INI(`Skyrim.ini`、`Fallout4.ini`、`Oblivion.ini` など)がプロファイルにもプレフィックスにもない場合、Eidos は MO2 と同じく、ゲームフォルダの既定ファイル(`Skyrim_Default.ini`、`Fallout4_Default.ini` など)を先にプロファイルへコピーします。インスタンスがゲームのコピーを動かしているときは、既定ファイルはそのコピーから取られます。プレフィックスとゲームフォルダは変更されません。

### MOD のインストール

インストーラーは、Simple のアーカイブ、FOMOD、Wrye Bash の BAIN パッケージ(サブパッケージにチェックを入れると順に統合されます)、そして Oblivion の OMOD パッケージを扱います。OMOD のスクリプトは、Eidos が対応する OBMM コマンドを使っているか、Eidos が知っている 3 つの C# インストーラーのどれかであれば実行されます。Eidos はそれ以外の C# や Visual Basic のコードを実行せず、そのことを伝えます。どの推測も配置を認識できないときは、書庫の木を見せてデータのルートを指させる手動のピッカーが開きます。

FOMOD の MOD を再インストールまたは更新すると、ウィザードは前回のインストールの
回答にチェックが入った状態で、それ以降に選択肢が変わった最初のステップで開き、
変更点を一覧にします。Reinstall with new choices はインストーラーの既定値から
始めます。`eidos install --replace` または `--merge` は保存された回答を使い、合わ
なくなっていれば変更点を一覧にしてインストールを断ります。

### Diagnostics

Diagnostics タブはライブの Health チェックを実行します。欠けたマスター、LOOT が dirty と
示すプラグイン、有効なプラグインがどれも読み込まないアーカイブ、MOD 一覧が今も mods
フォルダと一致しているか、FUSE パススルーがオンかどうか、そして要求されているときは、
それに必要な起動 capability があるかどうかを報告します。実行後には、スクリプトエクステンダ
自身のログが各プラグイン DLL について何と言っているかを表示するので、SKSE のプラグインが
読み込まれたかどうかが分かります。さらに、前回の正常な起動以降のゲーム更新、スクリプト
エクステンダの欠落やゲームのバージョンとの不一致(エクステンダのダウンロードページと、
ダウンロードした書庫をインストールするボタン付き)、Eidos を `%command%` 付きで起動しない
Steam の起動オプション、DLSS 用にオフのままの NVAPI、フレーム生成を止める排他的フル
スクリーン、`LinuxVersion=true` のない ENB の `enblocal.ini`、F4SE と SFSE のプラグイン
宣言、そして前回のセッションのクラッシュログとそこに名前の出る MOD も報告します。

プロファイルの INI とプラグインのチェックは、Fallout 4、Fallout 4 VR、Starfield のカスタム INI の `[General]` にある `sTestFile` の行(ゲームに `plugins.txt` を無視させます。Fix はプロファイルの写しからそれらを削除し、元のファイルを `<ini>.pre-fix` として残します)を探します。さらに、Starfield で有効な `.esp` プラグイン、そして blueprint フラグ、`BlueprintShips-` の接頭辞、`.esm` の拡張子のどれかを欠く、またはメインのプラグインが有効でない blueprint プラグインも報告します。システムのチェックは、Proton が必要とする値を下回る `vm.max_map_count` や open files のハードリミット、そして NTFS、exFAT、FAT 上のゲーム、プレフィックス、インスタンスを知らせます。MOD のチェックは、ゲームの `Data` を指していない BodySlide のデータパス、ツールが `Overwrite/Root` に書いた `Data` フォルダ、パッチ対象の MOD にルーズファイルが負けているパッチ、そしてスクリプトエクステンダの Papyrus スクリプトを置き換える MOD を挙げます。

Check for updates は、各 MOD の Nexus の要件も読み込みます。Diagnostics は、見つからない、または無効になっている必須 MOD を一覧し、別の方法で満たしている要件は Ignore で非表示にできます。

このタブはゲームを動かす Proton のビルドも示し、新しい Proton が準備したプレフィックスを古い Proton が動かす前に警告します。Rebuild は壊れたプレフィックスを脇へ移し、Steam が新しいものを作れるようにします([troubleshooting.md](troubleshooting.md#どの-proton-がゲームを動かすかそして壊れたプレフィックス))。そのほかのカードは、一度も準備されていない、またはレジストリが古いプレフィックス、Mod Manager Download のリンクを Eidos 以外のプログラムが受け取っていること(Register で直ります)、入力より古いツールの出力(ツールをもう一度実行するボタン付き)、そしてクリーニング済みまたは light のプラグインのコピーで、元のプラグインがその後変わったものを知らせます。各カードの説明は [troubleshooting.md](troubleshooting.md#health-カード) にあります。Copy report は、ホームフォルダとログイン名を伏せた、システムとすべての所見のレポートをクリップボードに入れ、バグ報告に使えます。

Skyrim SE、Enderal SE、Fallout 4 では、Diagnostics に Display カードもあります。プロファイルの `SkyrimPrefs.ini`(`EnderalPrefs.ini`、`Fallout4Prefs.ini`)に設定されたウィンドウのサイズとモードを表示し、プロファイルにまだファイルがない場合はプレフィックス側のコピーの値を表示します。どちらにもサイズがない場合、入力欄には `/sys/class/drm` に載っている接続中で最大の画面の値が入るので、Steam Deck では 1280x800 になります。幅と高さは 320 から 16384 の整数です。Apply は `iSize W`、`iSize H`、`bFull Screen`、`bBorderless` をプロファイルのコピーに書き込みます。プロファイルにコピーがなければ、先にプレフィックスのコピーを取り込みます。SSE Display Tweaks がウィンドウを設定している場合、Apply は同じサイズとモードを Overwrite にあるそのコピーにも書き込みます。MOD 自体のファイルは変更されません。

タブの一番上にある Game files カードは[ゲームファイル](#ゲームファイル-ストアのインストールかコピーか)で、コレクションの順序のカードは[コレクションの順序を保つ](#コレクションの順序を保つ)で、Find the mod behind a problem は[テスト実行](#問題の原因になっている-mod-を見つける)で説明しています。

### ゲームの起動

ウィンドウ経由でゲームを起動するには、そのゲームの Steam 起動オプションにプログラムの
絶対パスを設定してください。Steam はシェルの `PATH` を読まないからです
([install.md](install.md#そのあと-steam-をここへ向ける)):

```
~/.local/bin/eidos-gui %command%
```

Colony からの場合、パスは `~/.local/share/Colony/apps/Eidos/eidos-linux` です。Eidos は
そのゲームのインスタンス(最後に使ったもの)で開くので、ポータブルインスタンスも
グローバルと同じように見つかります。Run を押せば統合ビュー越しに起動します。

Start the game at once when a store opens Eidos をオンにすると(Preferences、General、Running a game。既定ではオフ)、Eidos はこのクリックを省きます。Health を確認し、ウィンドウを表示せずにゲームを起動します。Health が問題を挙げたとき、MOD 一覧に対応が必要なとき、プレイ前に実行するよう設定したツールの出力が古いとき、Skyrim SE、Enderal SE、Fallout 4 でプロファイルにまだウィンドウサイズがないときは、いつもどおりウィンドウが開きます(最後の場合は Diagnostics タブで開きます)。1 回の起動だけウィンドウを出したい場合は、コマンドの前に `EIDOS_WINDOW=1` を付けます: `EIDOS_WINDOW=1 ~/.local/bin/eidos-gui %command%`

どのストアも開いていないウィンドウでは、Run はゲームを自分では起動せず、Eidos が Proton や Wine でゲームを直接起動することはありません。Run は、そのコピーを持つストアに起動を頼み、ストアが Eidos を起動します。

- Steam は、上の起動オプションが設定されていて、ゲームに Proton プレフィックスがあれば
  (Steam が初めてゲームを起動したときに作ります)、`steam -applaunch <appid>` を実行
  します。Steam が閉じていれば先に Steam が起動します。
- Heroic(GOG または Epic のコピー、ネイティブ版でも Flatpak 版でも)は、Heroic のゲーム
  設定で Eidos がラッパー(wrapper)になっていて、実行ファイルが `eidos-gui`(または
  `eidos-linux`)の絶対パスで引数がないとき、`heroic://launch` リンクを受け取ります。
  Heroic が閉じていれば先に Heroic が起動します。
- Legendary 単体は、`~/.config/legendary/config.ini` のゲームの `[<app>]` セクションか
  `[default]` に `wrapper =` と `eidos-gui`(または `eidos-linux`)の絶対パスがあるとき、
  `legendary launch <app>` を実行します。

Run リストにあるスクリプトエクステンダのローダー、ランチャー、ゲームの実行ファイルは、
どれもこのようにストアに渡され、ターミナルでそのいずれかに対して実行する
`eidos tool <instance> run <entry>` も同じです。Heroic の外にある GOG のコピーなど、一部の
コピーは Eidos がそのストアに渡せません。その場合 Run は、そのストアからゲームを起動するよう
告げます。

この受け渡しは、このインスタンスを最後に使ったものとして記録し、ストアはそのインスタンスで
2 つ目の Eidos ウィンドウを開きます。Start the game at once がオフなら、そこで Run を押します。
オンなら、上のどれかの場合がそのウィンドウを開かせない限り、そのウィンドウは自分を表示せずに
ゲームを起動します。最初のウィンドウはその実行を追わないため、遊び終えたらそのウィンドウで F5
を押して一覧を読み直してください。ストアの設定がない場合や、スクリプトエクステンダのローダーが
ゲームの実行ファイルの隣にない場合、Run は何も起動せず、何をどこに設定するかを、動いている
バイナリの実際のパス入りで表示します。

ゲームやツールの実行中は、Run が Stop に変わります。2 回押すと、その実行が起動したすべての
プログラムを終了し、Eidos は通常の終了後と同じようにセッションを回収してアンマウントします。
停止された実行が正常な起動として数えられることはありません
([troubleshooting.md](troubleshooting.md#閉じないゲームやツール))。

Bethesda のタイトルでは、Steam の `%command%` はたいてい `<Game>Launcher.exe` を指しています。
Eidos はそれを実行しません。あのランチャーは `Data` を再走査して `plugins.txt` を書き直す別の
設定アプリで、たった今展開したロード順を台無しにします。Eidos は、スクリプトエクステンダの
ローダーが入っていればそれを、なければゲームの実行ファイルを実行し、後者へ落ちるときは
そう言います。

Eidos は有効な MOD の DLL を走査して `d3dcompiler_47.dll` の import を探し、Microsoft の DLL を
プレフィックスへコピーし、そのうえで初めて `WINEDLLOVERRIDES=d3dcompiler_47=n,b` を設定します。
自分で設定する必要はありません。

### プロファイルごとの変数とラッパー

プロファイルは、独自の環境変数とラッパーコマンドを `profiles/<name>/launch-env.ini` に 1 行 1 項目で持てます。

```ini
env=PROTON_ENABLE_NVAPI=1
env=DXVK_HUD=fps
wrapper=gamemoderun
wrapper=gamescope -W 1280 -H 800 -f -- %command%
```

これらは、そのプロファイルのすべての `eidos play`(Steam の `%command%` で起動したゲーム、またはストアが開いたウィンドウで Run が起動したゲーム)と、すべてのツール実行に適用されます。`eidos shell` には変数だけが渡され、ラッパーは付きません。最初の `wrapper=` 行が最も外側です。`%command%` を含む `wrapper=` 行ではその位置にコマンドが入ります(Steam の起動オプションと同じです)。含まない行では末尾にコマンドが付きます。ラッパーは Eidos の専用名前空間の中で動くので、MOD が見えます。

ここに書いた変数は、Eidos が同じ名前に設定する値を置き換え、`tools.ini` にあるツール自身の `env=` 行はその両方を置き換えます。`WINEDLLOVERRIDES` だけは、Eidos が ENB、ReShade、同梱 DLL のために設定するオーバーライドの後ろに追加されます。両方に名前がある DLL はプロファイルの設定になり、それ以外は元の設定のままです。

View -> INI editor は、このファイルをどのゲームでも最後のタブとして開きます。空行と `#` または `;` で始まる行は読み飛ばされます。保存すると、Eidos が無視する行番号が表示されます。`env=NAME=value` でも `wrapper=command` でもない行と、Steam の起動オプションでは許される、最初の語が `NAME=value` の `wrapper=` 行です。その変数は代わりに `env=` の行に書いてください。コマンドなしの `eidos play <instance>` は、実行が受け取る変数とラッパーを一覧します。Diagnostics の Copy report には、変数名とラッパーのプログラム名が値なしで載ります。

## ツール

xEdit、BodySlide、DynDOLOD などのツールは、ゲームの Wine プレフィックス(Steam の Proton
プレフィックス、または GOG や Epic のコピーのために Heroic が用意したもの)の中で、統合
ビュー越しに動きます:

```sh
eidos tool skyrimse add BodySlide "<path>/CalienteTools/BodySlide/BodySlide.exe"
eidos tool skyrimse run BodySlide
eidos tool skyrimse run --exe "<path>/GenerateFNISforUsers.exe"  # exe を登録せずに一度だけ実行する
eidos prereqs skyrimse            # 登録したツールが必要とするものと、その状態
eidos prereqs skyrimse --install  # 足りないものを取ってくる
```

Pandora、Nemesis、FNIS、BodySlide、DynDOLOD、TexGen、xLODGen、Synthesis は、登録しなくても
見つかります。Pandora、Nemesis、FNIS、BodySlide、Synthesis には取り込み先の MOD があらかじめ
設定されているので、出力は専用の MOD に入ります(詳細は
[tools.md](tools.md#ツールの出力を専用の-mod-へ送る))。

ツールに付けたタイトルが、Eidos がどのランタイムと DLL を用意するかを決めます。`BodySlide`
なら DirectX のライブラリが付き、`BS` には何も付きません。ウィンドウでは Executables の
ダイアログが、前提条件それぞれの実際の状態を欄の下に表示し、足りないものはボタンになって
います。

リリースバンドルは、`runtimes/` に vcrun2022 のインストーラー(x86 と x64)、.NET 8
Desktop Runtime 8.0.12、.NET 10 ランタイム 10.0.10 を同梱し、`install.sh` がそれらを
`~/.local/share/Colony/Eidos/runtimes/` にコピーするので、
`eidos prereqs <instance> --install` はダウンロードなしでそれらをインストールします。
Eidos は Microsoft の vcrun2022 と .NET 8 のインストーラーを、winetricks なしでゲームの
プレフィックスの中でサイレント実行します。`eidos-linux` とソースビルドには `runtimes/`
フォルダがないので、同じ固定されたファイルを Microsoft からダウンロードします。Synthesis が
必要とする .NET 10 SDK(約 300 MB)は常にダウンロードです。

一覧表、前提条件の三段階、DynDOLOD が winetricks では入れられない .NET ランタイムを要る理由、
そして MOD として入れたツールが自分のフォルダではなく統合されたパスから起動される理由は
[tools.md](tools.md) にあります。

## 拡張

Eidos は作り直さずに拡張できます。`~/.config/Colony/Eidos/addons/` に置いた TOML の
マニフェストが、Extensions の一覧にツールを、Diagnostics タブにチェックを足します。Eidos の
中に何かが読み込まれるわけではありません。拡張は Eidos が実行するプログラムです。
[extensions.md](extensions.md) を参照してください。
