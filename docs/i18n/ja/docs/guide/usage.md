# Eidos の使い方

実践的な手引き。CLI、GUI、Steam の起動オプション、ソースからのビルド、そして
概念実証スクリプト。何かおかしいと思ったときにどうするかは
[troubleshooting.ja.md](troubleshooting.md) を参照してください。

## 使う(CLI)

```sh
eidos games                       # ここに入っている対応ゲーム(MO2 の一覧と同じ)
eidos init skyrimse               # MOD 用インスタンスを作る
# ...各 MOD をフォルダのまま <instance>/mods/ へ置く(グローバルインスタンスは
#    ~/.local/share/Colony/Eidos/instances/skyrimse にある。`eidos init` が自分の場所を表示する)...
eidos install skyrimse mod.7z     # または、落としてきた書庫をインストールする(Simple / FOMOD)
eidos import skyrimse <mo2-profile>  # 既存の MO2 プロファイルの順序 + プラグイン状態を引き継ぐ
eidos sort skyrimse               # プラグインのロード順を LOOT で並べ替える
eidos play skyrimse               # 何がマウントされるかを表示する
eidos play skyrimse -- <command>  # MOD をゲームに重ねた状態で <command> を実行する
eidos shell skyrimse              # 統合ビューでシェルを開く。書き込みは Overwrite に入る
eidos check skyrimse              # ウィンドウなしで健全性チェック(スクリプト向けに --json)
eidos sessions skyrimse           # 記録されたゲームとツールの実行を新しい順に表示
eidos sessions skyrimse diff      # 終了コード 0 で終わった直近の実行から何が変わったかを表示
eidos collection skyrimse <link>  # Nexus のコレクションを、作者が組んだとおりにインストールする
eidos nexus update skyrimse --apply  # 手元のファイルを置き換えた Nexus のファイルをインストールする
eidos pack skyrimse backup.eidos  # インスタンス丸ごとを一つのファイルに。よそへ移すために
eidos unpack backup.eidos <folder>   # 向こうのマシンで元に戻す
```

`eidos tool`、`eidos prereqs`、`eidos nexus`、`eidos nxm`、`eidos export` が
残りを埋めます。引数なしで `eidos` を実行すれば全一覧が出ます。

### ターミナルからの健全性チェック

`eidos check <instance>` は、ウィンドウを開かずに、**Diagnostics** タブにあるプレフィックス、プラグイン、欠けたマスター、スクリプトエクステンダのチェックを実行します。SSH 越しや Game Mode でも動かせ、バグ報告にも貼れます。**Copy report** と同じシステム情報の行を出力し、続いて検出ごとに 1 行を出力します。ホームフォルダは `~`、ログイン名は `<user>` に置き換えて表示します。終了コードは、問題が見つからなければ 0(助言だけなら 0 のまま)、問題が 1 つ以上見つかれば 1、Eidos がチェックできなかったとき(引数の誤り、開けないインスタンス、検出できないゲーム)は 2 です。

`eidos check <instance> --json` は代わりに JSON オブジェクトを 1 つ出力します。最上位のフィールドは `eidos`(バージョン)、`game`、`instance`、`system`(`proton`、`flatpak_steam`、`passthrough`、`session`、`distro`、`kernel`、`dev_fuse`、`fusermount3`)、`findings` です。各検出は `code`、`level`(`problem` または `advice`)、その `args` からなり、各コードの説明文は Diagnostics タブに表示されます。

### 統合ビューでのシェル

`eidos shell <instance>` は、ゲームから見える状態のゲームフォルダで `$SHELL`(なければ `/bin/sh`)を起動します。有効な MOD はすべて `Data` に重ねられ、Root MOD はゲームのルートに重ねられ、そこへ書き込まれたものはすべて Overwrite に入ります。`eidos shell <instance> -- <command>` は代わりにコマンドを 1 つだけ実行します。たとえば `eidos shell skyrimse -- ls Data/meshes` や、NifSkope のようなネイティブツールです。この実行はゲームのセッションと同じくインスタンスのロックを保持するので、終了するまでウィンドウは変更を保存できず、`eidos sessions` には `shell` という名前で記録され、ゲームの起動としては記録されません。コマンド実行中の Ctrl+C は Stop と同じように実行を止めます。Eidos がコマンドを終了させ、セッションを回収し、アンマウントします。対話シェルでは Ctrl+C は通常どおりシェルのものです。実行を終えるには `exit` と入力します。

### インスタンス: グローバルとポータブル

上のコマンドはどれもインスタンスを指しています。`skyrimse` が指すのは
**グローバル**のほう - `~/.local/share/Colony/Eidos/instances/skyrimse` に集約して置かれ、
Eidos が管理します。もう一方は**ポータブル**。好きな場所(二台目のドライブ、
ゲーム用のパーティション)に置ける自己完結したフォルダで、移動でき、隔離
されていて、MO2 のポータブルインスタンスとまったく同じです。ゲーム ID を取る
コマンドは、どれもポータブルインスタンスのフォルダを同じように受け取ります:

```sh
eidos init skyrimse /mnt/games/EidosSkyrim   # そこにポータブルインスタンスを作る
eidos install /mnt/games/EidosSkyrim mod.7z  # どのコマンドもフォルダを受け取る
eidos play /mnt/games/EidosSkyrim -- %command%
```

フォルダは自分自身を説明します(`eidos-instance.ini` がゲーム名を持つ)。だから
他には何も要りません - そして環境変数の `EIDOS_INSTANCE=<folder>` はゲーム ID を
そのフォルダへ振り向けます。Steam の起動オプションで重宝します。作ったり開いたり
したポータブルインスタンスは `~/.config/Colony/Eidos/instances.ini` に(最近使った
順で)記憶されます。GUI のようこそ画面はそれらを一覧して一クリックで開けるように
し、Steam からの起動は最後に遊んだものに着地し、`nxm://` ハンドラはそこへ
ダウンロードします。知っておく価値のある注意が二つ。ポータブルフォルダを手で移動
しても残らないのは、古い場所への絶対パスで登録したツールの項目だけです(後述の
`eidos pack` / `eidos unpack` はそれを直してくれます。素の `mv` は直しません)。
そして共有ランタイムキャッシュ
(`~/.local/share/Colony/Eidos/runtimes/`)は意図的にマシン全体のままです -
78 MB の .NET ホストはインスタンスごとに持つものではありません。

Eidos は自分のファイルを `Colony/Eidos` の下に置きます。Colony 系のどのプログラムも使う配置です。あなたが選んだもの(設定、Nexus のセッション、インスタンス一覧、自分で書いたゲームとアドオンの定義)は `~/.config/Colony/Eidos/`、グローバルインスタンス(`instances/`)、ダウンロードしたランタイム、セッションログ(`logs/`)は `~/.local/share/Colony/Eidos/`、LOOT のマスターリストは `~/.cache/Colony/Eidos/` で、無くなればいつでも再ダウンロードされます。

古い Eidos はこれらを `~/.config/eidos/`、`~/.local/share/eidos/`、`~/.local/state/` に置いていました。更新後の初回起動がそれらを**コピー**し、ログにそう書きます。グローバルインスタンスはバイト単位のコピーではなくハードリンクで移すので、数十ギガバイトの MOD も一瞬で移り、余分な容量も使いません。ツールの登録も新しいフォルダを指すよう書き換えます。古いディレクトリはそのままの姿で残ります - 何も削除しないので、更新の失敗でサインインやセーブを失うことはありません - 納得したら自分で消してください。コピーができない場合(ディスクが一杯か読み取り専用、古いインスタンスフォルダが別のドライブにある、そこからゲームがまだ動いている)、Eidos は古い場所を使い続け、次回の起動で再び試みます。古いインスタンスフォルダを指したままの Steam の起動オプションは、移動後のインスタンスを開きます。ただし余分な容量を使わないのは最初だけです。移動後に削除や再インストールをした MOD やダウンロードは、古いインスタンスフォルダを通じて古いコピーがディスクに残り続けるので、その容量を取り戻すには `~/.local/share/eidos/<game>/` を削除してください。

ポータブルインスタンスは決して移動しません。置いた場所にそのまま残ります。

一箇所だけはきっぱり拒否されます。**ゲームのインストールフォルダの中**
(MO2 のベテランがつい取る反射)。あの木は Steam のものです - 更新、
「整合性の確認」、アンインストールがそれを書き換えたり消したりして、あなたの
環境ごと持っていきます - そして Eidos はゲームのルートに重ねてマウントするので、
その中のインスタンスは自分のマウント先の内側に座ることになります。ウィザードも
`eidos init` も `eidos play` も断ります。フォルダはゲームの隣に置いてください
(同じドライブの兄弟なら手軽さは変わりません)。

`play` は、プライベートな名前空間の中で、インスタンスの MOD をゲーム自身の
`Data` ディレクトリに重ねてマウントし(bind-stash 経由なので、デーモンは元の
ファイルをそのまま読めます)、そのビュー越しにコマンドを実行します。書き込み
(セーブ、再生成された設定)はインスタンスの `overwrite/` レイヤーに落ちます。
ゲームのインストール先も MOD の元データも一バイトも変わりません。

### Wabbajack リスト

Eidos には Wabbajack のインストーラーはありません。リストは Eidos の外で CLF3 または Jackify を使ってインストールし、ウィザードでそのインストール先フォルダーをポータブルインスタンスとして選んでください。Eidos はフォルダーを MO2 の構成として読みます: `mods/`、`profiles/<名前>/modlist.txt`、プラグインリストです。インストーラーが書いた `ModOrganizer.ini` は保持され、上書きされることはないので、リスト自身の実行ファイルの登録はそのまま残ります。

多くのリストは、改変したゲームのコピーを入れた `Stock Game` または `Game Root` フォルダーを作り、MO2 はそこからゲームを起動します。Eidos は Steam のインストールを起動し、別のゲームフォルダーを指定する設定はありません。ウィザードはそのようなフォルダーを見つけると確認画面で知らせるだけで、ほかには何もしません。リストがそこに置いたファイルは、自分でいずれかの mod の `Root/` フォルダーに移してください。CLF3 は BSA と DDS のファイルを独自のツールで作り直すため、結果が Wabbajack のインストールと異なることがあり、リストの作者もそのサポートはしません。

### MOD 一覧

MO2 と同じく、プロファイルはそれぞれ自分の `modlist.txt`(どの MOD が有効で、
どの優先度か)を持ち、MOD のフォルダ自体はインスタンスで共有の `mods/` に
あります。手で `mods/` に置いたフォルダはまだ一覧に載っていません。それは
**最高の優先度で無効**として現れます - ウィンドウの一覧の末尾、MO2 が置くのと
同じ場所です - だから有効にすれば、競合ではそれが勝ちます。古いバージョンは
それを先頭に置いていたので、他のどの MOD にも上書きされていました。

フォルダは共有なので、MOD を削除したり改名したりすると、すべてのプロファイルが
変わります。その行はどのプロファイルの `modlist.txt` からも消され、あるいは
そこで改名され、それ以外については各プロファイルが自分の状態と順序を保ちます。
MOD が一つも残らなかったプロファイルは、空の `modlist.txt` を持つのではなく、
`modlist.txt` そのものを持ちません。空のものは壊れたファイルとして読まれ、次の
インストールを止めてしまっていたからです。

ウィンドウは MOD 一覧とロード順の自分用の写しをもとに動きます。開いている間に
別の Eidos プロセスがそのどちらかを書くと - 端末での `eidos install` や
`eidos sort`、コレクション、Steam が始めたセッション、二つ目のウィンドウ -
ウィンドウの次の編集は、その作業を上書きする代わりに拒否されます。ウィンドウは
ディスクから読み直し、
*Not saved: another Eidos process changed the mod list. It has been reloaded - redo the change.*
と告げます(ロード順の場合も同様です)。失われるのはその一クリックだけなので、もう一度やってください。
Rename、New mod、Add separator、Remove、そして Overwrite を MOD に変える操作は、
`mods/` に触る前に確認を行うので、拒否された編集はディスク上の何も変えません。
INI エディタも同じく、開いた後に変わったファイルの上へ保存することを拒みます。

### セーブはプロファイルのもの

プロファイルはそれぞれ自分のセーブを `profiles/<name>/saves/` に持ち、実行して
いる間はそのフォルダが Proton プレフィックスの中のゲームのセーブフォルダに重ねて
マウントされます。プロファイルの初回起動は、プレフィックスにすでにあるセーブを
そこへ一度だけコピーするので、後でプロファイルから消したセーブは消えたままです。
実行が終わるたびに、プロファイルの最新のセーブが Steam Cloud のためにプレフィックス
へコピーし戻されます。Eidos が置いたのではないプレフィックスのセーブは、まず
プロファイルに `orphan-<time>-<name>` として保管され、上書きされることは決して
ありません。

最初のコピーの後に Eidos を通らずにプレフィックスへ入ってきたセーブ - Steam Deck
からの Steam Cloud のダウンロード、Eidos を使わない起動 - は、プロファイルの
セーブがマウントされている間は隠れたままです。それを消すものは何もありません。
起動時に実行のログでその名前が挙げられます(ウィンドウからの起動ならインスタンスの
`logs/run-*.log`、Steam からの起動なら Steam のコンソール)。挙げられるのは、
そのファイルの組が変わるたびに一度だけです。それで遊ぶには、そのセーブと
コセーブをプロファイルの `saves/` フォルダへコピーしてください。

### 前回の正常な実行から何が変わったか

`eidos play` または `eidos tool run` による実行は、ウィンドウ、ターミナル、Steam のどこから始めても、`<instance>/logs/sessions/` に記録を書き込みます。内容は、プロファイル、有効な各 mod とそのバージョンおよび Nexus のファイル ID、プラグインの順序、各プロファイル INI のチェックサム、ゲーム実行ファイルのバージョン、Eidos のバージョン、終了コード、その実行で作られたセーブです。新しい 50 件が残り、`logs/` はパックしたインスタンスに含まれません。`eidos sessions <instance> diff` は、終了コード 0 で終わった直近のゲーム実行を現在の状態と比べます。`diff <id>` で一覧から別の記録を選べます。Eidos はここではまだクラッシュを検出せず、Proton 上でクラッシュしたゲームも終了コード 0 で終わることがあります。選ばれた実行がそれに当たる場合は、`diff <id>` でより前の記録を指定してください。

### 特権の要る手順はない

Eidos は完全に rootless で動きます。プライベートな user + mount 名前空間の中で
マウントするので、setuid のヘルパーもデーモンも要らず、与える権限もありません。

`sudo setcap cap_sys_admin+ep "$(command -v eidos)"` は**任意**で、開くのはただ
一つ、カーネルの FUSE パススルーだけです。以前のデーモンがこれでゲームを壊し、最
も可能性の高い原因を避ける変更がまだゲームで再測定されていないため、既定では無効
です(下記)。この capability があると、Eidos は user 名前空間ではなく素の mount
名前空間を取ります。MOD の展開はどちらでも同じです。


昔の `setcap` の案内が消えた理由 - そして FUSE パススルーが無効で出荷される
理由 - は
[troubleshooting.ja.md](troubleshooting.md#なぜパススルーは既定で無効なのか)
にあります。

## Nexus のコレクションをインストールする

```sh
eidos collection skyrimse nxm://skyrimspecialedition/collections/rqhcxy/revisions/latest
eidos collection skyrimse rqhcxy --dry-run     # 読むだけ。何が起きるかを言う
```

ウィンドウの中でなら、リンクを **File -> Open a Nexus collection...** に貼り付けて
*Install this collection* を押します。

### これが「この MOD 群を落としてくる」ではない理由

コレクションは**レシピ**であって、買い物リストではありません。そしてそのレシピは
ほとんどが Nexus の API からは見えません。インストールの順序、各 MOD のスクリプト
インストーラに作者が与えた回答、ファイルの競合でどの MOD が勝つか、どのプラグインが
どこに読み込まれるか、バイナリのパッチ - その全部が、コレクション自身の書庫の中の
`collection.json` にあります。同じ MOD を落としてきて既定のオプションのまま
インストールしても、出来上がるのは別のゲームです。

そこで Eidos は書庫を落とし、レシピを読み、それを適用します:

| コレクションが言うこと | Eidos がすること |
| --- | --- |
| `phase` | その順にインストールし、任意の構成要素は最後に回す |
| `choices` | 各 FOMOD への作者の回答を再生し、できないときはそう言う |
| `modRules` | 各ファイルで正しい MOD が勝つように MOD 一覧を並べ替える |
| `plugins` / `pluginRules` | LOOT のルールをあなたの userlist へ統合して並べ替える |
| `INI Tweaks/` | それ自体を一つの MOD としてインストールする |
| `tools` | どのツールを前提としているかを伝える。何も作らない |

構成要素はインストールされるそばから**有効**になります。入る場所は MOD 一覧の
末尾、インストールの順序のまま、`modRules` が動かす前です - どの一覧にも載らない
MOD は、どこにも読み込まれない MOD であり、ディスクの上でじっと動かないまま
置かれたコレクションは、レポートには見えなかった唯一の失敗だからです。

状態は構成要素**一つごとに**
`<instance>/collections/<slug>-<revision>.state.json` へ書かれます - そのリビジョンの
フォルダの中ではなく、その隣に。コレクションが自分の帳簿を同梱できないように
するためです - だから 200 個中 147 個目で中断したインストールは 147 個目から
続きます。書き込みは一時的な名前で行い、そこから所定の名前へ付け替えるので、
中断が残すのは古い記録か新しい記録のどちらかであって、どちらかの半分ということは
決してありません。もし読めなくなったときは、Eidos は黙ってコレクション全体を
最初からやり直すのではなく、そこで止まってそう言います。同じコマンドをもう一度
実行してください。

すでに持っているコレクションの新しいリビジョンをインストールすると、前の
リビジョンのフォルダを引き継ぎます。変わっていない構成要素はその場で検証され、
作者がファイルを更新した構成要素は古いフォルダの中で置き換えられ、新しい
リビジョンが外した構成要素はインストールされたまま残り、無効にするか削除するかを
あなたが決められるようレポートに名前が出ます。別のプロファイルが有効にしている
フォルダは決して引き継ぎません。mods フォルダは共有なので、そのプロファイルが
知らないうちに変わってしまうからです。代わりに新しいリビジョンは自分の写しを
その隣にインストールし、レポートは古いほうをこのプロファイルで無効にするよう
求めます。削除しろとは決して言いません。古いリビジョンへ戻るときも同じように
そのフォルダを引き取り直し、引き取れないものは新しい写しをインストールします。
このように構成要素を置き換えるとき、そのフォルダの中であなたがファイルを変更または追加していた場合は、古いフォルダを先に `<name>_backup` として隣に残します。これはゲームに読み込まれることはなく、レポートにその名前が出ます。

前のリビジョンの残りが有効のままだと、そのインストールは作者が組んだとおりの
ものとは数えられません。それを無効にすればその注記は消えます。`--no-optional`
で飛ばした構成要素は引き継がれず、同じように名前が出ます。引き継ぎそのものが
失敗したときは、実行は *previous revision: its folders could not be taken over*
とその理由を示して止まります。それを直して、同じコマンドをもう一度実行して
ください。

### 取り繕わないこと

**無料の Nexus アカウントでは構成要素の MOD を取ってこられません。** Nexus は API
経由では無料会員にダウンロードのリンクを発行しません。どのファイルにもサイト自身の
「Mod Manager Download」ボタンが要ります。コレクションの**書庫**そのものは無料
会員でも問題なく落とせるので - レシピは丸ごと読めます - 構成要素はそれぞれ、自分で
取ってくるためのページの URL を正確に添えて報告されます。これは Nexus の商売上の
決まりであって、何度やり直しても通り抜けられません。サイト自身のボタンで取って
きて、同じコマンドをもう一度実行してください。そうした構成要素は実行のたびに
`downloads/` の中を探されるので、あなたが渡したぶんだけコレクションは仕上がって
いきます。

ウィンドウでは、無料アカウントだとコレクションのペインにまとめての取得の代わりに
*Fetch the N missing required files, one by one* が出ます。これは足りない必須
ファイルの最初の一つの Nexus ページを開き、そのファイルが `downloads/` に届くのを
待ってから次を開きます。各ファイルでページのダウンロードボタンを押すのは、今まで
どおりあなたです。ペインには進み具合 (*3 of 12*) と *Skip*、*Stop* が出ます。
代わりに同じ MOD の別のファイルが届いた場合は、ペインが両方のファイル ID を示し、
コレクションが指定したほうを待ち続けます。任意の構成要素はこの対象に入らず、
それぞれの *Open* ボタンが残ります。

コレクションの記述どおりに適用されます。**バイナリのパッチ**(それぞれ記録された CRC と照合します)、**ファイルの上書き**(指定されたファイルは MO2 と同じく `.mohidden` で隠します)、そしてファイルがコレクションの書庫の中を一緒に運ばれてくる構成要素(`bundle`)です。コレクションが手で取ってくることを
前提にしている構成要素(`browse`、`manual`)は、作者自身の指示をそのまま
レポートまで運びます。名前がすでにあなたの MOD と同じ構成要素は、決してその上に
ではなく、空いている名前を取ってその隣にインストールされます。そしてどれがそう
だったかはレポートが言います。

### レポート

レポートの眼目は、「インストール済み」が信じるに値するものであることです。
インストーラへの回答を全部は再生できなかった構成要素は、**インストールはされた
けれど、コレクションが求めるとおりではない**ものです - 見かけがよく似ている成功と
同じ扱いにはせず、独立した一行を与えます。ディスク上のファイルが作者のものと違う
からです。コレクションの中の何も名指ししていなかった順序のルール、矛盾するルールの
輪に捕まった MOD、存在しない LOOT のグループ、そしてこのバージョンの Eidos が
理解しないマニフェストの部分も、どれも同じように並びます。

もう一方のやり方 - そういうものをログに書いて、インストールは済んだことにする
やり方 - こそ、誰にも原因を突き止められない理由でコレクションが違う姿で動くように
なる道です。

## インスタンスを別のマシンへ移す

`eidos pack` はインスタンスを丸ごと - MOD の一つ残らず、ロード順、プロファイル
全部、セーブの入った Overwrite、そして全部のインストール元になった書庫まで -
一つのファイルに書き出します。`eidos unpack` はそれを元に戻します:

```sh
eidos pack skyrimse ~/backup.eidos                  # フォルダを渡してもよい。ゲーム名と日付から名前が付く
eidos unpack ~/backup.eidos /mnt/games/EidosSkyrim  # 向こうのマシンで
```

`eidos pack --dry-run` は、何が入り、何が入らず、それはなぜか、そしてどれだけの
空きが要るかを、何も書かずにそのまま並べます。手元にすでにあるファイルについては
`eidos unpack --info` が同じことをします。

7-Zip が読めなかったものがあっても、あるいはバックアップに入っているはずのものを
走査が飛ばさざるを得なかったとしても(シンボリックリンク、読めなかったフォルダ、
7-Zip に安全には渡せない名前)、書庫は書き出され、名前も付きます - 持って
おく価値はあるからです - が、`eidos pack` は **1** で終了し、何が欠けているかを
告げます。欠けたバックアップは成功ではありませんし、これは `&&` の前に置かれる
コマンドです。

`.eidos` ファイルは独自の名前をまとった 7-Zip の書庫です。これは偽装ではなく選択
です。MOD を一つ入れるだけでも 7-Zip はすでに必須なので依存は増えませんし、いつ
か Eidos を失っても、バックアップは手元のどの書庫ソフトでも開けます。圧縮は
LZMA2 の `-mx1` - テクスチャの多い構成で元の約 43%、`-mx9` が数ポイント余分に縮
めるのに費やす時間のごく一部で済みます。テクスチャもメッシュもすでに圧縮された形
式で、辞書を大きくしても見つかるものはほとんど残っていません。自分の中身について
は意見が違うというなら `--level`(0、1、3、5、7、9)がそれを上書きし、
`--no-downloads` は `downloads/` を外します。

既定のレベル 1 では、ファイルは**最大 16 MB のソリッドブロック**に収められます。
70 GB のバックアップからファイル一つを取り出しても、デコードされるのはせいぜいそ
のファイルが入っているブロックだけで、前に並ぶものを全部展開することはありませ
ん。ゲームのデータの pack も、ファイルを一つずつ圧縮する場合に比べて 2 - 5 倍、
展開は 2 - 4 倍速くなります。代わりに損傷に弱くなります。壊れた 1 バイトがそのブ
ロックのファイルをすべて巻き込み、最大 16 MB 分の隣のファイルを失うことがありま
す。この場合に備えるのが、後で説明する修復データです。ほかのレベルはすべて非ソ
リッドのままです。ファイルはそれぞれ独立したストリームになり、壊れた 1 バイトで
失うのはそのファイル一つです。レベル 0 はファイルを圧縮せずに格納します。レベル
3 以上では LZMA2 がもともと 16 MB 以上の単位で処理するので、ソリッドブロックにす
ると計測では遅くなりました。レベル 5 では、メッシュの pack に 1.4 倍、テクスチャ
の展開に 6.8 倍の時間がかかりました。

pack はインスタンスのロックを取るので、ゲームや別の Eidos がそのインスタンスへ書
いている間は走れません - バックアップはスナップショットであって、ぶれた像ではあ
りません。書き込みは `.part` の名前で行われ、ディスクへ確実に書き出されたあと、
あなたが選んだ名前を得る前に `7z t` で丸ごと読み戻されます。この検査はすべてのブ
ロックをデコードし、すべてのチェックサムを照合します。もう一台のマシンで展開するときと同じ作業です。これで分かるのは書き込み直後にディスクが返した内容であって、ドライブがそれを保ち続けることではありません。そのために後で説明する修復データがあります。検査に失敗すると `.part` は削除され、あなたの選んだ名前では
何も書かれず、`eidos pack` は 7-Zip が損傷を見つけた行を示します。中断または失敗
した pack が残すのは、明らかに未完成だと分かるものか、何もないかのどちらかで、完
成したように見えて実はそうでない `.eidos` ファイルではありません。

par2cmdline がインストールされていれば(Arch では `sudo pacman -S par2cmdline`、
Debian と Ubuntu では `sudo apt install par2`、Fedora では
`sudo dnf install par2cmdline`)、`eidos pack` は書庫の隣に PAR2 の修復データも書
きます。`backup.eidos.par2` といくつかの `backup.eidos.volNN+MM.par2` ファイルで、
合計は書庫の 5% と小さな索引です。これらは書き込まれたときの名前のまま `.eidos` ファイルと同じフォルダに置き、一緒にコピーしてください。修復データなしで移したバックアップには直す材料がなく、修復データは書庫の名前を記録しているので、名前を変えたバックアップとはもう合いません。`eidos unpack` は名前でこれらを見つけ、何かを展開する前に書庫を照合します。末尾が切れて 7-Zip が開けなくなったバックアップも対象です。数バイトが壊れていれば、par2 が先に書庫を修復し、壊れたコピーを
`backup.eidos.1` として残します。このため、書庫のフォルダに書庫と同じ大きさの空き容量が要ります。5% で補えない損傷なら、ファイルを一つも書かない
うちに展開を止めます。同じ名前の古いバックアップのものなど、書庫に合わない修復ファイルは、7-Zip が書庫を読んで無傷だと確認できれば使われず、展開時にその旨が表示されます。par2 のないマシンでも展開は行われ、修復データを使わなかっ
たという警告が出ます。`--no-recovery` を付けると修復データなしで pack し、
`eidos pack --dry-run` は修復データを書くかどうかを表示します。

### 入らないもの、そしてその理由

| 入らないもの | 理由 |
| --- | --- |
| Proton プレフィックス | あれはマシンの形をしています(ドライブの割り当て、*このマシンの*ファイルシステムを映した `Z:`)。しかも Eidos は `eidos prereqs <instance> --install` で一分もあれば作り直します。運んだところで、向こうのマシンがどのみち作り直すもののために書庫がおよそ倍になるだけです。 |
| ゲーム本体 | インスタンスは、自分の中に含まないゲームに MOD を当てるものです。向こうでは Steam から入れてください。 |
| インスタンスの外にあるツール | xEdit、DynDOLOD といった面々は、それぞれ独自のインストーラを持つ第三者のバイナリです。書庫にはその**名前**が入るので、unpack すれば新しいマシンにどれが足りないのかがそのまま分かります。 |
| `logs/`、`.eidos.lock`、`prereqs.done`、`prereqs.log` | バックアップを作ったマシンの記録です。とくに `prereqs.done` は、そこに無いプレフィックスにランタイムのライブラリがもう入っていると言い張ることになります。 |
| `loot/`、ただし `userlist.yaml` を除く | Eidos が必要に応じて取り直すマスターリストのキャッシュです。自分で書いた LOOT のルールはキャッシュではありませんし - あれを取り直してくれるものは誰もいません - だからあのファイル一つは一緒に乗っていきます。 |
| `.base/`、`.base-root/` | セッションの間ゲーム自身のファイルを退避しておく、空のマウントポイントです。 |
| 書きかけのファイル | 一時停止したダウンロード(`*.unfinished`)、進行中のアトミックな書き込み(`*.eidos-tmp*`)。 |
| シンボリックリンク | 7-Zip はリンクを辿って指す先をコピーしてしまいます。絶対リンクなら、よそのディレクトリ木をバックアップへ引き込むということです。代わりに報告し、バックアップは不完全とみなされます。別のドライブへリンクされた `mods/` や `downloads/` は書庫に**入りません**。リンクされた `downloads/` を意図して外してバックアップするなら、`--no-downloads` を渡してください(ウィンドウなら *Include downloads/* のチェックを外します)。意図した除外は欠落には数えられません。 |

これらはどれも、書庫のルートの `eidos-backup.ini` に理由付きで載ります - だから
「ここに何が入っていないのか」への答えは当て推量ではなく `cat` です。同じ
ファイルは、インスタンスが以前どこにあったか、どのプロファイルが有効だったか、
展開するとどれだけの大きさになるか、そして新しいマシンでどのツールが要るかも
記録します。

ダウンロードの記録(`downloads/*.meta`)は、`url=` の行を**空にして**入ります。
あの URL は署名付きの Nexus のリンクです。数時間で効かなくなりますし、ファイルを
落としたアカウントの `user_id` を抱えています。バックアップは誰かに渡すために
作るものなので、それは持たせません。ダウンロードをもう一度見つけられるようにする
もの - MOD の id、ファイルの id、バージョン - は残ります。

### ウィンドウの中では

どちらも **File** メニューにあります。*Pack this instance...* と
*Unpack a backup...* です。unpack はようこそ画面の、インスタンスの一覧の下にも
あります。いちばんそれを必要とするマシンとは、まだインスタンスを一つも持って
いないマシンだからです。

Pack のダイアログは、実行に移る前に下見を見せます。ファイルが何個で、どれだけの
大きさで、そのうちどれだけが `downloads/` で、書庫はおおよそどれくらいになり、ど
のツールが名前だけ載って運ばれないのか。*Write recovery data* のチェックボックス
は、par2 がインストールされていればオンになり、なければインストールすべきパッケー
ジ名とともに灰色になります。Unpack のダイアログはファイルを選んだその場でバック
アップのマニフェストを読むので、それがどのゲームのものか、いつ作られたか、以前ど
こにあったか、そのツールのどれがここに足りないのかを - フォルダを渡す前に - 教え
られます。

どちらもプログレスバー付きのワーカースレッドで走るので、作業中もウィンドウは応え
続け、終わればそのバーがそのまま報告になります。pack は走っている間ずっと
インスタンスのロックを握ります。読んでいる最中、他の何にもそのインスタンスを
触らせません - バックアップを、ぶれた像ではなくスナップショットにしているのは
それです。

### unpack が直すもの

フォルダをただコピーしただけでは、ツールのボタンはどれも古いマシンのパスを指した
ままになります。`eidos unpack` は、古いインスタンスのルートを名指ししている値を、
それだけを書き換えます。`tools.ini` の `exe`、`workdir`、番号付きの `arg` キー、
そして各 MOD の `meta.ini` の `installationFile`。そもそもインスタンスの中に
なかったツール(`/opt/xedit/SSEEdit.exe`)はそのままの姿で残され、入れ直すものと
して一覧に出ます - 他人の xEdit がどこにあったかを当てるのは修復ではなく創作
です。インスタンスが自分を集約型と名乗るかポータブルと名乗るかも直すので、後の
コマンドは今ある場所を探しに行きます。

unpack は次のものを断ります。空でないフォルダ(上書きするつもりなら `--force`
を渡してください)、マニフェスト自身の数字に足りないディスク、自分より新しい
Eidos が作った書庫、そして選んだフォルダの*外*に書き出されるエントリを持つ書庫。

その後は:

```sh
eidos prereqs /mnt/games/EidosSkyrim --install   # Proton プレフィックスを作り直す
eidos play /mnt/games/EidosSkyrim
```

## GUI

```sh
cargo run -p eidos-gui
```

Colony 共通のテーマで描かれた、MO2 風の初回起動ウィザードが動きます。
ようこそ -> インスタンスの種類(ポータブル / グローバル)-> ゲーム -> 名前と
場所 -> 概要 -> 作成 -> メイン画面。ようこそ画面は既知の既存インスタンス
(グローバルもポータブルも、最後に使った順)も一覧して一クリックで開けるように
します - インスタンスの切り替え役も兼ねます - そしてすでにインスタンスがある
フォルダをウィザードに指すと、上から作り直すのではなくそのまま引き継ぎます
(そのフォルダが別のゲームのものなら、きっぱり断ります)。

二ペインのメインウィンドウもできています。プロファイルの選択(切り替え、または
現在のものを複製して新規作成)、絞り込み・選択・並べ替え・セパレータでの
グループ化・カテゴリでの絞り込み・右クリックからの操作ができる MOD 一覧、
そして Data / Plugins / Conflicts / Overwrite / Saves / Downloads /
Diagnostics のタブと、実行対象を選べる Run ボタン。

並べ替えは先頭 / 末尾へ送るだけではありません。MO2 の狙いを定めた移動もここに
あります - 最初に競合する MOD の上へ、最後の下へ、指定した優先度へ、あるいは
セパレータのグループの中へ。どれも共通の移動ヘルパー一つを通るので、行を消して
から挿し直すときに出る off-by-one は五箇所ではなく一箇所にしかありません。

### 環境設定

左上の **Eidos** をクリックすると、二つのペインの代わりに環境設定が開きます。
もう一度クリックする(または **Close** を押す)と元に戻ります。Colony の
どのプログラムとも同じく、General、Appearance、Accessibility が先に並び、
そのあとに Mod list、Nexus、About が続きます。変更はすべてその場で適用され、
保存されます。Save ボタンはありません。

- **General**: Eidos が開くゲーム、ウィンドウの大きさ、インターフェースの言語、
  ツールフォルダ、ゲームの実行方法。ウィンドウは英語とフランス語に対応しています。
  **System** は `LC_ALL`、`LC_MESSAGES`、`LANG` に従い、変更はその場で
  反映されます。`eidos` のコマンドラインは常に英語で応答します。
- **Appearance**: テーマ(25 のファミリ、57 のパレット、既定は Eidos の羊皮紙)、
  アクセントカラー、文字の大きさ、エフェクト、そしてライブプレビュー。
- **Accessibility**: ハイコントラスト、ディスレクシアに配慮したフォント、
  モーションの軽減、そして Appearance の文字サイズに掛け合わされる読書用の
  文字サイズ。

これらは `~/.config/Colony/Eidos/preferences.json` に保存されます。以前の Eidos が
`settings.ini` に保存していたテーマは、初回に引き継がれます。

### 列、並べ替え、グループ化

一覧は最初から四列を描き、八列を用意しています。Category、Content、Version、
Author、Installed、Nexus id、Game、Flags。View メニューでチェックを入れて
ください。既定が八列全部でないのは意図的です - 全部の列を出した一覧には名前の
列の余地が残りません。実際に読んでいるのはその列です。

見出しをクリックすればその列で並べ替わります。もう一度で逆順、三度目で
**ロード順**に戻ります。これは聞こえるより重要です。一覧をドラッグできるのは
ロード順のときだけだからです。挿入の隙間は本物の一覧を指しているのに、
並べ替えられた行はまったく別の場所にあります。並べ替えが効いている間は挿入の帯を
描かず、誰も狙っていない場所に落とすのではなくドラッグを断ります - MO2 と同じ
ことを、同じ理由で。View メニューはそう言い、戻る道も出します。

View メニューは一覧全体を**グループ化**もできます。カテゴリ別か、出所別
(Nexus からか、手で入れたか)。グループの見出しはセパレータではありません。
名前を変えたり色を付けたり動かしたりする実体は後ろにありませんし、折りたためて、
折りたたんでも件数は見出しに残ります。並べ替えやグループ化のもとでは、セパレータは
一覧から退きます - セパレータはロード順で後ろに続く行の頭に立つものであり、
どちらもその行を動かしてしまったからです。

### マウスとキーボード

MOD をダブルクリックで Information、Ctrl+ダブルクリックでそのフォルダ、
Shift+ダブルクリックで Nexus のページ。Ctrl+F でカーソルが絞り込み欄に入ります。
文字を打つとその文字で始まる次の MOD へ飛び、もう一度押せば最初のものに留まらず
残りを順に辿ります。どれも、絞り込みや折りたたんだセパレータ・折りたたんだ
グループが隠している行には着地できません - 見えない選択を動かすことこそ、次の
Space が見てもいない MOD を切り替える原因です。

セパレータのメニューの「Collapse others」は、そのグループ以外を全部
折りたたみます。ドラッグ中に折りたたんだグループの上で止まると開くので、
ドラッグをいったんやめずに中へ落とせます - 止まったときだけで、通り過ぎる
だけでは開きません。

Ctrl+Z は MOD リストまたはロード順への直前の変更を取り消します。チェック、移動、一括無効化、LOOT による並べ替えが対象です。
Ctrl+Shift+Z でやり直します。ウィンドウは 50 ステップを保持し、F5、ゲームやツールの実行終了、
プロファイルの切り替え、別の Eidos プロセスによるリストの変更のときに履歴を破棄します。
MOD のインストール、名前の変更、削除はディスク上のフォルダーを変えるため、それより前に戻る
取り消しは拒否されます。

### 一覧が MOD について教えること

助言のフラグが二つ。どちらも字形で、ホバーすると説明が出ます。
**No valid game data** は、MOD の一番上にこのゲームが読み込むものらしきものが
何もない、という意味です。フォルダを一階層上げる必要があるのかもしれませんし、
このゲーム向けの MOD ではないのかもしれません。**Another game** は、MOD 自身の
`meta.ini` が別のゲームを指している、という意味です。どちらも何も止めません -
MOD はそのまま展開されます - 行のメニューの「Mark as valid」がどちらも
黙らせます。MO2 自身の `validated=` キーを通すので、片方のマネージャで太鼓判を
押した MOD はもう片方でも静かに現れます。

配置の判定は意図的に甘くしてあります。`Root/` の木も数え、読めないフォルダも
数え、空のフォルダも数えます。五百行の一覧では、警告が間違っているほうが、
警告が出ないより悪いからです。

### セーブや他の MOD が使っている MOD を無効にするとき

MOD を無効にする前、または削除する前に、Eidos はプロファイルの最新のセーブ
三つのプラグイン一覧を読みます。そのどれかがその MOD のプラグインを使っていると、
一覧の上にバーが出てプラグイン名を挙げ、「Disable anyway」か「Cancel」を待ちます
(Esc でも取り消せます)。Remove は、もう一度クリックするよう求めるメッセージに
同じ名前を加えます。読むのは Skyrim と Fallout 4 のセーブだけで、ほかのゲームでは
確認なしに無効になります。

MOD の Information の General タブには、その MOD が必要とする MOD と、その MOD を必要とする MOD が、有効なプラグインのマスターから読み取って一覧されます。ほかの MOD が必要とする MOD を無効にすると同じバーが出て、「Disable them too」ならそれを必要とするすべての MOD と、さらにそれらを必要とする MOD も無効にし、「Keep them enabled」なら対象だけを無効にします。 Health タブの不足マスターカードには "Enable what provides them" があります。不足している各マスターを含む Mod を有効にし、存在するのにチェックが外れているマスタープラグインにチェックを入れます。

### 触る前に MOD を控えておく

「Back up this mod」はそのフォルダを `<name>_backup` として脇にコピーします
(次は `_backup2`、以下同様 - 控えが前の控えを置き換えることはありません)。
コピーは**動きません**。MOD ではなく、チェックボックスは何もせず、統合ビューにも
何も足しません。チェックを入れれば同じ MOD の複製二つを重ねて展開することに
なるからです。「Restore this backup over the mod」は二クリックで元に戻します。
今の中身がまず脇へ退けられ、コピーが成功してから初めて捨てられます。

**Data** は統合ビューの本物の木で、一階層ずつ展開します。ノードを開く費用は、
有効な MOD 全部を再帰的に歩くのではなく、そのノードを持つレイヤーごとに
ディレクトリを一回読むだけです。答えを返すのはマウントが供給するのと同じ
レイヤースタックなので、whiteout や隠しファイルも尊重され、このタブがゲームの
見るものと食い違うことはありません。名前で絞り込み、争っているファイルだけに
絞り、Size と Modified の列で何がどこにあるかを片付け、どの行でもファイル
マネージャで Reveal できます。
MOD の最上位にある `meta.ini`、`readme.txt`、`fomod/`、`Root/` は、このタブでもマウントでも Data に含まれません。最初の三つは MOD マネージャ用で、`Root/` は代わりにゲームフォルダへ入ります。ゲームやツールがこれらの名前で書いたファイルは Overwrite に入り、表示されたままです。**Plugins** は ESP/ESM/ESL のロード順です
(切り替え、手での並べ替え、あるいは LOOT での並べ替えと、その後のレポートの
閲覧。レポートの助言のリンクはブラウザで開きます)。ヘッダには、有効なプラグインの数がインデックス空間ごとにゲームの上限と並んで表示され(例: `full 231/254, light 512/4096`)、どれかが満杯になるとオレンジ色になります。LOOT で並べ替えたあと、新規レコードがすべて light の範囲に収まるフルプラグインは、ホバーでそのことを表示し、行のメニューに Flag as light が出ます。Eidos は light フラグを立てたコピーを `<plugin> (light)` という新しい MOD に書き込み、MOD 一覧のいちばん下(最も高い優先度)に置きます。元のプラグインには触れないので、その MOD を無効にすれば元に戻ります。プロファイルの最新のセーブ三つのどれかがそのプラグインをフルプラグインとして読み込んでいる場合は拒否します。読めるのは Skyrim と Fallout 4 のセーブだけなので、Starfield ではセーブを確認しません。LOOT が調べるのはレコードの範囲だけです。セルやワールドスペースを追加するプラグインは、フラグを立てる前に xEdit で確認してください。**Conflicts** はファイル
ごとの勝ち負けを説明します。**Overwrite** はゲームが書いたものを一手で本物の
MOD に変えます。**Saves** は各セーブのヘッダを解析し - キャラクター、レベル、
場所、プレイ時間 - そこに焼き込まれたプラグイン一覧を今のものと突き合わせ、
必要な MOD を有効にするボタンを添えます。名前を挙げて後はご自由に、では退屈な
ほうの半分だからです。

「Information...」は MOD ごとのダイアログを開きます。general、conflicts、
filetree、INI tweaks、notes。filetree から(そして Data の木から)どのファイルも
**隠せます** - `<name>.mohidden` に改名され、削除せずに仮想ビューから外れるので、
ある MOD の迷子のメッシュ三つを、優先度に触らずに黙らせられます。filetree は
普通のファイル操作もします。新規フォルダ、改名、削除、開く。どれも一つの
リゾルバを通り、その MOD の中の素直なパスでないものはすべて拒否します - `..` も、
絶対パスも、シンボリックリンクである構成要素も。辿ってしまえば削除が MOD
フォルダの外に出てしまうからです。改名は最後の構成要素だけを置き換えるので、
移動になることは決してありませんし、すでに使われている名前は、黙ってその
ファイルを置き換えるのではなく拒否します。削除は二クリック。ここで唯一、
もう一度クリックしても取り消せない操作です。

filetree でも Data の木でも、行の **View** はそのファイルをプレビューします。
画像とテキスト。DDS や NIF は違います - あれにはこの木が持たないブロック
デコーダとレンダラが要ります - が、空の枠を見せる代わりにそう言い、Reveal を
指します。テキストは 64 KB まで読み、どこで止めたかを言います。プレビューは
一瞥であり、Papyrus のログは百メガバイトになりうるからです。**INI Tweaks** は
MOD が `INI Tweaks/` フォルダで配っている断片を一覧します。有効なものは起動時に
優先度順でプロファイルのゲーム INI へ統合され、その回の INI を取り込むときに
外されます - さもないと tweak が黙って設定そのものになり、無効にしても何も
起きなくなります。

ダウンロードは **Downloads の一覧から MOD 一覧の位置へドラッグ**すれば、その
優先度でインストールできます。ファイルマネージャからウィンドウへ落とした書庫や
フォルダもインストールされます(そちらは X11 か XWayland のセッションが要り
ます - winit がファイルのドロップを実装しているのは X11 だけです)。ダウンロード
自体も一時停止と再開ができます。一時停止は転送を止めて途中のファイルを残し、
Resume は新しいリンクを取り直して止まったところから続けます。

Downloads タブは転送の待ち行列ではなく、書庫の**書棚**です。名前で絞り込み
(親しみやすい MOD 名でも通るので、「skyui」で `SkyUI_5_2_SE-12604-5-2SE.7z` が
見つかります)、新しい順・名前・サイズ・状態で並べ替え、用の済んだ書庫は
**隠せます** - ファイルは残して行だけを落とすので、本をしまうことは燃やすこと
ではありません。「Show hidden」で戻り、同じボタンで隠しを解きます。
「Remove N installed」は、すでにインストールした MOD の書庫を二クリックで
削除します。消えるのは**画面に出ているもの**だけ。どれのことかは、絞り込みで
言ったのですから。

### MOD の更新

ツールバー右端の更新ボタンは、インストール済みの
各ファイルを、Nexus でそれを置き換えたファイルと比べます。作者は新しいアップロードを
古いものの後継として印を付け、Eidos は MOD の `meta.ini` が記録しているファイル ID
からその連鎖をたどります。連鎖が後継を示さないときは、代わりに MOD ページの
バージョンを比べます。

「Information...」の **Nexus files** タブは、Nexus 上の MOD のファイルを新しい順に
並べ、ここにインストールされているものと、それを置き換えるものに印を付けます。
後者の行には **Update** ボタンがあります。プレミアムアカウントなら Eidos がファイルを
自分でダウンロードします。無料アカウントならファイルのページを開き、そこで
Mod Manager Download がファイルを送り返し、書庫が `downloads/` に届いた時点で
インストールが始まります。その先はいつものインストールです。FOMOD は MOD を
インストールしたときの答えで開き、続く確認では「Keep a backup of the existing mod」に
チェックが入った状態で Replace を選べます。前回の確認で何を選んでいても同じです。
Replace は MOD の優先度と、有効かどうかを保ちます。

複数の Nexus ファイルを抱えるフォルダ(メインファイルにオプションのファイルを混ぜ込んだ
ものなど)は断ります。新しいメインファイルで置き換えると、ほかのファイルが失われる
からです。それらは手で更新してください。

`eidos nexus update skyrimse --apply` は同じ確認をしたうえで、プレミアムアカウントなら
新しいファイルをそれぞれダウンロードし、`--replace --backup` でそのフォルダの上に
インストールします。無料アカウントでは代わりに、ファイルのページごとに `OPEN <url>`
を表示します。複数のファイルをまとめたフォルダは理由を添えて飛ばします。保存された
回答のない FOMOD の MOD(Eidos が回答を残す前にインストールしたものなど)は、
インストーラーの既定値では再インストールしません。その更新は失敗し、一度ウィンドウから
MOD を更新するよう伝えるメッセージを出します。ウィンドウでの更新が回答を保存します。
選ぶものが何もないインストーラーの FOMOD は、いつも通りインストールします。
どれかの更新が失敗すればコマンドは 1 で終わります。

### Nexus のコレクション

コレクションのリンクを貼るか、サイト上でクリックすると、Eidos はそのリビジョンの
構成要素を一覧し、それぞれをこのインスタンスと突き合わせます。インストール済み、
ダウンロード済み、未取得。*Install this collection* を押せば、そこからレシピ全体が
ワーカースレッドで走ります。pack と unpack の仕事と同じプログレスバーが付き、
終わればそのバーがそのままレポートになります。何が適用され、何が名前を挙げられる
だけなのかについて上で書いたことは、ここでも一語違わずそのまま当てはまります。
ウィンドウと `eidos collection` は、表玄関が二つある一つのエンジンです。

コレクションを読めるのは**そのコレクション自身のゲーム**に対してだけです。
Fallout 4 のインスタンスを開いた状態で Skyrim のコレクションを開くと、間違った
MOD 一覧と突き合わせる代わりに名前を挙げて断ります。そこでの「インストール
済み」も「未取得」も、答えの形をした雑音でしかないからです。

更新を確認すると、Eidos はこのインスタンスにインストール済みの各コレクションの最新リビジョンも Nexus に問い合わせます。MOD リストの上の1行に、新しいリビジョンがあるコレクションと、追加 (+)、更新 (~)、除外 (-) された MOD の数が表示されます。カーソルを重ねると MOD 名が見られます。インストール済みリビジョンのレシピがキャッシュに残っていない場合、数は表示されません。**更新**を押すと新しいリビジョンがコレクションペインで開き、*Install this collection* で実行できます。この一覧は確認のたびに作り直され、保存されません。

### オフラインモード

**Preferences -> Nexus -> Offline** は Eidos が Nexus に接続すること自体をやめさせ
ます。更新確認、サインイン、ダウンロード、コレクションは、接続エラーで失敗する
代わりにそう言います。自分で入れない限り無効です - 古い Eidos が書いた設定
ファイルにはこのキーがなく、無いものを「有効」と読めば、更新した人全員の
ネットワークを切ってしまいます。

**Preferred servers** はダウンロードが好む CDN のノードに順位を付けます。良い
ものから先に。選べる複数のミラーが渡されるのはプレミアム会員だけなので、それ
以外の人には Nexus が選び、この設定は何も変えません。これは並び順であって、
絞り込みではありません。挙げたノードが今日どれも出てこなくても、ダウンロードは
Nexus が最初に出したノードから行われます。

**Categories** は表示するだけでなく編集できます。MOD 一つにも選択全体にも
割り当て、同じダイアログからカタログ自体を編集し、ゲームの公式カテゴリ一覧を
Nexus から取ってこられます。カタログのファイルはどちらも MO2 のもの
(`categories.dat` と `nexuscatmap.dat`)なので、共有したインスタンスは
カタログを一つに保ちます。 Nexus からダウンロードした MOD は、「Nexus から取得」でカタログの対応付けが済んでいれば、インストール時にカテゴリが付きます。

**View -> INI editor** はプロファイルのゲーム INI を編集します - 起動のたびに
上書きされる Proton プレフィックスの奥のものではなく、残るほうの写しです。
**View -> Log** はセッションログを読みます。**View -> Extensions** は自分の
アドオンを一覧します。[extensions.ja.md](extensions.md) を参照。

インストールは何でも受け付けます。Simple と FOMOD の経路に加え、Wrye Bash の
**BAIN** パッケージ(サブパッケージにチェックを入れると順に統合されます)、
そしてどの推測も配置を認識できないときに書庫の木を見せてデータのルートを指させる
**手動**の選択画面。断られる書庫はありません。

FOMOD の MOD を再インストールまたは更新すると、ウィザードは前回のインストールの
回答にチェックが入った状態で、それ以降に選択肢が変わった最初のステップで開き、
変更点を一覧にします。**Reinstall with new choices** はインストーラーの既定値から
始めます。`eidos install --replace` または `--merge` は保存された回答を使い、合わ
なくなっていれば変更点を一覧にしてインストールを断ります。

**Diagnostics** は生きた健全性チェックを走らせます。何より起動できるかどうか、
欠けたマスター(最も当たるクラッシュの予兆)、有効なプラグインがどれも読み込ま
ない書庫、MOD 一覧が今も mods フォルダと一致しているか、そして実行後には -
スクリプトエクステンダ自身のログが各プラグイン DLL について何と言っているか。
「SKSE のプラグインは読み込まれたのか?」が推測から証拠に変わります。
さらに、前回の正常な起動以降のゲーム更新、スクリプトエクステンダの欠落やゲームのバージョンとの不一致(エクステンダのダウンロードページと、ダウンロードした書庫をインストールするボタン付き)、Eidos を `%command%` 付きで起動しない Steam の起動オプション、DLSS 用にオフのままの NVAPI、フレーム生成を止める排他的フルスクリーン、`LinuxVersion=true` のない ENB の `enblocal.ini`、F4SE と SFSE のプラグイン宣言、そして前回のセッションのクラッシュログとそこに名前の出る MOD も報告します。
更新の確認では、各 mod の Nexus 上の要件も読み込みます。Diagnostics は、見つからない、または無効になっている必須 mod を一覧し、別の方法で満たしている要件は Ignore で非表示にできます。

GUI からゲームを起動するには、そのゲームの Steam 起動オプションに実行ファイルの
絶対パスを設定してください(Steam は PATH の `~/.cargo/bin` を見ません):

```
~/.cargo/bin/eidos-gui %command%
```

Eidos はそのゲームのインスタンスで開きます - 最後に使ったものなので、ポータブル
インスタンスもグローバルと同じように見つかります。Run を押せば統合ビュー越しに
起動します。

**Start the game at once when a store opens Eidos** をオンにすると (Preferences、General、Running a game)、Eidos はこのクリックを省きます。Health を確認し、ウィンドウを表示せずにゲームを起動します。Health が問題を挙げたとき、MOD リストに対応が必要なとき、プレイ前に実行するよう設定したツールの出力が古いときは、いつもどおりウィンドウが開きます。1 回の起動だけウィンドウを出したい場合は、コマンドの前に `EIDOS_WINDOW=1` を付けます (`EIDOS_WINDOW=1 ~/.cargo/bin/eidos-gui %command%`)。

Steam の外では、Run は Proton や Wine でゲームを自分で起動しません。そのコピーを持つストアに起動を頼み、ストアが Eidos を起動します。

- Steam は、上の起動オプションが設定されていれば `steam -applaunch <appid>` を実行します。Steam が閉じていれば先に Steam が起動します。
- Heroic (GOG または Epic のコピー、ネイティブ版でも Flatpak 版でも) は、Heroic のゲーム設定で Eidos がラッパー (wrapper) になっていて、実行ファイルが `eidos-gui` の絶対パスで引数がないとき、`heroic://launch` リンクを受け取ります。Heroic が閉じていれば先に Heroic が起動します。
- Legendary 単体は、`~/.config/legendary/config.ini` のゲームの `[<app>]` セクションか `[default]` に `wrapper =` と `eidos-gui` の絶対パスがあるとき、`legendary launch <app>` を実行します。

すると Eidos は最後に使ったインスタンスで 2 つ目のウィンドウを開くので、そちらで Run を押します。最初のウィンドウはその実行を追わないため、遊び終えたらそのウィンドウで F5 を押してリストを読み直してください。ストアの設定がない場合や、スクリプトエクステンダーのローダーがゲームの実行ファイルの隣にない場合、Run は何も起動せず、何をどこに設定するかを、動いている実行ファイルの実際のパス入りで表示します。

Bethesda のタイトルでは、Steam の `%command%` はたいてい `<Game>Launcher.exe` を
指しています。Eidos はそれを実行しません。あのランチャーは `Data` を再走査して
`plugins.txt` を書き直す別の設定アプリで、たった今展開したロード順を台無しに
します。スクリプトエクステンダのローダーが入っていればそれに、なければゲームの
実行ファイルに差し替え、後者へ落ちるときはそう言います - SKSE の MOD が全部
死んだまま起動するゲームは、起動しないゲームより悪いからです。

ここの古い案内は `WINEDLLOVERRIDES="d3dcompiler_47=n"` を強いていました。もう
要りませんし、そもそも正確でもありませんでした。*native* への上書きが効くのは、
本物の `d3dcompiler_47.dll` がすでにプレフィックスにある場合だけです。今の Eidos
は有効な MOD の DLL の import を走査し、本物の Microsoft の DLL 自体を配置し、
そのうえで初めて上書きを設定します。

## 概念実証を試す

ゲームは要りません。user 名前空間の非特権 OverlayFS だけで、union +
copy-on-write + 無改変 + 名前空間ごとのスコープを実証します(Linux >= 5.11):

```sh
./scripts/poc-overlay.sh
```

```sh
eidos tool skyrimse add BodySlide "<path>/CalienteTools/BodySlide/BodySlide.exe"
eidos tool skyrimse run BodySlide
eidos prereqs skyrimse            # 登録したツールが必要とするものと、その状態
eidos prereqs skyrimse --install  # 足りないものを取ってくる
```

ツールに名前を付ける前に一つ。**その名前が、Eidos がどのランタイム DLL を用意
するかを決めます** - `BodySlide` なら DirectX のライブラリが付き、`BS` には何も
付きません。GUI では Executables のダイアログが、前提条件それぞれの実際の状態を
欄の下に表示し、足りないものはボタンになっています。

一覧表、前提条件の三段階、DynDOLOD が winetricks では入れられない .NET
ランタイムを要る理由、そして MOD として入れたツールが自分のフォルダではなく統合
されたパスから起動される理由は [tools.ja.md](tools.md) にあります。

ソースからのビルドとリポジトリの構成は
[../internals/contributing.md](../../../../internals/contributing.md) にあります。

## 拡張

Eidos は作り直さずに拡張できます。`~/.config/Colony/Eidos/addons/` に置いた
TOML のマニフェストが、Extensions の一覧にツールを、Health タブにチェックを
足します。Eidos の中に何かが読み込まれるわけではありません - 拡張は Eidos が
実行するプログラムです。[extensions.ja.md](extensions.md) を参照。
