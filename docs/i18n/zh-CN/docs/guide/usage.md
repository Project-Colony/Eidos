# 使用 Eidos

实用手册:CLI、GUI、Steam 启动选项、从源码构建,以及概念验证脚本。事情看起来不对
劲时该怎么办,见 [troubleshooting.zh-CN.md](troubleshooting.md)。

## 用起来(CLI)

```sh
eidos games                       # 本机装了哪些受支持的游戏(相当于 MO2 的那份列表)
eidos init skyrimse               # 创建一个模组实例
# ...把每个模组作为一个文件夹放进 <instance>/mods/(全局实例位于
#    ~/.local/share/Colony/Eidos/instances/skyrimse;`eidos init` 会打印出你的那个)...
eidos install skyrimse mod.7z     # 或者安装一个下载好的压缩包(Simple / FOMOD)
eidos import skyrimse <mo2-profile>  # 接管已有 MO2 配置档的顺序与插件状态
eidos sort skyrimse               # 用 LOOT 排序插件加载顺序
eidos play skyrimse               # 显示将会挂载什么
eidos play skyrimse -- <command>  # 在模组盖住游戏的视图下运行 <command>
eidos shell skyrimse              # 在合并视图里开一个 shell,写入的内容进入 Overwrite
eidos check skyrimse              # 不开窗口跑健康检查(脚本用 --json)
eidos sessions skyrimse           # 按从新到旧列出已记录的游戏和工具运行
eidos sessions skyrimse diff      # 显示自上次以退出码 0 结束的运行以来的变化
eidos collection skyrimse <link>  # 按作者构建它的方式安装一个 Nexus 合集
eidos nexus update skyrimse --apply  # 安装取代了你那些文件的 Nexus 文件
eidos pack skyrimse backup.eidos  # 整个实例装进一个文件,好搬到别处去
eidos unpack backup.eidos <folder>   # 在另一台机器上把它放回去
```

`eidos tool`、`eidos prereqs`、`eidos nexus`、`eidos nxm` 与 `eidos export` 补齐了
这一组;不带参数运行 `eidos` 可看到完整列表。

### 从终端运行健康检查

`eidos check <instance>` 不打开窗口就运行 **Diagnostics** 标签页里的前缀、插件、缺失 master 和脚本扩展器检查,所以可以通过 SSH 或在 Game Mode 下运行,结果也能放进 bug 报告。它先打印与 **Copy report** 相同的系统信息行,再为每条发现打印一行,主目录显示为 `~`,登录名显示为 `<user>`。没有发现问题时退出码为 0(只有建议仍为 0),至少发现一个问题时为 1,Eidos 无法检查时为 2:参数错误、无法打开的实例,或检测不到的游戏。

`eidos check <instance> --json` 改为打印一个 JSON 对象。顶层字段为 `eidos`(版本)、`game`、`instance`、`system`(`proton`、`flatpak_steam`、`passthrough`、`session`、`distro`、`kernel`、`dev_fuse`、`fusermount3`、`max_map_count`、`open_files_hard`)和 `findings`。`max_map_count` 和 `open_files_hard` 是数字,Eidos 无法读取时为 `null`。每条发现由 `code`、`level`(`problem` 或 `advice`)和它的 `args` 组成;Diagnostics 标签页显示每个代码对应的句子。

### 合并视图中的 shell

`eidos shell <instance>` 在游戏所见的游戏文件夹里启动你的 `$SHELL`(没有就用 `/bin/sh`):每个已启用的模组挂载在 `Data` 之上,Root 模组挂载在游戏根目录之上,写到那里的一切都进入 Overwrite。`eidos shell <instance> -- <command>` 则只运行一条命令,例如 `eidos shell skyrimse -- ls Data/meshes`,或 NifSkope 这样的原生工具。这次运行像游戏会话一样持有实例锁,所以在你退出之前窗口无法保存更改,它在 `eidos sessions` 中以 `shell` 为名记录,绝不算作一次游戏启动。对命令按 Ctrl+C 会像 Stop 一样停止运行:Eidos 结束该命令、收集会话并卸载。在交互式 shell 中,Ctrl+C 照常属于 shell;输入 `exit` 结束运行。

### 实例:全局与便携

上面每条命令都作用于某个实例。`skyrimse` 指的是**全局**那一个 - 集中存放在
`~/.local/share/Colony/Eidos/instances/skyrimse`,由 Eidos 管理。另一种是**便携**的:一个自包含的
文件夹,放在你想放的任何地方(第二块硬盘、游戏分区),可移动、彼此隔离,和 MO2 的
便携实例完全一样。凡是接受游戏 id 的命令,同样接受便携实例的文件夹:

```sh
eidos init skyrimse /mnt/games/EidosSkyrim   # 在那里创建一个便携实例
eidos install /mnt/games/EidosSkyrim mod.7z  # 每条命令都接受这个文件夹
eidos play /mnt/games/EidosSkyrim -- %command%
```

这个文件夹是自描述的(它的 `eidos-instance.ini` 写明了游戏),所以别的什么都不需要
- 而环境里的 `EIDOS_INSTANCE=<folder>` 会把一个游戏 id 重定向到该文件夹,这在 Steam
启动选项里很方便。你创建过或打开过的便携实例会被记住(最近使用的在前),记在
`~/.config/Colony/Eidos/instances.ini` 里;GUI 的欢迎界面把它们列出来供一键打开,
Steam 启动会落在你上次玩的那一个上,`nxm://` 处理器也下载进它里面。有两点值得知道:
手工移动便携文件夹后一切照旧,只有你用指向旧位置的绝对路径注册的工具条目除外(下面的
`eidos pack` / `eidos unpack` 会替你把那些路径修好,单纯一条 `mv` 不会);而共享的
runtime 缓存(`~/.local/share/Colony/Eidos/runtimes/`)是有意保持
全机器共用的 - 一个 78 MB 的 .NET host 不该每个实例来一份。

Eidos 把自己的文件放在 `Colony/Eidos` 下,这是 Colony 家族每个程序都用的布局:`~/.config/Colony/Eidos/` 放你的选择(偏好设置、你的 Nexus 会话、你的实例列表、你写的游戏与附加组件定义),`~/.local/share/Colony/Eidos/` 放全局实例(`instances/`)、下载的运行时和会话日志(`logs/`),`~/.cache/Colony/Eidos/` 放 LOOT 主列表,缺失时随时会重新下载。

更早的 Eidos 把这些放在 `~/.config/eidos/`、`~/.local/share/eidos/` 和 `~/.local/state/`。升级后的第一次启动会把它们**复制**过来,并在日志里说明。全局实例用硬链接而不是逐字节复制来迁移,所以几十 GB 的模组转眼就能搬完,也不占用额外空间,它的工具条目也会改为指向新文件夹。旧目录原样保留 - 什么都不删,所以一次糟糕的升级不会让你丢掉登录状态或存档 - 等你确认没问题,可以自己删掉。如果无法复制(磁盘已满或只读、旧实例文件夹在另一块磁盘上、游戏仍在从那里运行),Eidos 会继续使用旧位置,并在下次启动时再试。仍指向旧实例文件夹的 Steam 启动选项会打开迁移后的实例。不过不占用额外空间只是一开始:迁移后你删除或重装的模组和下载,其旧副本会通过旧实例文件夹继续留在磁盘上,删除 `~/.local/share/eidos/<game>/` 才能收回这部分空间。

便携实例永远不会被移动:它留在你放它的地方。

有一个位置被直接拒绝:**游戏安装文件夹内部**(MO2 老手的条件反射)。那棵目录树归
Steam 所有 - 一次更新、一次"验证文件完整性"或一次卸载都可能重写或删除它,把你整套
配置一并带走 - 而且 Eidos 挂载在游戏根目录之上,放在那里的实例会位于它自己的挂载目标
里面。向导、`eidos init` 和 `eidos play` 都会拒绝;请把文件夹紧挨着游戏放(同一块盘
上的同级目录一样方便)。

`play` 把实例的模组挂载到游戏自己的 `Data` 目录之上(通过一个 bind-stash,这样守护
进程读到的仍是原始文件),挂在一个私有命名空间里,然后让命令穿过这个视图运行。写入
(存档、重新生成的配置)落在实例的 `overwrite/` 层;游戏安装目录和每一个模组源都
逐字节保持原样。

### Wabbajack 列表

Eidos 没有 Wabbajack 安装器。请在 Eidos 之外用 CLF3 或 Jackify 安装列表，然后在向导中把安装文件夹选为便携实例。Eidos 按 MO2 的布局读取该文件夹：`mods/`、`profiles/<名称>/modlist.txt` 和插件列表。安装器写入的 `ModOrganizer.ini` 会被保留，绝不会被覆盖，因此列表自带的可执行文件仍保持注册。

许多列表会添加一个 `Stock Game` 或 `Game Root` 文件夹，里面是修改过的游戏副本，MO2 从那里启动游戏。Eidos 启动的是 Steam 安装，也没有指向其他游戏文件夹的设置。向导发现这样的文件夹时，只会在确认界面提示，不会做其他事：请自己把列表放在那里的文件移到某个模组的 `Root/` 文件夹中。CLF3 用自己的工具重建 BSA 和 DDS 文件，所以结果可能与 Wabbajack 安装不同，列表作者也不为其提供支持。

### 模组列表

和 MO2 一样,每个配置档都有自己的 `modlist.txt`(启用了哪些模组、各自是什么优先级),
而模组文件夹放在实例共享的 `mods/` 里。你手工放进 `mods/` 的文件夹还没有被列入:它会
以**禁用状态出现在最高优先级** - 也就是窗口列表的底部,MO2 也把它放在那里 - 所以一旦
你启用它,它就会赢下自己的冲突。更早的版本把它放在顶部,在那里其他每一个模组都盖过了它。

因为文件夹是共享的,删除或重命名一个模组会改变每一个配置档:它那一行会从每个配置档的
`modlist.txt` 里删掉,或在其中改名,而其余部分每个配置档都保留自己的状态和顺序。一个
没剩下任何模组的配置档干脆没有 `modlist.txt`,而不是留一个空的,空的那种曾被读成损坏
的文件,挡住了下一次安装。

窗口基于它自己的一份模组列表和加载顺序副本工作。如果在它打开期间另一个 Eidos 进程写了
其中任何一个 - 终端里的 `eidos install` 或 `eidos sort`、一个合集、一次由 Steam 启动的
会话、第二个窗口 - 窗口的下一次编辑就会被拒绝,而不是覆盖掉那份工作。它会从磁盘重新
加载,并显示 *Not saved: another Eidos process changed the mod list. It has been reloaded - redo the change.*
(加载顺序也是同样的说法);丢掉的只有那一次点击,再点一次就好。Rename、New mod、
Add separator、Remove,以及把 Overwrite 变成一个模组,都会在动 `mods/` 之前先做检查,
所以一次被拒绝的编辑不会改动磁盘上的任何东西。INI 编辑器同样会拒绝把内容存到一个自它
打开以来已被改动过的文件上。

### 存档属于配置档

每个配置档把自己的存档放在 `profiles/<name>/saves/` 里,在一次运行期间,这个文件夹会
挂载到 Proton 前缀里游戏的存档文件夹之上。一个配置档第一次启动时,会把前缀里已有的存档
复制进来,只复制一次,所以你之后从配置档里删掉的存档就一直是删掉的。每次运行之后,配置
档里最新的存档会被复制回前缀,供 Steam Cloud 使用;前缀里一个不是 Eidos 放进去的存档,
会先以 `orphan-<time>-<name>` 的名字保留在配置档里,绝不会被覆盖。

在那次首次复制之后、没经过 Eidos 就落进前缀的存档 - 从 Steam Deck 来的一次 Steam Cloud
下载、一次不经 Eidos 的启动 - 在配置档的存档挂载期间是看不见的。没有什么会删掉它:启动
时会在这次运行的日志里点出它的名字(从窗口启动是实例的 `logs/run-*.log`,从 Steam 启动
则是 Steam 的控制台),每当这组文件发生变化就点一次。要玩它,在 Saves 选项卡上按 Import。Import 会把它连同它的 co-save 一起
复制进配置档,不会替换配置档里的任何存档。

### 自上次正常运行以来的变化

无论从窗口、终端还是 Steam 启动，每次通过 `eidos play` 或 `eidos tool run` 的运行都会在 `<instance>/logs/sessions/` 写一条记录：配置文件、每个启用的 mod 及其版本和 Nexus 文件 ID、插件顺序、每个配置文件 INI 的校验和、游戏可执行文件的版本、Eidos 版本、退出码，以及这次运行创建的存档。保留最新的 50 条，`logs/` 不会进入打包的实例。`eidos sessions <instance> diff` 把最近一次以退出码 0 结束的游戏运行与当前状态比较；`diff <id>` 从列表中选另一条记录。Eidos 目前不检测崩溃，在 Proton 下崩溃的游戏仍可能以退出码 0 结束：如果选中的运行属于这种情况，请用 `diff <id>` 指定更早的一条。

### 不需要任何特权步骤

Eidos 完全以无 root 方式运行。它挂载在私有的 user + mount 命名空间里,所以没有 setuid
助手程序,没有守护进程,也没有什么要授权的。

`sudo setcap cap_sys_admin+ep "$(command -v eidos)"` 是**可选的**,只决定一件事:
内核 FUSE passthrough,而它默认关闭,因为较早版本的守护进程开着它会弄坏游戏,而避开
最可能原因的改动还没有在游戏里重新测量过(见下)。带上这个 capability 后,Eidos 取
的是普通的 mount 命名空间而不是 user 命名空间;两种方式部署模组的结果一模一样。


旧的 `setcap` 建议为什么被移除 - 以及 FUSE passthrough 为什么出厂就是关的 - 在
[troubleshooting.zh-CN.md](troubleshooting.md#为什么-passthrough-默认关闭)
里有解释。

## 安装一个 Nexus 合集

```sh
eidos collection skyrimse nxm://skyrimspecialedition/collections/rqhcxy/revisions/latest
eidos collection skyrimse rqhcxy --dry-run     # 读一遍它,说出将会发生什么
```

在窗口里:把链接粘贴进 **File -> Open a Nexus collection...**,然后按下
*Install this collection*。

### 为什么这不是"把这些模组下载下来"

一个合集是一份配方,不是一张购物清单,而这份配方几乎没有哪一部分是从 Nexus API 看得见
的。安装顺序、作者给每个模组的脚本化安装器所填的答案、文件冲突时哪个模组胜出、哪些插件
加载在哪里、二进制补丁 - 这一切都住在合集自己压缩包里的一个 `collection.json` 中。把
同样的模组下载下来、用它们的默认选项装上,得到的是另一个游戏。

所以 Eidos 下载那个压缩包,读这份配方,再把它施加下去:

| 合集说 | Eidos 做 |
| --- | --- |
| `phase` | 按那个顺序安装,可选成员排在最后 |
| `choices` | 回放作者对每个 FOMOD 的答案,做不到时如实说明 |
| `modRules` | 重排模组列表,让该赢的模组赢下每个文件 |
| `plugins` / `pluginRules` | 把 LOOT 规则并进你的 userlist 并排序 |
| `INI Tweaks/` | 把它们作为一个独立的模组安装 |
| `tools` | 告诉你它期待哪些工具;什么也不创建 |

成员在安装的同时就被**打开**,按安装顺序排在模组列表的末尾,在 `modRules` 把它们挪到
位之前 - 没有东西列出的模组,就是没有东西加载的模组,而一个静静躺在磁盘上不起作用的
合集,正是报告唯一看不见的那种失败。

状态在**每一个**成员之后都写进
`<instance>/collections/<slug>-<revision>.state.json` - 在那个修订版的文件夹旁边,
绝不在它里面,这样一个合集就没法夹带自己的账本 - 所以一次在 200 个成员里停在第 147 个
的安装会从 147 接着来。它先写成一个临时名字再改名就位,所以一次中断留下的要么是旧记录、
要么是新记录,绝不会是两者的一半;万一它读不出来,Eidos 会停下并说明,而不是悄悄把整个
合集从头再跑一遍。再跑一遍同一条命令就行。

安装一个你已经有的合集的较新修订版时,它会接管上一个修订版的文件夹:没变的成员就地校验,
作者更新了文件的成员在它原来的文件夹里被替换,新修订版去掉的成员则保持已安装,并在报告
里被点名,由你去禁用或删除。另一个配置档启用着的文件夹绝不会被接管,因为 mods 文件夹是
共享的,那个配置档会在你不知情的情况下跟着变:新修订版会改为在它旁边装一份自己的拷贝,
报告则请你在这个配置档里禁用旧的那个,而绝不是删除它。退回一个较旧的修订版时,用同样的
方式把它的文件夹接管回来,接管不了的就装一份新的拷贝。
每当这样替换一个成员,而你曾在它的文件夹里改过或加过文件时,旧文件夹会先以 `<name>_backup` 的名字留在旁边,它绝不会被加载进游戏,报告也会点出它的名字。

一个来自更早修订版、仍然启用着的遗留模组,会让这次安装算不上作者构建的那一份;你禁用它
之后,这条说明就会消失。你用 `--no-optional` 跳过的成员不会被接管,也会以同样的方式被
点名。如果接管本身失败,运行会停下,给出 *previous revision: its folders could not be taken over*
以及原因;把那个问题解决,再跑一遍这条命令。

### 它不会假装什么

**免费的 Nexus 账号取不到成员模组。** Nexus 不通过 API 给免费账号签发下载链接;每一个
文件都需要站点自己的 "Mod Manager Download" 按钮。合集的压缩包本身用免费账号下载没有
问题 - 所以你能把整份配方读完 - 但每一个成员都会带着它确切的页面 URL 被报告出来,由你
自己去取。这是 Nexus 的一条商业规则,重试多少次也绕不过去。用站点的那个按钮把它们取
下来,再跑一遍这条命令:这些成员每一次运行都会在 `downloads/` 里找一遍,所以你供上
多少,合集就跟着完成多少。

在窗口里,免费账号在合集面板中看到的是
*Fetch the N missing required files, one by one*,取代分批获取。它在 Nexus 上打开
第一个缺少的必需文件的页面,等这个文件落进 `downloads/`,再打开下一个。每个文件页面上
的下载按钮仍然由你自己按。面板显示进度 (*3 of 12*),并提供 *Skip* 和 *Stop*。如果落
下来的是同一个模组的另一个文件,面板会写出两个文件 id,并继续等待合集指定的那个。可选
成员不在其中,保留各自的 *Open* 按钮。

按合集的描述施加:**二进制补丁**(每个都按记录的 CRC 校验)、**文件覆盖**(指定的文件像 MO2 那样用 `.mohidden` 隐藏),以及那些文件随合集压缩包一起走的成员(`bundle`)。合集指望你手工去取的成员(`browse`、
`manual`)会把作者自己的说明一路带进报告。一个名字已经和你某个模组撞上的成员,会用
一个没被占用的名字装在它旁边,绝不盖在它上面,报告里也会说明是哪些。

### 那份报告

报告的意义在于让"已安装"值得信任。一个安装器答案没能全部回放的成员是**已安装,但不是
合集要求的那样** - 它单占一行,与它表面上很像的那些成功分开,因为磁盘上的文件和作者的
不一样。在合集里什么也没点到的排序规则、卡在互相矛盾的规则环里的模组、并不存在的 LOOT
分组,以及清单里这个版本的 Eidos 不理解的任何部分,也全都会被列出来。

另一条路 - 把这类事情记进日志,然后宣布安装完成 - 正是一个合集最后跑歪、而原因谁也查
不出来的由来。

## 把一个实例搬到另一台机器

`eidos pack` 把一整个实例 - 每一个模组、加载顺序、全部配置档、装着你存档的 Overwrite,
以及一切东西当初是从哪些压缩包装进来的 - 写进单独一个文件。`eidos unpack` 把它放回去:

```sh
eidos pack skyrimse ~/backup.eidos                  # 或者给一个文件夹:文件名按游戏和日期来取
eidos unpack ~/backup.eidos /mnt/games/EidosSkyrim  # 在另一台机器上
```

`eidos pack --dry-run` 会准确列出什么会进去、什么不会以及为什么,还有它需要多少空间,
而不写出任何东西。`eidos unpack --info` 对你手上已有的文件做同样的事。

如果 7-Zip 有什么东西读不出来,或者遍历时不得不跳过某个你会预期出现在备份里的东西(一条
符号链接、一个读不了的文件夹、一个没法安全交给 7-Zip 的名字),压缩包照样会写出来并改成
正式名字 - 它还是值得留着的 - 但 `eidos pack` 会以 **1** 退出,并说清楚缺的是什么。
一份不完整的备份不算成功,而这是一条人们会摆在 `&&` 前面的命令。

一个 `.eidos` 文件就是一个换了自己名字的 7-Zip 压缩包,这是一种选择而不是伪装:装
模组本来就少不了 7-Zip,所以这不多添任何依赖;而且哪天你手上没有 Eidos 了,你的备份
照样能用任何一个解压工具打开。它用 LZMA2 以 `-mx1` 压缩 - 在一份贴图很多的模组列
表上大约是原始体积的 43%,而 `-mx9` 为了多省那么几个百分点要花的时间是它的好几倍。
贴图和 mesh 本来就是已经压缩过的格式;留给更大的字典去找的东西非常少。如果你对自
己的内容有不同看法,`--level`(0、1、3、5、7、9)可以改掉这个默认值,而
`--no-downloads` 会把 `downloads/` 排除在外。

在默认的级别 1 下,文件被放进**最大 16 MB 的固实块**里。从一个 70 GB 的备份里取出
一个文件,最多只需解码它所在的那一块,绝不会把排在它前面的东西统统解压一遍;打包游
戏内容也比每个文件单独压缩快 2 到 5 倍,解包快 2 到 4 倍。代价在损坏时才显现:一个
坏掉的字节可能连带它所在块里的所有文件,最多 16 MB 的相邻文件。下文介绍的恢复数据
正是用来应对这种情况的。其他级别都保持非固实:每个文件各自是一个数据流,一个坏字节
只会丢掉这一个文件。级别 0 只存储文件、不做压缩。从级别 3 起,LZMA2 本身就按
16 MB 或更大的分片工作,固实块在测量中反而更慢:在级别 5,打包 mesh 要花 1.4 倍的时
间,解包贴图要花 6.8 倍。

打包会取走实例锁,所以游戏或者另一个 Eidos 正在往那个实例里写的时候它跑不起来 -
备份是一张快照,不是一团糊。它先以 `.part` 结尾的名字写出,刷写到磁盘,再用 `7z t`
从头到尾读回一遍,通过之后才会改成你选的名字。这次检查会解码每一块并核对每一个校
验和,和在另一台机器上解包时做的工作相同。它说明的是写完之后磁盘立刻读回的内容,而不是这块盘以后还能保住它;那是下文恢复数据的用处。如果检查失败,`.part` 会被删除,你选的名
字下不会写入任何东西,`eidos pack` 会引用 7-Zip 发现损坏的那一行。一次被打断或失
败的打包留下的是一个明显没写完的东西,或者什么都不留,而不是一个看着完整、其实不是
的 `.eidos` 文件。

装了 par2cmdline 时(Arch 上 `sudo pacman -S par2cmdline`,Debian 和 Ubuntu 上
`sudo apt install par2`,Fedora 上 `sudo dnf install par2cmdline`),`eidos pack`
还会在压缩包旁边写出 PAR2 恢复数据:`backup.eidos.par2` 和几个
`backup.eidos.volNN+MM.par2` 文件,总共是压缩包的 5% 外加一个小索引。把它们用写出时的名字和 `.eidos` 文件放在同一个文件夹里,并且一起复制:不带它们搬走的备份就没有可用来修复的东西,而且恢复数据记下了压缩包的名字,改过名的备份就和它们对不上了。`eidos unpack` 按名字找到它们,在解出任何东西之前先用它们核对压缩包,结尾被截断、7-Zip 已经打不开的备份也一样。如果
有几个字节坏了,par2 会先修好压缩包,并把损坏的副本保留为 `backup.eidos.1`,为此压缩包所在的文件夹里需要有和压缩包一样大的空闲空间;超出这
5% 所能弥补的损坏会让解包在写出任何一个文件之前就停下。和压缩包对不上的恢复文件,比如同名的旧备份留下的那些,在 7-Zip 读完压缩包并确认它完好时不会被使用,解包会说明这一点。在没有 par2 的机器上解包
照样进行,但会警告恢复数据没有被用上。`--no-recovery` 打包时不写恢复数据,
`eidos pack --dry-run` 会说明是否会写。

### 里面没有什么,以及为什么

| 排除在外的 | 为什么 |
| --- | --- |
| Proton 前缀 | 它是照着这台机器的形状长的(盘符映射、对*本机*文件系统的一个 `Z:` 视图),而 Eidos 用 `eidos prereqs <instance> --install` 一分钟就能重建它。带上它会让压缩包差不多翻一倍,只为了运送一个另一台机器反正得重新生成一遍的东西。 |
| 游戏本体 | 一个实例给一款它并不包含的游戏装模组。到那边从 Steam 装就是了。 |
| 实例之外的工具 | xEdit、DynDOLOD 之类是有自己安装程序的第三方二进制。压缩包里记着它们的**名字**,所以解包时会明确告诉你新机器上缺的是哪几个。 |
| `logs/`、`.eidos.lock`、`prereqs.done`、`prereqs.log` | 这些是做备份那台机器的记录。尤其是 `prereqs.done`,它会声称运行时库已经装在一个根本不存在的前缀里。 |
| `loot/`,`userlist.yaml` 除外 | 一份 masterlist 缓存,Eidos 需要时会重新取回来。你自己的 LOOT 规则不是缓存 - 没人会去重新取它们 - 所以那一个文件跟着一起走。 |
| `.base/`、`.base-root/` | 空的挂载点,一次会话期间游戏自己的文件寄放在那里。 |
| 写了一半的文件 | 一个暂停中的下载(`*.unfinished`),一次进行中的原子写入(`*.eidos-tmp*`)。 |
| 符号链接 | 7-Zip 会跟着它走,把它指向的东西复制进来;对一条绝对链接来说,这意味着把一棵外部的目录树拽进你的备份里。它们改为被报告出来,而且这份备份算作不完整:一个链接到另一块盘上的 `mods/` 或 `downloads/` 根本不会被打包。要有意地不带一个链接过去的 `downloads/` 来做备份,就传 `--no-downloads`(或在窗口里取消勾选 *Include downloads/*);一次有意的排除不算缺失。 |

这里的每一条,都会连同它的理由写进压缩包根目录的 `eidos-backup.ini` - 所以"这里面
没有什么"的答案是 `cat`,不是猜。同一个文件还记下实例原本住在哪里、当时哪个配置档是
活动的、解包之后有多大,以及新机器会需要哪些工具。

下载记录(`downloads/*.meta`)会进去,但它们的 `url=` 那一行被**清空**了。那个 URL 是
一条签名过的 Nexus 链接:它几小时之内就失效,而且带着下载该文件那个账号的 `user_id`。
备份是做来递给别人的,所以它不带这个。让这次下载还能被重新找到的一切 - 模组 id、文件
id、版本号 - 都留着。

### 在窗口里

两个都在 **File** 菜单里:*Pack this instance...* 和 *Unpack a backup...*。解包在欢迎
界面上也有一份,就在实例列表下方,因为最需要它的那台机器,正是一个实例都还没有的
那台。

Pack 对话框会先预览再动手:有多少个文件、多大、其中 `downloads/` 占了多少、压缩包
大致会有多大,以及哪些工具只记了名字而没有带上。它的 *Write recovery data* 复选框
在装了 par2 时是勾选的,没装时则变灰,并写明要安装的软件包。Unpack 对话框在你选中
文件的那一刻就读取备份的清单,所以它能告诉你里面装的是哪款游戏、什么时候做的、原
本住在哪里,以及它的哪些工具在这里缺着 - 都在你给它一个文件夹之前。

两个都跑在一条工作线程上,带一个进度条,所以它们干活的时候窗口照样有反应,而进度条在
完成时就变成那份报告。打包会在整个过程中一直持有实例锁:实例被读取期间,别的东西一律
不许碰它 - 备份之所以是一张快照而不是一团糊,靠的就是这个。

### 解包会修好什么

单纯复制一份文件夹,会让每一个工具按钮都指着旧机器上的路径。`eidos unpack` 只重写那些
写着旧实例根目录的值,也仅限这些:`tools.ini` 里的 `exe`、`workdir` 和带编号的 `arg`
键,以及每个模组 `meta.ini` 里的 `installationFile`。一个从来就不在实例内部的工具
(`/opt/xedit/SSEEdit.exe`)会被原样留着,并被列为需要重新安装的东西 - 猜别人的 xEdit
装到哪儿去了是编造,不是修复。它还会订正实例自称是集中式还是便携式,好让后面的命令到
它现在所在的地方去找它。

解包会拒绝这些:非空的文件夹(如果你就是要覆盖,加上 `--force`)、装不下清单自报体积
的磁盘、由比你更新的 Eidos 做出来的压缩包,以及任何含有会被写到你所选文件夹*之外*的
条目的压缩包。

之后:

```sh
eidos prereqs /mnt/games/EidosSkyrim --install   # 重建 Proton 前缀
eidos play /mnt/games/EidosSkyrim
```

## GUI

```sh
cargo run -p eidos-gui
```

一个 MO2 风格的首次启动向导,使用 Colony 共享的主题绘制:欢迎 -> 实例类型
(便携 / 全局)-> 游戏 -> 名称与位置 -> 摘要 -> 创建 -> 主界面。欢迎界面也会列出每一个
已知的现有实例(全局与便携,最近使用的在前)供一键打开 - 它同时就是实例切换器 - 而把
向导指向一个已经装着实例的文件夹时,它会原样接管,而不是覆盖着新建(若该文件夹属于
另一款游戏,则直接拒绝)。

双栏主窗口也已经做好:一个配置档选择器(切换,或复制当前的来新建一个),一个可过滤、
可选择、可重排、可用分隔条分组、可按分类收窄并右键操作的模组列表,外加 Data / Plugins /
Conflicts / Overwrite / Saves / Downloads / Diagnostics 各标签页,以及一个带运行目标
选择器的 Run 按钮。

重排不只有置顶/置底:MO2 那些精确移动这里也有 - 移到第一个冲突模组之上、最后一个之下、
移到一个明确的优先级,或移进某个分隔条的分组。它们全都走同一个共享的移动助手,所以
先删行再插回去带来的差一错误只存在于一个地方,而不是五个。

### 偏好设置

点击左上角的 **Eidos**,偏好设置就会取代两个窗格打开;再点一次(或点 **Close**)即可
返回。和每一个 Colony 程序一样,General、Appearance 和 Accessibility 排在最前,
然后是 Mod list、Nexus 和 About。每一项改动都立即生效并保存;没有 Save 按钮。

- **General**:Eidos 打开的游戏、窗口大小、界面语言、工具文件夹、游戏如何运行,
  以及窗口在后台时是否用桌面通知告知长任务结束。
  窗口支持英语和法语;**System** 跟随 `LC_ALL`、`LC_MESSAGES` 或 `LANG`,改动立即
  生效。`eidos` 命令行始终用英语回答。
- **Appearance**:主题(25 个系列、57 套配色,默认是 Eidos 的羊皮纸)、强调色、
  文字大小、效果,以及实时预览。
- **Accessibility**:高对比度、适合阅读障碍者的字体、减少动效,以及一个与
  Appearance 中的文字大小相乘的阅读文字大小。

这些设置保存在 `~/.config/Colony/Eidos/preferences.json` 里。更早的 Eidos 存在
`settings.ini` 里的主题会在第一次启动时被迁移过来。

**About -> Version** 里有版本检查,默认开启。启动时,每天最多一次,Eidos 会向 GitHub 询问 `Project-Colony/Eidos` 的最新版本。如果它比正在运行的这一份新,菜单栏会在 Help 后面显示 `Eidos 1.24.0 is available: release notes`,点这个链接会打开该版本的页面和它的更新日志。Eidos 从不自己下载或替换自己。离线模式下不做这项检查。由包管理器装在 `/usr` 下的副本也不做检查,因为由包管理器负责更新;`install.sh --system` 放置 Eidos 的 `/usr/local` 算作你自己的安装。

### 列、排序与分组

列表开箱画四列,一共提供八列:Category、Content、Version、Author、Installed、Nexus
id、Game、Flags。在 View 菜单里勾选。默认不是八列全开,这是有意的 - 每一列都显示的
列表就没地方留给名称了,而名称才是你真正在读的那一列。

点任意列标题即按它排序。再点一次反向,第三次点回到**加载顺序**,这比听上去更要紧:
加载顺序是列表唯一可以拖动的顺序,因为插入间隙寻址的是真实列表,而排序后的行完全在
别的地方。排序开着的时候,插入条不再绘制,拖动会被拒绝,而不是落到没人瞄准的位置 -
MO2 就是这么做的,理由也一样。View 菜单会写明这一点,并给出回去的方法。

View 菜单还能把整个列表**分组**,按分类或按来源(来自 Nexus,还是手工安装的)。分组
标题不是分隔条:它们背后没有东西可以重命名、上色或移动,它们可以折叠,折叠时计数留在
标题上。排序或分组之下,分隔条会离开列表 - 分隔条统领的是加载顺序中跟在它后面的那些
行,而排序和分组都把那些行挪走了。

### 鼠标与键盘

双击模组打开 Information,Ctrl+双击打开它的文件夹,Shift+双击打开它的 Nexus 页面。
Ctrl+F 把光标放进过滤框。敲一个字母跳到下一个以它开头的模组,再按一次继续走完其余的,
而不是卡在第一个上。它们都不会落到被过滤、被折叠的分隔条或被折叠的分组藏起来的行上 -
移动一个你看不见的高亮,正是下一次按空格会切换一个你根本没在看的模组的原因。

分隔条菜单里的 "Collapse others" 会折叠除该组之外的每一组。拖动过程中,停在一个折叠的
分组上会把它展开,于是模组可以直接放进去,不必先放弃这次拖动 - 是停留,不是掠过。

Ctrl+Z 撤销对模组列表或加载顺序的上一次改动:一次勾选、一次移动、一次批量禁用、一次 LOOT 排序。Ctrl+Shift+Z 重做。
窗口保留 50 步,在按 F5、游戏或工具运行结束、切换配置档以及另一个 Eidos 进程改动列表时
清空。安装、重命名或移除模组会改变磁盘上的文件夹,所以越过这类操作的撤销会被拒绝。

### 过滤列表

Filters 按钮为每个条件列出一行:已启用、有冲突、有更新、无分类、已在 Nexus
上推荐 (endorsed)、已跟踪 (tracked)、有 Nexus id、有隐藏文件、没有有效的游戏
数据、用于另一个游戏、有备注,以及每种内容一行(插件、BSA 或 BA2 压缩包、贴图、
网格、脚本、脚本扩展器插件、界面文件、声音、FaceGen)。每点击一次,该行就按
关闭、"only"、"except" 的顺序切换,然后回到关闭。最上面一行在"满足所有已开启的
条件"和"满足其中任意一个"之间切换。名称框和分类列表始终会进一步缩小结果。隐藏
文件这一行只看已启用的模组。

### 列表会告诉你一个模组的哪些事

两个提示性标记,都是一个字形,悬停给出解释。**No valid game data** 意思是这个模组顶层
没有任何东西看起来像本作会加载的内容;它可能需要把文件夹上移一层,也可能根本不是这款
游戏的模组。**Another game** 意思是模组自己的 `meta.ini` 写的是另一款游戏。两者都不拦
任何事 - 模组照样部署 - 行菜单里的 "Mark as valid" 可以让任一个闭嘴,走的是 MO2 自己的
`validated=` 键,所以你在一个管理器里担保过的模组,到另一个里也是安静的。

布局检查是刻意宽松的:一棵 `Root/` 树算,读不了的文件夹算,空文件夹也算。在一个五百行
的列表上,一个错误的警告比一个漏掉的警告更糟。

### 停用存档或其他模组用到的模组

在停用或移除一个模组之前,Eidos 会读取该配置档最新三个存档的插件列表。只要其中一个
存档用到了这个模组里的插件,列表上方就会出现一条提示栏,列出这些插件,并等待你点
"Disable anyway" 或 "Cancel"(按 Esc 也会取消)。Remove 会把同样的插件名加进它
要求再点一次的提示里。只读取 Skyrim 和 Fallout 4 的存档;其他游戏不询问,直接停用。

模组的 Information 里的 General 标签页会列出它需要的模组和需要它的模组,依据已启用插件的主文件读取。停用其他模组需要的模组时会出现同样的提示栏:"Disable them too"会同时停用所有需要它的模组,以及需要那些模组的模组;"Keep them enabled"则只停用所选的。 Health 标签页上的缺少主文件卡片有 "Enable what provides them":它会启用包含每个缺失主文件的模组,并勾选存在但未勾选的主插件。

### 动一个模组之前先给它做备份

"Back up this mod" 把它的文件夹复制到旁边,叫 `<name>_backup`(然后是 `_backup2`,
以此类推 - 备份永远不会替换上一个)。这份副本是**惰性的**:它不是模组,它的勾选框
什么也不做,对合并视图毫无贡献,因为勾上它就会把同一个模组的两份拷贝叠着部署。
"Restore this backup over the mod" 两下点击把它放回去;当前内容会先被挪到一边,只有
在复制成功之后才丢弃。

**Data** 是合并视图的一棵真实目录树,一次展开一层,所以打开一个节点的代价是每个含有它
的图层各读一次目录,而不是递归遍历每一个启用的模组。回答它的是挂载所依据的同一套图层
栈,所以 whiteout 与隐藏文件都被遵守,这个标签页不可能和游戏将会看到的东西相左。按
名称过滤它,收窄到只看有争议的文件,用 Size 与 Modified 两列理清什么在哪里,任意一行
都可以在文件管理器里 Reveal。
模组顶层的 `meta.ini`、`readme.txt`、`fomod/` 和 `Root/` 不进入 Data,这个标签页和挂载里都一样:前三个是给模组管理器用的,`Root/` 则改去游戏文件夹。游戏或工具以这些名字写下的文件会落进 Overwrite,并保持可见。**Plugins** 是 ESP/ESM/ESL 的加载顺序(勾选、手工重排,
或者用 LOOT 排序并阅读排序后的报告,报告里的建议链接会在你的浏览器中打开)。它的标题栏按索引空间统计已启用的插件数量,并与游戏的上限对照,例如 `full 231/254, light 512/4096`,某个空间满了就变成橙色。LOOT 排序之后,新记录全部落在 light 范围内的完整插件会在悬停时说明这一点,它那一行的菜单里也会出现 Flag as light。Eidos 会把带 light 标志的副本写进一个名为 `<plugin> (light)` 的新模组,放在模组列表最底部(优先级最高),原插件不动,所以停用这个模组就能撤销。如果该配置档最新三个存档中有一个把这个插件作为完整插件加载,Eidos 会拒绝。只读取 Skyrim 和 Fallout 4 的存档,所以在 Starfield 上不会检查任何存档。LOOT 只检查记录范围:会添加单元格或世界空间的插件,标记之前先在 xEdit 里看一下。
**Conflicts** 解释每个文件的赢家与输家。**Overwrite** 一步把游戏写出来的东西变成一个
真正的模组。**Saves** 解析每个存档的头部 - 角色、等级、地点、游戏时长 - 并把烘进存档
的插件列表与你当前的做差异比较,还带一个按钮来启用它需要的模组,因为只把它们的名字
念出来、剩下的留给你自己弄,那是无聊的那一半。

将鼠标悬停在插件上,会显示它的来源、作者、头部版本和表单版本、说明的前 300 个字符、它的主文件,以及在 LOOT 排序之后 LOOT 的消息。 在 Skyrim、Skyrim SE、Skyrim VR 和 Enderal SE 上,游戏还会读取与已加载插件同名的 INI;INI 列会标出这些插件,点击即以只读方式打开该文件。

Data 选项卡中的 `.exe` 行有 Add tool 和 Run 两个按钮。Add tool 会打开 Executables 编辑器并填入该文件(按下 Save 之前不会保存任何内容);Run 会像已注册的工具一样,通过合并视图把它运行一次。Save tree 会把合并后的整个 Data 树写入文本文件，每个文件一行，并注明提供它的 Mod，其中已去除您的主目录和用户名，可用于错误报告。

Steam Cloud 从其他设备下载的存档,或不经 Eidos 的启动写下的存档,会落进游戏自己的存档文件夹,而游戏运行期间配置档的存档会盖住这个文件夹。Saves 选项卡在标题下方那一行显示它们的数量,Import 会把每个存档连同它的 co-save 一起复制进配置档。配置档里已有同名存档的,会以 `orphan-<time>-<name>` 导入;配置档里的任何内容都不会被替换。

"Information..." 打开一个按模组的对话框:general、conflicts、filetree、INI tweaks、
notes。从 filetree(以及从 Data 树)里,任何文件都可以被**隐藏** - 重命名为
`<name>.mohidden`,这会把它从虚拟视图里剔除而不删除它,于是一个模组里三个碍事的 mesh
可以被压掉,而不用去动优先级。filetree 也做常规的文件操作:新建文件夹、重命名、删除、
打开。它们全都经过同一个解析器,任何不是该模组内部普通路径的东西都会被拒绝 - 不许
`..`,不许绝对路径,任何一段都不许是符号链接,因为跟着它走会让一次删除跑到模组文件夹
之外去。重命名只替换最后一段,所以它永远不可能变成一次移动;而且名字已被占用时它会
拒绝,而不是悄悄替换掉那个文件。删除要点两下;它是这里唯一一个再点一次也撤不回来的
操作。

filetree 或 Data 树里任意一行上的 **View** 会预览该文件:图片和文本。不支持 DDS 或
NIF - 那需要一个块解码器和一个这棵树没有的渲染器 - 但它们会明说,而不是给你一个空框,
并指向 Reveal。文本最多读到 64 KB 并说明它在哪里停下,因为预览是瞥一眼,而一份
Papyrus 日志可以有一百兆。**INI Tweaks** 列出模组在自己的 `INI Tweaks/` 文件夹里带来
的片段;启用的那些会在启动时按优先级顺序合并进配置档的游戏 INI,并在采集这次运行的
INI 时再摘下来 - 否则一条 tweak 会悄悄变成一项设置,禁用它也就什么都不做了。

一个下载可以**从 Downloads 列表拖到模组列表的某个位置上**,以那个优先级安装;从文件
管理器拖到窗口上的压缩包或文件夹也一样会安装(这后半件事需要 X11 或 XWayland 会话 -
winit 只为 X11 实现了文件拖放)。下载本身可以暂停和继续:暂停会停止传输并保留已下载
的部分,Resume 会重新解析一个新链接并从停下的地方接着下。

Downloads 标签页是一个压缩包**库**,不是传输队列。按名称过滤它(也认友好的模组名,
所以 "skyui" 能找到 `SkyUI_5_2_SE-12604-5-2SE.7z`),按最新、名称、大小或状态排序,
并且可以**隐藏**一个你用完了的压缩包 - 这会保留文件而只去掉那一行,把书放回架上不等于
烧掉它。"Show hidden" 把它们带回来,同一个按钮也取消隐藏。"Remove N installed" 两下
点击删除你已经安装过的模组的压缩包,而且只删**屏幕上**的那些:过滤就是你表明你指的是
哪些的方式。

**Preferences -> Nexus -> Install downloads when they finish** 默认关闭。开启后，窗口打开期间结束的 Nexus 下载会直接安装，不必再去 Downloads 标签页。这是常规安装：FOMOD 会打开它的安装器，模组列表里已有的名称会询问怎么处理。窗口打开之前、或选项开启之前就在 `downloads/` 里的压缩包不会被动，你取消过安装的下载也一样。在合集面板中打开的合集的成员，以及等待中的 Update 所等的文件，只由各自的流程安装。游戏或另一个 Eidos 占用实例时，安装会等到它空闲。

### 模组更新

工具栏右端的更新按钮会把每个已安装的文件与 Nexus 上取代它的
文件相比较。作者会把一次新上传标记为某个旧文件的后继,Eidos 从模组 `meta.ini` 记录的
文件 ID 出发沿这条链往下找。链上没有后继时,改为比较模组页面的版本。

模组右键菜单里的 Track 和 Untrack 会把该模组加入或移出你在 Nexus 上的跟踪模组,
这样网站的通知就与你在这里跟踪的内容一致。每次检查更新时,Eidos 还会从 Nexus 读取你的
推荐(endorsement)和跟踪模组(两次请求),并按模组自己的 Nexus 域名,把每个模组的
Endorsed 和 Tracked 标记设成一致。两边不一致时,以 Nexus 为准。任一列表读取失败时,
检查结果会说明这一点,并保持那些标记不变。

"Information..." 的 **Nexus files** 标签页列出该模组在 Nexus 上的文件,最新的在前,
并标出这里安装的那个和取代它的那个。后者那一行有一个 **Update** 按钮。premium 账户由
Eidos 自己下载文件。免费账户则打开文件页面,在那里 Mod Manager Download 把文件发回来,
压缩包到达 `downloads/` 时安装开始。之后就是平常的安装:FOMOD 以模组安装时的答案打开,
随后的询问提供 Replace,并勾选 "Keep a backup of the existing mod",不论你上次询问时
选了什么。Replace 保留模组的优先级和启用状态。

它旁边的 **Nexus page** 标签页显示模组的描述，以及页面上每个文件版本的更新日志，最新的在前。第一次打开该标签页时，Eidos 从 Nexus 的 GraphQL API 读取这两项内容，这个 API 不计入每小时的请求额度；读取的内容会保留到 Eidos 关闭或你按下 **Refresh** 为止。内容以纯文本显示：BBCode 和 HTML 格式会被去掉，链接的地址写在链接文字之后，图片和视频不显示。文字上方的 **Endorse** 和 **Track** 与模组右键菜单的作用相同。成人模组的页面会保持隐藏，除非你的 Nexus 账户设置为显示成人内容；没有分级的页面在任何情况下都保持隐藏。

Replace 替换模组文件夹之前，Eidos 会按文件名和大小比较旧文件夹与新文件夹，并读取两边插件的头部。Update、合集更新以及在安装询问中选择的 Replace 都适用。随后状态行会统计新增、删除和大小改变的文件数，并列出新版本需要而旧版本不需要的每个 master。“Information...”的 **General** 标签页末尾有一个 **Last update** 部分，列出版本、新增或删除的插件、新增或不再需要的 master、ESM、ESL 或 ESH 标志改变的插件、该模组现在共享或不再共享文件的模组，以及文件。以相同大小重写的文件不会列出。报告保存在实例的 `logs/updates/<mod>.json` 中，`eidos pack` 不会打包它；全新安装或向该文件夹 Merge 会删除它。`eidos install --replace` 会在 `changes:` 行输出同样的数字。

包含多个 Nexus 文件的文件夹(例如混入了一个可选文件的主文件)会被拒绝:用新的主文件
替换它会丢掉其他文件。这些请手动更新。

`eidos nexus update skyrimse --apply` 做同样的检查,然后在 premium 账户上下载每个新
文件,并用 `--replace --backup` 安装到它的文件夹上。在免费账户上则改为为每个文件页面
打印 `OPEN <url>`。合并了多个文件的文件夹会被跳过并说明原因。没有保存答案的 FOMOD
模组(例如在 Eidos 开始保存答案之前安装的)不会用安装器的默认值重新安装:这次更新会
失败,并提示你在窗口中更新该模组一次,窗口会保存答案。安装器没有任何可选项的 FOMOD
照常安装。只要有一个更新失败,命令就以 1 退出。

### Nexus 合集

粘贴一个合集链接 - 或者在站点上点一个 - Eidos 就会列出该修订版的成员,每一个都与当前
实例对照:已安装、已下载,或缺失。*Install this collection* 接着会在一条工作线程上把
整份配方跑完,用的是和打包、解包那两件活一样的进度条,而进度条在完成时就变成那份报告。
上面关于什么会被施加、什么只是被点名的一切,在这里逐字成立:窗口和 `eidos collection`
是同一个引擎的两个前端。

没有链接时，**File -> Open a Nexus collection...** 会打开在 **Browse** 标签页上。它列出为当前打开实例的游戏发布的合集，每次 20 个，按下载最多、最近更新或最新排序，搜索框会把列表缩小到名称或正文匹配的合集。每一行给出作者、最新修订版、模组数、下载量和一个日期。**View** 会在 **Link** 标签页上打开该合集的最新修订版，和粘贴它的链接一样。标记为成人内容的合集会被略去，除非你的 Nexus 账户显示成人内容；没有分级的合集总是被略去，列表下方的那一行会把这两类都计数。浏览需要已登录的 Nexus 账户，和这个面板的其他部分一样。

一个合集只能对着**它自己的游戏**读取。在加载着 Fallout 4 实例时打开一个 Skyrim 合集,
它会指名拒绝,而不是把成员对着错误的模组列表去比对 - 在那里每一个"已安装"和每一个
"缺失"都是披着答案外形的噪声。

检查更新时，Eidos 还会向 Nexus 询问此实例中每个已安装合集的最新修订版。模组列表上方的一行会列出有较新修订版的合集，并统计新增 (+)、更新 (~) 和移除 (-) 的模组数量，把鼠标移上去可看到名称。如果已安装修订版的配方不再缓存，则没有数量。点击**更新**会在合集面板中打开较新的修订版，由 *Install this collection* 执行安装。该列表在每次检查时重建，不会保存。

安装完成后，Eidos 仍会保留每个已安装合集的规则。如果之后的拖动让其中两个模组违反了一条前后顺序规则，**Diagnostics** 标签页会为该合集显示一张卡片，列出第一对这样的模组，并统计不再成立的规则数量。只计算当前配置档中启用的模组；陷入循环的规则会被跳过，因为没有任何顺序能满足它们。**Restore collection order** 会把该合集的模组移回满足每条规则的顺序，在规则允许的地方保留你自己的顺序，不属于该合集的模组则留在原位。Ctrl+Z 可撤销此操作。`eidos check` 会以 `collection_order_broken` 列出同一发现。该检查需要 `collections/` 中该修订版的配方，因此缓存配方已被删除的合集不会被检查。

### 离线模式

**Preferences -> Nexus -> Offline** 让 Eidos 完全不去联系 Nexus,也跳过每天一次的 GitHub 版本检查。更新检查、登录、下载和
合集都会这么说明,而不是以一个连接错误失败。它默认是关的,除非你打开 - 更早的 Eidos
写出的设置文件里没有这个键,而把缺失的键读成"开",会把每一个升级上来的人的网络都掐断。

**Preferred servers** 给一次下载优先选用的 CDN 节点排序,最好的在前。只有 premium
账号才会拿到不止一个镜像可选,所以对其他所有人来说是 Nexus 挑,这项设置什么也不改变。
它是一个排序,不是一个过滤器:如果你点名的节点今天一个都没提供,下载照样进行,用
Nexus 最先给出的那个节点。

**Categories** 是可编辑的,不只是拿来显示:把它们指派给一个模组或一整批选中的模组,
在同一个对话框里编辑目录本身,并从 Nexus 拉取这款游戏的官方分类列表。两个目录文件都是
MO2 自己的(`categories.dat` 和 `nexuscatmap.dat`),所以共享的实例保有同一份目录。 从 Nexus 下载的模组,在“从 Nexus 获取”映射好目录之后,安装时会自动归类。

**View -> INI editor** 编辑配置档的游戏 INI - 是会持久保留的那一份,而不是埋在 Proton
前缀里、每次启动都被覆盖的那一份。**View -> Log** 读会话日志。**View -> Extensions**
列出你自己的附加组件;见 [extensions.zh-CN.md](extensions.md)。

安装什么都接受:Simple 与 FOMOD 两条路,加上 Wrye Bash 的 **BAIN** 包(勾选子包,它们
按顺序合并),以及一个**手动**选择器 - 当没有启发式认得出布局时,它展示压缩包的目录树,
让你指出数据根目录在哪。没有压缩包会被拒绝。

重新安装或更新一个 FOMOD 模组时，向导打开时会勾好上次安装的答案，停在此后选项
有变化的第一步，并列出变化。**Reinstall with new choices** 则从安装器的默认值开始。
`eidos install --replace` 或 `--merge` 沿用保存的答案，答案不再适用时会列出变化并
拒绝安装。

**Diagnostics** 跑实时健康检查:首先是启动能力,缺失的 master(单一最可靠的崩溃预测
指标),没有任何活动插件会加载的档案,模组列表是否仍与 mods 文件夹一致,以及 - 在一次
运行之后 - 脚本扩展器自己的日志对它每一个插件 DLL 说了什么,这把"我的 SKSE 插件加载了
吗?"从一次推断变成了证据。
它还会报告:自上次干净启动以来的游戏更新,缺失或与游戏版本不匹配的脚本扩展器(附扩展器的下载页面,以及安装你下载的档案的按钮),没有用 `%command%` 启动 Eidos 的 Steam 启动选项,DLSS 需要却仍关闭的 NVAPI,阻止帧生成的独占全屏,没有 `LinuxVersion=true` 的 ENB `enblocal.ini`,F4SE 和 SFSE 插件的声明,以及上次会话的崩溃日志和其中点名的模组。
检查更新时还会读取每个 mod 在 Nexus 上的前置要求。Diagnostics 会列出缺失或已禁用的前置 mod,已通过其他方式满足的要求可用 Ignore 忽略。

要通过 GUI 启动游戏,把该游戏的 Steam 启动选项设成这个二进制的绝对路径(Steam 看不到
PATH 上的 `~/.cargo/bin`):

```
~/.cargo/bin/eidos-gui %command%
```

Eidos 会在这款游戏的实例上打开 - 你上次用的那一个,所以便携实例和全局实例一样能被重新
找到;点 Run 让它穿过合并视图启动。

打开 **Start the game at once when a store opens Eidos**(Preferences、General、Running a game)后,Eidos 会省掉这次点击:它先检查 Health,再不显示窗口直接启动游戏。Health 列出问题、模组列表需要处理,或设为在游戏前运行的工具输出已过期时,窗口照常打开。想在某一次启动时看到窗口,就在命令前加上 `EIDOS_WINDOW=1`:`EIDOS_WINDOW=1 ~/.cargo/bin/eidos-gui %command%`。

在 Steam 之外,Run 不会自己用 Proton 或 Wine 启动游戏。它请拥有这份副本的商店来启动,再由商店启动 Eidos:

- Steam:设好上面的启动选项后,运行 `steam -applaunch <appid>`。Steam 没开时会先启动 Steam。
- Heroic(GOG 或 Epic 副本,原生版或 Flatpak 版):当 Eidos 是 Heroic 里该游戏设置中的一个包装器(wrapper),可执行文件为 `eidos-gui` 的绝对路径且不带参数时,它会收到一个 `heroic://launch` 链接。Heroic 没开时会先启动 Heroic。
- 单独的 Legendary:当 `~/.config/legendary/config.ini` 在游戏的 `[<app>]` 段或 `[default]` 下有 `wrapper =` 加 `eidos-gui` 的绝对路径时,运行 `legendary launch <app>`。

随后 Eidos 会在你上次用的实例上打开第二个窗口,你在那里点 Run。第一个窗口不跟踪这次运行,所以玩完后在它里面按 F5 重新载入列表。商店的设置缺失,或脚本扩展器的 loader 不在游戏可执行文件旁边时,Run 什么也不启动,并显示要在哪里设置什么,带上正在运行的二进制的真实路径。

Bethesda 各作在 Steam 里的 `%command%` 通常指向 `<Game>Launcher.exe`。Eidos 从不运行
它:那个 launcher 是一个独立的设置程序,它会重新扫描 `Data` 并重写 `plugins.txt`,把
刚刚部署好的加载顺序毁掉。它会换上脚本扩展器的 loader(如果装了),否则换上游戏本体的
二进制,并在不得不回退时说明 - 一个每个 SKSE 模组都不生效的游戏,比一个起不来的游戏
更糟。

这里更早的说明曾强制 `WINEDLLOVERRIDES="d3dcompiler_47=n"`。现在不再需要,而且那从来
就不太对:覆盖为 *native* 只在前缀里已经有一个真正的 `d3dcompiler_47.dll` 时才有用。
Eidos 现在会扫描已启用模组的 DLL 导入,自己部署那个真正的微软 DLL,然后才设置这个覆盖。

不需要游戏。它只用 user 命名空间里的非特权 OverlayFS(Linux >= 5.11)就证明了 union +
copy-on-write + 零改动 + 按命名空间隔离:

```sh
./scripts/poc-overlay.sh
```

## 工具

xEdit、BodySlide、DynDOLOD 之类的工具,在游戏的 Proton 前缀里穿过合并视图运行:

```sh
eidos tool skyrimse add BodySlide "<path>/CalienteTools/BodySlide/BodySlide.exe"
eidos tool skyrimse run BodySlide
eidos prereqs skyrimse            # 已注册的工具需要什么,以及它的状态
eidos prereqs skyrimse --install  # 把缺的都取回来
```

给工具命名之前有一件事要知道:**标题决定了 Eidos 为它准备哪些运行时 DLL** -
`BodySlide` 会拿到它的 DirectX 库,`BS` 什么也拿不到。在 GUI 里,Executables 对话框会
在输入框下方显示每项前置条件的真实状态,缺的那些是按钮。

那张表、三个前置条件层级、DynDOLOD 为什么需要一个 winetricks 装不了的 .NET 运行时,
以及作为模组安装的工具为什么是从合并路径而不是它自己的文件夹启动的,都在
[tools.zh-CN.md](tools.md) 里。

从源码构建以及仓库布局在
[../internals/contributing.md](../../../../internals/contributing.md)。

## 扩展

Eidos 不必重新构建就能扩展:`~/.config/Colony/Eidos/addons/` 里的一份 TOML 清单,就能往
Extensions 列表加一个工具,或往 Health 标签页加一项检查。没有任何东西被加载进 Eidos -
一个扩展是它运行的一个程序。见 [extensions.zh-CN.md](extensions.md)。
